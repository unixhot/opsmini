# 备份与恢复

## 一键的程度不一样

| 动作 | 一键程度 | 为什么 |
|---|---|---|
| 备份 | ✅ 真的点一下就跑，也可定时 | 只读源数据 + 写目标目录，失败重试即可，无破坏性 |
| 恢复 | ⚠️ 「一键」但有三道前置 | 恢复会覆盖生产数据，必须有预检、恢复前快照和自动回滚 |

把恢复做成「点一下就覆盖」，等于给用户一个没有撤销键的删除按钮。所以界面上叫**一键恢复（带预检与自动回滚）**。

## 备份什么

三种对象，写在「备份对象」里，每行一个：

| 写法 | 含义 |
|---|---|
| `/var/www` | 目录（或单个文件），打包为 `tar.gz` |
| `mysql:opsmini` | 数据库，通过 `mysqldump` 导出后压缩 |
| `redis:/var/lib/redis/dump.rdb` | Redis 快照文件，直接打包该文件 |

MySQL 备份使用面板已配置的连接信息（本机 socket），参数为 `--single-transaction --routines --triggers`，保证 InnoDB 表的一致性快照而不锁表。

**不支持**：PostgreSQL、Docker volume、块设备/文件系统级快照、增量备份、备份加密。这些都在后续版本考虑，本版不承诺。

## 快照长什么样

```
<数据目录>/data/backups/web-20261029-020000/
├── manifest.json                 # 元数据：对象、大小、sha256、主机名、版本
└── data/
    ├── var_www.tar.gz
    ├── opsmini.sql.gz
    └── redis.rdb.gz
```

目录权限 `0700`，文件 `0600`。`manifest.json` 里记录每个分片的 sha256，恢复时会逐个校验。

不引入 restic/borg 这类「仓库型」备份工具：它们要去重、加密、快照链，功能强但会带来 15–25MB 依赖，而且恢复时必须用同一工具。当前是「自包含的分片 + 清单」，任何一台机器解开就能恢复。

## 备份流程

```
校验全部对象（路径存在、库名非空、redis 路径可读）
   ↓  先全部校验再动手：否则 5 个对象里第 2 个写错，
      会在已经产出 4 个归档之后才失败，留下半个快照
逐个执行（串行，避免 IO 打满）
   ↓  每个对象完成即写入 manifest，失败不产生「半个备份」
计算总校验和 → 按保留策略清理旧快照 → 写备份历史
```

保留份数默认 7，`0` 表示全部保留。清理按**整目录**删除最旧的，绝不删单个分片（否则清单失效）。

## 恢复流程（三道闸门）

**① 预检**

- 必须输入快照名做二次确认（防误选）
- 目标父目录存在且可写
- `mysql` 客户端可用（恢复数据库时）
- 快照文件齐全、sha256 与清单一致

**② 恢复前自动快照**

把当前状态先备份一份（目录走同一套打包逻辑，数据库走 dump），失败可回到这一步。

**③ 执行与回滚**

- 还原 → 健康检查
- 任一检查失败 → **自动回滚到步骤②的快照** → 在事件中心产生一条 critical 事件

健康检查项：目录比对文件数与抽查校验和、MySQL 执行 `SELECT 1` 并核对关键表行数、Redis `PING` 与 keyspace 对比。

回滚的可靠性来自「同分区 rename 是原子的」：恢复前把目标目录 `mv` 成 `xxx.pre-restore-<时间戳>`，失败时 `mv` 回来。

## 面板操作

**面板设置 → 备份恢复**：

| 区域 | 内容 |
|---|---|
| 备份对象 | 每行一个，支持目录 / `mysql:库名` / `redis:路径` |
| 保留份数 | 默认 7，0 表示不清理 |
| 立即备份 | 跑一次，完成后刷新快照列表 |
| 快照列表 | 名称、时间、大小、对象数、预检结果 |
| 恢复 | 输入快照名确认后执行，返回预检明细与结果 |
| 备份历史 | 每次运行的结果（含失败原因） |

## 定时备份

备份是**计划任务的第四种类型**（与面板任务 / 系统 crontab / 用户 crontab 并列），复用同一套调度、启停与失败告警。

在 **计划任务 → 新建任务 → 类型选「备份任务」** 中配置：

| 字段 | 说明 |
|---|---|
| 备份对象 | 与备份页相同的行语法 |
| 保留份数 | 覆盖旧快照的策略 |
| 执行周期 | cron 表达式，常用预设（每天 02:00 等） |
| 通知渠道 | 面板 / 邮件 / 企业微信 / 钉钉 / 飞书 |
| 保留本地副本 | 用了远端目标时，上传成功后是否保留本地一份 |

与手动「立即备份」走的是**同一个引擎**，产物完全一致——不存在「手动能恢复、定时的不行」这种情况。

失败会写回任务状态（`上次状态 / 上次错误 / 连续失败次数`），同时落一条备份历史，触发内置告警规则「备份失败数」。

## 远端目标：代码就绪，本版不启用

`internal/backup` 里已经实现了 S3 兼容（OSS / MinIO / AWS，自写 SigV4 签名）和 SFTP 两种远端存储，但**v1.4.0 不作为交付内容**：

- 面板不引导配置远端目标
- 文档不建议在生产使用
- 未做真机联调验收（只有单元测试与 S3 签名向量测试）

需要异地存放时，在 `config.yaml` 里加目标即可启用，无需改代码：

```yaml
backup:
  targets:
    - name: oss-bj
      type: s3
      endpoint: oss-cn-beijing.aliyuncs.com
      bucket: my-backup
      region: cn-beijing
      access_key: "..."
      secret_key: "..."
```

配置后备份页会出现「远端目标」选择，可将快照上传并浏览/取回远端快照。上传在本地快照完整落盘之后进行，所以上传失败不会在远端留下半个备份。

**注意**：这条链路没有经过真机联调，正式用之前请先在一个非生产目录上验证一次完整往返（上传 → 列表 → 恢复到临时目录）。

## 已知限制

- 大目录备份期间会持续占用 IO，建议错开业务高峰（默认 02:00）
- MySQL 通过本机 socket 备份，不支持远端数据库实例
- 恢复是「覆盖式」的：只还原快照里包含的对象，不会清理快照之外的新增文件
- 单个快照不做加密，含敏感数据的目录请确保数据目录权限与备份介质安全
