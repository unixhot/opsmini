## 1. 三条边界（先钉死，后面所有设计都受它约束）

### 1.1 单机 vs 被纳管

| 场景 | OpsMini 提供什么 |
|---|---|
| 单机（无 OpsAnt） | 指标、变更、事件中心、AI 排障、容器与计划任务。**不采集日志** |
| 被 OpsAnt 纳管 | 上面全部 + **替掉主机上那个 filebeat**：接收并执行平台下发的 filebeat 任务配置 |

对外定位：**OpsMini 是 node_exporter + filebeat 的合体替代品**。用户装机二选一——装两个进程两个包，
或者只装一个 OpsMini；平台侧不改任何东西（同一份任务配置、同一个 ES/Kafka/Logstash 出口）。

单机不采日志的理由：没有日志平台就没有"日志送到哪"的答案，硬塞配置界面只会让用户配一个发不出去的管道。
`tasks.d/` 为空时管道不启动（零 goroutine、零内存），面板里也没有"新建任务"入口。

### 1.2 多机能力归 OpsAnt

多机编排、批量执行、主机分组、服务存活、端口监听、证书到期——全部不做。
OpsMini 只做"这台机器自己能判断的事"。

### 1.3 单目录原则

所有落盘在 `/data/opsmini` 内，卸载 = `rm -rf`。布局见 §1.4。

### 1.4 标准目录布局

```
/data/opsmini/
├── opsmini            二进制
├── config.yaml        配置（paths.data 指向下面）
├── opsmini.db         SQLite
├── opsmini.log        服务日志
└── data/              一切运行期数据
    ├── changes/  reports/  safety/  skills/  templates/   # 已有
    ├── plugins/        # 插件：包、配置、数据、run/*.sock
    ├── logs/           # 日志管道：主配置 + tasks.d/ + registry.db + spool/
    └── backups/        # 备份产物（备份源自动排除自身）
```

唯一目录外落盘是 `/etc/systemd/system/opsmini.service`（systemd 安装产物，非数据）。

## 3. 基线检查：13 → 45

现有 13 项：`ssh_root_login` `ssh_password_auth` `ssh_port` `ssh_protocol` `shadow_empty_pass`
`pass_max_days` `login_no_pass` `shadow_perm` `passwd_perm` `sshd_perm` `firewall_enabled`
`highrisk_port` `cron_suspicious`。

新增方向（沿用现有 `key/title/status/detail/suggestion/weight` 结构，不改评分公式）：

| 分类 | 新增项 | 权重 |
|---|---|---|
| 账号与认证 | 空口令账号、UID 0 非 root、无主文件、密码最短长度、复杂度、锁定阈值、sudo 授权清单 | 高 |
| SSH | MaxAuthTries、ClientAliveInterval、AllowUsers、X11Forwarding、PermitEmptyPasswords、LoginGraceTime | 高 |
| 文件权限 | `/etc/gshadow`、`/etc/group`、`/etc/crontab`、`/boot`、`/etc/ssh/*key` 私钥权限 | 高 |
| 内核参数 | `ip_forward`、`accept_redirects`、`accept_source_route`、`rp_filter`、`syncookies`、`randomize_va_space`、core dump | 中 |
| 审计与日志 | auditd 状态、rsyslog 状态、`/var/log` 权限、日志保留配置 | 中 |
| 服务与端口（本机合规） | 危险服务监听（telnet/ftp/tftp）、`0.0.0.0` 高危端口、Docker socket 权限 | 高 |
| 容器 | `--icc`、`--userns-remap`、特权容器数量 | 中 |
| Web 服务 | 版本、目录列表、`.git`/`.env` 可访问、TLS 协议版本 | 中 |

注：这里的"危险服务监听"是本机配置合规（读本地端口表判断是否暴露），与归 OpsAnt 的
"端口可用性监控/存活探测"是两件事，不冲突。

## 4. 告警规则：12 → 24

现有 12 条全是"采样指标 > 阈值"，新增 12 条事件型，均在本机能力范围内：

| 新规则 | 需要的新采集 | 说明 |
|---|---|---|
| 磁盘写满预测 | 24h 线性斜率 | 比"已用 90%"更早 |
| 磁盘只读 / 文件系统错误 | 挂载状态 + dmesg | ext4 error 是故障前兆 |
| 僵尸进程数 > N | `ps` 统计 Z | — |
| OOM Killer 触发 | `journalctl -k` | 事后告警但关键 |
| 内核崩溃 / 硬件错误 | `journalctl -k`（MCE/EDAC） | — |
| 系统意外重启 | boot time 变化 | — |
| NTP 时间偏移过大 | `timedatectl` / chrony | 时间漂移毁掉日志时序 |
| 计划任务执行失败 | 现有 cron `last_status` | 数据已有，缺规则 |
| Docker daemon 不可用 / 容器意外退出 | 现有 docker SDK | — |
| 备份任务失败 | 依赖备份模块 | 备份做完再加 |
| 日志管道停滞 / 丢弃率高 | `opsmini_log_*` 指标 | 日志做完再加 |
| 告警抑制 | 同一规则 30 分钟内只通知一次 | 现有只在"未恢复"期间去重 |

## 5. 明确不做

| 不做 | 原因 |
|---|---|
| 多机集中管理、服务存活、端口监听、证书到期 | 需要平台视角，归 OpsAnt |
| K8s / Docker autodiscover | OpsMini 不装在 K8s 里 |
| Windows 采集 | 只跑 Linux |
| 变更因果推断、变更审批流 | 需要反事实推理 / 属于配置审计系统 |
| eBPF | 内核兼容成本高，放在日志之后单独评估 |
| 网站管理、数据库管理 | 与单机 Agent 定位冲突，暂停 |

## 6. 批次与顺序

**注意**：`v1.4-change-awareness.md` 里已经用过 M1~M5 编号（变更感知的五个里程碑），
为避免混淆，这里的批次用 **B1~B6（Batch）**；子文档内部的 L*/P* 编号保持各自含义。

| 批次 | 内容 | 依赖 | 可独立部署验收 |
|---|---|---|---|
| **B1** | 日志管道：tail 抽取 → filestream → ES output → registry → `tasks.d` 热加载 | 无 | 是（手工放任务文件） |
| **B2** | 日志 processor 全集（31 个）+ multiline + 磁盘 spool + 实时预览 | B1 | 是 |
| **B3** | 日志 Kafka / Logstash（Lumberjack v2）+ 管道指标 | B2 | 是 |
| **B4** | 插件系统：proto 扩展 + 安装/卸载/启停 + socket 协议 + cgroup 限制 | 无（可与 B1-B3 并行） | 是 |
| **B5** | 日志 `LogTask` 下发 + 任务状态回报 + 插件 OpsAnt 下发联调 | B1-B4 | 需 OpsAnt 配合 |
| **B6** | 备份恢复 + 基线 45 项 + 告警 24 条 | B5 | 是 |

排序理由：

1. **日志先于插件**：日志要的 Kafka / Lumberjack 输出端本来就是插件契约的试金石，反过来做契约会缺一半场景。
2. **插件与日志并行**：两者唯一交汇点是 B5 的 proto 扩展，可各自独立跑通再合并。
3. **备份最后**：复用日志验证过的"大文件传输 + 断点续传"，也依赖插件定的存储抽象。
4. **B5 必须等 OpsAnt**：单机自测覆盖不了下发与状态回报，这是唯一的跨项目依赖，要提前对齐工期。

## 7. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| filebeat 配置兼容度不足 | 平台下发的任务在 OpsMini 上跑不起来，兼容承诺失效 | 用平台**现网任务配置**做回归样本；B5 做双机比对 |
| Lumberjack v2 实现偏差 | Logstash 侧丢数据或重复 | 对着 beats 协议逐帧校验，跑 ACK 断网重连用例 |
| `script` processor 语义差异 | 用户脚本在 goja 上行为不同 | 只支持 ES5.1 并明确文档化；复杂逻辑建议仍用 filebeat |
| 插件权限模型不足 | 第三方插件越权读文件 | MVP 只信任官方签名插件；第三方默认最小能力 + 文档写明边界 |
| 备份恢复失败 | 覆盖生产数据 | 强制"恢复前自动快照 + 失败自动回滚"，在测试主机做破坏性验证 |
| 一次性做太多 | v1.4.0 延期 | 按 B1-B6 分批部署验收，每批独立跑通再进下一批 |

## 8. v1.4.0 发布前的验收门槛

1. 单机模式（不接 OpsAnt）：面板全部功能正常，`tasks.d` 为空时日志模块零开销。
2. 纳管模式：平台下发 filebeat 任务 → ES 里能查到数据，字段与真 filebeat 一致。
3. 同一批主机里既有 filebeat 主机又有 OpsMini 主机，同一份任务两边产出等价。
4. 备份：一个目录 + 一个数据库能完整还原；故意制造失败，能自动回滚。
5. 基线 45 项、告警 24 条在真实主机跑一遍，无误报。
6. 卸载：`install.sh -U` 后除数据目录外无残留，`--purge` 后彻底干净。
