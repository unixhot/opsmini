# 日志采集管道设计（对标 Filebeat）

> 状态：设计稿（2026-10-29，按决策修订）
> 目标：让 OpsMini 同时具备「指标采集（node_exporter 兼容）+ 日志采集（filebeat 兼容）」。
> 三条决策：**完整支持 filebeat 的数据处理能力**；**输出只做 ES / Kafka / Logstash 三种**；K8s 相关一律不做。
> 一条更硬的约束（见 §5）：**采集任务由 OpsAnt 下发，一个任务 = 一份 filebeat 配置，OpsMini 必须能原样吃下它。**
> 目标是「同一套任务，装 filebeat 能跑，装 OpsMini 也能跑」——OpsMini 是 filebeat 的 drop-in 替代，不是另一套体系。
> 第四条决策：**单机场景不采集日志**。日志能力只在被 OpsAnt 纳管后启用——它的价值是替掉主机上那个 filebeat，
> 而不是给单机用户加一个日志功能。没有平台时，日志模块不占任何资源、不出现任何配置入口。
> 前置结论：**不引入 libbeat**，做 filebeat 的兼容实现。

---

## 1. 体积账（本设计最关键的决策）

filebeat 是 Go 写的，但它是"大而全"的 Go：

| 方案 | 体积增量 | 风险 |
|---|---|---|
| `import github.com/elastic/beats/v7/libbeat` | **+45~60MB**（K8s autodiscover 的 client-go、全量 outputs、elastic-agent-client、monitoring 全部拖进来） | libbeat 对 Go 版本与依赖版本敏感，与 OpsMini 现有依赖树冲突；升级节奏被 Elastic 绑死 |
| 自研 filebeat 兼容实现 | **+6~9MB**（见 §6 明细） | 需要自己实现 dissect / script / lumberjack，工作量大但可控 |
| 独立 sidecar 复用官方 filebeat | 主程序 0 增量，但要额外分发 90MB 二进制 | 破坏"单二进制交付"这个核心卖点 |

**选择：自研。** 单二进制、`CGO_ENABLED=0`、37MB 是 OpsMini 的立身之本，为了日志把体积翻倍不划算。

现状对比：OpsMini `-s -w` 后 **37MB**；filebeat 8.15 linux/amd64 **约 95MB**。自研后预期 **43~46MB**。

## 2. 功能划线

### 2.1 input（与 filebeat 对齐）

| 支持 | 说明 |
|---|---|
| `filestream` / `log` | 多文件 glob、文件轮转（inode 变化）、文件截断检测、`ignore_older`、`exclude_files`、`close_inactive` |
| `multiline` | `pattern` / `negate` / `match: after\|before` / `max_lines` / `timeout` |
| `encoding` | utf-8、gbk（国内日志常见）、latin1 |
| `json`（input 级解析） | `keys_under_root`、`overwrite_keys`、`expand_keys` |
| `container`（stdout 文件） | 仅支持读 `/var/lib/docker/containers/*/*-json.log`，**不做** Docker/K8s autodiscover |

**不做**：`udp`/`tcp`/`syslog` input（用 syslog processor 处理文件日志即可）、`journald` input（v2 评估，需 cgo 或 journalctl 子进程）、`winlog`（Windows 事件日志）。

### 2.2 processor（完整支持，见 §3）

filebeat 8.x 共 38 个 processor + 全局 `when` 条件。**31 个v1.4.0全做**，5 个二期，2 个平台相关不做（明细见 §3.2）。

### 2.3 output（按决策只做三种）

| output | 协议 | 说明 |
|---|---|---|
| Elasticsearch | `_bulk` NDJSON over HTTP | 支持 `index` 日期模板、`pipeline`、`username/password`、`api_key`、TLS、`bulk_max_size`、`flush_interval`、`backoff` |
| Kafka | Kafka 协议（`franz-go`，纯 Go） | 支持 `topic`、`partition.hash/round_robin/random`、`compression`（gzip/snappy/lz4/zstd）、SASL/PLAIN、TLS、`required_acks` |
| Logstash | **Lumberjack v2（Beats 协议）** | 支持 `hosts`、`loadbalance`、TLS、`ttl`、`slow_start`、`compression_level`；这是与 Logstash 对接的唯一方式，必须自己实现协议 |

**不做**：Loki、Redis、File、Console、S3、OpsAnt 直连。
（OpsAnt 需要日志时，从同一个 ES 或 Kafka 消费——日志总线只保留一份，避免造第二条链路。）

### 2.4 瘦身清单：相对 filebeat 少的是什么

定位是"把 filebeat 瘦身后嵌进 OpsMini"，所以必须把少掉的部分列清楚——**少的部分都是单机场景用不到的**：

| 砍掉 | 原因 | 影响 |
|---|---|---|
| Kubernetes / Docker autodiscover | OpsMini 不装在 K8s 里；容器日志按固定路径读即可 | 容器编排环境用不了 |
| Beats central management（`management.*`） | 配置只从 OpsAnt 下发 | — |
| `monitoring.*` 自上报到 ES | 用自己的 `/metrics` 暴露管道指标 | 平台侧改用 OpsMini 的指标 |
| 7 个 output（Loki/Redis/File/Console/S3/MQTT/Logstash-其它模式） | 只保留 ES/Kafka/Logstash | 用到别的出口装原版 filebeat |
| Windows 相关（`winlog` input、`decode_xml_wineventlog`、`translate_sid`） | OpsMini 只跑 Linux | Windows 主机用原版 |
| `translate_ldap`、`add_*_metadata` 的部分子项 | 需要外部服务或平台元数据 | 二期评估 |
| 打包体积里的 k8s client-go / elastic-agent-client | 正是瘦身的主要收益 | — |

一句话：**filebeat 是通用采集器，OpsMini 是"Linux 单机 + 被纳管"这一种场景的专用实现。**
判断标准是"同一份 YAML 能不能跑"，不是"字段一个不少地认识"。

## 3. processor 清单与实现成本

### 3.1 v1.4.0全做（31 个）

| 分类 | processor | 说明 / 实现要点 |
|---|---|---|
| 字段增删改 | `add_fields` `add_tags` `drop_fields` `include_fields` `rename` `copy_fields` `move_fields` `truncate_fields` | 纯 map 操作，注意 `@metadata` 与 `fields.*` 的路径语义 |
| 类型与编码 | `convert`（int/float/string/bool/ip）、`urldecode_fields`、`decode_base64_field`、`decompress_gzip_field` | `convert` 要处理失败策略（`ignore_missing`/`fail_on_error`） |
| 结构化解析 | `decode_json_fields`、`decode_csv_fields`、`decode_xml`、`decode_duration`、`dissect`、`extract_array`、`syslog` | `dissect` 需实现 `%{field}` `%{field->}` `%{?skip}` `%{+append}` `%{&key}` 全套语法 |
| 标识与富化 | `add_id`、`add_locale`、`add_host_metadata`、`add_network_direction`、`community_id`、`fingerprint`、`registered_domain` | `community_id` 实现 v1 哈希算法；`registered_domain` 内置公共后缀表（可裁剪到常用 TLD）；`add_host_metadata` 精简为 host.name/os/arch/ip |
| 流程控制 | `drop_event`、`when` 条件、`dns`（带正向/反向缓存）、`timestamp`、`replace`、`script` | `when` 支持 `equals` `contains` `regexp` `range` `and/or/not`；`timestamp` 需支持 filebeat 的时间格式串（`2006-01-02T15:04:05.999Z07:00` 等） |

`script` 是唯一需要嵌入运行时的：filebeat 默认 `lang: javascript`。**建议用 `goja`（纯 Go ES5.1 引擎，+3.5MB）**，这样用户现有的 filebeat script 配置能直接搬过来；若坚持省体积，可换 `gopher-lua`（+1MB）但要改脚本语法（不兼容）。

### 3.2 二期 / 不做

| processor | 结论 | 原因 |
|---|---|---|
| `add_cloud_metadata` | 二期 | 要适配阿里云/腾讯云/AWS 等多套元数据服务，单机场景用得少 |
| `add_process_metadata` | 二期 | 需从 `/proc` 反查进程信息，Linux 可做，价值中等 |
| `add_observer_metadata` | 二期 | Beats 自身观测元数据，用 OpsMini 自己的 host 字段替代更合理 |
| `decode_cef` | 二期 | 安全设备 CEF 格式专用，纯 Go 可写但受众极小 |
| `translate_sid` | 二期 | Windows/Samba SID 翻译 |
| `decode_xml_wineventlog` | 不做 | Windows 事件日志专用 |
| `translate_ldap` | 不做 | 需要连接 LDAP 服务，属于平台能力（OpsAnt 做更合适） |

## 4. 架构

```
                    ┌──────────────── pipeline (每 input 一个) ─────────────────────┐
文件系统 ──▶ input ─▶│ harvester(每文件一 goroutine) ─▶ 内存队列 ─▶ processor 链 (31 个) │─▶ output ─▶ ES / Kafka / Logstash
   ▲                 └──────────────────────────────────────────────────────────────────┘
   │                                     │ 背压
   │                                     ▼
   └── registry(inode+offset) ◀── 磁盘 spool（满了落盘，at-least-once）
```

1. **harvester**：单文件读取协程，负责"按行读 + 行缓冲 + 多行合并 + 轮转检测"。**复用 `internal/sentinel/logwatch.go` 的 tail 实现**（它已处理 inode 变化、截断、半行），抽成 `internal/pkg/tail` 给两处共用。
2. **队列**：内存 channel（默认 4096 事件/批）。满了写磁盘 spool（每批一个文件，原子 rename），output 恢复后按序回放——解决"ES 挂 10 分钟日志全丢"。
3. **processor 链**：纯函数 `func(*Event) []*Event`（`extract_array`/`decode_csv` 可能一进多出）。注册表按名字查，配置即数据，不做代码生成。
4. **output**：接口 `Publish(ctx, batch []Event) error`。三种实现共用重试/退避/限流框架，差异只在协议。
5. **registry**：`logs_registry` 表（与 `change_offsets` 同构），只有 output 确认成功后才推进 offset —— 这是 at-least-once 的关键。

## 5. 配置从哪来：OpsAnt 下发，一个采集任务 = 一份 filebeat 配置

这是本设计与「自研日志功能」最本质的区别：**OpsMini 不自己发明任务格式**。
日志平台的统一设计是「一个采集任务 = 一份 filebeat 配置文件」，OpsAnt 把这坨 YAML 原样下发，
OpsMini 只负责加载与执行。

**单机场景不启用日志采集**：日志不是给单机用户的功能，它存在的意义是"被 OpsAnt 纳管的主机不必再装一个 filebeat"。
因此：

- 没有任何自动启用的采集任务，`tasks.d/` 为空时管道根本不启动（零 goroutine、零内存、零磁盘）；
- 面板里**没有"新建采集任务"入口**——任务只从 OpsAnt 下发。面板只负责「看任务、看状态、看实时数据」；
- 手工放一个 YAML 进 `tasks.d/` 仍然会生效（这是留给调试与离线验证的口子，不是产品路径），
  但它与下发的文件走完全相同的加载逻辑，不存在第二套解析。

这样做的原因很实际：一台单机装 OpsMini，是为了看指标、查变更、用 AI 排障；它没有日志平台，也没有
"把日志送到哪"的答案。硬塞一个日志配置界面，只会让用户配一个发不出去的管道。

### 5.1 为什么必须原样兼容 filebeat 配置

因为平台要能做到"同一套任务，下发到 filebeat 或 OpsMini 都能跑"：

| 主机上的采集器 | 平台下发什么 | 平台怎么下发 |
|---|---|---|
| node_exporter + filebeat | filebeat 的 YAML | 写 `/etc/filebeat/inputs.d/<task>.yml` → `systemctl reload filebeat` |
| 只装 OpsMini（被 OpsAnt 纳管） | **完全相同的 YAML** | 写 `/data/opsmini/data/logs/tasks.d/<task>.yml` → 触发 reload |

平台侧**不需要为 OpsMini 写第二套配置格式、不需要区分采集器类型**，只需要换目标路径与 reload 方式。
这是"兼容"的硬标准：**如果同一份 YAML 在 filebeat 上能跑、在 OpsMini 上报错，就是我们的 bug。**

### 5.2 目录布局（与 filebeat 一一对应）

```
filebeat                              OpsMini
/etc/filebeat/filebeat.yml        ↔   /data/opsmini/data/logs/opsmini.yml      # 主配置（output + 全局项）
/etc/filebeat/inputs.d/*.yml      ↔   /data/opsmini/data/logs/tasks.d/*.yml    # 采集任务，一任务一文件
/var/lib/filebeat/registry        ↔   /data/opsmini/data/logs/registry.db  # 读取位点
/var/lib/filebeat/filebeat.lock   ↔   /data/opsmini/data/logs/pipeline.lock
```

filebeat 侧对应的是 `filebeat.config.inputs.{enabled,path,reload.enabled}`；
OpsMini 用**相同语义**：主配置里写 `tasks.d` 路径与 reload 间隔，任务文件只负责 input + processors。

### 5.3 一个任务的两种写法，都接受

日志平台历史上会产出两种形态，OpsMini 两种都必须能吃：

```yaml
# 写法 A（推荐，与 filebeat 的 inputs 片段完全一致）：任务只描述采集
# /data/opsmini/data/logs/tasks.d/task-1024-nginx.yml
- type: filestream
  id: task-1024-nginx-access
  paths: ["/var/log/nginx/access.log"]
  fields:
    task_id: "1024"
    service: nginx
  processors:
    - dissect:
        tokenizer: '%{clientip} - - [%{ts}] "%{method} %{path} HTTP/%{version}" %{status}'
```

```yaml
# 写法 B：任务文件自带 output（平台按任务分配不同出口时用）
# OpsMini 的扩展：filebeat 需要多实例才能做到，我们允许 per-task 覆盖
filebeat.inputs:
  - type: filestream
    id: task-2048-app
    paths: ["/var/log/app/*.log"]
output.elasticsearch:
  hosts: ["http://10.0.0.5:9200"]
  index: "app-%{+yyyy.MM.dd}"
```

规则：**任务文件里有 output 就用它，没有就继承主配置的 output**。filebeat 原生不支持 per-input output，
所以写法 B 属于 OpsMini 的扩展能力——下发方要保证「只有目标确定为 OpsMini 时才用写法 B」。
这条边界写清楚，避免同一份配置在 filebeat 上静默跑错出口。

### 5.4 热加载语义（与 filebeat reload 对齐）

| 行为 | filebeat | OpsMini |
|---|---|---|
| 新增任务文件 | 下个扫描周期生效 | 同（默认 10s 扫描 `mtime`） |
| 修改任务文件 | 重建该 input 的 harvester | 同，**位点保留**（按 `input.id` + inode 找回） |
| 删除任务文件 | 停止该 input | 同，位点保留 24h 再清 |
| 主配置 output 变更 | 需重启 | 重建 output，队列里的事件先落 spool 再重发 |

任务文件必须带 `id`（filebeat 8 的 filestream 也要求 `id`）：**`id` 是位点与状态的主键**，
没有 `id` 时按「文件路径 + input 序号」派生一个稳定 ID，否则改配置就会重读整个文件。

### 5.5 下发通道（proto 扩展）

与插件共用一次协议扩展，新增下行 `LogTask`：

```proto
message LogTask {
  string job_id  = 1;
  string action  = 2;   // apply | remove | reload | status
  string task_id = 3;   // 平台侧任务 ID，落到 fields.task_id
  string filename= 4;   // tasks.d 下的文件名（不含路径）
  bytes  content = 5;   // 完整 YAML（原样落盘，不做二次加工）
  string sha256  = 6;   // 内容摘要，Agent 据此判断是否需要重写
  bool   strict  = 7;   // true = 未知字段导致加载失败；false = 记 warning 继续
}

message LogTaskResult {
  string job_id   = 1;
  string task_id  = 2;
  string status   = 3;  // applied | running | failed | removed
  string error    = 4;
  repeated string warnings = 5;  // 未知字段、字段类型不符等
}
```

选择专用消息而不是复用 `PushFileTask` 的三个理由：

1. **幂等**：`sha256` 相同就不重写文件、不触发 reload；
2. **可回收**：`task_id` 让 Agent 能回报"这个任务现在什么状态"，而不是只能回报"文件写成功了"；
3. **可回滚**：写入用临时文件 + `rename` 原子替换，加载失败自动恢复上一版。

### 5.6 状态回报（OpsAnt 需要看什么）

Agent 每 30s（或状态变化时）上报每个任务的一行：

```json
{"task_id":"1024","input_id":"task-1024-nginx-access","state":"running",
 "files_open":2,"bytes_read":10485760,"events_sent":88123,"events_dropped":0,
 "queue_depth":12,"last_error":"","out":"elasticsearch","updated_at":"2026-10-29T08:50:00+08:00"}
```

OpsAnt 侧据此在主机详情页显示"任务是否真的在采集"，而不是只显示"配置已下发"。
**这两个状态经常不一致**（路径写错、权限不足、磁盘满），只有回报才能发现。

### 5.7 兼容性矩阵（哪些字段必须一致）

| 字段 | 要求 | 说明 |
|---|---|---|
| `@timestamp` | ✅ 必须 | 事件时间，ES 索引与看板都靠它 |
| `log.file.path` / `log.offset` | ✅ 必须 | 溯源用，缺了就无法定位 |
| `input.type` / `input.id` | ✅ 必须 | 多任务区分 |
| `host.name` / `host.os.*` / `host.arch` | ✅ 必须 | 平台按主机聚合 |
| `ecs.version` | ✅ 必须 | 输出 `8.11.0`，与 filebeat 对齐 |
| `agent.type` / `agent.version` / `agent.id` | ⚠️ 可配置 | 默认 `opsmini`（真实值）；平台模板强依赖 `filebeat` 时改配置 |
| `fields.*` | ✅ 必须 | 任务里声明的自定义字段原样输出 |
| `event.dataset` | ✅ 必须 | 未声明时用 `input.id` 派生 |

`agent.type` 的处置（已定）：**默认输出真实值 `opsmini`，可通过配置改成 `filebeat`**。
放在 OpsMini 自己的 `config.yaml` 里，不污染任务文件——任务文件必须是 100% 原生的 filebeat YAML：

```yaml
# /data/opsmini/config.yaml
logpipeline:
  compatibility:
    # opsmini（默认）| filebeat
    # 设为 filebeat 时 agent.type 输出 filebeat，用于直接复用现成的 ES 索引模板与看板
    agent_type: opsmini
```

之所以做成"每台机器可配"而不是全局常量：迁移期间同一批主机里可能一部分复用旧模板、一部分用新模板，
放在本机配置里最灵活。

### 5.8 未知字段的处理（strict 开关）

filebeat 配置里必然有我们不支持的段（例如 `setup.*`、`monitoring.*`、`processors: [add_cloud_metadata]`）。
策略：

- 默认 `strict=false`：**忽略未知字段，记录 warning 并回传给 OpsAnt**，管道照常跑；
- `strict=true`：出现未知字段即加载失败，任务不启动 —— 用于灰度验证阶段，避免"以为在采集其实没采"。

`output.*` 是唯一不能"忽略"的段：出口类型不支持必须硬失败，否则日志会静默丢失。

## 6. Logstash output：为什么必须实现 Lumberjack v2

filebeat 到 Logstash 不走 HTTP，走 Beats 私有的 **Lumberjack v2** 协议（TCP + 自定义二进制帧）。要支持 Logstash output，就得实现它：

```
握手：客户端发 "2W" + windowSize(uint16)   → 服务端回 "2W" + windowSize
数据帧：
  version(1B=2) type(1B)  payloadLen(uint32BE)  payload
  type: 'W' = window size（窗口内已发字节数）
        'C' = compressed（payload 是 zlib 压缩后的若干 'J'/'D' 帧）
        'J' = JSON 帧（一条完整事件）
        'D' = data 帧（配合 seq 做分片，大事件用）
  seq(uint32BE) —— 'J'/'D' 帧特有，服务端据此回 ACK
ACK：服务端发 version(2) type('2') seq(4) 表示已落盘
```

实现要点：

- **窗口机制**：未 ACK 的字节数不能超过 windowSize，否则阻塞（这是背压的来源，天然与队列配合）；
- **必须是 at-least-once**：收到 ACK 才能推进 offset，未 ACK 的事件重启后重发（Logstash 侧靠 `document_id` 去重）；
- **压缩**：`compression_level` 默认 3，用标准库 `compress/zlib`；
- **TLS**：Logstash 通常开 5044 + TLS，需支持 `ssl.certificate_authorities` 单向校验。

代码量约 600 行，零外部依赖（标准库 `net` + `compress/zlib` + `encoding/binary`）。

## 7. 体积明细（37MB 起算）

| 组件 | 增量 |
|---|---|
| tail + registry + input(filestream/multiline/encoding) | +1.5MB |
| 31 个 processor（含 dissect/syslog/decode_xml/dns） | +1.2MB |
| `script` processor（goja，JS） | +3.5MB |
| Elasticsearch output（HTTP + NDJSON 自写） | +0.2MB |
| Kafka output（franz-go） | +2.5MB |
| Logstash output（Lumberjack v2 自写） | +0MB |
| spool 压缩（`klauspost/compress` zstd，可选） | +1.5MB |
| **合计** | **+8.9MB → 约 46MB** |

若把 `script` 换成 `gopher-lua`（不兼容 filebeat 的 JS 语法）可降到 **+6.4MB / 约 43MB**。建议保持 goja，兼容性比 3MB 体积重要。

参照：filebeat 本体 95MB，且不含 OpsMini 的面板、Agent、AI、安全模块。

## 8. 配置文件（filebeat 原生格式，不做二次发明）

**解析器直接吃 filebeat 的 YAML 结构**，不定义自己的 schema。三个必须兼容的语法细节：

| 细节 | 处理 |
|---|---|
| 顶层 `filebeat.inputs:` 与裸 `inputs:` | 两种都接受（filebeat 8 用前者，平台早期配置可能是后者） |
| `filebeat.config.inputs.path` 指向的外部片段 | 支持，用于"任务文件只有 input"的写法 A |
| 顶层 `output.elasticsearch/kafka/logstash` | 与 input 同级，按 filebeat 的字段名解析，不换名字 |

主配置 `opsmini.yml`（output + 全局项）与任务文件分离，与 filebeat 的 `filebeat.yml` + `inputs.d/*.yml` 同构：

```yaml
# 主配置：/data/opsmini/data/logs/opsmini.yml（平台下发或安装时生成）
filebeat.config.inputs:
  enabled: true
  path: /data/opsmini/data/logs/tasks.d/*.yml
  reload.enabled: true
  reload.period: 10s

output.elasticsearch:
  hosts: ["http://127.0.0.1:9200"]
  index: "opsmini-%{+yyyy.MM.dd}"
  bulk_max_size: 2000
  flush_interval: 5s
```

```yaml
# 任务文件：/data/opsmini/data/logs/tasks.d/task-1024-nginx.yml（一个任务一个文件，写法 A）
- type: filestream
  id: task-1024-nginx-access
  paths: ["/var/log/nginx/access.log"]
  exclude_files: ['\.gz$']
  multiline:
    pattern: '^\s'
    negate: false
    match: after
  fields:
    task_id: "1024"
    service: nginx
    env: prod
  processors:
    - decode_json_fields:
        fields: ["message"]
        target: ""
        overwrite_keys: true
    - dissect:
        tokenizer: '%{clientip} - - [%{ts}] "%{method} %{path} HTTP/%{version}" %{status}'
        field: "message"
        target_prefix: ""
    - drop_fields:
        fields: ["agent", "ecs", "host.architecture"]
```

三种 output 的完整写法（都在主配置里，互斥）：

```yaml
output.elasticsearch:
  hosts: ["http://127.0.0.1:9200"]
  index: "opsmini-%{+yyyy.MM.dd}"
  bulk_max_size: 2000
  flush_interval: 5s

output.kafka:
  hosts: ["127.0.0.1:9092"]
  topic: "opsmini-logs"
  partition.hash:
    hash: ["host.name"]
  compression: gzip
  required_acks: 1

output.logstash:
  hosts: ["127.0.0.1:5044"]
  loadbalance: true
  compression_level: 3
  ttl: 60s

queue.disk:
  path: /data/opsmini/data/logs/spool
  max_size: 512MB

# 以下 filebeat 段会被识别但忽略（strict=false 时记 warning）
# setup.* / monitoring.* / logging.* / path.*
```

## 9. 面板交互（只读，不新建）

单机不配日志任务，所以面板这一页是**观测页而不是配置页**，三个区块：

1. **任务列表**：从 `tasks.d/` 读到的任务（task_id / 路径 / output / 状态 / 速率 / 来源=下发或手工），
   **没有"新增"按钮**。想改任务去 OpsAnt 改——这是唯一入口，避免两套语义。
2. **实时预览**：选一个任务，看最近 50 条**经过 processor 之后**的事件（JSON）。这是 filebeat 最缺的能力
   （它只有 `test output` 验连通性），调 multiline 和 dissect 时不可或缺。
3. **管道健康**：每个任务的已读字节、发送条数、丢弃条数、队列深度、最近错误；三种 output 的连接状态与重试次数。

未纳管（`tasks.d/` 为空）时，这一页显示"当前主机未接入日志平台"，而不是一个空表格让人以为坏了。

## 10. eBPF 的位置

方向是"指标 + 日志 + eBPF = 完整可观测 Agent"，但顺序要讲究：

| 阶段 | 能力 | 依赖 | 体积 |
|---|---|---|---|
| v1.4.0 | 指标（已有）+ 日志（本设计） | 无 | +9MB |
| v1.6 | eBPF 网络/进程观测 | 内核 ≥ 5.4 + BTF，`cilium/ebpf`（纯 Go） | +3~5MB |
| v1.7 | 安全检测（替代 FIM、提权检测） | 上一阶段 + 规则引擎 | 复用 |

理由：CentOS 7（内核 3.10）与多数云厂商定制内核跑不了 eBPF，而日志/指标 100% 可用；99% 的排障靠"指标 + 日志 + 变更"就能闭环，eBPF 解决的是进程级因果，属深水区且支撑成本高。

---

## 11. 实施拆分

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| L1 | tail 层抽取 + registry + filestream input + ES output | `/var/log/syslog` 完整入 ES，重启从断点续读不丢不重 |
| L2 | **`tasks.d` 多文件加载 + 热加载 + 位点按 `input.id` 保留** | 一个任务一个文件；改文件不重启即生效且不重读 |
| L3 | multiline + processor 框架 + 12 个常用 processor | nginx 日志经 decode_json + dissect 后字段正确 |
| L4 | 剩余 19 个 processor（含 dissect 全语法、script/goja、dns、community_id） | filebeat 官方 processor 用例逐条对照通过 |
| L5 | 磁盘 spool + 背压 + 管道指标 + 实时预览 | 停 ES 5 分钟，恢复后日志补齐且内存不涨 |
| L6 | Kafka output + Logstash output（Lumberjack v2） | 三个 output 各验证一次，含断网重连与 ACK 语义 |
| L7 | `LogTask` 下发 + 任务状态回报（对齐 filebeat 兼容矩阵） | **同一份 YAML 分别在装了 filebeat 和 OpsMini 的主机上跑，ES 文档字段一致** |
| L8 | 性能压测（目标：单核 5000 行/秒，内存 < 80MB） | 压测报告归档 |

L7 是这套设计的验收核心，也是最容易出问题的地方：**同一份配置、两台主机、两种采集器，产出必须等价**。
建议直接拿日志平台现网产出的任务配置做回归样本，而不是自己编几份"看起来合理"的 YAML。

性能目标保守是有意的：单机面板真实日志量通常 100~2000 行/秒，5000 留 2.5 倍余量，也避免为性能把代码写成不可读的零拷贝。
