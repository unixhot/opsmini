# 主機安全設計

> 本文講的是**「主機安全」這個功能是怎麼設計和實現的**：每項檢測看什麼、判據是什麼、分數怎麼算、邊界在哪、為什麼這麼選。
>
> 對應程式碼：`internal/service/{security,baseline,loginsecurity,firewall,fim,threat,securitymonitor}.go`、`internal/api/v1/{security,baseline,fim,threat,firewall}.go`、`internal/router/router.go`。

---

## 1. 設計目標與非目標

### 目標

| 目標 | 具體含義 |
| --- | --- |
| **零依賴** | 不裝 agent、不依賴核心模組、不連中心服務，二進位制帶起來就能審 |
| **可解釋** | 每一項檢測都能點開看到「讀了哪個檔案、看到什麼值、為什麼判不合格、建議怎麼改」 |
| **可動手** | 發現問題後能直接在面板裡修（改防火牆、跑體檢、重建基線、標記威脅已處理） |
| **給人看，也給 AI 看** | 同一份結論既渲染成頁面，也作為只讀工具交給內建 Agent |
| **不越權** | 只讀能力登入即可用；任何改系統的動作都要單獨的許可權點 + root 身份 |

### 非目標（是取捨，不是沒做完）

- **不做 HIDS 替代品**：不做核心 syscall 鉤子、不做 eBPF 探針、不做全流量檢測。這類能力必須常駐高許可權採集，與"單二進位制、幾十 MB、可隨手裝"的定位衝突。
- **不做多機態勢**：單機給出單機結論。多臺機器的彙總屬於 OpsMini Server / Proxy 的職責。
- **不自帶規則庫引擎**：基線判據寫在程式碼裡（14 項），不接受 YAML 規則熱載入。規則可熱載入聽起來靈活，但會讓"為什麼這臺機器 62 分"變得無法復現。規則外接是演進方向（見 §16）。
- **不替代專業合規掃描**：不做等保/CIS 的完整條目覆蓋與出證，只做"日常能被看見、能被執行"的那部分。

## 2. 能力地圖

主機安全頁面是六個頁籤，本質是**五個檢測模組 + 一個彙總檢視**：

| 頁籤 | 檢測什麼 | 資料來源 | 觸發方式 | 是否改系統 |
| --- | --- | --- | --- | --- |
| 安全總覽 | 彙總裁剪：總分、等級、五模組得分與一句話結論 | 其餘五個模組的落庫結果 | 開啟頁面 | 否 |
| 基線體檢 | 14 項主機加固現狀 | `/etc/ssh/sshd_config`、`/etc/passwd`、`/etc/shadow`、`/etc/login.defs`、crontab、監聽埠 | 手動點「開始體檢」 | 否 |
| 登入安全 | 暴力破解、異常登入、SSH 加固建議 | `/var/log/auth.log` 或 `/var/log/secure` | 開啟頁面 | 否 |
| 防火牆 | 當前後端與規則；放行/封禁埠、啟停 | `ufw` / `firewall-cmd` / `iptables` 的實際狀態 | 手動操作 | **是** |
| 檔案完整性 | 關鍵檔案是否被改/被刪 | 8 個系統關鍵檔案的 SHA256 | 後臺每 60 秒 | 否 |
| 威脅檢測 | 挖礦程序、可疑計劃任務、可疑自啟動 | `/proc`、crontab、`/etc/rc.local`、systemd 服務列表 | 後臺每 5 分鐘 + 手動 | 否（處置要人來做） |

設計上的一個明確決定：**只有防火牆會改動系統**。其餘四個模組是純觀察者，即使誤判也只會讓分數難看，不會讓機器出事。

## 3. 架構：兩條互不依賴的通路

OpsMini 裡有兩套和安全相關的東西，它們看起來像，實際上是兩條獨立通路：

```
                  ┌──────────── 體檢通路（pull，給人看） ────────────┐
  /etc、/proc ───▶ │ BaselineService  登入分析  FIM  威脅掃描        │ ──▶ SQLite ──▶ 安全頁面 + 評分
  認證日誌        │ SecurityService 彙總打分                        │
                  └──────────────────────────────────────────────────┘

                  ┌──────────── 感知通路（push，給 Agent） ──────────┐
  auth.log、站點   │ sentinel 採集器（logwatch/authwatch/           │ ──▶ 訊號 ──▶ 事件 ──▶ 策略
  目錄、程序表     │ filewatch/procwatch/netwatch/metricwatch）      │        ──▶ Agent 處置
                  └──────────────────────────────────────────────────┘
```

**為什麼分成兩條，而不是合併成一條？**

| 維度 | 體檢通路 | 感知通路 |
| --- | --- | --- |
| 互動模型 | 拉：你開啟頁面 / 點掃描 | 推：採集器一直在跑 |
| 輸出 | 清單 + 分數（可長期儲存的狀態快照） | 訊號 → 事件（有時效性的流） |
| 消費者 | 人 | 策略引擎 + AI Agent |
| 判定性格 | 「現狀合不合規」 | 「剛剛發生了什麼」 |
| 誤判代價 | 分數難看 | 可能觸發自動處置 |

合併會讓兩邊互相拖累：體檢要能隨時重算，感知要能持續增量；一條通路加個狀態機，另一條就被迫帶著它跑。

**代價也要說清楚**：兩條通路各自解析認證日誌（`service/loginsecurity.go` 與 `sentinel/authwatch.go` 是兩套正則），口徑存在漂移風險。這是已知技術債，見 §16。

## 4. 安全評分模型

總分 100，五個模組固定權重：

| 模組 | 滿分 | 為什麼是這個權重 |
| --- | --- | --- |
| 基線體檢 | 40 | 唯一「你可以主動改好」的部分，也最能反映日常運維水位 |
| 登入安全 | 20 | 公網機器出事十有八九從這裡開始 |
| 防火牆 | 15 | 有或沒有，直接決定暴露面 |
| 檔案完整性 | 15 | 被改關鍵檔案通常意味著已經失守 |
| 威脅檢測 | 10 | 權重低是因為它最容易被誤判（見 §10） |

### 各模組計分規則（與程式碼一一對應）

**基線（0–40）**：按權重加權，不是按條目數。

```
got   = Σ(pass 項權重) + Σ(warn 項權重 × 0.5)
total = Σ(全部項權重) = 32
得分  = int(40 × got / total)
```

三態語義：`pass` 算滿分、`warn` 算半分、`fail` 算 0。warn 存在的理由是有些項「沒做但不算錯」（比如 SSH 還用 22 埠：風險真實但常見，直接判 0 分會讓分數失去區分度）。

**登入安全（0–20）**：

| 情況 | 得分 |
| --- | --- |
| 未發現暴力破解，24h 無失敗 | 20 |
| 24h 有失敗登入但未達暴力破解閾值 | 16（固定扣 4） |
| 發現 n 個疑似暴力破解目標 | `20 − 5n`，下限 0 |

**防火牆（0–15）**：啟用 15，未啟用 0。二元判定，沒有中間態。

**檔案完整性（0–15）**：`15 − 3n`（n = 24h 內變更條數），下限 0。一條變更扣 3 分意味著改 5 個關鍵檔案即歸零。

**威脅檢測（0–10）**：從 10 起扣，`critical` 扣 5、`warning` 扣 2、其他扣 1，下限 0。

### 等級對映

| 分數 | 等級 |
| --- | --- |
| ≥ 90 | 優秀 |
| ≥ 75 | 良好 |
| ≥ 60 | 一般 |
| < 60 | 危險 |

### 這個模型的取捨

- **不給資產價值加權**：OpsMini 不知道這臺機器上跑的是什麼業務，猜一個"重要性係數"只會讓分數變成玄學。
- **不用 CVSS**：CVSS 評的是漏洞嚴重性，這裡評的是主機配置與執行現狀，兩者不是一回事。
- **不設負分**：單項扣到 0 就停，避免一個模組拖崩全域性後分數失去意義。
- **分數可復現**：輸入一樣、程式碼一樣，分數一定一樣。這是能拿它做「改完再看一眼」比較的前提。

## 5. 基線體檢

### 執行方式

一次掃描生成一個 `ScanID`（納秒時間戳），14 項結果各寫一行 `baseline_results`，頁面只展示**最新批次**，歷史批次留在庫裡可對比。

純檔案解析，不調 `lynis` / `oscap` 之類外部工具——那些工具在最小化系統裡經常不存在，且輸出難以結構化。

### 判定細節

- `sshd_config` 會同時讀主檔案與 `/etc/ssh/sshd_config.d/*.conf`（現代發行版把配置拆到 drop-in 目錄，只讀主檔案會誤判）。
- 「未顯式配置」與「顯式配錯」區分開：前者給 `warn`（發行版預設值不確定），後者給 `fail`。
- `/etc/shadow`、`/etc/passwd` 直接解析文字，不依賴 NSS 配置——避免 LDAP/SSSD 參與的機器上判定漂移。
- 高危埠用固定清單：`23 Telnet`、`445 SMB`、`135 RPC`、`1433 MSSQL`、`3389 RDP`。

完整 14 項清單見 [附錄 A]](#附录-a基线-14-项清单)。

### 為什麼權重寫死在程式碼裡

改權重就能改分數。如果權重可配置，同一臺機器在兩個客戶那裡分數不同，"體檢"就失去公信力。要調整權重，走程式碼評審。

## 6. 登入安全

### 資料來源與開銷

只讀認證日誌的尾部：`tail -n 5000`，優先 `/var/log/auth.log`（Debian 系）再 `/var/log/secure`（RHEL 系），沒有則返回空報告而不是報錯。日誌可能有幾百 MB，全量讀取會打爆記憶體。

**統計視窗要說準確**：實現上的視窗是「日誌尾部 5000 行」，不是嚴格的時間視窗。欄位名沿用了 `failed_count_24h` / `success_count_24h`，因為被掃爆的公網機器 5000 行往往不到 24 小時，而清靜的機器 5000 行可能好幾天。這個偏差是已知問題（§15），沒有做嚴格 24 小時過濾的原因見下。

### 三類判據

| 判據 | 規則 | 輸出 |
| --- | --- | --- |
| 暴力破解 | 同一賬戶在統計視窗內失敗（含 `Failed password` 與 `Invalid user`）**累計 ≥ 5 次** | 賬戶名 + 次數 + 涉及 IP 列表，按次數倒序 |
| Top 失敗來源 | 按 IP 聚合失敗次數取前 10 | IP + 次數 |
| 異常登入 | 成功登入中 `user == root` | 時間 + 使用者 + IP + 原因「root 賬戶直接 SSH 登入」 |

SSH 加固建議不寫死文案，而是讀當前 `sshd_config` 判斷每條是否已做（`PermitRootLogin`、`PasswordAuthentication`、改埠、Protocol 2），頁面上直接顯示「已做/未做」。

### 為什麼不做 GeoIP 與 UA 分析

離線環境是硬需求。一個能裝在內網、不聯網、不給外部服務發日誌的安全面板，比一個能畫出漂亮世界地圖但要聯網的面板更有用。所以異常判定只依賴本機可見的事實（時間、賬戶、IP 頻次）。

### 為什麼沒做嚴格 24 小時過濾

`syslog` 的時間戳不帶年份（`Aug 14 07:00:01`），要按時間過濾必須推斷年份並處理跨年迴繞；凌晨 0 點前後、容器時區不一致、日誌被 logrotate 截斷都會讓推斷出錯。錯一年就是把整段歷史算成「剛剛」。

用「尾部 N 行」代替時間視窗，代價是視窗長度漂浮，好處是**永不因時間解析出錯而誤判**。真要精確，正路是讓感知層按 `observed_at` 在庫裡做視窗查詢（它本來就帶時間），這也是 §16 裡統一事實層的動機之一。

### 閾值 5 的解釋

低於 5 次的多半是人工敲錯密碼；5 次以上在 24 小時內、來自同一批 IP，才具備"在試"的特徵。這個閾值在真實公網機器上會被大量掃描越過——這正是它的用途：**它不是用來精確識別的，而是用來告訴你這臺機器正在被掃**。

## 7. 防火牆

### 後端自動識別

不假設系統裝了什麼，讀實際狀態決定後端：

| 後端 | 判定 | 支援的寫操作 |
| --- | --- | --- |
| `ufw` | `ufw status` 可讀 | 放行/封禁埠、啟用、停用、按編號刪規則 |
| `firewalld` | `systemctl is-active firewalld` | 放行/封禁埠（`--permanent` + `--reload`）、啟用、停用 |
| `iptables` | 存在規則鏈 | 放行/封禁埠（`-I INPUT 1`）、按編號刪規則；**不支援面板內停用** |

`iptables` 後端故意不提供「停用」：清空規則鏈等於把所有機器裸奔，破壞性太高，要求人自己上機器操作。

### 防鎖死設計（這是本模組最關鍵的一條）

**啟用防火牆前，先自動放行面板自身埠和 SSH 22**，然後再 `enable`。

順序不能反。反過來就是經典事故：防火牆一開，8888 和 22 同時被擋，人只剩控制檯可用。`panelPort` 由啟動時的配置注入，不是寫死的 8888。

### 引數校驗與超時

| 防線 | 做法 |
| --- | --- |
| 許可權 | 所有寫操作 `requireRoot()`，非 root 直接返回 `ErrNeedRoot` |
| 埠 | `int` 型別 + 1–65535 範圍校驗，不接受字串 |
| 協議 | 列舉 `tcp`/`udp` |
| 注入 | 全部走 `exec.Command(name, args...)`，不經 shell，引數無法被拼接成第二條命令 |
| 卡死 | 每條防火牆命令 10 秒超時（`context.WithTimeout`），失敗返回 stderr 原文 |

### 與 Agent 封禁的關係

系統裡有兩種封禁，故意分開管理：

| 來源 | 落點 | 生命週期 | 誰清理 |
| --- | --- | --- | --- |
| 頁面規則（人配） | `ufw`/`firewalld` 規則表 | 長期，直到人刪 | 人 |
| Agent 封禁（事件驅動） | `iptables -I INPUT -s <ip> -j DROP` + `blocked_ips` 表 | 帶 TTL，到期自愈 | `SweepBlocks()` 自動解封 |

分開的原因：Agent 的封禁必須能自愈（誤封要能自己好），人的規則不能被自愈邏輯順手刪掉。兩套各管各的，頁面上分別可見。

## 8. 檔案完整性（FIM）

### 監控物件

預設 8 個系統關鍵檔案，首次啟動（基線為空時）自動建基線：

```
/etc/passwd  /etc/shadow  /etc/group   /etc/ssh/sshd_config
/etc/crontab /etc/sudoers /etc/hosts   /etc/resolv.conf
```

其中 `/etc/passwd`、`/etc/shadow`、`/etc/sudoers` 變更記為 `critical`，其餘 `warning`。

### 檢測迴圈

每 60 秒對每個啟用項算一次 `SHA256 + size + mtime`：

- 算不出來（檔案不存在）→ 記一條「檔案被刪除」，`critical` 級別按路徑判斷
- 雜湊不一致 → 記一條「檔案內容發生變化」，帶新舊雜湊
- 一致 → 什麼都不做

### 關鍵設計：變更後基線自動前移

檢測到變化並落庫後，**基線立即更新為新雜湊**。

這是有意為之：如果基線不前移，同一次變更會每 60 秒報一次，一天 1440 條告警，人就再也不看了。前移之後的效果是「一次變更一條告警」，而**下一次再變還會報**——真被反覆改，仍然看得見。

代價：連續兩次變更如果發生在同一個 60 秒視窗內，只會留下一條記錄。這在這個精度下可接受（要更細得上 inotify，見 §16）。

「重建基線」是人工動作：你改完 `sudoers` 之後點一下，告訴系統"現在的狀態是對的"。

### 與感知層 filewatch 的分工

|  | 安全頁 FIM | 感知層 filewatch |
| --- | --- | --- |
| 看什麼 | 8 個系統關鍵檔案 | 站點根目錄新增的可執行指令碼 |
| 判據 | 雜湊比對 | 副檔名 + WebShell 內容特徵（`eval($_POST`、`base64_decode` 等） |
| 目的 | 發現「系統被動過」 | 發現「網站被種了馬」 |

兩者不重疊，也不互相引用。

## 9. 威脅檢測

三個掃描器，每 5 分鐘一輪，啟動時先跑一次。

| 掃描器 | 看什麼 | 判據 | 級別 |
| --- | --- | --- | --- |
| 程序 | `/proc` 全量程序（名稱 + 命令列） | 命中挖礦關鍵詞（`xmrig`、`minerd`、`kdevtmpfsi`、`kinsing`、`stratum` 等 11 個） | critical |
| 程序 | 程序可執行檔案路徑 | 位於 `/tmp` 或 `/dev/shm`（正常服務不該從這裡起） | warning |
| 計劃任務 | 系統 + 使用者 crontab | 命令含 `curl`、`wget`、`base64 -d`、`/dev/shm` | warning |
| 啟動項 | `/etc/rc.local` 非註釋行 | 含 `curl`、`wget`、`/tmp` | warning |
| 啟動項 | systemd 已啟用服務名 | 含 `miner`、`xmrig`、`kdevtmpfs` | critical |

### 去重與生命週期

按 `kind + name` 去重：命中已存在記錄只更新 `last_seen` 與詳情，不新增條目。狀態只有 `active` / `resolved`，**只有人能把它標記為已解決**——程序被殺掉之前，掃描器每 5 分鐘會再看到它，這正是我們要的（真威脅不該自己消失）。

### 對這套檢測的誠實評價

關鍵詞黑名單**改名即繞過**，這是公開的秘密。所以它的定位不是"能抓住所有挖礦"，而是：

1. 抓住**懶攻擊**——絕大多數殭屍網路落地用的是現成二進位制，名字都不改；
2. 配合「臨時目錄可執行」這類**行為特徵**，覆蓋改名的部分；
3. 剩下的靠感知層的程序行為與登入行為訊號補。

不吹能殺，能發現就報告，處置交給人（或人授權給 Agent）。

## 10. 資料模型

| 表 | 一行代表 | 關鍵欄位 |
| --- | --- | --- |
| `baseline_results` | 一次掃描裡的一項結果 | `scan_id`（批次）、`category`、`item_key`、`status`](pass/fail/warn)、`detail`、`suggestion`、`weight` |
| `fim_baselines` | 一個被監控檔案的當前基準 | `path`](unique)、`sha256`、`size`、`mod_time`、`enabled` |
| `fim_changes` | 一次檔案變更事件 | `path`、`old_sha256`、`new_sha256`、`level`](warning/critical)、`message`、`created_at` |
| `threat_findings` | 一個威脅條目 | `kind`](process/cron/startup)、`name`、`detail`、`severity`、`status`、`first_seen`、`last_seen`、`resolved_at` |

設計要點：

- 基線結果按 `scan_id` 分批，**永不覆蓋歷史**：想對比"上週和這周"是可查的。
- `fim_baselines` 與 `fim_changes` 分表：一個是狀態，一個是流水，混在一張表會讓"當前基準"和"變更歷史"互相汙染。
- `threat_findings` 帶 `first_seen/last_seen`：一眼看出這是剛出現的還是掛了三天沒人管。
- 沒有獨立的安全庫檔案，全部落在 `opsmini.db` 裡，跟著備份走（和麵板其他資料一致）。
- 表名注意：安全基線結果是 `baseline_results`，感知層的「學習基線」（EWMA 期望值）是 `baselines`，兩者無關，別混。

## 12. 面板自身的安全邊界

安全模組自己也是攻擊面，所以：

| 風險 | 處理 |
| --- | --- |
| 命令注入 | 所有外部命令 `exec.Command` + 引數陣列，從不拼 shell；埠是 `int`、協議是列舉 |
| 許可權提升 | 寫操作先 `requireRoot()`，非 root 直接拒絕，不做"盡力而為" |
| 長時間卡住 | 外部命令 10 秒超時 |
| 自鎖 | 啟用防火牆前先放行面板埠與 22 |
| 隱私 | 只讀日誌中的登入事件，不落密碼、不落命令全文（只用於判定的欄位才進庫） |
| 越權呼叫 | 每個寫介面都有獨立許可權點，不靠前端隱藏按鈕來"控制" |

## 13. 效能與資源開銷

| 動作 | 開銷 | 說明 |
| --- | --- | --- |
| 基線體檢 | 14 次小檔案讀取 + 一次埠表，毫秒級 | 只在人點的時候跑 |
| 登入分析 | `tail -5000` 一次，單次 < 50ms | 開啟頁面時跑，不快取 |
| FIM 檢查 | 8 個檔案 SHA256，每 60 秒 | 全是 KB 級小檔案，CPU 可忽略 |
| 威脅掃描 | 遍歷 `/proc` 數百程序 + crontab + systemctl 一次，每 5 分鐘 | 唯一的"重"動作，仍然在百毫秒量級 |
| 常駐記憶體 | 不計額外快取，全部走同一條 SQLite 連線 | 無獨立程序，無後臺佇列 |

沒有常駐取樣器、沒有額外 goroutine 池：FIM 與威脅掃描共用一個迴圈（`SecurityMonitor`），一個 ticker 管一件事。

## 14. 和自主 Agent 的關係

三處介面，都是**單向提供事實**，不存在"安全模組指揮 Agent"這種耦合：

| 方向 | 形態 | 說明 |
| --- | --- | --- |
| 安全 → AI | 只讀工具 `security_status` | Agent 可以讀「評分 + 五模組摘要」來回答"這臺機器安全嗎"，工具是 `RiskReadonly` + `security.view` |
| 安全 → AI（寫） | 工具 `firewall_rule` | 改防火牆是寫操作，走 L1/L2 分級，需要確認 |
| 感知層 → Agent | 訊號 → 事件 → 策略 | 由 sentinel 獨立負責，與本節的安全模組不共享狀態 |

**當前沒有做的事（有意為之）**：威脅檢測結果、FIM 變更不進事件匯流排。原因是這兩類結果誤報率高於感知層的訊號（關鍵詞匹配、基線自動前移都會產生噪音），直接餵給自動處置策略風險太大。等誤報率有實測資料後再接，見 §16。

## 15. 已知限制

| 限制 | 影響 | 備註 |
| --- | --- | --- |
| 無核心級檢測 | rootkit、隱藏程序（`/proc` 被 hook）看不到 | 定位決定，不打算做 |
| FIM 只覆蓋 8 個檔案 | 自定義路徑、目錄遞迴、新增檔案監控都沒有 | 目前靠感知層 filewatch 補站點目錄 |
| 威脅檢測靠關鍵詞 | 改名即繞過 | 見 §9 的誠實評價 |
| 基線 14 項固定 | 無法覆蓋等保/CIS 全量條目 | 演進方向是規則外接 |
| 評分不含業務重要性 | 測試機和核心庫伺服器同分 | 不做，避免玄學 |
| 認證日誌格式依賴 | 非 rsyslog/journald 文字格式的機器可能讀不到 | 相容性靠 `/var/log/secure` 兜底 |
| 登入統計視窗漂浮 | `tail -5000` 行，非嚴格 24 小時（欄位名沿用 24h） | 見 §6「為什麼沒做嚴格 24 小時過濾」 |
| 兩套日誌解析 | 安全頁與感知層口徑可能漂移 | 已知技術債 |
| 無報告匯出 | 只能頁面看，不能出 PDF/HTML 合規報告 | 演進方向 |

## 16. 演進方向

按優先順序：

1. **FIM 可配置**：支援自定義路徑、目錄遞迴、白名單（`/etc/` 下高頻變化的檔案先排除掉），以及 inotify 事件驅動替代 60 秒輪詢。
2. **基線規則外接**：14 項 → YAML 規則包，支援匯入 CIS / 等保二級條目集，同時把"當前用的是哪套規則集"記進結果，保證分數可復現。
3. **統一日誌事實層**：`service/loginsecurity.go` 與 `sentinel/authwatch.go` 共用一套解析器，消除口徑漂移。
4. **威脅檢測增強**：接入 `ausearch`（auditd 審計日誌）與可選 YARA 規則，從關鍵詞升級到行為與特徵雙軌。
5. **安全結果進事件匯流排**：在誤報率可量化之後，把 `critical` 級威脅與 `critical` 級 FIM 變更接入策略引擎，讓 Agent 能自主處置（例如發現 WebShell 落地 → 隔離 → 報告）。
6. **合規報告匯出**：一鍵出單檔案 HTML 報告（沿用計劃任務報告那套渲染），含分數、逐項結論、整改建議。

## 附錄 B：評分算例

一臺典型公網 Ubuntu 機器：

| 模組 | 實測 | 得分 |
| --- | --- | --- |
| 基線 | 14 項中 12 項 pass、2 項 warn（SSH 用 22 埠、`PASS_MAX_DAYS` 未設） | got = 32 − 1×0.5 − 2×0.5 = 30.5 → `int(40×30.5/32)` = **38** |
| 登入 | 24h 內 2000 次失敗，命中 3 個暴力破解目標 | `20 − 5×3` = **5** |
| 防火牆 | ufw 已啟用 | **15** |
| 檔案完整性 | 24h 內 1 處變更（`/etc/hosts`） | `15 − 3` = **12** |
| 威脅檢測 | 1 個 warning（`/tmp` 下的可執行程序） | `10 − 2` = **8** |
| **總分** |  | **78 → 良好** |

這個分數在解釋上站得住：配置基本合理（基線 38），但正在被爆破（登入 5），扣分主要來自真實攻擊而不是誤判。整改路徑也清楚——開啟防火牆來源限制、上 fail2ban 或用 Agent 封禁，登入分會回來。
