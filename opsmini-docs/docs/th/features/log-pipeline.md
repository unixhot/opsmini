# ท่อบันทึก

OpsMini มีตัวเรียกใช้การเก็บบันทึกที่**เข้ากันได้กับการกำหนดค่า Filebeat**ในตัว มันเก็บ ประมวลผล และส่งบันทึกบนโฮสต์ตามการกำหนดค่างานไปยัง Elasticsearch / Kafka / Logstash ตำแหน่งเทียบเท่ากับ "filebeat บนโฮสต์ที่ถูกจัดการ" แต่ไม่จำเป็นต้องติดตั้งโปรเซสเพิ่มเติม

## ค่าเริ่มต้นคือปิดอยู่

ต้องอธิบายให้ชัดก่อน: **การติดตั้งค่าเริ่มต้นจะไม่เก็บบันทึกใด ๆ** ไม่มี goroutine ไม่สแกนไดเรกทอรี ไม่กินหน่วยความจำ

เปิดใช้งานได้สามระดับ หากข้อใดข้อหนึ่งเป็นจริงก็จะเริ่มทำงาน:

| วิธี | เงื่อนไขการทริกเกอร์ | การใช้งาน |
|---|---|---|
| ไฟล์งาน | มี `.yml` / `.yaml` ปรากฏในไดเรกทอรี `tasks.d` | กำหนดค่าการเก็บข้อมูลบนเครื่องเดียวด้วยตนเอง |
| สวิตช์ชัดเจน | `logpipeline.enabled: true` ใน `config.yaml` | ต้องการบังคับเปิด (แม้ยังไม่มีงานชั่วคราว) |
| แพลตฟอร์มส่งลงมา | ได้รับ `LogTask` ที่ส่งมาจาก OpsAnt และบันทึกลงดิสก์ | จัดการรวมศูนย์หลายเครื่อง |

ในทางกลับกัน เมื่อ `enabled: false` และไม่มีไฟล์งาน ท่อจะหยุดนิ่งโดยสมบูรณ์——นี่คือสถานะเริ่มต้นของสถานการณ์ "ใช้เองบนเครื่องเดียว"

## โครงสร้างไดเรกทอรี

```
<数据目录>/logs/
├── main.yml          # 主配置（filebeat 形状：output + 全局参数）
├── tasks.d/          # 采集任务，一个任务一个文件
│   ├── nginx.yml
│   └── app-1024.yml
├── registry.db       # 每个文件的读取位置（inode + offset）
└── spool/            # 输出失败时的磁盘队列
```

`main.yml` รับผิดชอบ "ส่งไปที่ไหน" ส่วน `tasks.d/*.yml` รับผิดชอบ "เก็บอะไร" การแยกส่วนนี้สอดคล้องกับ `filebeat.yml` + `inputs.d/` ของ filebeat ดังนั้นการกำหนดค่า filebeat ที่มีอยู่แล้วสามารถแยกออกมาใช้ได้โดยตรง

## เขียนงานอย่างไร

**วิธี A (แนะนำ)**: งานอธิบายเฉพาะการเก็บข้อมูลเท่านั้น เอาต์พุตถูกกำหนดโดย `main.yml` เป็นเอกภาพ

```yaml
# tasks.d/nginx.yml
- type: filestream
  id: nginx-access
  paths:
    - /var/log/nginx/access.log
  fields:
    service: nginx
    env: prod
  parsers:
    - ndjson:
        target: ""
        add_error_key: true
  processors:
    - drop_fields:
        fields: ["agent.ephemeral_id", "ecs.version"]
    - add_fields:
        target: ""
        fields:
          cluster: bj-prod
```

**วิธี B**: ไฟล์งานมี `output` ในตัว ใช้สำหรับ "งานต่างกันส่งไปที่ต่างกัน" นี่คือส่วนขยายของ OpsMini เมื่อเทียบกับ filebeat——filebeat ต้องใช้หลายอินสแตนซ์จึงจะทำได้

```yaml
output.elasticsearch:
  hosts: ["http://10.0.0.5:9200"]
  index: "app-%{+yyyy.MM.dd}"
```

ยอมรับทั้งสองวิธี โดยวิธี B มีลำดับความสำคัญสูงกว่า `main.yml`

## การโหลดซ้ำแบบร้อน

`tasks.d` กระทบยอดทุก 10 วินาที:

- ไฟล์งาน **เพิ่มใหม่** → เริ่มเก็บข้อมูลหลังการแยกวิเคราะห์; หากการแยกวิเคราะห์ล้มเหลว **จะไม่เขียนทับ** เวอร์ชันเก่าที่กำลังทำงานอยู่ เพื่อหลีกเลี่ยง "แก้ไขฟิลด์ผิดหนึ่งฟิลด์ทำให้การเก็บข้อมูลหยุดทั้งหมด"
- ไฟล์งาน **แก้ไข** → จะสร้างใหม่ก็ต่อเมื่อแฮชเนื้อหาเปลี่ยน การส่งเนื้อหาเดิมซ้ำจะไม่ทำให้เกิดการรีสตาร์ท (การรีสตาร์ทจะทำให้บัฟเฟอร์ multiline หายและเปิดไฟล์ทั้งหมดใหม่)
- ไฟล์งาน **ลบ** → หยุดงานนั้น

ชื่อไฟล์งานต้องเป็น `*.yml` / `*.yaml` เท่านั้น ห้ามมีพาธ ห้ามขึ้นต้นด้วยจุด——ชื่อไฟล์เป็นฟิลด์เดียวที่อาจถูกใช้จากระยะไกลเพื่อเขียนออกนอกไดเรกทอรี ดังนั้นจึงจำกัดตายตัวไปเลย

## โปรเซสเซอร์ที่รองรับ

โปรเซสเซอร์ Filebeat 31 ตัว ครอบคลุมความต้องการในการทำความสะอาดข้อมูลทั่วไป:

| หมวดหมู่ | โปรเซสเซอร์ |
|---|---|
| เพิ่ม ลบ แก้ไขฟิลด์ | `add_fields` `add_tags` `drop_fields` `include_fields` `rename` `copy_fields` `move_fields` `truncate_fields` |
| ชนิดและการแยกวิเคราะห์ | `convert` `decode_json_fields` `decode_csv_fields` `decode_duration` `dissect` `syslog` `decode_xml` `decode_base64_field` `decompress_gzip_field` `urldecode_fields` `extract_array` |
| เงื่อนไขและการควบคุมโฟลว์ | `drop_event` `script` |
| เวลาและตัวระบุ | `timestamp` `add_id` `fingerprint` |
| เมทาดาทา | `add_host_metadata` `add_observer_metadata` `add_locale` `add_network_direction` |
| เครือข่ายและโดเมน | `community_id` `registered_domain` |
| การแทนที่ข้อความ | `replace` |

## เอาต์พุต

| ประเภท | คำอธิบาย |
|---|---|
| `elasticsearch` | รองรับตัวแปรเทมเพลต index, ชื่อผู้ใช้และรหัสผ่าน, ขนาดแบตช์ และ timeout |
| `kafka` | รองรับการยืนยันตัวตน SASL, ตัวแปร topic, นโยบายพาร์ทิชัน |
| `logstash` | โปรโตคอล Lumberjack v2 พร้อม TLS (รองรับทั้งรูปแบบ `logstash` / `lumberjack`) |

เมื่อไม่ได้กำหนดค่าเอาต์พุต งานจะยังคงเก็บข้อมูลตามปกติแต่การส่งจะล้มเหลว แผงจะแสดงข้อผิดพลาดในสถานะไปป์ไลน์——จะไม่ทิ้งข้อมูลแบบเงียบๆ

## แนวทางที่ไม่ทำให้ข้อมูลสูญหาย

รูปแบบการส่งข้อมูล (delivery semantics) คือ **at-least-once**:

1. อ่านบันทึกเป็นชุด → ส่ง
2. **หลังจากส่งสำเร็จแล้วเท่านั้น**จึงเลื่อน offset ใน `registry.db`
3. ส่งล้มเหลว → เขียนลง `spool/` (ขีดจำกัดเริ่มต้น 512MB) → backoff แล้วลองใหม่
4. กระบวนการ crash → เมื่อรีสตาร์ทจะส่งซ้ำจาก offset ที่ยืนยันครั้งล่าสุด อาจซ้ำแต่จะไม่สูญหาย

ในทางธุรกรรม การส่งบันทึกซ้ำเป็นชุดมักไม่ก่อให้เกิดอันตราย (ฝั่ง ES สามารถใช้ตัวประมวลผล `fingerprint` เพื่อทำ idempotent ได้) แต่การสูญหายของบันทึกนั้นไม่อาจแก้ไขได้ จึงเลือกแบบแรก

## ตัวอย่างแบบเรียลไทม์

แท็บ **บันทึก → ไปป์ไลน์** ในแผงสามารถดูได้ว่า:

- ไปป์ไลน์กำลังทำงานอยู่หรือไม่, ประเภทเอาต์พุตปัจจุบัน, ข้อผิดพลาดของเอาต์พุต
- จำนวนไฟล์ที่เก็บของแต่ละงาน, อัตราการอ่าน, เวลาของเหตุการณ์ล่าสุด
- ปริมาณ spool ที่ค้างสะสม
- คำเตือนการกำหนดค่า (ฟิลด์ที่ไม่รู้จัก, พาธไม่มีอยู่ ฯลฯ)

เลือกงานหนึ่งเพื่อ**ดูตัวอย่างเหตุการณ์ล่าสุด 20 รายการแบบเรียลไทม์** เพื่อดูว่าหลังผ่านเชนโปรเซสเซอร์แล้วมีหน้าตาอย่างไร——ไม่ต้องไปค้นใน ES ก่อน และไม่ต้องแก้การกำหนดค่าแล้วรีสตาร์ท นี่คือวิธีที่เร็วที่สุดในการดีบัก processor

## ทำไมต้องรองรับ Filebeat

สามเหตุผล:

1. **ต้นทุนการย้ายระบบ**: เทมเพลตดัชนี ES, นโยบาย ILM, แดชบอร์ด Kibana ที่มีอยู่ไม่ต้องแก้ไข `agent.type` ยังสามารถตั้งเป็น `filebeat` เพื่อนำกลับมาใช้ได้โดยตรง
2. **อ่านง่ายสำหรับการปฏิบัติการ**: การกำหนดค่าการเก็บรวบรวมเป็น YAML ชุดที่ฝ่ายปฏิบัติการคุ้นเคยที่สุด ไม่จำเป็นต้องเรียนรู้ DSL ใหม่
3. **ไม่เพิ่ม dependency ใหม่**: ความสามารถถูกสร้างไว้ในไบนารีเดี่ยว ไม่ต้องติดตั้ง filebeat เพิ่มเพื่อเก็บรวบรวมบันทึก

## ส่วนที่ไม่ได้ทำ

ขีดเส้นอย่างตรงไปตรงมา เพื่อไม่ให้เข้าใจผิด:

- **ไม่ทำ module / autodiscover** (Nginx module, Kubernetes autodiscover): แผงแบบเครื่องเดี่ยวไม่มีบริบทของการจัดการคอนเทนเนอร์
- **ไม่ทำการจัดการ ILM และ index template**: นั่นเป็นเรื่องของฝั่ง ES
- **ไม่ทำการรวมศูนย์ข้ามโฮสต์**: การเก็บข้อมูลหลายเครื่องถูกจัดการแบบรวมศูนย์โดย OpsAnt ที่ส่งงานลงมา OpsMini ทำเพียงฝั่งผู้ปฏิบัติงานเท่านั้น
- **ไม่รองรับเอาต์พุตทั้งหมดของ Filebeat** (มิดเดิลแวร์อื่นนอกเหนือจาก Logstash Beat, Redis, Kafka): ทำเพียงสามแบบคือ ES / Kafka / Logstash

## ข้อมูลอ้างอิงการกำหนดค่า

```yaml
# config.yaml
logpipeline:
  enabled: false            # สวิตช์แข็ง; เมื่อเป็น true จะเริ่มทำงานแม้ไม่มีไฟล์งาน
  tasks_dir: ""             # ค่าเริ่มต้น <ไดเรกทอรีข้อมูล>/logs/tasks.d
  config_file: ""           # การกำหนดค่าหลัก ค่าเริ่มต้น <ไดเรกทอรีข้อมูล>/logs/main.yml
  strict: false             # เมื่อเป็น true ฟิลด์ที่ไม่รู้จักในงานจะทำให้เกิดข้อผิดพลาดแทนที่จะเป็นคำเตือน
  agent_type: opsmini       # เขียนลงใน agent.type; ตั้งเป็น filebeat เพื่อใช้เทมเพลตที่มีอยู่ซ้ำ
```

ในสถานการณ์หลายเครื่อง ไฟล์งานเหล่านี้ถูกส่งลงมาจาก OpsAnt ผ่าน gRPC ผู้ปฏิบัติการกำหนดค่าบนแพลตฟอร์ม ฝั่งโฮสต์ไม่จำเป็นต้องแก้ไขด้วยมือ
