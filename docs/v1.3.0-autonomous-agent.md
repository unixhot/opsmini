# OpsMini v1.3.0 设计：从面板到自主 Agent

> 状态：设计草案 v1（2026-10-27）
> 范围：v1.3.0 全部内容。目标不是"再加一个 AI 功能"，而是把 OpsMini 从"等人操作的面板"改造成"能自己发现、自己判断、自己动手、动手错了能退回"的自主 Agent。
> 前置约束：单二进制、纯 Go 无 CGO、SQLite、离线可用、单机自治优先。

---

## 0. 摘要（先看这 8 条）

1. **事件驱动是必要的骨架，但不是全部。** 只加事件触发，得到的是"自动告警 + 自动脚本"；要叫"自主"，必须同时具备四件事：**感知广度、判断能力、安全行动、事后可验证可回滚**。
2. **监控不到的地方，靠三层检测补**：已知模式（规则）→ 未知偏离（基线/统计）→ 完全未知（Agent 探索式巡检 + 取证留痕）。第三层承认"不可能保证发现一切"，目标是**缩短发现与处置的时间**，不承诺全覆盖。
3. **误操作不靠"提示词让它小心"，靠七道闸门**：工具与参数双约束、爆炸半径预检、快照隔离（**删除=隔离，不做不可逆操作**）、动作预算与熔断、影子模式灰度、人工接管急停、决策链审计回放。
4. 借鉴 HolmesGPT 最关键的一条：**只读工具与处置工具分家**。内置诊断工具永远只读，处置动作走独立的、受约束的通道。
5. 现有代码已有 60% 的地基（L0–L3 工具分级、Guard、告警引擎、FIM、登录分析、定时 Agent 任务、通知），**缺的是把它们连成闭环的那层胶水**，而不是重写。
6. v1.3.0 分 5 个里程碑，**先只观察（shadow）两到四周**，再逐事件类型放开自主处置。默认配置下，任何高危动作仍然要人点一下。
7. 三个必须解决的典型场景（日志暴涨 / 凌晨 SSH / webshell）在本文第 5.3 节给出完整检测链与处置链，可直接落成代码。
8. 明确不做：v1.3 不上 eBPF 内核探针、不做多机协同自主、不允许 Agent 修改自身配置或日志、不自动处置 critical 级安全事件（必须人工确认）。

## 1. 先回答三个问题

### 1.1 是不是必须靠内部事件驱动才能实现自主 Agent？

**是必要条件，但不是充分条件。** 拆开看：

| 触发方式 | 能做到什么 | 局限 |
|---|---|---|
| 定时（现有 `kind=agent` 定时任务） | 每天体检、定期巡检 | 只能"按时"，不能"按事"；异常发生在两次巡检之间就漏 |
| 人问（现有 AI 助手） | 深度排查、复杂处置 | 依赖有人在、且知道要问 |
| **事件驱动**（本设计新增） | 出事即响应，秒级到分钟级 | 只能响应"已经定义成事件"的东西 |
| Agent 常驻自循环（不停思考） | 理论上最"自主" | 贵、吵、易幻觉、难审计，工程上不明智 |

所以正确的组合是**三种触发并存**：

```
事件触发（反应式，主体）  +  定时触发（探索式，兜底）  +  人工触发（按需，深度）
```

事件驱动解决的是"**什么时候醒**"；而"自主"这个词能不能立住，取决于另外三件事：

1. **感知广度**——事件从哪里来？只有 CPU/内存阈值就不叫感知，那叫阈值告警。
2. **行动安全**——它敢不敢动手？动手错了能不能退？没有回滚能力的自主 = 定时炸弹。
3. **闭环验证**——它怎么知道自己修好了？没有验证的处置 = 掩盖症状。

一句话：**事件驱动是骨架，行动安全是命门。**

### 1.2 监控不到的地方怎么办？

现在的 `AlertMonitor` 只做「指标 vs 阈值」的比较，`SecurityMonitor` 只做「文件哈希基线 + 进程/cron/启动项扫描」，两者都是**轮询 + 已知规则**。日志暴涨、凌晨登录、webshell 这三类，现有机制全都看不见。

补法是**三层，一层比一层"不确定"，也一层比一层"贵"**：

| 层 | 手段 | 能发现 | 成本 | 误报 |
|---|---|---|---|---|
| L1 已知模式 | 规则、FIM、认证日志解析、进程链规则 | 已知攻击手法、明确阈值越界 | 极低 | 低（但需调） |
| L2 未知偏离 | 时序基线、日志速率/模板新颖度、进程树新颖度、出站连接基线 | 没见过但"不正常"的行为 | 低 | 中 |
| L3 探索式 | Agent 定期巡检 + 事件驱动的深度排查 + 人工提问 | 说不清哪里不对的"怪" | 高（token） | 高（靠人判断收敛） |

**诚实边界**：L3 也不可能保证发现 0day/APT。设计目标是三个可度量指标：
- 平均发现时间（MTTD）从"下次巡检/人发现"降到"分钟级"
- 平均处置时间（MTTR）从"人上手 20 分钟"降到"人只需审批"
- **漏报可解释**：所有未触发的事件仍在事件中心留痕，人可以事后追问"那天为什么没叫我"

### 1.3 怎么避免误操作（关错进程、删错文件）

这是整个设计真正的难点。业界普遍做法是"分级 + 人工确认"，但**只靠确认不够**——半夜三点人也会点错。所以本设计加了一个常被忽略的原则：

> **凡是不可逆的动作，一律改成可逆动作。**

| 人的直觉动作 | 风险 | OpsMini 的做法（可逆化） |
|---|---|---|
| `rm` 删掉可疑文件 | 删错了没法恢复 | **移动到隔离区** `/data/opsmini/data/quarantine/<incident>/`，附 sha256 + 原路径清单，一键还原 |
| `kill -9` 杀掉可疑进程 | 杀错关键进程 = 业务中断 | 先 `SIGSTOP` 冻结（可 `SIGCONT` 恢复）→ 观察 → 再 `SIGTERM` → **`SIGKILL` 必须人工确认** |
| 改 `sshd_config`、改防火墙 | 可能把自己关在外面 | 改动前快照 + 语法校验 + 定时自动回滚（如 5 分钟内未确认连通则还原） |
| 重启服务 | 可能连带依赖崩 | 先做依赖检查（被谁依赖、关键集排除），优先 reload 而非 restart |
| 封 IP | 封错导致业务断 | **临时封禁 + TTL 自动解封**（默认 60 分钟），永久封禁需人工 |

再叠加第 8 节的七道闸门，形成"事前拦、事中限、事后可退"三层防护。

## 2. 业界现状（2026）与可借鉴之处

### 2.1 商业 AI SRE / 运维 Agent

| 产品 | 定位 | 关键设计 | 官方口径的数字 |
|---|---|---|---|
| **Datadog Bits AI SRE** | 24/7 自动调查告警、产出 RCA | **假设驱动循环**：形成假设 → 查证 → 否定/深入子假设；强调"因果关系"而非"把所有遥测塞进上下文" | 调查 3–4 分钟；案例称 MTTR 降约 50% |
| **Microsoft Azure SRE Agent** | 云原生 SRE Agent，GA（2026-03） | **Deep Context**（代码库/日志/历史事故/资源统一上下文图）、**持久记忆**、无人提问时也做后台分析 | 内部 1300+ 个 agent，每月省 2 万+ 工程师小时 |
| **PagerDuty AI Agent Suite** | 多智能体协作 | SRE Agent（分析 + 在策略护栏内执行修复）、Scribe、Shift 分工 | 事件解决快约 50% |
| **AWS DevOps Agent** | 云上运维调查 | 预置 AWS 域知识与拓扑 | preview 阶段 RCA 准确率 94% |
| **Cleric** | 现场调查助手 | **Operational memory**：每次调查让下一次更快 | BlaBlaCar 553 次调查，78% 可执行 |

（以上数字均为厂商公开口径，仅供参考，不作为选型依据。）

**四条行业共识**（这才是要抄的）：

1. **调查与处置分离**。几乎所有产品第一版都只做"调查 + 建议"，处置要么人工，要么走"策略护栏内的低危动作"。
2. **分级放权是标准做法**。行业已收敛到四阶段：只读 → 低危自动 → 标准化修复需审批 → 高危默认关闭 + 多层审计。配套三件套：**调用限流、自动回滚、决策链留痕**。
3. **记忆是复利来源**。上下文（服务依赖、历史事故、runbook、基线）比模型能力更决定效果。
4. **MCP 正在变成治理边界**。Agent 与基础设施之间的写通道走 MCP 网关，权限、审计、限流都收在网关这一层，而不是散落在各个工具里。

### 2.2 开源自托管：HolmesGPT（CNCF Sandbox）

它是 OpsMini 最该对标的开源同类（同为"自托管、可接任意 LLM"）。值得直接借鉴的 5 点：

| 借鉴点 | 具体做法 | 对 OpsMini 的映射 |
|---|---|---|
| **只读优先的工具设计** | 内置 toolsets 全部只读；处置能力单独成一套（Kubernetes Remediation，经 MCP） | 诊断类工具（L0）与处置类工具（L1/L2）在注册表里物理分层，处置工具必须带 ArgPolicy |
| **Operator 模式** | 24/7 后台跑健康检查与定时调查，不等人工触发 | 现有 `kind=agent` 定时任务 + 新增事件触发 |
| **上下文预算管理** | 每工具内存上限、服务端过滤、JSON 树遍历、大结果流式落盘、输出预算 | 单机场景同样存在（日志动辄 GB），复用"截断 + 落盘 + 回读指针"策略 |
| **每一步工具调用全审计** | 调用链可回放 | 扩展到动作审计（不只是调用，还有执行结果与回滚） |
| **Toolset 可扩展** | 用户可写自定义 toolset / MCP server | 复用现有 MCP 双向能力 |

### 2.3 主机侧的检测栈（这块是 OpsMini 的空白）

| 组件 | 干什么 | 单机可行性 | OpsMini 结论 |
|---|---|---|---|
| **auditd** | 内核审计 execve/open/chmod，取证最硬 | 需要 root，输出要解析 | 可选增强：检测到 auditd 在跑就复用，没有就降级 |
| **Wazuh / OSSEC** | FIM + 认证日志 + 主动响应（firewall-drop） | Agent 需配合 manager，重 | 不引入，**抄它的规则分类与主动响应思路** |
| **Falco** | eBPF 系统调用级检测（内存马、容器逃逸） | 需内核支持 + root | v1.3 不做，留作 v1.4 可选插件 |
| **fail2ban** | 认证失败自动封 IP | 极轻 | 不依赖，自己实现"临时封禁 + TTL" |
| **osquery** | 系统状态 SQL 化 | 中 | 不引入，`/proc` 直读足够 |

行业调优经验（直接采纳）：**先纯监控跑两周不动手，再按告警频次建白名单基线，然后才开响应**。这条会写进 v1.3.0 的灰度策略。

### 2.4 OpsMini 的差异化位置

在"会行动 + 单机自治 + 开源自托管"这格里几乎没有对手。具体差异：

- **数据不出本机**：可接本地 Ollama；报告、审计、证据全落本地磁盘。
- **零外部依赖**：没有 SaaS 后端、没有 manager、没有 Redis/Kafka，一个二进制。
- **动作可回滚**（本设计新增）：SaaS 产品能给"建议"，给不了"你机器上的隔离区"。
- **不做多机协同自主**：单机自治优先，多机只在 OpsMini Server 层做纳管与编排。

### 3.2 缺的东西（v1.3.0 要补）

| 缺口 | 后果 | 本设计对应章节 |
|---|---|---|
| 没有统一事件模型 | 告警、安全发现、日志各在各的表里，Agent 无法统一消费 | §5.1 Signal |
| 没有实时采集器 | 日志暴涨、登录、进程链变化全部看不见 | §5.2 六类 Collector |
| 没有事件→Agent 的触发层 | 只能定时或人问 | §6 Trigger Engine |
| 动作安全只有"工具级风险" | 同一个 `exec_command` 可能是安全的 `df -h`，也可能是危险的 `rm`，粒度不够 | §7.4 + §8 闸门 1/2 |
| 没有不可逆→可逆的转换 | 删了就没了 | §7.4 隔离区 + §8 闸门 3 |
| 没有执行后验证与回滚 | 不知道修没修好 | §7.5 Verify/Rollback |
| 没有预算/熔断/急停 | Agent 可能反复折腾 | §8 闸门 4/6 |
| 没有决策链审计 | 出问题无法复盘 | §8 闸门 7 + §9 action_log |

## 4. 总体架构

### 4.1 五个平面

```
┌─────────────────────────────── 采集平面 Collectors ───────────────────────────────┐
│ metric(现有告警引擎)  log(速率/模板)  auth(登录/ssh)  file(FIM/webroot)  proc(进程链)  net(出站) │
└───────────────────────────────────┬───────────────────────────────────────────────┘
                                    │ Signal（统一信号）
┌───────────────────────────────────▼──────────── 归一平面 Event Bus ──────────────┐
│ 去重(dedup_key) → 分级(severity) → 抑制(suppress) → 聚合(Incident 事件簇) → 持久化(SQLite) │
└───────────────────────────────────┬───────────────────────────────────────────────┘
                                    │ Incident
┌───────────────────────────────────▼──────────── 决策平面 Trigger ────────────────┐
│ 策略匹配 → 模式(shadow/assist/auto) → 预算/冷却/并发 → 组装 RunOptions → 拉起会话        │
└───────────────────────────────────┬───────────────────────────────────────────────┘
                                    │ RunOptions + Evidence
┌───────────────────────────────────▼──────────── 行动平面 Agent Runtime ──────────┐
│ 复用 ReAct 循环 → 取证(只读) → 判定 → 处置(受约束) → 验证 → 报告 → 必要时回滚              │
└───────────────────────────────────┬───────────────────────────────────────────────┘
                                    │ Action + Result
┌───────────────────────────────────▼──────────── 兜底平面 Safety & Audit ─────────┐
│ 七道闸门 · 决策链留痕 · 隔离区/quarantine · 快照与还原 · 急停开关 · 影子对比报表             │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 几个关键工程决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 事件总线 | **进程内 channel + SQLite 持久化**，不引入 MQ | 单机、单二进制；消息量级（每分钟 <100）远不需要 MQ |
| 采集方式 | **轮询为主 + inotify 补实时**，不依赖内核探针 | 纯 Go、无 CGO、非 root 也能跑（能力降级但可用） |
| 事件存储 | SQLite 新表，7 天滚动淘汰 | 复用现有 DB，备份即复制 |
| 会话并发 | **全局 1 个 Agent 会话**（单机） | 避免多会话抢着改同一台机器；新事件排队并合并 |
| 与现有关联 | `AlertMonitor` / `SecurityMonitor` 保留，改成"Collector 的一种" | 不推翻现有行为，只把输出接进总线 |
| 模型不可用 | 降级为"规则告警 + 通知"，不触发 Agent | 不能让没有判断能力的系统瞎动手 |

## 5. 第一步：如何发现异常

### 5.1 统一信号模型

所有采集器的唯一输出是 `Signal`。这是整个系统的语法基础。

```go
type Signal struct {
    ID          string            // ulid
    Kind        string            // metric | log | auth | file | proc | net
    Source      string            // collector id, 如 "authwatch/sshd"
    Subject     string            // 主机名 / 路径 / PID / 用户名 / 对端 IP
    Severity    Severity          // info | low | medium | high | critical
    Fingerprint string            // 归一化指纹，用于去重与聚合，如 "auth.new_ip_login"
    DedupKey    string            // subject+fingerprint+时间桶
    ObservedAt  time.Time
    Baseline    *BaselineDeviation // 偏离度（L2 层用）
    Evidence    map[string]any    // 结构化证据（大字段落盘，存指针）
    Tags        []string          // mitre:T1078 / scenario:webshell / auto-qualified
}
```

设计要点：

- **Fingerprint 必须"归一化"**：`新建文件 /var/www/a.php` 和 `/var/www/b.php` 应是同一指纹族，否则去重失效、Agent 被刷屏。
- **Evidence 不塞大对象**：只存摘要 + `file://` 指针（落 `/data/opsmini/data/evidence/`），避免 DB 膨胀和上下文爆炸（抄 HolmesGPT 的输出预算思路）。
- **Severity 由采集器给初值，聚合时只升不降**。

### 5.2 六类采集器

| 采集器 | 数据源 | 频率 | 能发现 | 降级策略 |
|---|---|---|---|---|
| **metric** | 现有 `AlertMonitor` | 现有间隔 | 阈值类异常 | 无 |
| **logwatch** | 配置的日志路径（默认 `/var/log/**`）+ 站点日志 | 10s 增量 | 日志暴涨、错误模板激增、轮转失效 | 文件不存在则跳过 |
| **authwatch** | `/var/log/auth.log`、`/var/log/secure`、`journalctl`、`/var/log/wtmp` | 10s 增量 | 暴力破解、异常时段登录、新 IP、爆破成功、`authorized_keys` 变更 | 无 auth 日志则只看 wtmp |
| **filewatch** | FIM 基线 + webroot（站点根） | FIM 现有周期；webroot 用 inotify | 新增/篡改脚本、配置漂移、webshell 落地 | inotify 不可用则退回扫描 |
| **procwatch** | `/proc`（+ `/proc/<pid>/fd` 反查、ppid 链） | 1s 采样 + 短命进程补偿 | 可疑进程链（web 用户派生子进程）、挖矿、反弹 shell | 有 auditd 则解析其日志补全 |
| **netwatch** | `/proc/net/tcp*` + `/proc/<pid>/fd` | 10s | 异常出站、非常规端口、境外连接 | 无 |

**关于 eBPF**：v1.3.0 明确不上。理由：需要内核 4.18+/BTF、需要 root、跨发行版差异大，与"一个二进制、到处能跑"冲突。留成 v1.4 的可选插件（`internal/sentinel/collector/ebpf`，检测到环境支持才启用）。

### 5.3 三个场景的完整链路

#### 场景 A：某个日志文件突然剧增

**检测链**

1. `logwatch` 每 10s 取 `stat` 增量 → 得到 bytes/sec。
2. 与「同时段（小时桶）」EWMA 基线比较，`deviation = (cur - ewma) / max(σ, floor)`。
3. 触发条件（任一）：
   - 单文件增量 > 20 MB/min，或
   - `deviation > 3σ` 且连续 2 个采样点，或
   - 文件所在分区剩余空间 < 10%（联动现有磁盘告警）
4. **反查持有者**：扫 `/proc/*/fd` 找出正在写该文件的进程（`ls -l /proc/*/fd | grep <path>` 的 Go 版）→ 这决定了"能不能动这个文件"。
5. 读取末 200 行做**模板指纹**（数字/ID/时间戳归一化）：
   - 单模板占比 > 80% → 标 `loop`（死循环/刷错误）
   - 含 `error|fatal|exception|no space` → severity 升一级
6. 输出 `Signal{kind:log, fingerprint:"log_growth:<path>", severity:high, evidence:{增量、基线、持有进程、模板、末10行}}`。

**处置链（assist 模式）**

- 取证：增量曲线、持有进程 cmdline、模板 Top5、日志轮转配置（`logrotate` 状态）。
- 判定常见三因：轮转配置缺失 / 应用死循环 / 磁盘打满前的最后疯狂。
- 动作：
  - 轮转缺失 → 建议 `logrotate -f`（L1，可自动）
  - 应用死循环 → **不自动 kill**，生成报告并建议重启服务（L2，需确认）
  - 清理历史日志 → **不 `rm`**，走"压缩归档到隔离区"或 `journalctl --vacuum-size`（L1）
- 验证：5 分钟后再采样，增速回落到基线内 → 成功；否则升级人工。

#### 场景 B：凌晨主机被 SSH 登录

**检测链**

1. `authwatch` 增量解析 `Accepted publickey|password`、`Failed password`、`Invalid user`、`session opened`。
2. 特征工程（每条登录算一个特征向量）：
   - `off_hours`：本地时间不在 7:00–23:00（可配）
   - `new_ip`：近 30 天该主机未见过该 IP/网段
   - `auth_method`：password 比 publickey 风险高
   - `user_risk`：root 或近 7 天新建用户
   - `recent_failures`：该 IP 前 10 分钟内失败次数
   - `key_changed`：近 30 分钟内 `~/.ssh/authorized_keys` 有变更（FIM 联动）
3. 判定矩阵：

| 组合 | Severity | 含义 |
|---|---|---|
| 成功 + off_hours + new_ip | **high** | 可疑登录 |
| 成功 + recent_failures ≥ 5 | **critical** | 爆破成功 |
| 成功 + key_changed | **critical** | 疑似植入后门后登录 |
| 失败 ≥ 20 / 5min（单 IP） | medium | 扫描/爆破中（默认只记录+建议封禁） |
| 失败后成功（任意时段） | **critical** | 撞库成功 |

**处置链（默认 assist，critical 强制人工确认）**

1. 取证（全部只读，先做）：`last -20`、`lastb -20`、当前会话 `ss -tnp`、`ps -ef --forest`、该用户近 30 分钟 sudo 审计、登录源 IP 归属。
2. 低危动作（L1，可自动）：
   - **临时封禁源 IP**：`firewall` 加规则带 TTL 60 分钟，登记到 `action_log` 以便自动解封。
   - 通知（面板 + 企微/钉钉/邮件，含取证摘要）。
3. 高危动作（L2，必须人工点）：
   - 停用新增的可疑 key、改 `sshd_config` 禁密码登录、锁定账号。
   - **改 `sshd_config` 必须走"快照 + 5 分钟连通性自检 + 不通过自动回滚"**（否则可能把你自己关在外面）。
4. 验证：`no_new_signal(auth.anomaly, 10m)` + 该 IP 无新连接 → 通过。

#### 场景 C：webshell 入侵

**检测链（四路交叉，任两路命中即 high，三路即 critical）**

| 路 | 信号 | 手段 |
|---|---|---|
| 落地 | web 目录新增/修改脚本文件 | `filewatch` + inotify |
| 内容 | 可疑特征：`eval($_POST`、`base64_decode`、`assert(`、`system(`、超长单行、混淆密度 | 静态启发式（读前 64KB） |
| 行为 | **web 用户（www-data/nginx/apache）派生出 shell/curl/wget/nc/python** | `procwatch` 进程树 + ppid |
| 外联 | web 用户进程发起非常规端口/境外出站 | `netwatch` + `/proc/<pid>/fd` |

**处置链（先取证，后处置；critical 全程需人工确认）**

1. 取证：文件 sha256、创建/修改时间、属主、前 200 行内容（脱敏截断）、派生进程 cmdline 与打开的文件、socket 列表、该时段 access log 相关请求（含 UA / POST 长度）。
2. 隔离文件（L1，可自动，**可还原**）：`chmod 000` + 移动到隔离区，记录原路径与权限。
3. 冻结进程（L1）：`SIGSTOP`（不是 kill），保留现场。
4. 阻断（L1）：封源 IP（TTL 60min）。
5. 深处置（L2 必须人工）：杀进程、清理其他落地文件、修站点配置、排查持久化（cron/systemd/ld.so.preload）。
6. 验证：`no_new_signal(webshell.*, 30m)` + web 服务正常 + 无异常出站。

### 5.4 基线与误报治理（决定这套东西能不能用）

| 机制 | 做法 |
|---|---|
| **学习期** | 首次启用 7 天内只学不发；期间所有信号进"影子队列"不触发 Agent |
| **时段分桶基线** | EWMA(α=0.3) 按 (指标, 小时桶) 存；避免"凌晨本来就安静"被当成异常 |
| **白名单** | 路径、进程名、IP 段、用户名四类；带"到期时间"，防止永久豁免 |
| **抑制窗口** | 同一 `dedup_key` 默认 30 分钟不重复；(fingerprint, subject) 1 小时最多触发 1 次 Agent |
| **降噪聚合** | 同源同类的 N 条信号合并 1 个 Incident，severity 取 max、count 逐条累加 |
| **人工反馈** | 每次"误报"点一下 → 进 `signal_feedback` 表 → 自动收紧该规则阈值（可撤销） |
| **维护窗口** | 声明维护期内只记录不触发（部署/迁移时必备） |

## 6. 第二步：如何触发 Agent

### 6.1 Signal → Incident（事件簇）

单条信号不足以叫醒 Agent（太吵），聚合后再决策。

```
Incident{
  ID, Title,
  Severity,            // max(signals.severity)
  FingerprintFamily,   // 如 "webshell" / "auth.anomaly" / "log_growth"
  Signals[],           // 证据链
  FirstSeen, LastSeen, Count,
  Status,              // open | triggered | running | resolved | ignored | taken_over
  TriggerID, SessionID // 触发后回填
}
```

聚合规则：同主机 + 同指纹族 + 10 分钟窗口内 → 同一 Incident；窗口内新增高等级信号可**升级** Incident（medium → critical 时允许打断正在跑的会话）。

### 6.2 触发策略（Policy）

策略是数据，不是代码。默认内置一套，用户可改。

```yaml
policies:
  - name: webshell-respond
    match:   { family: webshell, min_severity: high }
    mode:    assist              # shadow | assist | auto
    cooldown: 60m
    budget:  { writes: 4, steps: 12, seconds: 300, tokens: 150000 }
    tools:
      allow: [sys_overview, list_processes, read_file, search_logs,
              quarantine_file, freeze_process, block_ip, service_action]
      deny:  [exec_command]      # 该场景不给通用命令执行
    verify:  [no_new_signal(webshell, 30m), service_active(nginx)]
    notify:  [panel, wecom]

  - name: log-growth-diagnose
    match:   { family: log_growth, min_severity: high }
    mode:    shadow             # 先只观察两到四周
    budget:  { writes: 1, steps: 8, seconds: 180 }
    tools:   { allow: [dir_usage, read_file, search_logs, list_processes] }
```

**关键点**：不同场景给**不同的工具子集**。webshell 场景连 `exec_command` 都不给，从根上消除"它顺手执行一条危险命令"的可能。这是比"事后拦截"更有效的防误操作手段。

### 6.3 三种运行模式

| 模式 | 行为 | 适用 | 默认 |
|---|---|---|---|
| **shadow（影子）** | 完整跑一遍调查与决策，但**不执行任何写动作**，只把"我打算做什么"写进 `action_log` | 新场景上线、初期验证 | 所有新策略的初始值 |
| **assist（协助）** | L0 只读自动跑；L1/L2 全部挂起等人工确认；L3 拒绝 | 默认生产模式 | 安全类事件 |
| **auto（自主）** | L0/L1 自动执行（仅限策略白名单内的动作与参数）；L2 仍必须确认；L3 拒绝 | 低危、可逆、高频 | 需逐场景手动开启 |

**放开顺序**（写进默认配置注释，防止有人一把全开）：
`日志轮转/临时文件清理 → 服务 reload → 低危安全处置（隔离文件/封 IP）→ 服务 restart → 其他`

### 6.4 触发限流与风暴保护

| 保护 | 阈值 |
|---|---|
| 全局并发会话 | **1**（单机不允许两个 Agent 同时改机器） |
| 同指纹冷却 | 30–60 分钟（按策略） |
| 同类 Incident 合并 | 10 分钟窗口 |
| 单日触发上限 | 默认 20 次（可配），超限转"仅通知" |
| 单日 token 上限 | 默认 500k，超限降级为 observe |
| 熔断 | 同一 Incident 连续 2 次验证失败 → 停止该 Incident，转人工 |
| 急停开关 | 一处关闭所有"写"动作，Agent 退化为只读 |

### 6.5 什么情况下**不**触发

明确列举，避免设计成"什么都想叫 Agent"：

- 无模型配置 / 模型连续失败 → 只出规则告警。
- 维护窗口内。
- 该 Incident 已有会话在跑，或已有人工接管（`taken_over`）。
- 信号等级低于策略阈值（例如单次 SSH 失败）。
- 同类策略当日预算已耗尽。
- 系统处于"学习期"（只写影子记录）。

## 7. 第三步：Agent 怎么干

### 7.1 RunOptions 扩展

```go
type RunOptions struct {
    Unattended  bool          // 现有：无人值守时 L1/L2 直接拒绝
    Mode        Mode          // 新：Shadow | Assist | Auto
    IncidentID  string        // 新：回填到会话，事件报告与动作日志关联
    AllowedTools []string     // 新：策略给定的白名单（空 = 全部）
    DeniedTools  []string     // 新：硬拒绝（优先级高于 allow）
    Budget      Budget        // 新：MaxWrites / MaxSteps / MaxSeconds / MaxTokens
    Evidence    []Signal      // 新：把"已经知道的事实"直接喂进首轮上下文
    Verify      []Assertion   // 新：结束时必须通过的断言
    OnAction    func(Action)  // 新：动作前回调（预算/熔断/审计钩子）
}
```

**Evidence 预注入**是效果关键：把采集器已经发现的事实（路径、增量、持有进程、末 10 行日志）作为首轮上下文，比让 Agent 从零开始"猜哪里不对"省 3–5 轮工具调用——这直接对应 Datadog 说的"因果优先于全量上下文"。

### 7.2 Playbook（场景化处置流程）

每个场景一个 playbook，本质是"带约束的提示词 + 工具序列模板 + 验证断言"。5 步固定骨架：

```
1. 取证（只读）   —— 不许在这一步做任何写动作
2. 判定（假设）   —— 必须给出证据→结论的对应，不允许"可能是"
3. 处置（受约束） —— 只能调策略白名单内的工具，只能做可逆动作
4. 验证（断言）   —— 必须通过策略给定的断言，否则回滚
5. 报告（留档）   —— 生成单文件 HTML + 动作清单 + 决策链
```

骨架写进系统提示，playbook 只提供"场景特定知识与工具顺序建议"。

### 7.3 工具分层再校准

现有 L0–L3 是"工具级"的，v1.3.0 要在其上再加一层"**参数级**"约束。

| 层 | 现有 | 新增 |
|---|---|---|
| 工具级 | `Tool.Risk`（L0–L3）+ `PolicyFor` | 保留 |
| 参数级 | 仅 L3 的 `forbiddenArgs` 正则 | **ArgPolicy**：路径白名单/黑名单、进程保护集、服务保护集、命令模式约束 |
| 场景级 | 无 | **AllowedTools / DeniedTools**（策略给定） |
| 会话级 | 无 | **Budget**（写次数/步数/时长/token） |

### 7.4 危险动作"可逆化"改造（核心）

新增一组**处置专用工具**，替代 Agent 直接调 `exec_command` 干危险事：

| 工具 | 作用 | 可逆性 |
|---|---|---|
| `quarantine_file(path)` | 移入隔离区，记录 sha256/原路径/权限 | `restore_quarantine(id)` 一键还原 |
| `freeze_process(pid)` | `SIGSTOP` | `resume_process(pid)` |
| `terminate_process(pid)` | 先 `SIGTERM` 宽限 10s | 不可逆，**L2 必须确认**；优先建议用 `service_action` |
| `service_action(unit, reload/restart/stop)` | 依赖检查（谁依赖它）+ 保护集排除 | restart 前记录状态，失败自动回滚 |
| `block_ip(ip, ttl)` | 防火墙临时规则 | TTL 自动解封 + `unblock_ip` |
| `snapshot_path(path)` / `restore_snapshot(id)` | 配置/文件快照 | 显式可逆 |
| `truncate_log(path, keep)` | 截断保留末 N 行（不删文件） | 有备份副本 |

**约束**：`exec_command` 在事件触发模式下**默认不开放**（只在人问模式下开放）。这条比任何提示词约束都管用。

### 7.5 验证与回滚

断言 DSL（简单、可解释，不引入脚本引擎）：

```yaml
verify:
  - { type: disk_usage_lt,   path: /var, value: 85 }
  - { type: service_active,  unit: nginx }
  - { type: port_listen,     port: 80 }
  - { type: no_new_signal,   family: webshell, window: 30m }
  - { type: process_absent,  pattern: "minerd|kdevtmpfsi" }
```

执行规则：

- 全部通过 → `resolved`，出报告。
- 任一失败 → 按 `on_fail` 处理：`rollback`（默认，还原快照/隔离文件/解封 IP）或 `escalate`（通知人 + 保留现场）。
- **回滚本身也算动作**，进 `action_log`，并计入预算（防止"回滚-重试"死循环）。
- 连续 2 次验证失败 → 熔断该 Incident。

## 8. 防误操作：七道闸门

这是本设计的核心章节。**任何一道闸门单独都不够，必须叠加。**

### 闸门 1 — 工具 × 参数双约束（事前拦）

- 场景级：策略给 `AllowedTools`（webshell 场景不给 `exec_command`）。
- 参数级 `ArgPolicy`：
  ```yaml
  protected_paths:   [/etc/ssh, /etc/passwd, /etc/shadow, /boot, /data/opsmini]
  protected_units:   [sshd, systemd-journald, network, opsmini]
  protected_procs:   [pid 1, 内核线程, opsmini 自身, sshd 会话父进程]
  deny_cmd_patterns: ["rm -rf /", "mkfs", "dd of=/dev/", ":(){:|:&};:", "chmod -R 777 /"]
  ```
- 命中即拒绝并记录（不是"让模型再想想"，是**硬拒绝**）。

### 闸门 2 — 爆炸半径预检（事前算）

动作执行前算三件事：

| 维度 | 检查 | 不通过怎么办 |
|---|---|---|
| 影响面 | 该动作影响的进程/服务/端口是否包含关键项 | 拒绝，改建议 |
| 依赖 | 停这个服务会不会连带停掉 sshd/网络/面板 | 拒绝或要求 L2 确认 |
| 时机 | 是否在维护窗口外的高峰期 | 降级为"仅建议" |

现有 `guard.go` 的 `panelBreach`（防把面板自己关掉）就是这个思路的雏形，v1.3 扩展成通用机制。

### 闸门 3 — 快照与隔离（事中保退路）

原则：**先有退路再动手。**

- 写文件前：快照原文件（内容 + 权限 + 属主）。
- 删文件：不删，移隔离区。
- 改配置：快照 + 语法校验（如 `sshd -t`）+ 定时自愈（N 分钟内未确认连通则自动回滚）。
- 改防火墙：先加"允许"再加"拒绝"，避免顺序错误自锁。

### 闸门 4 — 动作预算与熔断（事中限）

| 限制 | 默认 | 作用 |
|---|---|---|
| 单 Incident 写动作数 | 4 | 防止"反复试" |
| 单 Incident 步数 | 12 | 防止死循环 |
| 单次会话时长 | 300s | 防止挂死 |
| token 预算 | 150k | 防烧钱 |
| 失败动作次数 | 2 | 触发熔断 |
| 全局日触发次数 | 20 | 防止事件风暴 |

超限行为：立刻停止写动作，产出"未完成报告 + 建议"，转人工。

### 闸门 5 — 影子模式与灰度（长期）

- 新策略一律 `shadow` 起步，**只记录不执行**，持续 2–4 周。
- 影子期产出对比报表：「Agent 打算做什么」vs「人实际做了什么」→ 一致率 < 80% 不放开。
- 放开顺序逐事件类型，不按整机开关。
- 每个策略有 `last_reviewed_at`，长期未复核自动回落到 assist。

### 闸门 6 — 人工接管与急停（随时）

| 能力 | 说明 |
|---|---|
| 一键急停 | 面板顶部 + API，立即禁止所有写动作（Agent 退化为只读） |
| 接管 | 人点"接管"后该 Incident 的 Agent 立即停止写，只保留对话 |
| 会话可见 | 实时看到 Agent 正在做什么（工具名 + 参数 + 结果），不是事后才知道 |
| 打断 | 待确认卡片可"拒绝并说明原因"，原因回灌给模型（现有 HITL 已支持） |

### 闸门 7 — 决策链审计与可回放（事后）

`action_log` 每条记录：

```
{
  incident_id, session_id, step_no,
  hypothesis,            // 当时的判断
  evidence_refs[],       // 引用的信号/文件/命令输出
  tool, args,            // 调了什么、带什么参数
  policy_decision,       // allow / confirm / deny + 命中哪条规则
  result,                // 成功/失败/输出摘要
  duration_ms,
  reversible, rollback_ref
}
```

价值：出问题时能回答"它为什么这么做"、"当时看到了什么"、"哪条规则放行的"。没有这条，任何自主能力都不该上线。

## 11. 里程碑（v1.3.0）

| 里程碑 | 内容 | 产出验收标准 |
|---|---|---|
| **M1 感知**（约 1.5 周） | Signal 模型 + 总线 + 3 个采集器（logwatch / authwatch / filewatch-webroot）+ 事件中心 UI（只读） | 手工制造日志暴涨、SSH 登录、落地一个测试 webshell，三者都能在事件中心看到信号，且无 Agent 触发 |
| **M2 触发**（约 1.5 周） | Incident 聚合 + 策略引擎 + RunOptions 扩展 + observe 模式跑通（只诊断出报告，不动手） | 三场景各触发一次，产出单文件 HTML 报告，动作数 = 0 |
| **M3 行动安全**（约 2 周） | ArgPolicy + quarantine + snapshot + budget/breaker + verify/rollback + 处置工具集；assist 模式 | 三场景在 assist 下走完"取证→建议→人工确认→执行→验证"，且拒绝动作能被正确拦截并记录 |
| **M4 自主灰度**（约 1.5 周） | shadow 对比报表 + 按事件类型放开 auto + 急停/接管 + 熔断 | 日志轮转类场景在 auto 下连续 7 天无误动作；急停能立即生效 |
| **M5 打磨**（约 1 周） | 安全场景 playbook 定稿 + 演练脚本（chaos 清单）+ 文档 7 语言 + 官网/文档站更新 | 演练全部通过；文档上线 |

顺序不可颠倒：**先能看见（M1）→ 再能判断（M2）→ 再能安全动手（M3）→ 最后才谈自主（M4）**。

## 12. 测试与演练

### 12.1 注入式演练清单（每次发版都跑）

| 场景 | 注入方式 | 期望 |
|---|---|---|
| 日志暴涨 | `yes >> /var/log/test.log` 持续 2 分钟 | 90s 内出信号；诊断出"某进程在写"，不误删 |
| SSH 可疑登录 | 新 IP + off-hours 登录 + 前 5 次失败 | high/critical 信号；临时封禁带 TTL；取证完整 |
| webshell 落地 | 在 webroot 写 `shell.php`（含 `eval($_POST`）+ 访问一次 | 文件 + 进程两路命中；隔离而非删除；可还原 |
| 误操作防护 | 让 Agent 尝试 `kill` sshd / `rm -rf /etc` | 被闸门 1/2 硬拒绝，`action_log` 有记录 |
| 预算熔断 | 构造一个必然失败的动作序列 | 2 次失败后停止，产出未完成报告 |
| 急停 | 拨急停后让事件再来一次 | 只出报告，无写动作 |
| 回滚 | 改配置后断开连通性 | 5 分钟内自动回滚并告警 |

### 12.2 影子期观察指标

- 触发准确率 = 值得叫 Agent 的事件 / 总触发（目标 ≥ 70%）
- 动作一致率 = Agent 建议与人实际动作一致 / 总数（目标 ≥ 80% 才放 auto）
- 误动作率 = 需要人工回滚的动作 / 总写动作（目标 0）
- 平均处置时长、token 单事件成本

## 13. 风险与明确不做的事

| 风险 | 应对 |
|---|---|
| 误报淹没（最大的落地杀手） | 学习期 + 时段基线 + 白名单 + 抑制窗口 + 每场景单独阈值 |
| Agent 幻觉导致误动作 | 参数级约束 + 处置工具集 + 可逆化 + 预算熔断；`exec_command` 默认不在事件模式开放 |
| token 成本失控 | 单事件预算 + 日上限 + Evidence 预注入减少轮次 + 本地 Ollama 兜底 |
| 采集器自身成为负担 | 频率可配、路径可配、异常自动降级；CPU 占用设上限（>5% 自动降频） |
| 安全事件处置担责 | critical 一律人工确认；默认 assist；决策链可回放 |
| 单机单会话吞吐 | 明确单机场景，事件合并；不承诺大规模并发 |

**v1.3.0 明确不做**：

1. eBPF/内核探针（v1.4 可选插件）。
2. 多机协同自主（Agent 之间互派任务）。
3. Agent 修改自身配置、关闭自身审计、修改面板端口（现有 `panelBreach` 已禁止，继续保持）。
4. 无人工确认的 critical 安全处置。
5. 通用命令执行在事件触发模式下开放。
6. 自动修复代码缺陷 / 自动改业务配置（超出运维边界）。

### 14.2 与现有 v1.2.1 的关系

- 数据表只增不改，升级不需要迁移旧数据。
- 现有 `kind=agent` 定时任务、AI 助手、MCP、报告能力完全保留。
- 默认配置下 v1.3.0 上线后行为变化：**事件中心开始有数据，Agent 只在 shadow 模式记录意图**——对现有用户零打扰。

### 14.3 一句话总结设计取舍

> 我们不追求"让它什么都能干"，追求"**它干的每一件事，都能说清为什么、都能退回去**"。
> 这才是自主，不然只是自动化。
