# 自律 Agent（イベントセンター）

「AI アシスタント」は**あなたが聞けば答える**：あなたが現象を説明し、それが調査して結論を出す。
「自律 Agent」は**それ自身が見張る**：コレクターがバックグラウンドでホストを継続的に観察し、注目に値する事象を発見すると自ら調査を開始し、あなたが設定した境界に従って「記録のみ / まず確認してから行動 / 自動対処」を決定し、その判断・根拠・アクションをすべて記録に残す。

両者のモデル、ツールセット、ガードレールは同一のものであり、違いは**誰が起動するか**だけである。

## 一つの閉ループ

```
コレクター（常駐、2s–20s 段階分け）
   ↓  Signal に正規化（フィンガープリント重複排除、DB 保存）
集約（同一事象を一つの Incident に折り畳み、カウントは増えるが行数は増えない）
   ↓
イベントセンター（あなたが見るリスト）
   ↓  family + 重大度でポリシーをマッチング
ポリシーエンジン（shadow は分析のみ / assist は読み取り自動・書き込みは承認要 / auto はホワイトリストで自動）
   ↓
Agent 多段調査（ReAct、ツール呼び出しを一件ずつ記録）
   ↓  アクションは書き込み予算 + クールダウン + リスクレベルで制約
検証（任意のアサーション：アクションが実際に有効になったか確認）
   ↓  検証失敗時は自動で一度リトライ
記録（イベント → 実行 → 一件ずつのアクション → レポート → シャドーレビュー）
```

## コレクター

6種類の常駐コレクションは、すべて読み取り専用です：

| コレクター | 監視対象 | 典型的なレベル |
|---|---|---|
| ログ急増 | 時間単位バケットの EWMA ベースライン + 20MB/min のハードしきい値、そのファイルを保持するプロセスを逆引き | high |
| ログイン異常 | 非業務時間帯、初出 IP、ブルートフォース後の成功、`authorized_keys` が変更された直後 | high |
| Web ディレクトリへのスクリプト設置 | 14 種類の WebShell シグネチャ、強いシグネチャは直接 high | high |
| 不審なプロセス派生 | Web ユーザーによる shell / curl / python の起動、マイニングプロセス名 | critical |
| 異常な外部通信 | 想定外の宛先とポートへのアウトバウンド接続 | high |
| メトリクスアラート | CPU / メモリ / ディスク / 負荷 / サービス状態など 24 件のルール | medium–high |

収集頻度はカテゴリごとに段階分けされており（2s–20s）、すべてポーリングまたはファイル読み取りであり、常駐 agent プロセスは不要で、システム設定も変更しません。

## イベント集約：1件か複数件か

同じ対象で繰り返し問題が発生する場合、画面を埋め尽くすのではなく、必ず1件のイベントにカウントを持たせる。ルール：

| シナリオ | 動作 |
|---|---|
| 同一オブジェクトの反復変化（設定変更、サービスの再起動ループ） | 未処理の間は継続的に折りたたみ、`次数` をインクリメント |
| 同一シナリオで複数のソース（10 個の IP によるブルートフォース） | 1件に折りたたみ、メンバーリストは展開可能（上限 50、総数は実際のまま記録） |
| **メトリクスアラート / ログ急増** | **イベントが処理されない限り継続的に折りたたむ**——誰も処理していないアラートは「1件の未対応事項」であり、10 分ごとに新しいイベントが1件増えるわけではない |
| ログイン異常（ログイン成功） | 同一 IP は半日以内で折りたたみ、日をまたぐと新しい観察として扱う |
| 無視済み / 処理済み後に再発生 | **新規に1件作成**、古いイベントには併合しない |

> v1.4 より前は、メトリクスアラートが 10 分のウィンドウで分割され、1つの CPU ルールで一晩に 8 件の未対応アラートが生成されることがあった。現在は「未処理なら継続的に折りたたむ」に変更され、1回のアラートは1行になる。

## ポリシーエンジン

ポリシーは**データ**（パネル上で追加・削除・変更可能）であり、コードではありません。各ポリシーは以下を決定します：どのシナリオか、どのレベルから起動するか、どのモードを使うか、どれだけの予算を割り当てるか。

3つのモード：

| モード | 読み取り操作 | 書き込み操作 | 適用 |
|---|---|---|---|
| `shadow` シャドウ | 自動 | **一律拒否**、記録のみ「どうするつもりか」 | 新規シナリオはまず2週間観察 |
| `assist` アシスト | 自動 | ポップアップ/人手による承認待ち | デフォルト推奨 |
| `auto` 自動 | 自動 | **ホワイトリスト内の低リスク操作のみ**自動実行 | 十分に検証済みのシナリオ |

6つの組み込みポリシー：

| ポリシー | シナリオ | デフォルトモード | できること |
|---|---|---|---|
| `webshell-respond` | WebShell | assist | フォレンジック → ファイル隔離、プロセス凍結、一時的IPブロック（いずれも復元可能） |
| `auth-anomaly` | ログイン異常 | assist | フォレンジック → 送信元IPの一時的ブロック |
| `proc-anomaly` | 不審プロセス | assist | フォレンジック → 凍結（killはしない） |
| `log-growth` | ログ急増 | shadow | 誰が書いているか、なぜかを特定、どうするつもりのみ記録 |
| `net-anomaly` | 異常な外部通信 | shadow（デフォルト無効） | 読み取り専用の調査 |
| `change-review` | 不審な変更 | shadow（強制） | 今回の変更が悪意あるものか判断し、ロールバック/許可の提案を行う |

各ポリシーにはさらに4つの予算上限と1つのクールダウンがあります：**書き込み操作上限、最大ステップ数、最大実行秒数、最大token数、クールダウン秒数**。いずれかを超過した場合、そのラウンドは直ちに終了し、ありのまま記録します。

クールダウン中はイベントに「ポリシーXに一致したが、当該ポリシーはクールダウン中（残りN）、今回は自動分析を行わない、人手で判断してください」と明記されます——サイレントにスキップされることはありません。

## 攻撃チェーン

単一のイベントでは見落としやすい：WebShell の設置が 02:10、不審なプロセスが 02:14、外部通信が 02:20 と、3 つの独立したイベントは別々のことのように読める。攻撃チェーンはそれらを 1 回の侵入としてつなぎ合わせる。

5 つの段階：**初期アクセス → 実行・設置 → 永続化 → 外部通信・制御 → 影響**。

関連付けの根拠（いずれも説明可能で、異議を唱えられる）：

- 共有指標（同一 IP、同一パスルート、同一ドメイン）
- 時間の近接（15 分以内が最も強く、1 時間以内は弱い証拠とみなす）
- 段階の進行（新たな段階は加点、段階の後退はより強い共有指標がある場合のみ許可）
- 総合スコア ≥ 0.45 の場合のみ統合

意図的に厳しくしたルール：

- **単独のブルートフォースではチェーンを開始しない**。各パブリックホストは毎日スキャンされており、失敗ログインを「攻撃チェーンの起点」とみなすと、この機能は即座に信頼性を失う。後続で設置や外部通信が現れた場合にのみ統合する
- **指標アラートやログの急増は決してチェーンに入れない**。それらは症状であり、段階ではない
- **変更はデフォルトでチェーンに入れない**。ただし、ルールの再確認で不審と判定され、かつ変更箇所が再起動をまたいで存続できる場所（`authorized_keys`、cron、systemd、sudoers、`ld.so.preload`、PAM、profile など）であり、チェーン上にすでに設置または外部通信が現れている場合を除く
- **3 つ以上の段階、または「実行・設置 + 外部通信・制御」が同時に現れた場合**にのみ critical へ昇格し通知する

> 攻撃チェーンは注目の優先度を上げるだけである。**Agent の権限を拡大することはない**：予算、モード、利用可能なツールは一切変わらず、「攻撃チェーンに属する」という理由でより多くの書き込み操作が許可されることもない。

## 対応トランザクション：アクションは取り消せるか、取り消せないと明示するかのいずれか

Agent が書き込み操作を実行する際、各操作を対応トランザクションログに記録します：

- **可逆アクション**（ファイルの隔離、プロセスの凍結、IP のブロック、ログの切り詰め、スナップショットの取得）は、対応失敗時に**逆順でロールバック**
- **不可逆アクション**（ファイルの削除、コマンドの実行、設定の変更）はロールバックできず、レポートには「N 項は取り消し不可、手動確認が必要」と明記されます——ロールバック済みと偽ることはありません
- ロールバック結果は正直に 3 種類に分類：取り消し済み / 取り消し不可 / ロールバック失敗

イベント詳細ページでは、ロールバックされていないアクションに対して直接「ロールバック」をクリックでき、Agent を待つ必要はありません。

## シャドウレビュー

`shadow` モードで実行した処置には、事後に自動レビューが付きます：**事実**を見て、その時の判断がまだ必要だったかどうかを判定します。

| 結論 | 意味 |
|---|---|
| `would_help` | 当時実行して確かに有効だった（問題が継続して存在） |
| `unnecessary` | 当時実行しなくても正しかった（問題が自然に解決 / 誤検知だった） |
| `unknown` | 証拠不十分、結論を出さない |

これは「シャドウモード」を「見るだけで練習しない」から「練習したら誰かが添削する」へ変える鍵です：連続して複数の `unnecessary` が出れば、ポリシーのしきい値が低すぎることを示しており、引き締めるべきです。連続して `would_help` が出れば、assist に昇格できることを示しています。

## フィードバック抑制

同一のイベントグループが 7 日以内に 2 回手動で無視された場合、以降の同種のものは**Agent を起動しなくなります**（記録はされ、リストにも表示されますが、自動分析は行われません）。

理由は明白です。1 回の無視は一時的な状況かもしれませんが、2 回の無視は設定の問題です。このルールにより、「関心のないアラート」がトークンを消費しなくなります。

## 変更系イベントの鉄則

ポリシーをどう設定しても、`family=change` のイベントは**調査のみ可能で、アクションは実行できません**：

- 強制的に shadow へ降格し、書き込み予算をゼロにし、書き込みツールをすべて無効化し、ステップ上限を 8 にします

これは潔癖症ではなく、攻撃面の問題です。「監視対象の設定ファイルを書き込む」だけで Agent にアクションを実行させられるなら、それは攻撃者にリモートトリガーの経路を一つ増やしているのと同じです。

## パネルの使い方

「イベントセンター」ページ上部の6つのフィルターには、いずれもカウントが付いています：

| フィルター | 確認できる内容 |
|---|---|
| 対応待ち | 発生済みで、まだ誰も処理していない |
| 覚醒待ち | まだトリガー条件に達しておらず、後続のシグナルを待っている |
| すべて | フィルターなし |
| 対応済み | 調査完了、または手動で解決済みとマーク |
| 失敗 | 実行失敗 / 検証未通過 |
| 無視済み | 対応不要と判断したもの |

イベント詳細ではドリルダウンできます：関連シグナル、Agent 実行記録、アクションチェーンごと（ツール、パラメータ、判定、生出力）、レポート、攻撃チェーンコンテキスト。

2つの手動アクション：

- **無視**：対応不要としてマークし、フィードバック抑制統計に入れる
- **自分で引き継ぐ**：「この件は自分で処理する」と宣言し、Agent は自動で動作しなくなる（新しいシグナルは引き続き記録される）

## スケジュールと記録

- 実行ごとに `AgentRun` レコードを1件残す（モード、ステップ数、ツール数、書き込み回数、所要時間、結論、リトライ有無）
- レポートは単一ファイル HTML としてアーカイブし、イベントごとに開くかダウンロードできる
- すべてのアクション（ツール呼び出し、承認、拒否、ロールバック）は監査ログに記録される

## 一言で言う境界

OpsMini は無人運用の root 自律インテリジェントエージェントを**提供しません**。目標とする形態は「自律調査 + 段階的認可」です。Agent は発見、証拠収集、判断、提案を担当し、破壊的操作は人による認可またはホワイトリストによる制限で収束させます。
