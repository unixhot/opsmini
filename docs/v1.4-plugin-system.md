# 插件系统设计（OpsAnt 下发，OpsMini 执行）

> 状态：设计稿（2026-10-29）
> 定位：OpsMini 四大核心能力之四。前三个（命令执行、文件分发、指标采集）已上线，缺插件管理，导致"超级 Agent + 插件生态"只实现了一半。

---

## 1. 为什么必须做成"下发式"

先说清楚**不做什么**：OpsMini 不做插件市场、不做插件仓库 UI、不做跨主机编排。这些归 OpsAnt。

OpsMini 在这条链路上的角色只有一个：**执行器 + 报告者**。

```
OpsAnt（PaaS）
  ├─ 插件仓库：包存储（OSS/本地）、版本元数据、签名
  ├─ 策略中心：哪个主机组装哪些插件、什么版本、什么配置
  └─ 下发通道 ──gRPC 双向流（4507，Agent 主动连）──▶ OpsMini Agent
                                                        ├─ 校验签名与平台
                                                        ├─ 落盘、解包、建用户
                                                        ├─ 启停插件进程
                                                        └─ 回执：状态/日志/指标
```

三条硬约束：

1. **Agent 不出站新增端口**。所有指令走现有 4507 双向流，插件包由 Agent 主动 HTTP 拉取（不是 Server 推分片）——拉取可断点续传，且天然适配"Agent 在 NAT 后面"。
2. **OpsMini 面板不得反向调用 OpsAnt 控制面 4508**（v1.4 已定的边界铁律）。插件页只展示本地已装插件与状态，**不提供"浏览市场"**；装什么由 OpsAnt 决策。
3. **内核不开后门**。插件不能链接 OpsMini 内部包、不能拿到 `*gorm.DB`、不能直接写 `change_events`。插件与内核的唯一通道是文件系统约定 + 本地 socket。

## 2. 插件是什么：进程，不是 Go plugin

| 方案 | 结论 | 理由 |
|---|---|---|
| `plugin.Open()`（Go 原生） | ❌ 否决 | 必须与主程序完全一致的 Go 版本与依赖哈希；升级 OpsMini 就全废；崩溃会带走整个进程 |
| 独立进程 + 约定协议 | ✅ 采用 | 崩溃隔离、可限资源、可用任意语言写、升级互不影响 |
| WASM | ⏳ 备选 | 沙箱最好，但生态与调试体验差，等有第三方开发者再评估 |

**最小可运行形态**：一个可执行文件 + 一个 `plugin.yaml` 清单 + 一个 Unix socket。
Agent 负责拉起进程、传配置、定期探活、收集输出；插件只做自己的业务。

## 3. 包格式

```
foo-collector-1.2.0-linux-amd64.tar.gz
├── plugin.yaml          # 清单（必需）
├── bin/plugin           # 入口可执行（必需，单文件，静态链接）
├── config.schema.json   # 配置 schema（可选，面板据此渲染表单）
├── ui/index.html        # 面板页面（可选，v2 支持）
├── README.md            # 说明（可选）
└── SIGNATURE            # ed25519 签名（必需，对整包 sha256 签名）
```

### 3.1 清单

```yaml
apiVersion: opsmini.plugin/v1
id: foo-collector              # 全局唯一，^[a-z0-9][a-z0-9-]{2,40}$
name: Foo 采集器
version: 1.2.0                 # semver
vendor: 速云科技
description: 采集 Foo 服务的队列深度与消费速率
kind: collector                # collector | action | panel
entry: bin/plugin              # 相对包内路径
platform: [linux/amd64, linux/arm64]

# 能力声明：Agent 据此决定给不给权限，也是审计依据
capabilities:
  - metrics                    # 允许向 Agent 上报指标
  - read:/etc/foo              # 只读挂载点（白名单前缀）
  - exec:systemctl             # 允许执行的白名单命令
  - net:outbound               # 允许主动外连

# 运行约束
runtime:
  user: opsmini-plugin         # 统一低权用户，Agent 创建
  memoryLimitMB: 128
  cpuQuotaPercent: 20
  restartPolicy: on-failure    # always | on-failure | never
  socket: /data/opsmini/data/plugins/run/foo-collector.sock

# 依赖（仅同机已装插件，不做跨插件包管理）
requires:
  opsmini: ">=1.5.0"           # 与 apiVersion 不同，这是主机 Agent 版本要求
```

### 3.2 签名与来源

- 签名公钥**编译进 Agent**（可被 `--plugin-allow-unsigned` 覆盖，仅用于开发）。
- 校验顺序：包 sha256 → ed25519 签名 → `apiVersion` 兼容 → `platform` 匹配 → 清单字段合法性。
- 任一失败即拒绝安装，回执给 OpsAnt 具体原因（不装"半截插件"）。

## 4. 协议扩展（proto/agent/v1）

在现有 `ServerMessage` 里加一条下行，`AgentMessage` 里加一条上行。**不新建连接**。

```proto
message ServerMessage {
  oneof payload {
    RegisterAck   register_ack   = 1;
    ExecuteTask   execute_task   = 2;
    PushFileTask  push_file_task = 3;
    PullFileTask  pull_file_task = 4;
    Ping          ping           = 5;
    PluginTask    plugin_task    = 6;   // 新增
  }
}

message AgentMessage {
  oneof payload {
    Register      register       = 1;
    Heartbeat     heartbeat      = 2;
    TaskResult    task_result    = 3;
    FileChunkAck  file_chunk_ack = 4;
    FileChunkData file_chunk_data= 5;
    PluginResult  plugin_result  = 6;   // 新增
  }
}

// 下发：声明期望状态，而不是"执行一次命令"
message PluginTask {
  string job_id   = 1;
  string action   = 2;  // install | upgrade | remove | enable | disable | status
  PluginSpec spec = 3;  // action=status 时为空
}

message PluginSpec {
  string id       = 1;
  string version  = 2;
  string url      = 3;  // 包地址（http/https，Agent 主动下载）
  string sha256   = 4;  // 整包摘要
  string signature= 5;  // ed25519(base64)
  bytes  config   = 6;  // 插件配置（YAML/JSON 原样透传）
  bool   restart  = 7;  // upgrade 时是否保持运行
}

message PluginResult {
  string job_id   = 1;
  string plugin_id= 2;
  string action   = 3;
  string status   = 4;  // installed | running | stopped | removed | failed
  string version  = 5;
  string error    = 6;
  string log_tail = 7;  // 失败时带最后 4KB 日志，省得 OpsAnt 再拉一次
}
```

**为什么用"期望状态"而不是命令式脚本**：OpsAnt 的重试、幂等、对账都依赖"我想要什么"，而不是"我执行了什么"。Agent 收到 `install v1.2.0` 时若已是该版本，直接回 `installed` 而不重装。

包下载走 Agent 的 HTTP 客户端，支持 `Range` 断点续传，落盘在 `/data/opsmini/data/plugins/.cache/<sha256>.tar.gz`，重试时复用。

## 5. 生命周期

```
          ┌──────────┐  install   ┌──────────┐  enable  ┌────────┐
  (无) ──▶│ verified │──────────▶│ installed│─────────▶│ running│
          └──────────┘            └──────────┘          └────────┘
               │ 校验失败              │ disable              │ 崩溃
               ▼                       ▼                      ▼
           failed                  stopped ◀─────────────── crashed
                                      │ remove
                                      ▼
                                  removed（保留 /data/opsmini/data/plugins/<id>/data）
```

关键规则：

1. **升级 = 装新版本 → 探活成功 → 切软链 → 停旧进程**，失败自动回滚到旧版本（`current` 软链）。
2. **remove 默认保留数据目录**，`--purge` 才删；回执里明确告知保留了哪些路径。
3. **插件崩溃不影响 Agent**：进程由 Agent 的 supervisor 管理，按 `restartPolicy` 重启，连续 5 次失败进入 `crashed` 并不再重启（避免死循环烧 CPU）。
4. **配置变更**：写 `<plugin>/config.yaml` + 发 `SIGHUP`；插件不支持 SIGHUP 则重启进程。

目录布局：

```
/data/opsmini/data/plugins/
├── .cache/                      # 下载缓存（按 sha256）
├── foo-collector/
│   ├── current -> releases/1.2.0
│   ├── releases/1.2.0/...       # 解包内容，只读
│   ├── config.yaml
│   ├── data/                    # 插件自己的持久数据
│   └── plugin.log               # stdout/stderr 落盘（按天切割）
└── state.json                   # 已装清单与状态（Agent 重启后据此恢复）
```

## 6. 插件与内核的三条通道

| 通道 | 方向 | 用途 |
|---|---|---|
| Unix socket（插件↔Agent） | 双向 | 上报指标/事件、领取配置、心跳 |
| 共享目录 | Agent→插件 | 配置下发、证书、只读数据 |
| 进程退出码 + 日志 | 插件→Agent | 健康判定 |

socket 协议用**行分隔 JSON**（不是 gRPC）：插件作者用任何语言 10 行就能实现，也不需要 proto 代码生成。

```json
{"type":"hello","plugin":"foo-collector","version":"1.2.0","api":"1"}
{"type":"metric","name":"foo_queue_depth","value":128,"labels":{"queue":"default"},"ts":1793232000}
{"type":"event","level":"warn","message":"消费延迟超过 5s","fields":{"lag":5.2}}
{"type":"heartbeat"}
```

Agent 侧把它转成两类东西：`metric` → 追加到 `/metrics` 的 `opsmini_plugin_*` 前缀；`event` → 进 sentinel 总线（family=`plugin.<id>`），可被触发策略消费。

## 7. 权限模型（诚实的边界）

MVP 阶段能做到的：

- 独立系统用户 `opsmini-plugin`（无 shell、无 sudo）；
- cgroup v2 限制内存与 CPU（`runtime.memoryLimitMB` / `cpuQuotaPercent`）；
- `capabilities` 白名单校验：插件要 `read:/etc/foo` 就只挂载该路径；要 `exec:systemctl` 才给 PATH 包装脚本；
- 所有 install/remove/enable 记审计日志（谁、什么时候、哪个版本、签名指纹）。

MVP 阶段**做不到**的，必须写进文档而不是假装有：

- 不能阻止一个已获 `read:/etc` 的插件去读 `/etc/shadow`（同用户下文件系统权限即边界，除非上 mount namespace）；
- 不能阻止插件主动外连（除非配 `net:outbound` 白名单 + nftables 规则，属 v2）；
- 不能审计插件内部的系统调用（auditd/eBPF 才做得到，见 v1.6 评估）。

结论：**签名的意义是"来源可信"，不是"行为安全"**。官方插件默认全信任，第三方插件默认只给最小能力。

## 8. OpsAnt 侧需要配合的部分

Agent 端只负责执行，OpsAnt 要提供：

1. 插件包托管（OSS 或本地目录）+ 元数据表（id/version/os/arch/sha256/signature）；
2. 主机维度"期望插件集"（主机组 → 插件 + 版本 + 配置）；
3. 下发与对账循环：拉 `/agents` 状态，与期望集 diff，生成 `PluginTask`；
4. 结果聚合：把 `PluginResult` 落到主机详情页，失败带 `log_tail` 直接可看。

接口层面沿用 OpsAnt 现有的控制面风格（它已经有 `/agents` `/execute` `/pull` `/push`），新增 `/plugins` 与 `/plugins/assign` 即可。

## 9. 实施拆分

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | proto 扩展 + 包校验 + 安装/卸载/启停 + state.json | `opsmini plugin install ./foo.tar.gz` 能起进程并回执 |
| P2 | socket 协议 + 指标/事件注入 + cgroup 限制 | `/metrics` 出现 `opsmini_plugin_*`，事件进事件中心 |
| P3 | OpsAnt 下发联调（install/upgrade/remove/status） | 两端跑通，断网重连后状态一致 |
| P4 | 官方插件迁移：主机安全作为一个插件（可卸载） | 安全模块能以插件形式装上/卸掉，核心功能不受影响 |
| P5 | 面板插件（iframe + API 反代），第三方接入文档 | 一个 demo 面板插件跑起来 |

P4 是这套设计的真正考验：**如果主机安全拆不成插件，说明内核边界设计错了**。
