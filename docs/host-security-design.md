# OpsMini 主机安全设计

> 本文讲的是**「主机安全」这个功能是怎么设计和实现的**：每项检测看什么、判据是什么、分数怎么算、边界在哪、为什么这么选。
>
> 对应代码：`internal/service/{security,baseline,loginsecurity,firewall,fim,threat,securitymonitor}.go`、`internal/api/v1/{security,baseline,fim,threat,firewall}.go`、`internal/router/router.go`。

---

## 1. 设计目标与非目标

### 目标

| 目标 | 具体含义 |
|---|---|
| **零依赖** | 不装 agent、不依赖内核模块、不连中心服务，二进制带起来就能审 |
| **可解释** | 每一项检测都能点开看到「读了哪个文件、看到什么值、为什么判不合格、建议怎么改」 |
| **可动手** | 发现问题后能直接在面板里修（改防火墙、跑体检、重建基线、标记威胁已处理） |
| **给人看，也给 AI 看** | 同一份结论既渲染成页面，也作为只读工具交给内置 Agent |
| **不越权** | 只读能力登录即可用；任何改系统的动作都要单独的权限点 + root 身份 |

### 非目标（是取舍，不是没做完）

- **不做 HIDS 替代品**：不做内核 syscall 钩子、不做 eBPF 探针、不做全流量检测。这类能力必须常驻高权限采集，与"单二进制、几十 MB、可随手装"的定位冲突。
- **不做多机态势**：单机给出单机结论。多台机器的汇总属于 OpsMini Server / Proxy 的职责。
- **不自带规则库引擎**：基线判据写在代码里（14 项），不接受 YAML 规则热加载。规则可热加载听起来灵活，但会让"为什么这台机器 62 分"变得无法复现。规则外置是演进方向（见 §16）。
- **不替代专业合规扫描**：不做等保/CIS 的完整条目覆盖与出证，只做"日常能被看见、能被执行"的那部分。

## 2. 能力地图

主机安全页面是六个页签，本质是**五个检测模块 + 一个汇总视图**：

| 页签 | 检测什么 | 数据来源 | 触发方式 | 是否改系统 |
|---|---|---|---|---|
| 安全总览 | 汇总裁剪：总分、等级、五模块得分与一句话结论 | 其余五个模块的落库结果 | 打开页面 | 否 |
| 基线体检 | 14 项主机加固现状 | `/etc/ssh/sshd_config`、`/etc/passwd`、`/etc/shadow`、`/etc/login.defs`、crontab、监听端口 | 手动点「开始体检」 | 否 |
| 登录安全 | 暴力破解、异常登录、SSH 加固建议 | `/var/log/auth.log` 或 `/var/log/secure` | 打开页面 | 否 |
| 防火墙 | 当前后端与规则；放行/封禁端口、启停 | `ufw` / `firewall-cmd` / `iptables` 的实际状态 | 手动操作 | **是** |
| 文件完整性 | 关键文件是否被改/被删 | 8 个系统关键文件的 SHA256 | 后台每 60 秒 | 否 |
| 威胁检测 | 挖矿进程、可疑计划任务、可疑自启动 | `/proc`、crontab、`/etc/rc.local`、systemd 服务列表 | 后台每 5 分钟 + 手动 | 否（处置要人来做） |

设计上的一个明确决定：**只有防火墙会改动系统**。其余四个模块是纯观察者，即使误判也只会让分数难看，不会让机器出事。

## 3. 架构：两条互不依赖的通路

OpsMini 里有两套和安全相关的东西，它们看起来像，实际上是两条独立通路：

```
                  ┌──────────── 体检通路（pull，给人看） ────────────┐
  /etc、/proc ───▶ │ BaselineService  登录分析  FIM  威胁扫描        │ ──▶ SQLite ──▶ 安全页面 + 评分
  认证日志        │ SecurityService 汇总打分                        │
                  └──────────────────────────────────────────────────┘

                  ┌──────────── 感知通路（push，给 Agent） ──────────┐
  auth.log、站点   │ sentinel 采集器（logwatch/authwatch/           │ ──▶ 信号 ──▶ 事件 ──▶ 策略
  目录、进程表     │ filewatch/procwatch/netwatch/metricwatch）      │        ──▶ Agent 处置
                  └──────────────────────────────────────────────────┘
```

**为什么分成两条，而不是合并成一条？**

| 维度 | 体检通路 | 感知通路 |
|---|---|---|
| 交互模型 | 拉：你打开页面 / 点扫描 | 推：采集器一直在跑 |
| 输出 | 清单 + 分数（可长期保存的状态快照） | 信号 → 事件（有时效性的流） |
| 消费者 | 人 | 策略引擎 + AI Agent |
| 判定性格 | 「现状合不合规」 | 「刚刚发生了什么」 |
| 误判代价 | 分数难看 | 可能触发自动处置 |

合并会让两边互相拖累：体检要能随时重算，感知要能持续增量；一条通路加个状态机，另一条就被迫带着它跑。

**代价也要说清楚**：两条通路各自解析认证日志（`service/loginsecurity.go` 与 `sentinel/authwatch.go` 是两套正则），口径存在漂移风险。这是已知技术债，见 §16。

## 4. 安全评分模型

总分 100，五个模块固定权重：

| 模块 | 满分 | 为什么是这个权重 |
|---|---|---|
| 基线体检 | 40 | 唯一「你可以主动改好」的部分，也最能反映日常运维水位 |
| 登录安全 | 20 | 公网机器出事十有八九从这里开始 |
| 防火墙 | 15 | 有或没有，直接决定暴露面 |
| 文件完整性 | 15 | 被改关键文件通常意味着已经失守 |
| 威胁检测 | 10 | 权重低是因为它最容易被误判（见 §10） |

### 各模块计分规则（与代码一一对应）

**基线（0–40）**：按权重加权，不是按条目数。

```
got   = Σ(pass 项权重) + Σ(warn 项权重 × 0.5)
total = Σ(全部项权重) = 32
得分  = int(40 × got / total)
```

三态语义：`pass` 算满分、`warn` 算半分、`fail` 算 0。warn 存在的理由是有些项「没做但不算错」（比如 SSH 还用 22 端口：风险真实但常见，直接判 0 分会让分数失去区分度）。

**登录安全（0–20）**：

| 情况 | 得分 |
|---|---|
| 未发现暴力破解，24h 无失败 | 20 |
| 24h 有失败登录但未达暴力破解阈值 | 16（固定扣 4） |
| 发现 n 个疑似暴力破解目标 | `20 − 5n`，下限 0 |

**防火墙（0–15）**：启用 15，未启用 0。二元判定，没有中间态。

**文件完整性（0–15）**：`15 − 3n`（n = 24h 内变更条数），下限 0。一条变更扣 3 分意味着改 5 个关键文件即归零。

**威胁检测（0–10）**：从 10 起扣，`critical` 扣 5、`warning` 扣 2、其他扣 1，下限 0。

### 等级映射

| 分数 | 等级 |
|---|---|
| ≥ 90 | 优秀 |
| ≥ 75 | 良好 |
| ≥ 60 | 一般 |
| < 60 | 危险 |

### 这个模型的取舍

- **不给资产价值加权**：OpsMini 不知道这台机器上跑的是什么业务，猜一个"重要性系数"只会让分数变成玄学。
- **不用 CVSS**：CVSS 评的是漏洞严重性，这里评的是主机配置与运行现状，两者不是一回事。
- **不设负分**：单项扣到 0 就停，避免一个模块拖崩全局后分数失去意义。
- **分数可复现**：输入一样、代码一样，分数一定一样。这是能拿它做「改完再看一眼」比较的前提。

## 5. 基线体检

### 运行方式

一次扫描生成一个 `ScanID`（纳秒时间戳），14 项结果各写一行 `baseline_results`，页面只展示**最新批次**，历史批次留在库里可对比。

纯文件解析，不调 `lynis` / `oscap` 之类外部工具——那些工具在最小化系统里经常不存在，且输出难以结构化。

### 判定细节

- `sshd_config` 会同时读主文件与 `/etc/ssh/sshd_config.d/*.conf`（现代发行版把配置拆到 drop-in 目录，只读主文件会误判）。
- 「未显式配置」与「显式配错」区分开：前者给 `warn`（发行版默认值不确定），后者给 `fail`。
- `/etc/shadow`、`/etc/passwd` 直接解析文本，不依赖 NSS 配置——避免 LDAP/SSSD 参与的机器上判定漂移。
- 高危端口用固定清单：`23 Telnet`、`445 SMB`、`135 RPC`、`1433 MSSQL`、`3389 RDP`。

完整 14 项清单见 [附录 A](#附录-a基线-14-项清单)。

### 为什么权重写死在代码里

改权重就能改分数。如果权重可配置，同一台机器在两个客户那里分数不同，"体检"就失去公信力。要调整权重，走代码评审。

## 6. 登录安全

### 数据源与开销

只读认证日志的尾部：`tail -n 5000`，优先 `/var/log/auth.log`（Debian 系）再 `/var/log/secure`（RHEL 系），没有则返回空报告而不是报错。日志可能有几百 MB，全量读取会打爆内存。

**统计窗口要说准确**：实现上的窗口是「日志尾部 5000 行」，不是严格的时间窗口。字段名沿用了 `failed_count_24h` / `success_count_24h`，因为被扫爆的公网机器 5000 行往往不到 24 小时，而清静的机器 5000 行可能好几天。这个偏差是已知问题（§15），没有做严格 24 小时过滤的原因见下。

### 三类判据

| 判据 | 规则 | 输出 |
|---|---|---|
| 暴力破解 | 同一账户在统计窗口内失败（含 `Failed password` 与 `Invalid user`）**累计 ≥ 5 次** | 账户名 + 次数 + 涉及 IP 列表，按次数倒序 |
| Top 失败来源 | 按 IP 聚合失败次数取前 10 | IP + 次数 |
| 异常登录 | 成功登录中 `user == root` | 时间 + 用户 + IP + 原因「root 账户直接 SSH 登录」 |

SSH 加固建议不写死文案，而是读当前 `sshd_config` 判断每条是否已做（`PermitRootLogin`、`PasswordAuthentication`、改端口、Protocol 2），页面上直接显示「已做/未做」。

### 为什么不做 GeoIP 与 UA 分析

离线环境是硬需求。一个能装在内网、不联网、不给外部服务发日志的安全面板，比一个能画出漂亮世界地图但要联网的面板更有用。所以异常判定只依赖本机可见的事实（时间、账户、IP 频次）。

### 为什么没做严格 24 小时过滤

`syslog` 的时间戳不带年份（`Aug 14 07:00:01`），要按时间过滤必须推断年份并处理跨年回绕；凌晨 0 点前后、容器时区不一致、日志被 logrotate 截断都会让推断出错。错一年就是把整段历史算成「刚刚」。

用「尾部 N 行」代替时间窗口，代价是窗口长度漂浮，好处是**永不因时间解析出错而误判**。真要精确，正路是让感知层按 `observed_at` 在库里做窗口查询（它本来就带时间），这也是 §16 里统一事实层的动机之一。

### 阈值 5 的解释

低于 5 次的多半是人工敲错密码；5 次以上在 24 小时内、来自同一批 IP，才具备"在试"的特征。这个阈值在真实公网机器上会被大量扫描越过——这正是它的用途：**它不是用来精确识别的，而是用来告诉你这台机器正在被扫**。

## 7. 防火墙

### 后端自动识别

不假设系统装了什么，读实际状态决定后端：

| 后端 | 判定 | 支持的写操作 |
|---|---|---|
| `ufw` | `ufw status` 可读 | 放行/封禁端口、启用、停用、按编号删规则 |
| `firewalld` | `systemctl is-active firewalld` | 放行/封禁端口（`--permanent` + `--reload`）、启用、停用 |
| `iptables` | 存在规则链 | 放行/封禁端口（`-I INPUT 1`）、按编号删规则；**不支持面板内停用** |

`iptables` 后端故意不提供「停用」：清空规则链等于把所有机器裸奔，破坏性太高，要求人自己上机器操作。

### 防锁死设计（这是本模块最关键的一条）

**启用防火墙前，先自动放行面板自身端口和 SSH 22**，然后再 `enable`。

顺序不能反。反过来就是经典事故：防火墙一开，8888 和 22 同时被挡，人只剩控制台可用。`panelPort` 由启动时的配置注入，不是写死的 8888。

### 参数校验与超时

| 防线 | 做法 |
|---|---|
| 权限 | 所有写操作 `requireRoot()`，非 root 直接返回 `ErrNeedRoot` |
| 端口 | `int` 类型 + 1–65535 范围校验，不接受字符串 |
| 协议 | 枚举 `tcp`/`udp` |
| 注入 | 全部走 `exec.Command(name, args...)`，不经 shell，参数无法被拼接成第二条命令 |
| 卡死 | 每条防火墙命令 10 秒超时（`context.WithTimeout`），失败返回 stderr 原文 |

### 与 Agent 封禁的关系

系统里有两种封禁，故意分开管理：

| 来源 | 落点 | 生命周期 | 谁清理 |
|---|---|---|---|
| 页面规则（人配） | `ufw`/`firewalld` 规则表 | 长期，直到人删 | 人 |
| Agent 封禁（事件驱动） | `iptables -I INPUT -s <ip> -j DROP` + `blocked_ips` 表 | 带 TTL，到期自愈 | `SweepBlocks()` 自动解封 |

分开的原因：Agent 的封禁必须能自愈（误封要能自己好），人的规则不能被自愈逻辑顺手删掉。两套各管各的，页面上分别可见。

## 8. 文件完整性（FIM）

### 监控对象

默认 8 个系统关键文件，首次启动（基线为空时）自动建基线：

```
/etc/passwd  /etc/shadow  /etc/group   /etc/ssh/sshd_config
/etc/crontab /etc/sudoers /etc/hosts   /etc/resolv.conf
```

其中 `/etc/passwd`、`/etc/shadow`、`/etc/sudoers` 变更记为 `critical`，其余 `warning`。

### 检测循环

每 60 秒对每个启用项算一次 `SHA256 + size + mtime`：

- 算不出来（文件不存在）→ 记一条「文件被删除」，`critical` 级别按路径判断
- 哈希不一致 → 记一条「文件内容发生变化」，带新旧哈希
- 一致 → 什么都不做

### 关键设计：变更后基线自动前移

检测到变化并落库后，**基线立即更新为新哈希**。

这是有意为之：如果基线不前移，同一次变更会每 60 秒报一次，一天 1440 条告警，人就再也不看了。前移之后的效果是「一次变更一条告警」，而**下一次再变还会报**——真被反复改，仍然看得见。

代价：连续两次变更如果发生在同一个 60 秒窗口内，只会留下一条记录。这在这个精度下可接受（要更细得上 inotify，见 §16）。

「重建基线」是人工动作：你改完 `sudoers` 之后点一下，告诉系统"现在的状态是对的"。

### 与感知层 filewatch 的分工

| | 安全页 FIM | 感知层 filewatch |
|---|---|---|
| 看什么 | 8 个系统关键文件 | 站点根目录新增的可执行脚本 |
| 判据 | 哈希比对 | 扩展名 + WebShell 内容特征（`eval($_POST`、`base64_decode` 等） |
| 目的 | 发现「系统被动过」 | 发现「网站被种了马」 |

两者不重叠，也不互相引用。

## 9. 威胁检测

三个扫描器，每 5 分钟一轮，启动时先跑一次。

| 扫描器 | 看什么 | 判据 | 级别 |
|---|---|---|---|
| 进程 | `/proc` 全量进程（名称 + 命令行） | 命中挖矿关键词（`xmrig`、`minerd`、`kdevtmpfsi`、`kinsing`、`stratum` 等 11 个） | critical |
| 进程 | 进程可执行文件路径 | 位于 `/tmp` 或 `/dev/shm`（正常服务不该从这里起） | warning |
| 计划任务 | 系统 + 用户 crontab | 命令含 `curl`、`wget`、`base64 -d`、`/dev/shm` | warning |
| 启动项 | `/etc/rc.local` 非注释行 | 含 `curl`、`wget`、`/tmp` | warning |
| 启动项 | systemd 已启用服务名 | 含 `miner`、`xmrig`、`kdevtmpfs` | critical |

### 去重与生命周期

按 `kind + name` 去重：命中已存在记录只更新 `last_seen` 与详情，不新增条目。状态只有 `active` / `resolved`，**只有人能把它标记为已解决**——进程被杀掉之前，扫描器每 5 分钟会再看到它，这正是我们要的（真威胁不该自己消失）。

### 对这套检测的诚实评价

关键词黑名单**改名即绕过**，这是公开的秘密。所以它的定位不是"能抓住所有挖矿"，而是：

1. 抓住**懒攻击**——绝大多数僵尸网络落地用的是现成二进制，名字都不改；
2. 配合「临时目录可执行」这类**行为特征**，覆盖改名的部分；
3. 剩下的靠感知层的进程行为与登录行为信号补。

不吹能杀，能发现就报告，处置交给人（或人授权给 Agent）。

## 10. 数据模型

| 表 | 一行代表 | 关键字段 |
|---|---|---|
| `baseline_results` | 一次扫描里的一项结果 | `scan_id`（批次）、`category`、`item_key`、`status`(pass/fail/warn)、`detail`、`suggestion`、`weight` |
| `fim_baselines` | 一个被监控文件的当前基准 | `path`(unique)、`sha256`、`size`、`mod_time`、`enabled` |
| `fim_changes` | 一次文件变更事件 | `path`、`old_sha256`、`new_sha256`、`level`(warning/critical)、`message`、`created_at` |
| `threat_findings` | 一个威胁条目 | `kind`(process/cron/startup)、`name`、`detail`、`severity`、`status`、`first_seen`、`last_seen`、`resolved_at` |

设计要点：

- 基线结果按 `scan_id` 分批，**永不覆盖历史**：想对比"上周和这周"是可查的。
- `fim_baselines` 与 `fim_changes` 分表：一个是状态，一个是流水，混在一张表会让"当前基准"和"变更历史"互相污染。
- `threat_findings` 带 `first_seen/last_seen`：一眼看出这是刚出现的还是挂了三天没人管。
- 没有独立的安全库文件，全部落在 `opsmini.db` 里，跟着备份走（和面板其他数据一致）。
- 表名注意：安全基线结果是 `baseline_results`，感知层的「学习基线」（EWMA 期望值）是 `baselines`，两者无关，别混。

## 11. API 与权限

所有接口在 `/api/v1` 下，JWT 鉴权后可访问；写操作再叠加权限点。

| 方法 | 路径 | 能力 | 权限点 |
|---|---|---|---|

## 12. 面板自身的安全边界

安全模块自己也是攻击面，所以：

| 风险 | 处理 |
|---|---|
| 命令注入 | 所有外部命令 `exec.Command` + 参数数组，从不拼 shell；端口是 `int`、协议是枚举 |
| 权限提升 | 写操作先 `requireRoot()`，非 root 直接拒绝，不做"尽力而为" |
| 长时间卡住 | 外部命令 10 秒超时 |
| 自锁 | 启用防火墙前先放行面板端口与 22 |
| 隐私 | 只读日志中的登录事件，不落密码、不落命令全文（只用于判定的字段才进库） |
| 越权调用 | 每个写接口都有独立权限点，不靠前端隐藏按钮来"控制" |

## 13. 性能与资源开销

| 动作 | 开销 | 说明 |
|---|---|---|
| 基线体检 | 14 次小文件读取 + 一次端口表，毫秒级 | 只在人点的时候跑 |
| 登录分析 | `tail -5000` 一次，单次 < 50ms | 打开页面时跑，不缓存 |
| FIM 检查 | 8 个文件 SHA256，每 60 秒 | 全是 KB 级小文件，CPU 可忽略 |
| 威胁扫描 | 遍历 `/proc` 数百进程 + crontab + systemctl 一次，每 5 分钟 | 唯一的"重"动作，仍然在百毫秒量级 |
| 常驻内存 | 不计额外缓存，全部走同一条 SQLite 连接 | 无独立进程，无后台队列 |

没有常驻采样器、没有额外 goroutine 池：FIM 与威胁扫描共用一个循环（`SecurityMonitor`），一个 ticker 管一件事。

## 14. 和自主 Agent 的关系

三处接口，都是**单向提供事实**，不存在"安全模块指挥 Agent"这种耦合：

| 方向 | 形态 | 说明 |
|---|---|---|
| 安全 → AI | 只读工具 `security_status` | Agent 可以读「评分 + 五模块摘要」来回答"这台机器安全吗"，工具是 `RiskReadonly` + `security.view` |
| 安全 → AI（写） | 工具 `firewall_rule` | 改防火墙是写操作，走 L1/L2 分级，需要确认 |
| 感知层 → Agent | 信号 → 事件 → 策略 | 由 sentinel 独立负责，与本节的安全模块不共享状态 |

**当前没有做的事（有意为之）**：威胁检测结果、FIM 变更不进事件总线。原因是这两类结果误报率高于感知层的信号（关键词匹配、基线自动前移都会产生噪音），直接喂给自动处置策略风险太大。等误报率有实测数据后再接，见 §16。

## 15. 已知限制

| 限制 | 影响 | 备注 |
|---|---|---|
| 无内核级检测 | rootkit、隐藏进程（`/proc` 被 hook）看不到 | 定位决定，不打算做 |
| FIM 只覆盖 8 个文件 | 自定义路径、目录递归、新增文件监控都没有 | 目前靠感知层 filewatch 补站点目录 |
| 威胁检测靠关键词 | 改名即绕过 | 见 §9 的诚实评价 |
| 基线 14 项固定 | 无法覆盖等保/CIS 全量条目 | 演进方向是规则外置 |
| 评分不含业务重要性 | 测试机和核心库服务器同分 | 不做，避免玄学 |
| 认证日志格式依赖 | 非 rsyslog/journald 文本格式的机器可能读不到 | 兼容性靠 `/var/log/secure` 兜底 |
| 登录统计窗口漂浮 | `tail -5000` 行，非严格 24 小时（字段名沿用 24h） | 见 §6「为什么没做严格 24 小时过滤」 |
| 两套日志解析 | 安全页与感知层口径可能漂移 | 已知技术债 |
| 无报告导出 | 只能页面看，不能出 PDF/HTML 合规报告 | 演进方向 |

## 16. 演进方向

按优先级：

1. **FIM 可配置**：支持自定义路径、目录递归、白名单（`/etc/` 下高频变化的文件先排除掉），以及 inotify 事件驱动替代 60 秒轮询。
2. **基线规则外置**：14 项 → YAML 规则包，支持导入 CIS / 等保二级条目集，同时把"当前用的是哪套规则集"记进结果，保证分数可复现。
3. **统一日志事实层**：`service/loginsecurity.go` 与 `sentinel/authwatch.go` 共用一套解析器，消除口径漂移。
4. **威胁检测增强**：接入 `ausearch`（auditd 审计日志）与可选 YARA 规则，从关键词升级到行为与特征双轨。
5. **安全结果进事件总线**：在误报率可量化之后，把 `critical` 级威胁与 `critical` 级 FIM 变更接入策略引擎，让 Agent 能自主处置（例如发现 WebShell 落地 → 隔离 → 报告）。
6. **合规报告导出**：一键出单文件 HTML 报告（沿用计划任务报告那套渲染），含分数、逐项结论、整改建议。

## 附录 B：评分算例

一台典型公网 Ubuntu 机器：

| 模块 | 实测 | 得分 |
|---|---|---|
| 基线 | 14 项中 12 项 pass、2 项 warn（SSH 用 22 端口、`PASS_MAX_DAYS` 未设） | got = 32 − 1×0.5 − 2×0.5 = 30.5 → `int(40×30.5/32)` = **38** |
| 登录 | 24h 内 2000 次失败，命中 3 个暴力破解目标 | `20 − 5×3` = **5** |
| 防火墙 | ufw 已启用 | **15** |
| 文件完整性 | 24h 内 1 处变更（`/etc/hosts`） | `15 − 3` = **12** |
| 威胁检测 | 1 个 warning（`/tmp` 下的可执行进程） | `10 − 2` = **8** |
| **总分** | | **78 → 良好** |

这个分数在解释上站得住：配置基本合理（基线 38），但正在被爆破（登录 5），扣分主要来自真实攻击而不是误判。整改路径也清楚——打开防火墙来源限制、上 fail2ban 或用 Agent 封禁，登录分会回来。
