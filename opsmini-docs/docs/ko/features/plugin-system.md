# 플러그인 시스템

커널은 "모든 호스트에 필요한 일"만 수행합니다: 수집, 감사, Agent 런타임, 가드레일. 비즈니스 기능(특정 미들웨어의 지표, 특정 유형의 로그 파싱, 특정 플랫폼의 액션 연동)은 **플러그인**으로 확장합니다.

이렇게 하는 목적은 아키텍처의 미관을 추구하기 위해서가 아니라, 두 가지 구체적인 문제를 피하기 위해서입니다: **바이너리의 무한한 비대화**, 그리고 **새로운 기능 하나를 위해 버전을 하나 배포해야 하는 것**.

## 플러그인은 독립 프로세스이며, Go plugin이 아닙니다

- Go의 `plugin` 패키지는 컴파일 시점에 완전히 동일한 빌드 환경을 요구하므로, 버전이 다르면 반드시 깨지기 때문에 바로 제외했습니다
- 플러그인은 **독립 실행 파일**이며, 패널이 하위 프로세스로 실행하고 Unix socket을 통해 **줄 구분 JSON**으로 통신합니다
- 플러그인이 크래시되어도 패널에는 영향을 주지 않습니다: 프로세스 종료가 기록되고, 재시작 정책에 따라 다시 실행되며, 연속 실패 시 failed로 표시되고 재시도를 중단합니다

## 패키지 형식

```
foo-collector-1.2.0-linux-amd64.tar.gz
├── plugin.yaml          # 매니페스트
├── bin/plugin           # 진입점 (실행 파일)
├── SIGNATURE            # ed25519 서명 (전체 패키지 sha256에 대한 서명)
└── README.md            # 선택 사항
```

매니페스트 예시:

```yaml
apiVersion: opsmini.plugin/v1
id: foo-collector              # 전역 고유, ^[a-z0-9][a-z0-9-]{2,40}$
name: Foo 수집기
version: 1.2.0                 # semver
vendor: 速云科技
description: Foo 서비스의 큐 깊이와 소비 속도를 수집
kind: collector                # collector | action | panel
entry: bin/plugin              # 패키지 내 상대 경로
platform: [linux/amd64, linux/arm64]

capabilities:                  # 권한 선언, 동시에 감사 근거로 사용
  - metrics
  - read:/etc/foo
  - exec:systemctl
  - net:outbound

runtime:
  memoryLimitMB: 128
  cpuQuotaPercent: 20
  restartPolicy: on-failure    # always | on-failure | never

requires:
  opsmini: ">=1.4.0"           # 호스트 Agent 버전 요구 사항
```

설치 시 검증 순서 (하나라도 실패하면 거부하며, "반쪽짜리 플러그인"은 설치하지 않음):

1. 패키지 sha256 (서버 측 계산, 업로더가 선언한 값과 교차 검증 가능)
2. ed25519 서명
3. `apiVersion` 호환성
4. `platform` 현재 호스트와 일치하는지 여부
5. 매니페스트 필드 유효성, 버전 요구 사항

## 세 가지 채널

플러그인과 커널은 socket을 통해서만 네 가지 메시지를 주고받으며, 모두 한 줄짜리 JSON입니다:

| 메시지 | 방향 | 용도 |
|---|---|---|
| `hello` | 플러그인 → 패널 | 시작 핸드셰이크, 자신이 누구인지, 버전, 기능을 선언 |
| `metric` | 플러그인 → 패널 | 지표 보고 (모니터링 및 알람 규칙으로 진입) |
| `event` | 플러그인 → 패널 | 이벤트 보고 (신호로 변환되어 이벤트 센터로 진입 가능) |
| `heartbeat` | 플러그인 → 패널 | 생존 및 자체 점검 상태 |

플러그인은 데이터베이스에 직접 접근하지 않고, 패널 인터페이스를 직접 호출하지 않으며, 패널의 세션을 상속하지 않습니다.

## 라이프사이클

```
설치 (패키지 업로드 → 검증 → releases/<version>/에 압축 해제 → current 심볼릭 링크가 이를 가리킴)
   ↓
활성화 → 프로세스 시작 → hello 핸드셰이크 대기 → running 진입
   ↓
실행 → 크래시/종료 → restartPolicy에 따라 처리, 재시작 횟수와 마지막 오류 기록
   ↓
비활성화 → SIGTERM → 종료 대기 → 상태 stopped
   ↓
업그레이드 → 새 버전 압축 해제 → current 심볼릭 링크 전환 → 재시작 (이전 버전 디렉터리 보존, 롤백 가능)
   ↓
삭제 → 프로세스 중지 → 프로그램 파일 제거 (데이터 디렉터리 보존)
```

## 권한 경계: 무엇이 구현되었는지 명확히 설명

이 섹션은 반드시 솔직해야 합니다. 그렇지 않으면 "플러그인 보안"이 공허한 말이 됩니다.

**구현된 것:**

- 플러그인은 독립 프로세스이며, 크래시가 발생해도 패널이 중단되지 않습니다
- 설치 시 반드시 서명 검증을 해야 하며(명시적으로 unsigned 모드를 활성화하지 않는 한), 버전, 플랫폼, 매니페스트를 검증합니다
- 설치, 활성화, 비활성화, 삭제 모두 감사 로그에 기록됩니다
- 플러그인은 socket을 통해 통신하며, 패널 데이터베이스를 직접 조작할 수 없습니다

**현재 버전에서 구현되지 않은 것(있다고 가정하지 마세요):**

- **독립 시스템 사용자로 전환되지 않음**: 플러그인은 패널 프로세스의 사용자로 실행되며, 일반적으로 `root`입니다
- **cgroup 리소스 제한 없음**: 매니페스트의 `memoryLimitMB` / `cpuQuotaPercent`는 현재 선언일 뿐 강제되지 않습니다
- **`capabilities` 강제되지 않음**: 이는 선언 및 감사 근거일 뿐, 커널 수준 화이트리스트가 아닙니다
- **플러그인 내부의 시스템 호출을 감사할 수 없음**

따라서 결론은: **서명은 "출처를 신뢰할 수 있음"을 증명할 뿐, "동작이 안전함"을 증명하지 않습니다**. 신뢰하는 출처의 플러그인만 설치하세요; 서드파티 플러그인은 코드를 직접 감사하시기 바랍니다.

## 설치 전제 조건(현재 버전에서 주의할 점)

설치 시 `sha256` → 서명 → 매니페스트 순서로 검사합니다. 기본 설정에서는 **내장 공개 키가 없고 unsigned 모드도 활성화되어 있지 않으므로**, 그대로 업로드하면 거부되며 「플러그인 공개 키가 구성되지 않았고 unsigned 모드가 활성화되지 않았습니다」라는 오류가 발생합니다.

두 가지 해결 방법 중 하나를 선택하십시오(설정에 기록한 후 **패널을 재시작해야** 적용됩니다. 공개 키는 시작 시 읽기 때문입니다):

```bash
# 방식 1: ed25519 공개 키 구성(권장, 운영 환경)
curl -X POST http://127.0.0.1:8888/api/v1/settings \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"plugin_public_key":"<hex 编码的 32 字节公钥>"}'

# 방식 2: 개발/내부 네트워크 환경에서 서명되지 않은 패키지 임시 허용
curl -X POST http://127.0.0.1:8888/api/v1/settings \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"plugin_allow_unsigned":"true"}'
```

수정한 후 `systemctl restart opsmini`을 수행하고, 다시 「패널 설정 → 플러그인」에서 업로드하십시오.

> 현재 버전의 패널은 아직 이 두 설정 항목의 입력 인터페이스를 제공하지 않으며, 위의 API를 통하거나 설정 테이블을 직접 수정하는 방법만 가능합니다. 다음 버전에서 보완될 예정입니다.

## 패널 작업

**패널 설정 → 플러그인**:

| 작업 | 설명 |
|---|---|
| 업로드 설치 | `*.tar.gz` 패키지 선택, 최대 64MB |
| 활성화 / 비활성화 | 즉시 적용되며 패널 재시작이 필요하지 않음 |
| 재시작 | 특정 플러그인만 재시작 (예: 해당 플러그인의 설정 변경 시) |
| 삭제 | 프로그램 파일을 제거하며 데이터 디렉터리는 보존됨 |
| 이벤트 | 해당 플러그인이 최근 보고한 지표와 이벤트 확인 |

목록에서 각 플러그인의 이름, 버전, 유형, 상태(running / stopped / failed / installed), 재시작 횟수, 마지막 오류를 확인할 수 있습니다.

## 현황 설명

메커니즘은 완전하지만 **생태계는 현재 비어 있습니다** — v1.4.0에는 공식 플러그인 패키지가 포함되어 있지 않습니다. 즉, OpsMini를 설치한 후 플러그인 페이지가 비어 있는 것은 예상된 상태이며 오류가 아닙니다.

계획 중인 공식 플러그인 방향(미출시): 보안 베이스라인 확장 점검, 특정 미들웨어 지표 수집, 로그 파싱 규칙 패키지, 서드파티 플랫폼 액션 연동.
