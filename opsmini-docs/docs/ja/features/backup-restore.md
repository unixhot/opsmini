# バックアップと復元

## ワンクリックの程度は異なる

| 操作 | ワンクリック度 | 理由 |
|---|---|---|
| バックアップ | ✅ 本当にワンクリックで実行でき、スケジュールも可能 | ソースデータの読み取り専用 + ターゲットディレクトリへの書き込みのみで、失敗時はリトライすればよく、破壊性がない |
| リストア | ⚠️ 「ワンクリック」だが3つの前提条件がある | リストアは本番データを上書きするため、事前チェック、リストア前スナップショット、自動ロールバックが必須 |

リストアを「ワンクリックで上書き」にしてしまうのは、ユーザーに取り消しキーのない削除ボタンを渡すのと同じです。そのため、画面上では**ワンクリックリストア（事前チェックと自動ロールバック付き）**と呼んでいます。

## 何をバックアップするか

三種類のオブジェクトがあり、「バックアップ対象」に記述します。1行に1つずつ：

| 記法 | 意味 |
|---|---|
| `/var/www` | ディレクトリ（または単一ファイル）。`tar.gz` としてパッケージ化 |
| `mysql:opsmini` | データベース。`mysqldump` でエクスポート後に圧縮 |
| `redis:/var/lib/redis/dump.rdb` | Redis スナップショットファイル。そのファイルを直接パッケージ化 |

MySQL バックアップはパネルに設定済みの接続情報（ローカル socket）を使用し、パラメータは `--single-transaction --routines --triggers` です。これにより InnoDB テーブルの一貫性スナップショットを保証し、テーブルロックは行いません。

**非対応**：PostgreSQL、Docker volume、ブロックデバイス/ファイルシステムレベルのスナップショット、増分バックアップ、バックアップ暗号化。これらは今後のバージョンで検討予定であり、本バージョンでは保証しません。

## スナップショットの構成

```
<データディレクトリ>/data/backups/web-20261029-020000/
├── manifest.json                 # メタデータ：オブジェクト、サイズ、sha256、ホスト名、バージョン
└── data/
    ├── var_www.tar.gz
    ├── opsmini.sql.gz
    └── redis.rdb.gz
```

ディレクトリの権限は `0700`、ファイルは `0600`。`manifest.json` には各シャードの sha256 が記録されており、復元時に 1 つずつ検証されます。

restic/borg のような「リポジトリ型」バックアップツールは導入しません。これらは重複排除、暗号化、スナップショットチェーンを備えて高機能ですが、15–25MB の依存関係をもたらし、復元時には必ず同じツールを使う必要があります。現在は「自己完結したシャード + マニフェスト」であり、どのマシンでも展開すれば復元できます。

## バックアップフロー

```
全オブジェクトを検証（パスが存在、データベース名が空でない、redis パスが読み取り可能）
   ↓  まずすべて検証してから実行：そうしないと 5 個のオブジェクトのうち 2 番目に誤りがある場合、
      すでに 4 個のアーカイブを生成した後に失敗し、中途半端なスナップショットが残る
1 つずつ実行（直列、IO の飽和を避ける）
   ↓  各オブジェクトの完了時に manifest へ書き込み、失敗時は「中途半端なバックアップ」を生成しない
合計チェックサムを計算 → 保持ポリシーに従って古いスナップショットをクリーンアップ → バックアップ履歴を書き込み
```

保持数はデフォルトで 7、`0` はすべて保持を意味する。クリーンアップは**ディレクトリ全体**を単位として最も古いものを削除し、個々のシャードは決して削除しない（そうしないとマニフェストが無効になる）。

## 復旧フロー（三道ゲート）

**① プリチェック**

- スナップショット名を入力して二次確認を必須とする（誤選択防止）
- 対象の親ディレクトリが存在し、書き込み可能であること
- `mysql` クライアントが利用可能であること（データベース復旧時）
- スナップショットファイルが揃っており、sha256 がマニフェストと一致すること

**② 復旧前の自動スナップショット**

現在の状態をまずバックアップする（ディレクトリは同じパッケージングロジック、データベースは dump を使用）。失敗した場合はこのステップに戻ることができる。

**③ 実行とロールバック**

- リストア → ヘルスチェック
- いずれかのチェックが失敗 → **ステップ②のスナップショットへ自動ロールバック** → イベントセンターに critical イベントを1件生成

ヘルスチェック項目：ディレクトリはファイル数比較と抜き取りチェックサム、MySQL は `SELECT 1` を実行し主要テーブルの行数を照合、Redis は `PING` と keyspace を比較。

ロールバックの信頼性は「同一パーティション内の rename はアトミックである」ことから来ている：復旧前に目的ディレクトリを `mv` して `xxx.pre-restore-<时间戳>` とし、失敗時に `mv` で戻す。

## パネル操作

**パネル設定 → バックアップ復元**：

| 区域 | 内容 |
|---|---|
| バックアップ対象 | 1行に1つ、ディレクトリ / `mysql:库名` / `redis:路径` をサポート |
| 保持世代数 | デフォルト 7、0 はクリーンアップなしを意味する |
| 即時バックアップ | 1回実行し、完了後にスナップショット一覧を更新 |
| スナップショット一覧 | 名前、時刻、サイズ、対象数、事前チェック結果 |
| 復元 | スナップショット名を入力して確認後に実行し、事前チェックの明細と結果を返す |
| バックアップ履歴 | 各実行の結果（失敗理由を含む） |

## 定期バックアップ

バックアップは**スケジュールの第4のタイプ**（パネルタスク / システム crontab / ユーザー crontab と並列）であり、同じスケジューリング、起動・停止、失敗アラートの仕組みを再利用します。

**スケジュール → 新規タスク → タイプで「バックアップタスク」を選択** で設定します：

| フィールド | 説明 |
|---|---|
| バックアップ対象 | バックアップページと同じ行構文 |
| 保持世代数 | 古いスナップショットを上書きするポリシー |
| 実行周期 | cron 式、よく使うプリセット（毎日 02:00 など） |
| 通知チャネル | パネル / メール / 企業WeChat / DingTalk / Feishu |
| ローカルコピーを保持 | リモートターゲット使用時、アップロード成功後にローカルコピーを保持するか |

手動の「今すぐバックアップ」と**同じエンジン**で実行され、生成物は完全に同一です——「手動なら復元できるが、定期実行ではできない」ということはありません。

失敗時はタスク状態（`上次状态 / 上次错误 / 连续失败次数`）に書き戻され、同時にバックアップ履歴が1件記録され、組み込みアラートルール「バックアップ失敗数」がトリガーされます。

## リモートターゲット：コードは準備済み、本バージョンでは有効化しない

`internal/backup` には S3 互換（OSS / MinIO / AWS、独自実装の SigV4 署名）と SFTP の 2 種類のリモートストレージがすでに実装されていますが、**v1.4.0 では提供内容として含めません**：

- パネルではリモートターゲットの設定を案内しない
- ドキュメントでは本番環境での使用を推奨しない
- 実機での結合テスト・受け入れテストを実施していない（ユニットテストと S3 署名ベクターテストのみ）

遠隔地に保管する必要がある場合は、`config.yaml` にターゲットを追加するだけで有効化でき、コードの変更は不要です：

```yaml
backup:
  targets:
    - name: oss-bj
      type: s3
      endpoint: oss-cn-beijing.aliyuncs.com
      bucket: my-backup
      region: cn-beijing
      access_key: "..."
      secret_key: "..."
```

設定後、バックアップページに「リモートターゲット」の選択肢が表示され、スナップショットをアップロードしたり、リモートスナップショットを閲覧・取得したりできます。アップロードはローカルスナップショットが完全にディスクへ書き込まれた後に行われるため、アップロードが失敗してもリモートに中途半端なバックアップが残ることはありません。

**注意**：この経路は実機での結合テストを経ていません。正式に使用する前に、非本番のディレクトリで一度完全な往復（アップロード → 一覧表示 → 一時ディレクトリへの復元）を検証してください。

## 既知の制限

- 大規模ディレクトリのバックアップ中は継続的に IO を占有するため、業務のピーク時間を避けて実行することを推奨します（デフォルト 02:00）
- MySQL はローカル socket 経由でバックアップするため、リモートのデータベースインスタンスには対応していません
- リストアは「上書き式」です。スナップショットに含まれるオブジェクトのみを復元し、スナップショット外の新規ファイルは削除しません
- 単一のスナップショットは暗号化されません。機密データを含むディレクトリでは、データディレクトリの権限とバックアップメディアの安全を確保してください
