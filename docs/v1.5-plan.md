# OpsMini v1.5.0 实施计划

> 状态：**待确认**（2026-11-09 立项）
> 主题：**把自主 Agent 从「能跑」推到「敢让它跑」**，并补齐其余模块的欠账。
> 不在本版：备份远端目标的面板管理、插件系统演进（见 §2.2）。

---

## 0. 为什么是 v1.5.0

v1.3.0 把自主 Agent 的 M1~M5 走完了，演练也真跑过：日志暴涨能定位到持有进程、WebShell 能实际隔离并验证、SSH 爆破能识别注入后拒绝封禁。**功能性没有问题。**

但 `docs/v1.3.0-autonomous-agent.md §15.5` 自己列了 v1.3.1 的四个候选，一项都没做。加上设计文档里承诺、代码里空着的几处，缺口集中在三类：

1. **没有人工审批的中间档**：事件触发固定 `Unattended: true`，需要确认的动作直接拒绝。用户只能在「只读出报告」和「白名单内全自动」之间二选一，而 assist 本应是主力模式。
2. **成本与噪音不可控**：token 预算只统计不阻断，没有每日上限，没有维护窗口，没有连续失败熔断。长时间无人值守会烧钱、会刷事件。
3. **怕出事却没有兜底**：闸门 2「爆炸半径预检」只有三个名单，没有依赖图；`service_action` 这类高频动作直接缺失，只能退回 `exec_command`（无回滚）。

一句话：**能力闭环了，生产就绪度没跟上。** v1.5.0 就是补这一层。

## 2. 边界与原则

1. **审批必须落盘**：任何挂起等待人工的事件，重启后仍能继续，不能因为进程退出而永久卡住。
2. **预算先于能力**：新增任何自动处置之前，先让 token 与动作预算真正生效。
3. **降噪先于放开**：没有每日上限和维护窗口，不把任何新场景加入 auto。
4. **可逆性优先**：新处置原语必须自带"记录原状态 → 失败回退"，无法可逆的动作不新增。
5. **文档与代码同步**：本版每个模块完成时同步更新对应设计文档的 as-built 段。

## 3. 决策记录

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D1 | HITL 是复用还是重写 | **复用现有 `Approver` + `Agent.Resume()`** | `AIPendingApproval` 模型、`POST /ai/agent/approve`、`Resume()` 都已存在且交互式会话在用；事件触发只是绕过了它 |
| D2 | 事件挂起后状态怎么表达 | incident 增加 `awaiting_approval` 状态 + `approval_id` 字段 | 不能复用 `running`，否则前端无法区分"正在跑"和"等你点" |
| D3 | 审批超时 | 默认 30 分钟，超时转 `skipped` 并记录原因 | 无人值守场景不能无限挂起 |
| D4 | token 预算粒度 | 事件级（每 incident）+ 每日全局 | 事件级防单次失控，每日级防慢性烧钱 |
| D5 | 预算超限行为 | 立即停止本次运行，事件标 `budget_exceeded` | 不静默截断（会让报告残缺且用户无感） |
| D6 | 每日上限的计数器 | 存 settings 表按日期滚动，不用内存 | 重启不能丢，否则重启即重置 |
| D7 | 维护窗口 | 全局一个时间段 + 按策略可选覆盖 | 先满足"凌晨变更别告警"，不做复杂的日历 |
| D8 | `service_action` 回滚依据 | 记录 `active/enabled + start 时间`，失败时按原状态还原 | systemctl 状态有限可枚举，不需要通用快照 |
| D9 | 爆炸半径怎么算 | **静态依赖图（配置文件声明）+ 进程树**，不做动态推断 | 动态推断不可靠；声明式足够拦截"重启 nginx 会影响哪些上游" |
| D10 | Agent 首页与现有仪表盘的关系 | **合入资源仪表盘**：Agent 概览作为仪表盘的一个分区，不新增一级页面 | 两页回答的都是"这台机器现在怎么样"，分开要么重复要么割裂；单页滚动一次看完更顺，也少一份维护 |
| D11 | 跨会话记忆的存储 | 结构化 `agent_memories` 表（主体+事实+来源），不做向量检索 | 无 embedding 时可先用关键词+主体匹配，避免为记忆而引入向量库 |
| D12 | 备份加密的密钥来源 | 面板口令派生（scrypt）+ 每份备份独立 salt | 不引入 KMS 依赖；口令遗失即数据不可解，需在 UI 明确警示 |

### B1 Agent 可信度（P0，约 4~5 天）

#### B1.1 HITL 续跑

**现状**：`internal/router/sentinel.go:275` 事件触发固定 `Unattended: true`；`internal/aiagent/loop.go:432` 遇到 `PolicyConfirm` 直接拒绝并记 `skipped`。而 `Agent.Resume()`（`loop.go:225`）与 `POST /ai/agent/approve` 已存在，交互式会话正常在用。

**做法**：

1. `RunOptions` 增加 `SuspendOnConfirm bool`。事件触发时按策略决定：`assist` 置 true，`auto` 保持 false，`shadow` 不涉及写动作不受影响。
2. `loop.go:432` 的分支改为：`Unattended && !SuspendOnConfirm` 才拒绝；否则走现有的 `approver.Create()` 挂起路径。
3. 挂起时把 incident 置为 `awaiting_approval`，写入 `approval_id`（模型加字段）与 `approval_expires_at`。
4. 审批通过后 `Resume()` 续跑，结束时回填 incident 状态（`resolved`/`failed`/`skipped`）。
5. 超时（D3，默认 30 分钟）由后台扫描转为 `skipped`，summary 写明"审批超时"。
6. 前端事件详情页：`awaiting_approval` 状态下渲染工具名、参数预览、风险等级、「批准 / 拒绝」按钮，复用会话页的审批组件。

**验收**：
- 注入 WebShell 事件，`assist` 模式下运行到 `quarantine_file` 时前端出现审批卡片，incident 显示"待审批"
- 点批准 → 动作执行 → 验证通过 → incident `resolved`
- 点拒绝 → 动作不执行 → incident `skipped`，报告里写明被拒原因
- 挂起期间重启面板，重启后审批卡仍在，点击仍能续跑
- 超时后自动转 `skipped`

#### B1.2 token 预算 + 每日上限

**现状**：`internal/safety/safety.go:84` 的 `AddTokens()` 零调用点；`internal/trigger/engine.go:449` 组装 `RunOptions` 时没传预算。

**做法**：

1. `RunOptions` 增加 `MaxTokens int`，由策略配置给出（内置默认 200k/事件）。
2. `loop.go` 每轮 LLM 调用后累加 usage，调 `safety.AddTokens(incidentID, n)`，超限即终止并置 `budget_exceeded`（D5）。
3. 新增每日计数器：`settings` 表按 `agent_tokens:YYYY-MM-DD` 累计（D6），跨日自动换键；超限后新触发直接进 `skipped`，不启动 Agent。
4. 设置页「自主 Agent」Tab 增加两个输入框：单事件上限、每日上限（0 = 不限）。
5. 事件详情与报告头部显示本次消耗与当日剩余。

**验收**：
- 把单事件上限设为 1，触发一次运行 → 立即 `budget_exceeded`，无产物
- 每日上限设为 1k，连续触发两次 → 第二次直接 `skipped`，原因写明"当日额度用尽"
- 改系统时间跨日后，额度自动重置

#### B1.3 降噪治理

**现状**：只有单次预算与冷却（`trigger/engine.go:357`），没有维护窗口、每日触发上限、连续失败熔断。

**做法**：

1. **维护窗口**（D7）：设置页配置一个时间段（如 02:00–04:00），命中时事件仍记录但**不触发 Agent**，标 `suppressed=maintenance`。策略可声明 `ignore_maintenance: true` 跳过。
2. **每日触发上限**：按策略计，默认 50 次/天，超限后该策略不再触发，事件中心显示"该策略今日已达上限"。
3. **连续失败熔断**：同一策略连续 2 次 `failed`（`verify_state` 非空且非通过）即自动暂停该策略，需人工确认后恢复；恢复操作记审计。
4. 事件中心顶部增加一行统计：今日触发 / 已抑制 / 熔断中的策略。

**验收**：
- 配置维护窗口后在该时段注入信号 → 事件产生但无 Agent 运行，标记为维护期抑制
- 单策略触发到上限后，新事件不再拉起 Agent
- 连续两次验证失败后策略自动停用，页面有明确提示与恢复按钮

#### B1.4 采集器基线落库

**现状**：`internal/sentinel/logwatch.go:24` 的 EWMA 存在内存 map，重启即重学；只有 authwatch 的 seen IP 落库。

**做法**：

1. 新增 `collector_baselines` 表：`collector / subject / value / sample_count / updated_at`。
2. logwatch 每分钟把 EWMA 与计数写回（同 subject upsert），启动时加载。
3. 加载时若记录超过 7 天未更新，视为过期、重新学习（避免拿一个月前的基线判断今天的日志量）。
4. procwatch / netwatch 的同类基线一并纳入（当前也是内存）。

**验收**：
- 学习 10 分钟后重启面板，日志暴涨判定的基线不归零
- 把某条记录时间戳改到 8 天前重启，该 subject 重新学习（日志里有提示）

### B2 Agent 处置能力（P0，约 4 天）

#### B2.1 现有处置原语补回滚

**现状更正**（2026-11-09 核对代码）：处置工具**已经存在**，共 13 个写工具
（`write_file` / `delete_path` / `exec_command` / `kill_process` / `service_control` /
`docker_control` / `firewall_rule` / `cron_write` / `modify_sshd` / `clean_temp` /
`clean_logs` / `compress_dir` / `install_skill`）+ 17 个只读工具。
之前记的「缺 `service_action` / `terminate_process`」是误判——对应能力在
`service_control`（`tools/write.go:227`）与 `kill_process` 里。

**真正的缺口**：这两个工具执行后**没有回滚**，失败也不记录原状态。`service_control`
执行失败时只报告「执行失败」，不尝试恢复；`kill_process` 发信号前不检查进程树。

**做法**：

1. `service_control` 支持 `enable` / `disable`（当前只有 start/stop/restart/reload）。
2. 执行前记录原状态（`is-active`、`is-enabled`、`ActiveEnterTimestamp`，D8），写入
   journal 供回滚使用；执行后校验，失败按原状态回退并如实报告"回退也失败"。
3. `kill_process` 增加 `signal` 参数（默认 SIGTERM，可选 SIGKILL）与进程树校验：
   拒绝 pid 1、自身与父进程；子进程数超阈值（默认 20）时升级为需审批。
4. 两个工具的风险等级从 `RiskLowWrite` 调整为 `RiskMediumWrite`，默认不进 auto 白名单。

**验收**：
- 对一个测试服务执行 restart，成功后原状态记录可查；故意让 unit 名不存在 → 报告失败且不改动任何东西
- 停用一个原本 running 的服务后手动改坏 unit 文件，再执行 start 失败 → 自动回退到停止状态并说明
- 对一个有 30 个子进程的父进程执行 kill_process → 升级为待审批并列出子进程数

#### B2.2 闸门 2 爆炸半径预检

**现状**：`internal/safety/safety.go:99-185` 只有受保护路径/服务/进程三个名单，没有依赖分析。

**做法**：

1. 新增 `safety/dependency.go`：从 `config.yaml` 的 `safety.dependencies` 读声明式依赖（如 `nginx: [php-fpm]`、`mysql: [app-api]`），构建邻接表。
2. 动作前计算影响集：直接对象 + 一层下游（可配置深度，默认 1）。影响集非空时：
   - `auto` 模式：拒绝，降级为需审批
   - `assist` 模式：在审批卡片上列出"将影响 X、Y"，让人带着信息决策
3. 进程类动作另外叠加进程树：终止父进程时列出子进程数，超过阈值（默认 20）需审批。

**验收**：
- 声明 `nginx: [php-fpm]` 后重启 nginx，审批卡片显示"将影响 php-fpm"
- auto 模式下该动作被降级为待审批，不再直接执行
- 未声明依赖时行为与现在一致（不误伤）

#### B2.3 审计补强

**现状**：`ActionLog`（`internal/model/sentinel.go:202-217`）缺 `hypothesis` / `evidence_refs`；`critical` 级没有硬编码禁止 auto，只靠默认策略。

**做法**：

1. `ActionLog` 增加 `hypothesis`（模型当时的判断依据，从报告首段摘要）与 `evidence_refs`（引用的信号 ID 列表）。
2. 引擎硬编码：`severity=critical` 时强制 `assist`，即使策略写了 auto（D-新）。
3. 事件详情页的"决策链"视图按时间轴展示：信号 → 判断 → 动作 → 验证，每步可展开证据。

**验收**：
- 任意一次 auto 运行，ActionLog 里能查到当时的假设与引用信号
- 把某策略改成 critical + auto，实际运行仍是 assist，事件里标注"critical 强制审批"

### B3 Agent 可视化（P1，约 3 天）

#### B3.1 Agent 首页

**现状**：首页仍是资源仪表盘（`web/index.html:4699` 菜单第一项），事件中心是独立页。

**做法**：

1. 新增首页，四块：
   - **今天发生了什么**：今日事件数、自动处置数、待审批数（点击可下钻）
   - **待我确认**：`awaiting_approval` 列表，直接内联批准/拒绝
   - **自主等级**：当前各策略的 shadow/assist/auto 分布 + 一键切换
   - **额度**：今日 token 用量、剩余、熔断状态
2. 原资源仪表盘保留，移到第二项，路由不变（避免书签失效）。
3. 首页可关闭（设置里"使用经典仪表盘"），照顾习惯旧布局的用户。

**实现（as-built，与上面 1/2/3 不同）**：四块内容全部保留，但**不新开页面**，直接作为资源仪表盘的一个分区 —— 资源四卡之后接「AI 运维概览」：今日事件 / 自动处置 / 待我确认 / 今日信号四卡 → 待确认内联审批列表 → 自主等级 + 额度。原独立「总览」菜单项与 `page='home'` 已移除，默认页回到 `dashboard`；`/sentinel/agent-home` 接口不变。待确认列表为空时整块不渲染（四卡里已有计数）。第 3 条"可关闭"随之取消：概览就是仪表盘的一部分，无需开关。

**验收**：
- 有 `awaiting_approval` 事件时首页直接可批准，无需跳转
- 自主等级切换后立即生效，事件中心的下一次触发按新模式走

#### B3.2 shadow 对比报表

**现状**：只有单事件 `POST /sentinel/incidents/:id/shadow-review`（`internal/api/v1/sentinel.go:355`），没有聚合。

**做法**：

1. 新增 `GET /sentinel/shadow-report?days=7`：按场景聚合影子评审结果，输出"Agent 会做 X，人工实际做了 Y，一致/不一致"。
2. 报表页展示：一致率趋势、不一致样本列表（可跳转单事件）。
3. 首页"自主等级"块显示"最近 7 天影子一致率"，低于阈值（默认 80%）时该场景不允许升级到 auto（提示原因）。

**验收**：
- 跑过至少 5 次 shadow 后报表能出数据，样本可点击跳转
- 一致率低于 80% 的场景，切换 auto 时被拒绝并说明

### B5 跨会话记忆 + 发布（P2，约 3 天）

#### B5.1 跨会话长期记忆

**现状**：只有会话内 transcript 持久化（`internal/aiagent/memory.go:20-38`）。

**做法**（D11）：

1. 新增 `agent_memories` 表：`subject`（主机/服务/文件等实体）、`fact`（一句话事实）、`source_session`、`confidence`、`expires_at`。
2. 会话结束时（或显式工具调用）抽取记忆：只保留"关于这台机器的事实"（如"nginx 配置在 /etc/nginx/conf.d/app.conf"），不存对话内容。
3. 下次运行按 subject 命中注回上下文，最多 5 条，带来源可以溯源/删除。
4. 设置页提供记忆管理：查看、删除、全部清空。

**验收**：
- 第一次会话告知"备份目录是 /data/backup"，第二次新会话提到备份时能自动带出
- 删除该记忆后不再被引用
- 记忆条数有上限（默认 500），超出按置信度和时间淘汰

## 6. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| HITL 挂起后进程重启导致事件卡死 | 事件永久停在待审批 | 审批落库 + 启动时扫描超时项（B1.1 验收项） |

| 爆炸半径依赖靠人工声明，漏配则无保护 | 误判为无影响 | 未声明时按现有名单走，不降级；文档写明声明方式 |
| `service_action` 回滚本身失败 | 状态更乱 | 回滚失败必须如实报告并暂停该策略，不能假装成功 |
| Agent 概览与资源仪表盘分两页导致重复 | UI 成本 | 已合并为一页：概览作为仪表盘的一个分区，复用现有卡片样式，不新写图表 |
| 改动面大（14 个子项）一次性发布 | 回归风险 | 按 B0~B5 分批验收，每批独立可部署 |
| 人工审批变成新的噪音 | 用户嫌烦关掉 Agent | 首页「待我确认」集中展示 + 审批卡片给足证据，减少点开成本 |
