# ホストセキュリティ設計

> 本文では、**「ホストセキュリティ」という機能がどのように設計・実装されているか**を説明します。各検出項目が何を見るのか、判定基準は何か、スコアはどう計算するのか、境界はどこにあるのか、なぜそのように選んだのかを扱います。
>
> 対応コード：`internal/service/{security,baseline,loginsecurity,firewall,fim,threat,securitymonitor}.go`、`internal/api/v1/{security,baseline,fim,threat,firewall}.go`、`internal/router/router.go`。

---

## 1. 設計目標と非目標

### 目標

| 目標 | 具体的な意味 |
| --- | --- |
| **ゼロ依存** | エージェントをインストールせず、カーネルモジュールに依存せず、中央サービスに接続しない。バイナリを持ち込むだけで監査できる |
| **説明可能** | 各検出項目をクリックすると「どのファイルを読んだか、どんな値を見たか、なぜ不合格と判定したか、どう修正すべきか」が確認できる |
| **実行可能** | 問題を発見したらパネル上で直接修正できる（ファイアウォールの変更、ヘルスチェックの実行、ベースラインの再構築、脅威を処理済みとしてマーク） |
| **人にも AI にも見せる** | 同じ結論をページとしてレンダリングし、読み取り専用ツールとして内蔵 Agent にも提供する |
| **権限を越えない** | 読み取り専用機能はログインするだけで利用可能。システムを変更するあらゆる操作には個別の権限ポイント + root 身份が必要 |

### 非目標（トレードオフであり、未完成ではない）

- **HIDS の代替品にはしない**：カーネル syscall フック、eBPF プローブ、全トラフィック検出は行わない。こうした機能は常駐する高権限の収集を必要とし、「単一バイナリ、数十 MB、気軽にインストール可能」という位置づけと衝突する。
- **マルチホストの状況把握はしない**：単一ホストで単一ホストの結論を出す。複数マシンの集約は OpsMini Server / Proxy の責務である。
- **独自のルールライブラリエンジンは持たない**：ベースラインの判定基準はコード内に記述され（14 項目）、YAML ルールのホットリロードは受け付けない。ルールのホットリロードは柔軟に聞こえるが、「なぜこのマシンが 62 点なのか」が再現できなくなる。ルールの外部化は進化の方向である（§16 参照）。
- **専門的なコンプライアンススキャンの代替にはしない**：等保/CIS の完全な項目カバレッジと証明書発行は行わず、「日常的に可視化でき、実行できる」部分のみを行う。

## 2. 機能マップ

ホストセキュリティページは 6 つのタブで構成されており、本質的には**5 つの検出モジュール + 1 つの集約ビュー**です：

| タブ | 検出内容 | データソース | トリガー方法 | システムを変更するか |
| --- | --- | --- | --- | --- |
| セキュリティ概要 | 集約サマリー：総合スコア、レベル、5 モジュールのスコアと一言結論 | 残り 5 モジュールの保存結果 | ページを開く | いいえ |
| ベースライン診断 | 14 項目のホスト強化状況 | `/etc/ssh/sshd_config`、`/etc/passwd`、`/etc/shadow`、`/etc/login.defs`、crontab、リスンポート | 手動で「診断開始」をクリック | いいえ |
| ログインセキュリティ | ブルートフォース攻撃、異常ログイン、SSH 強化の推奨事項 | `/var/log/auth.log` または `/var/log/secure` | ページを開く | いいえ |
| ファイアウォール | 現在のバックエンドとルール；ポートの許可/ブロック、起動/停止 | `ufw` / `firewall-cmd` / `iptables` の実際の状態 | 手動操作 | **はい** |
| ファイル整合性 | 重要ファイルが変更/削除されたか | 8 つのシステム重要ファイルの SHA256 | バックグラウンドで 60 秒ごと | いいえ |
| 脅威検出 | マイニングプロセス、疑わしいスケジュール、疑わしい自動起動 | `/proc`、crontab、`/etc/rc.local`、systemd サービス一覧 | バックグラウンドで 5 分ごと + 手動 | いいえ（対処は人が行う） |

設計上の明確な決定：**システムを変更するのはファイアウォールのみ**です。残り 4 つのモジュールは純粋なオブザーバーであり、誤判定が発生してもスコアが悪化するだけで、マシンに障害を引き起こすことはありません。

## 3. アーキテクチャ：互いに依存しない2つの経路

OpsMini にはセキュリティ関連のものが2系統あり、見た目は似ているが、実際には独立した2つの経路である：

```
                  ┌──────────── 健診経路（pull、人に見せる） ────────────┐
  /etc、/proc ───▶ │ BaselineService  ログイン分析  FIM  脅威スキャン        │ ──▶ SQLite ──▶ セキュリティページ + スコア
  認証ログ        │ SecurityService 集約スコアリング                        │
                  └──────────────────────────────────────────────────┘

                  ┌──────────── 感知経路（push、Agent 向け） ──────────┐
  auth.log、サイト   │ sentinel コレクター（logwatch/authwatch/           │ ──▶ シグナル ──▶ イベント ──▶ ポリシー
  ディレクトリ、プロセステーブル     │ filewatch/procwatch/netwatch/metricwatch）      │        ──▶ Agent 対処
                  └──────────────────────────────────────────────────┘
```

**なぜ2つに分けるのか、1つに統合しないのか？**

| 観点 | 健診経路 | 感知経路 |
| --- | --- | --- |
| インタラクションモデル | プル：ページを開く / スキャンをクリック | プッシュ：コレクターが常時稼働 |
| 出力 | 一覧 + スコア（長期的に保存可能な状態スナップショット） | シグナル → イベント（時効性のあるストリーム） |
| 消費者 | 人 | ポリシーエンジン + AI Agent |
| 判定の性格 | 「現状がコンプライアンスに適合しているか」 | 「たった今何が起きたか」 |
| 誤判定のコスト | スコアが悪く見える | 自動対処がトリガーされる可能性 |

統合すると両者が互いに足を引っ張り合う：健診はいつでも再計算できる必要があり、感知は継続的に増分できる必要がある。一方の経路にステートマシンを追加すると、もう一方もそれを引きずって動かざるを得なくなる。

**コストも明確にしておく**：2つの経路はそれぞれ認証ログを解析しており（`service/loginsecurity.go` と `sentinel/authwatch.go` は2セットの正規表現である）、基準にドリフトが生じるリスクがある。これは既知の技術的負債であり、§16 を参照。

## 4. セキュリティスコアモデル

合計 100 点、5 つのモジュールに固定の重みを設定：

| モジュール | 満点 | この重みの理由 |
| --- | --- | --- |
| ベースラインチェック | 40 | 唯一「自ら積極的に改善できる」部分であり、日常運用の水準を最もよく反映する |
| ログインセキュリティ | 20 | パブリックネットワーク上のマシンのトラブルは十中八九ここから始まる |
| ファイアウォール | 15 | 有るか無いかが、そのまま露出面を決める |
| ファイル整合性 | 15 | 重要なファイルが変更されることは、通常すでに侵害されていることを意味する |
| 脅威検出 | 10 | 重みが低いのは、最も誤判定されやすいため（§10 参照） |

### 各モジュールの採点ルール（コードと一対一対応）

**ベースライン（0–40）**：項目数ではなく、重みで加重する。

```
got   = Σ(pass 項权重) + Σ(warn 項权重 × 0.5)
total = Σ(全部項权重) = 32
得分  = int(40 × got / total)
```

三態の意味：`pass` は満点、`warn` は半分、`fail` は 0 と計算する。warn が存在する理由は、一部の項目が「やっていないが間違いでもない」ためである（例えば SSH が依然として 22 番ポートを使用：リスクは現実だがよくあることで、直ちに 0 点と判定するとスコアの識別力が失われる）。

**ログインセキュリティ（0–20）**：

| 状況 | 得点 |
| --- | --- |
| ブルートフォース攻撃が未検出、24h 失敗なし | 20 |
| 24h 以内に失敗ログインがあるがブルートフォース閾値未満 | 16（固定で 4 減点） |
| n 個のブルートフォース疑惑ターゲットを検出 | `20 − 5n`、下限 0 |

**ファイアウォール（0–15）**：有効なら 15、無効なら 0。二元判定であり、中間状態はない。

**ファイル整合性（0–15）**：`15 − 3n`（n = 24h 以内の変更件数）、下限 0。1 件の変更で 3 点減点は、重要ファイルを 5 個変更すればゼロになることを意味する。

**脅威検出（0–10）**：10 から減点し、`critical` は 5 減点、`warning` は 2 減点、その他は 1 減点、下限 0。

### レベルマッピング

| スコア | レベル |
| --- | --- |
| ≥ 90 | 優秀 |
| ≥ 75 | 良好 |
| ≥ 60 | 普通 |
| < 60 | 危険 |

### このモデルのトレードオフ

- **資産価値による重み付けをしない**：OpsMini はこのマシン上でどんな業務が動いているか知らないため、「重要度係数」を推測するとスコアが根拠のないものになるだけである。
- **CVSS を使わない**：CVSS が評価するのは脆弱性の深刻度であり、ここで評価するのはホストの設定と運用の現状であり、両者は別物である。
- **マイナス点を設けない**：単一項目は 0 で止め、1 つのモジュールが全体を崩してスコアが意味を失うことを避ける。
- **スコアは再現可能**：入力が同じ、コードが同じなら、スコアは必ず同じになる。これが「変更後に再度確認する」比較に使える前提である。

## 5. ベースライン検査

### 実行方法

1回のスキャンで1つの `ScanID`（ナノ秒タイムスタンプ）を生成し、14項目の結果をそれぞれ1行ずつ `baseline_results` に書き込みます。ページには**最新バッチ**のみを表示し、過去のバッチはデータベースに保持して比較できるようにします。

純粋なファイル解析であり、`lynis` / `oscap` などの外部ツールは呼び出しません——これらのツールは最小化システムには存在しないことが多く、また出力の構造化が困難です。

### 判定の詳細

- `sshd_config` はメインファイルと `/etc/ssh/sshd_config.d/*.conf` の両方を読み取ります（現代のディストリビューションでは設定が drop-in ディレクトリに分割されているため、メインファイルのみを読むと誤判定します）。
- 「明示的に未設定」と「明示的に誤設定」を区別します。前者には `warn`（ディストリビューションのデフォルト値は不確定）を、後者には `fail` を付与します。
- `/etc/shadow`、`/etc/passwd` はテキストを直接解析し、NSS 設定に依存しません——LDAP/SSSD が関与するマシンでの判定の揺れを回避します。
- 高危険ポートは固定リストを使用します：`23 Telnet`、`445 SMB`、`135 RPC`、`1433 MSSQL`、`3389 RDP`。

完全な14項目のリストは [付録 A]](#附录-a基线-14-项清单) を参照してください。

### なぜ重みをコードにハードコードするのか

重みを変更すればスコアを変更できます。もし重みが設定可能であれば、同じマシンが2つの顧客先で異なるスコアになり、「検査」の信頼性が失われます。重みを調整する場合は、コードレビューを経由してください。

## 6. ログインセキュリティ

### データソースとコスト

認証ログの末尾のみを読み取ります：`tail -n 5000`、優先順位は `/var/log/auth.log`（Debian 系）を先に、次に `/var/log/secure`（RHEL 系）、存在しない場合はエラーではなく空のレポートを返します。ログは数百 MB に達することがあり、全量読み取りはメモリを枯渇させます。

**統計ウィンドウは正確に説明する必要があります**：実装上のウィンドウは「ログ末尾 5000 行」であり、厳密な時間ウィンドウではありません。フィールド名は `failed_count_24h` / `success_count_24h` を踏襲しています。というのも、スキャンされ尽くした公網マシンでは 5000 行が 24 時間に満たないことが多く、静かなマシンでは 5000 行が数日に及ぶことがあるからです。この偏差は既知の問題（§15）であり、厳密な 24 時間フィルタを実装していない理由は後述します。

### 3 種類の判定基準

| 判定基準 | ルール | 出力 |
| --- | --- | --- |
| ブルートフォース | 同一アカウントが統計ウィンドウ内で失敗（`Failed password` と `Invalid user` を含む）**累計 ≥ 5 回** | アカウント名 + 回数 + 関与 IP リスト、回数の降順 |
| Top 失敗元 | IP ごとに失敗回数を集計し上位 10 件 | IP + 回数 |
| 異常ログイン | 成功ログインのうち `user == root` | 時刻 + ユーザー + IP + 理由「root アカウントによる直接 SSH ログイン」 |

SSH 強化の推奨事項は固定文言ではなく、現在の `sshd_config` を読んで各項目が実施済みかどうかを判断します（`PermitRootLogin`、`PasswordAuthentication`、ポート変更、Protocol 2）。ページ上には「実施済み/未実施」を直接表示します。

### GeoIP と UA 分析を行わない理由

オフライン環境は必須要件です。イントラネットに設置でき、ネットワークに接続せず、外部サービスにログを送信しないセキュリティパネルは、美しい世界地図を描けてもネットワーク接続が必要なパネルよりも有用です。そのため、異常判定は本機で確認できる事実（時刻、アカウント、IP 頻度）のみに依存します。

### 厳密な 24 時間フィルタを実装していない理由

`syslog` のタイムスタンプには年が含まれていません（`Aug 14 07:00:01`）。時刻でフィルタするには年を推定し、年跨ぎの回り込みを処理する必要があります。午前 0 時前後、コンテナのタイムゾーンの不一致、logrotate によるログの切り詰めは、いずれも推定を誤らせます。年を 1 つ間違えると、履歴全体を「たった今」と計算してしまいます。

「末尾 N 行」を時間ウィンドウの代わりに使う代償はウィンドウ長が変動することであり、利点は**時刻解析の誤りによる誤判定が決して起きない**ことです。正確さが本当に必要なら、正攻法は感知層に `observed_at` に基づいてライブラリ内でウィンドウクエリを行わせることです（もともと時刻を持っています）。これも §16 で統一ファクト層を目指す動機の一つです。

### 閾値 5 の説明

5 回未満の大半は人手によるパスワード入力ミスです。24 時間以内に同一の IP 群から 5 回以上あって初めて「試行中」の特徴を備えます。この閾値は実際の公網マシン上では大量のスキャンによって越えられます——それこそがこの閾値の用途です：**これは正確に識別するためのものではなく、このマシンがスキャンされていることを伝えるためのものです**。

## 7. ファイアウォール

### バックエンドの自動識別

システムに何がインストールされているかを仮定せず、実際の状態を読み取ってバックエンドを決定します：

| バックエンド | 判定 | 対応する書き込み操作 |
| --- | --- | --- |
| `ufw` | `ufw status` が読み取り可能 | ポートの許可/ブロック、有効化、無効化、番号指定によるルール削除 |
| `firewalld` | `systemctl is-active firewalld` | ポートの許可/ブロック（`--permanent` + `--reload`）、有効化、無効化 |
| `iptables` | ルールチェーンが存在 | ポートの許可/ブロック（`-I INPUT 1`）、番号指定によるルール削除；**パネル内での無効化は非対応** |

`iptables` バックエンドは意図的に「無効化」を提供していません：ルールチェーンをクリアすることはすべてのマシンを無防備にすることを意味し、破壊性が高すぎるため、ユーザー自身がマシン上で操作することを求めます。

### ロックアウト防止設計（これが本モジュールで最も重要な項目）

**ファイアウォールを有効化する前に、まずパネル自身のポートと SSH 22 を自動的に許可**し、その後で `enable` を実行します。

順序を逆にしてはいけません。逆にすると典型的な事故になります：ファイアウォールを有効にした瞬間に 8888 と 22 が同時にブロックされ、ユーザーはコンソールしか使えなくなります。`panelPort` は起動時の設定から注入され、ハードコードされた 8888 ではありません。

### パラメータ検証とタイムアウト

| 防御線 | 方法 |
| --- | --- |
| 権限 | すべての書き込み操作で `requireRoot()`、非 root は直接 `ErrNeedRoot` を返す |
| ポート | `int` 型 + 1–65535 の範囲検証、文字列は受け付けない |
| プロトコル | 列挙 `tcp`/`udp` |
| インジェクション | すべて `exec.Command(name, args...)` を経由し、shell を経由しないため、パラメータを2つ目のコマンドとして結合することは不可能 |
| ハング | 各ファイアウォールコマンドは 10 秒タイムアウト（`context.WithTimeout`）、失敗時は stderr の原文を返す |

### Agent のブロックとの関係

システムには2種類のブロックがあり、意図的に分けて管理しています：

| ソース | 保存先 | ライフサイクル | クリーンアップ担当 |
| --- | --- | --- | --- |
| ページルール（人手設定） | `ufw`/`firewalld` ルールテーブル | 長期、人が削除するまで | 人 |
| Agent ブロック（イベント駆動） | `iptables -I INPUT -s <ip> -j DROP` + `blocked_ips` テーブル | TTL 付き、期限切れで自動回復 | `SweepBlocks()` が自動解除 |

分けている理由：Agent のブロックは自動回復できなければならない（誤ブロックが自力で解消できる必要がある）一方、人のルールは自動回復ロジックに巻き込まれて削除されてはなりません。2つの仕組みはそれぞれ独立して管理され、ページ上でも別々に表示されます。

## 8. ファイル整合性（FIM）

### 監視対象

デフォルトでは 8 個のシステム重要ファイルを監視し、初回起動時（ベースラインが空の場合）に自動でベースラインを作成します：

```
/etc/passwd  /etc/shadow  /etc/group   /etc/ssh/sshd_config
/etc/crontab /etc/sudoers /etc/hosts   /etc/resolv.conf
```

このうち `/etc/passwd`、`/etc/shadow`、`/etc/sudoers` の変更は `critical` として記録し、それ以外は `warning` とします。

### 検出ループ

60 秒ごとに、有効な各項目について `SHA256 + size + mtime` を 1 回計算します：

- 計算できない（ファイルが存在しない）→「ファイルが削除された」を 1 件記録し、`critical` レベルはパスに基づいて判断
- ハッシュが一致しない →「ファイル内容が変化した」を 1 件記録し、新旧のハッシュを付与
- 一致する → 何もしない

### 重要な設計：変更後にベースラインを自動で前進させる

変化を検出してデータベースに保存した後、**ベースラインは直ちに新しいハッシュへ更新されます**。

これは意図的な設計です：ベースラインを前進させない場合、同じ変更が 60 秒ごとに報告され、1 日で 1440 件のアラートとなり、誰も見なくなります。前進させることで「1 回の変更につき 1 件のアラート」となり、しかも**次にまた変更されれば再び報告されます**——本当に繰り返し改ざんされていれば、依然として検知できます。

代償：連続する 2 回の変更が同じ 60 秒のウィンドウ内で発生した場合、記録は 1 件しか残りません。この精度では許容範囲です（より細かくするには inotify が必要です。§16 参照）。

「ベースラインの再構築」は手動操作です：`sudoers` を変更した後にクリックして、システムに「現在の状態が正しい」と伝えます。

### 感知層 filewatch との役割分担

|  | セキュリティページ FIM | 感知層 filewatch |
| --- | --- | --- |
| 監視対象 | 8 個のシステム重要ファイル | サイトルートディレクトリに新規追加された実行可能スクリプト |
| 判定基準 | ハッシュ比較 | 拡張子 + WebShell 内容の特徴（`eval($_POST`、`base64_decode` など） |
| 目的 | 「システムが改ざんされた」ことを発見 | 「ウェブサイトに webshell が仕込まれた」ことを発見 |

両者は重複せず、互いを参照することもありません。

## 9. 脅威検出

3つのスキャナがあり、5分ごとに1ラウンド実行され、起動時にまず1回実行されます。

| スキャナ | 監視対象 | 判定基準 | レベル |
| --- | --- | --- | --- |
| プロセス | `/proc` の全プロセス（名前 + コマンドライン） | マイニングキーワード（`xmrig`、`minerd`、`kdevtmpfsi`、`kinsing`、`stratum` など11個）に一致 | critical |
| プロセス | プロセスの実行ファイルパス | `/tmp` または `/dev/shm` に存在（正常なサービスはここから起動すべきではない） | warning |
| スケジュール | システム + ユーザー crontab | コマンドに `curl`、`wget`、`base64 -d`、`/dev/shm` を含む | warning |
| 起動項目 | `/etc/rc.local` の非コメント行 | `curl`、`wget`、`/tmp` を含む | warning |
| 起動項目 | systemd で有効化されたサービス名 | `miner`、`xmrig`、`kdevtmpfs` を含む | critical |

### 重複排除とライフサイクル

`kind + name` で重複排除：既存のレコードに一致した場合は `last_seen` と詳細のみを更新し、新しいエントリは追加しません。状態は `active` / `resolved` のみで、**人間だけが解決済みにマークできます**——プロセスが強制終了されるまで、スキャナは5分ごとにそれを再び検出します。これこそが望ましい動作です（真の脅威は自然に消えるべきではありません）。

### この検出に対する正直な評価

キーワードブラックリストは**名前を変えるだけで回避できます**。これは公然の秘密です。したがってその位置づけは「すべてのマイニングを捕まえられる」ことではなく、次のとおりです：

1. **怠惰な攻撃**を捕まえる——ほとんどのボットネットは既製のバイナリをそのまま使用し、名前も変えません；
2. 「一時ディレクトリで実行可能」といった**行動特徴**と組み合わせて、名前変更された部分をカバーします；
3. 残りは知覚層のプロセス行動とログイン行動のシグナルで補います。

駆除できると誇張せず、発見できれば報告し、対処は人間に委ねます（または人間が Agent に権限委譲します）。

## 10. データモデル

| テーブル | 1行が表すもの | 主要フィールド |
| --- | --- | --- |
| `baseline_results` | 1回のスキャンにおける1件の結果 | `scan_id`（バッチ）、`category`、`item_key`、`status`](pass/fail/warn)、`detail`、`suggestion`、`weight` |
| `fim_baselines` | 監視対象ファイルの現在のベースライン | `path`](unique)、`sha256`、`size`、`mod_time`、`enabled` |
| `fim_changes` | 1回のファイル変更イベント | `path`、`old_sha256`、`new_sha256`、`level`](warning/critical)、`message`、`created_at` |
| `threat_findings` | 1件の脅威エントリ | `kind`](process/cron/startup)、`name`、`detail`、`severity`、`status`、`first_seen`、`last_seen`、`resolved_at` |

設計上のポイント：

- ベースライン結果は `scan_id` ごとにバッチ化され、**履歴を上書きすることは決してない**：「先週と今週」を比較したい場合も照会可能。
- `fim_baselines` と `fim_changes` はテーブルを分ける：一方は状態、もう一方は履歴であり、1つのテーブルに混在させると「現在のベースライン」と「変更履歴」が互いに汚染し合う。
- `threat_findings` は `first_seen/last_seen` を持つ：これが今出現したものか、それとも3日間放置されているものかを一目で判別できる。
- 独立したセキュリティ用データベースファイルは存在せず、すべて `opsmini.db` に格納され、バックアップと共に移動する（パネルの他のデータと同様）。
- テーブル名に注意：セキュリティベースラインの結果は `baseline_results`、感知層の「学習ベースライン」（EWMA 期待値）は `baselines` であり、両者は無関係なので混同しないこと。

## 12. パネル自体のセキュリティ境界

セキュリティモジュール自体も攻撃面であるため、以下のように対応します：

| リスク | 対応 |
| --- | --- |
| コマンドインジェクション | すべての外部コマンドは `exec.Command` + 引数配列で実行し、シェルで結合することは一切ない。ポートは `int`、プロトコルは列挙型 |
| 権限昇格 | 書き込み操作はまず `requireRoot()` を実行し、非 root は即座に拒否し、「ベストエフォート」は行わない |
| 長時間の停止 | 外部コマンドは 10 秒でタイムアウト |
| 自己ロック | ファイアウォール有効化前にパネルポートと 22 を許可する |
| プライバシー | ログ内のログインイベントのみを読み取り、パスワードやコマンド全文は保存しない（判定に使用するフィールドのみデータベースに格納） |
| 権限外呼び出し | 各書き込みインターフェースには独立した権限ポイントがあり、フロントエンドでボタンを隠すことで「制御」するものではない |

## 13. パフォーマンスとリソースオーバーヘッド

| 動作 | オーバーヘッド | 説明 |
| --- | --- | --- |
| ベースライン検査 | 14 回の小ファイル読み取り + 1 回のポートテーブル、ミリ秒レベル | 人がクリックした時のみ実行 |
| ログイン分析 | `tail -5000` 1 回、単回 < 50ms | ページを開いた時に実行、キャッシュなし |
| FIM チェック | 8 ファイルの SHA256、60 秒ごと | すべて KB 級の小ファイル、CPU は無視できる |
| 脅威スキャン | `/proc` 数百プロセス + crontab + systemctl を 1 回走査、5 分ごと | 唯一の「重い」動作、それでも百ミリ秒レベル |
| 常駐メモリ | 追加キャッシュなし、すべて同一の SQLite 接続を使用 | 独立プロセスなし、バックグラウンドキューなし |

常駐サンプラーも追加の goroutine プールもなし：FIM と脅威スキャンは 1 つのループを共有し（`SecurityMonitor`）、1 つの ticker が 1 つの処理を管理します。

## 14. 自律型 Agent との関係

三つのインターフェースは、いずれも**一方向的に事実を提供する**ものであり、「セキュリティモジュールが Agent を指揮する」といった結合は存在しません：

| 方向 | 形態 | 説明 |
| --- | --- | --- |
| セキュリティ → AI | 読み取り専用ツール `security_status` | Agent は「スコア + 五モジュールのサマリー」を読んで「このマシンは安全か」に回答できます。ツールは `RiskReadonly` + `security.view` |
| セキュリティ → AI（書き込み） | ツール `firewall_rule` | ファイアウォールの変更は書き込み操作であり、L1/L2 の段階分けを経て、確認が必要です |
| 感知層 → Agent | シグナル → イベント → ポリシー | sentinel が独立して担当し、本節のセキュリティモジュールとは状態を共有しません |

**現在行っていないこと（意図的）**：脅威検出の結果と FIM の変更はイベントバスに入れていません。理由は、これら二種類の結果は誤検知率が感知層のシグナル（キーワードマッチング、ベースラインの自動前進はいずれもノイズを生みます）よりも高く、自動処置ポリシーに直接与えるのはリスクが大きすぎるためです。誤検知率の実測データが得られてから接続します。§16 を参照。

## 15. 既知の制限

| 制限 | 影響 | 備考 |
| --- | --- | --- |
| カーネルレベルの検出なし | rootkit、隠しプロセス（`/proc` が hook される）は見えない | 位置づけによる決定であり、実装する予定はない |
| FIM は 8 ファイルのみをカバー | カスタムパス、ディレクトリの再帰、新規ファイルの監視はいずれもなし | 現状は感知層の filewatch でサイトディレクトリを補完 |
| 脅威検出はキーワード依存 | 名前を変えれば回避される | §9 の正直な評価を参照 |
| ベースラインは 14 項目で固定 | 等保/CIS の全項目をカバーできない | 進化の方向性はルールの外部化 |
| スコアに業務上の重要度を含まない | テスト機と中核 DB サーバーが同点になる | 実装しない、恣意性を避けるため |
| 認証ログの形式依存 | rsyslog/journald のテキスト形式でないマシンでは読み取れない可能性がある | 互換性は `/var/log/secure` でフォールバック |
| ログイン統計のウィンドウが変動 | `tail -5000` 行、厳密な 24 時間ではない（フィールド名は 24h のまま） | §6「なぜ厳密な 24 時間フィルタを実装していないか」を参照 |
| ログ解析が 2 系統 | セキュリティページと感知層で基準がずれる可能性がある | 既知の技術的負債 |
| レポート出力なし | ページで見るだけで、PDF/HTML のコンプライアンスレポートを出力できない | 進化の方向性 |

## 16. 進化の方向性

優先度順：

1. **FIM の設定可能化**：カスタムパス、ディレクトリの再帰、ホワイトリスト（`/etc/` 配下で頻繁に変化するファイルを先に除外する）をサポートし、さらに inotify イベント駆動で 60 秒ポーリングを置き換える。
2. **ベースラインルールの外部化**：14 項目 → YAML ルールパッケージ。CIS / 等保二級の項目セットのインポートをサポートし、同時に「現在どのルールセットを使用しているか」を結果に記録して、スコアの再現性を保証する。
3. **統一ログファクト層**：`service/loginsecurity.go` と `sentinel/authwatch.go` で共通のパーサーを共有し、基準のずれを解消する。
4. **脅威検出の強化**：`ausearch`（auditd 監査ログ）とオプションの YARA ルールを接続し、キーワードから行動と特徴のデュアルトラックへアップグレードする。
5. **セキュリティ結果のイベントバスへの投入**：誤検知率が定量化可能になった後、`critical` レベルの脅威と `critical` レベルの FIM 変更をポリシーエンジンに接続し、Agent が自律的に処理できるようにする（例：WebShell の着地を検出 → 隔離 → 報告）。
6. **コンプライアンスレポートのエクスポート**：ワンクリックで単一ファイルの HTML レポートを出力（スケジュールタスクレポートと同じレンダリングを使用）、スコア、項目ごとの結論、改善提案を含む。

| 分類 | 項目 | 重み | 判定 |
| --- | --- | --- | --- |
| ssh | SSH の root パスワードログインを禁止 | 3 | `PermitRootLogin` が `no`/`prohibit-password` の場合 pass と判定；未設定の場合は warn と判定；その他は fail と判定 |

重みの合計は 32。上記の計算式に従って 40 点に換算する。

## 付録 B：スコア計算例

典型的なパブリック Ubuntu マシン：

| モジュール | 実測 | スコア |
| --- | --- | --- |
| ベースライン | 14 項目中 12 項目 pass、2 項目 warn（SSH が 22 番ポートを使用、`PASS_MAX_DAYS` 未設定） | got = 32 − 1×0.5 − 2×0.5 = 30.5 → `int(40×30.5/32)` = **38** |
| ログイン | 24h 以内に 2000 回の失敗、3 つのブルートフォース標的にヒット | `20 − 5×3` = **5** |
| ファイアウォール | ufw 有効 | **15** |
| ファイル整合性 | 24h 以内に 1 箇所の変更（`/etc/hosts`） | `15 − 3` = **12** |
| 脅威検出 | 1 つの warning（`/tmp` 配下の実行可能プロセス） | `10 − 2` = **8** |
| **合計** |  | **78 → 良好** |

このスコアは解釈として妥当である：設定はほぼ合理的（ベースライン 38）だが、現在ブルートフォース攻撃を受けており（ログイン 5）、減点の主な原因は誤判定ではなく実際の攻撃である。改善の道筋も明確である——ファイアウォールの送信元制限を有効化し、fail2ban を導入するか Agent によるブロックを行えば、ログインスコアは回復する。
