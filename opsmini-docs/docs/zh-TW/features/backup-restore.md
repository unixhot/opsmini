# 備份與恢復

## 一鍵的程度不一樣

| 動作 | 一鍵程度 | 為什麼 |
|---|---|---|
| 備份 | ✅ 真的點一下就跑，也可定時 | 只讀源資料 + 寫目標目錄，失敗重試即可，無破壞性 |
| 恢復 | ⚠️ 「一鍵」但有三道前置 | 恢復會覆蓋生產資料，必須有預檢、恢復前快照和自動回滾 |

把恢復做成「點一下就覆蓋」，等於給使用者一個沒有撤銷鍵的刪除按鈕。所以介面上叫**一鍵恢復（帶預檢與自動回滾）**。

## 備份什麼

三種物件，寫在「備份物件」裡，每行一個：

| 寫法 | 含義 |
|---|---|
| `/var/www` | 目錄（或單個檔案），打包為 `tar.gz` |
| `mysql:opsmini` | 資料庫，透過 `mysqldump` 匯出後壓縮 |
| `redis:/var/lib/redis/dump.rdb` | Redis 快照檔案，直接打包該檔案 |

MySQL 備份使用面板已配置的連線資訊（本機 socket），引數為 `--single-transaction --routines --triggers`，保證 InnoDB 表的一致性快照而不鎖表。

**不支援**：PostgreSQL、Docker volume、塊裝置/檔案系統級快照、增量備份、備份加密。這些都在後續版本考慮，本版不承諾。

## 快照長什麼樣

```
<資料目錄>/data/backups/web-20261029-020000/
├── manifest.json                 # 後設資料：物件、大小、sha256、主機名、版本
└── data/
    ├── var_www.tar.gz
    ├── opsmini.sql.gz
    └── redis.rdb.gz
```

目錄許可權 `0700`，檔案 `0600`。`manifest.json` 裡記錄每個分片的 sha256，恢復時會逐個校驗。

不引入 restic/borg 這類「倉庫型」備份工具：它們要去重、加密、快照鏈，功能強但會帶來 15–25MB 依賴，而且恢復時必須用同一工具。當前是「自包含的分片 + 清單」，任何一臺機器解開就能恢復。

## 備份流程

```
校驗全部物件（路徑存在、庫名非空、redis 路徑可讀）
   ↓  先全部校驗再動手：否則 5 個物件裡第 2 個寫錯，
      會在已經產出 4 個歸檔之後才失敗，留下半個快照
逐個執行（序列，避免 IO 打滿）
   ↓  每個物件完成即寫入 manifest，失敗不產生「半個備份」
計算總校驗和 → 按保留策略清理舊快照 → 寫備份歷史
```

保留份數預設 7，`0` 表示全部保留。清理按**整目錄**刪除最舊的，絕不刪單個分片（否則清單失效）。

## 恢復流程（三道閘門）

**① 預檢**

- 必須輸入快照名做二次確認（防誤選）
- 目標父目錄存在且可寫
- `mysql` 客戶端可用（恢復資料庫時）
- 快照檔案齊全、sha256 與清單一致

**② 恢復前自動快照**

把當前狀態先備份一份（目錄走同一套打包邏輯，資料庫走 dump），失敗可回到這一步。

**③ 執行與回滾**

- 還原 → 健康檢查
- 任一檢查失敗 → **自動回滾到步驟②的快照** → 在事件中心產生一條 critical 事件

健康檢查項：目錄比對檔案數與抽查校驗和、MySQL 執行 `SELECT 1` 並核對關鍵錶行數、Redis `PING` 與 keyspace 對比。

回滾的可靠性來自「同分割槽 rename 是原子的」：恢復前把目標目錄 `mv` 成 `xxx.pre-restore-<時間戳>`，失敗時 `mv` 回來。

## 面板操作

**面板設定 → 備份恢復**：

| 區域 | 內容 |
|---|---|
| 備份物件 | 每行一個，支援目錄 / `mysql:庫名` / `redis:路徑` |
| 保留份數 | 預設 7，0 表示不清理 |
| 立即備份 | 跑一次，完成後重新整理快照列表 |
| 快照列表 | 名稱、時間、大小、物件數、預檢結果 |
| 恢復 | 輸入快照名確認後執行，返回預檢明細與結果 |
| 備份歷史 | 每次執行的結果（含失敗原因） |

## 定時備份

備份是**計劃任務的第四種型別**（與面板任務 / 系統 crontab / 使用者 crontab 並列），複用同一套排程、啟停與失敗告警。

在 **計劃任務 → 新建任務 → 型別選「備份任務」** 中配置：

| 欄位 | 說明 |
|---|---|
| 備份物件 | 與備份頁相同的行語法 |
| 保留份數 | 覆蓋舊快照的策略 |
| 執行週期 | cron 表示式，常用預設（每天 02:00 等） |
| 通知渠道 | 面板 / 郵件 / 企業微信 / 釘釘 / 飛書 |
| 保留本地副本 | 用了遠端目標時，上傳成功後是否保留本地一份 |

與手動「立即備份」走的是**同一個引擎**，產物完全一致——不存在「手動能恢復、定時的不行」這種情況。

失敗會寫回任務狀態（`上次狀態 / 上次錯誤 / 連續失敗次數`），同時落一條備份歷史，觸發內建告警規則「備份失敗數」。

## 遠端目標：程式碼就緒，本版不啟用

`internal/backup` 裡已經實現了 S3 相容（OSS / MinIO / AWS，自寫 SigV4 簽名）和 SFTP 兩種遠端儲存，但**v1.4.0 不作為交付內容**：

- 面板不引導配置遠端目標
- 文件不建議在生產使用
- 未做真機聯調驗收（只有單元測試與 S3 簽名向量測試）

需要異地存放時，在 `config.yaml` 里加目標即可啟用，無需改程式碼：

```yaml
backup:
  targets:
    - name: oss-bj
      type: s3
      endpoint: oss-cn-beijing.aliyuncs.com
      bucket: my-backup
      region: cn-beijing
      access_key: "..."
      secret_key: "..."
```

配置後備份頁會出現「遠端目標」選擇，可將快照上傳並瀏覽/取回遠端快照。上傳在本地快照完整落盤之後進行，所以上傳失敗不會在遠端留下半個備份。

**注意**：這條鏈路沒有經過真機聯調，正式用之前請先在一個非生產目錄上驗證一次完整往返（上傳 → 列表 → 恢復到臨時目錄）。

## 已知限制

- 大目錄備份期間會持續佔用 IO，建議錯開業務高峰（預設 02:00）
- MySQL 透過本機 socket 備份，不支援遠端資料庫例項
- 恢復是「覆蓋式」的：只還原快照裡包含的物件，不會清理快照之外的新增檔案
- 單個快照不做加密，含敏感資料的目錄請確保資料目錄許可權與備份介質安全
