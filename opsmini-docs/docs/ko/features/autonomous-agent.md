# 자율 Agent (이벤트 센터)

「AI 어시스턴트」는 **당신이 물으면 답하는** 방식입니다. 당신이 현상을 설명하면, 그것이 조사하고 결론을 제시합니다.
「자율 Agent」는 **스스로 지켜보는** 방식입니다. 수집기가 백그라운드에서 호스트를 지속적으로 관찰하다가, 살펴볼 가치가 있는 일을 발견하면 스스로 한 번의 조사를 시작하고, 당신이 설정한 경계에 따라 「기록만 / 먼저 묻고 움직임 / 자동 처리」를 결정한 뒤, 판단과 근거와 동작을 모두 기록으로 남깁니다.

둘의 모델, 도구 세트, 가드레일은 동일한 한 세트이며, 차이는 오직 **누가 시작하는가**에 있습니다.

## 하나의 닫힌 루프

```
수집기（상주, 2s–20s 등급별）
   ↓  Signal로 정규화（지문 중복 제거, DB 저장）
집계（같은 일을 하나의 Incident로 접어서, 카운트만 증가하고 행 수는 증가하지 않음）
   ↓
이벤트 센터（당신이 보는 목록）
   ↓  family + 심각도 기준으로 정책 매칭
정책 엔진（shadow는 분석만 / assist는 읽기 자동, 쓰기는 승인 필요 / auto는 화이트리스트 자동）
   ↓
Agent 다단계 조사（ReAct, 도구 호출 건별 기록）
   ↓  동작은 쓰기 예산 + 쿨다운 + 위험 등급 제약을 받음
검증（선택적 검증: 동작이 실제로 적용되었는지 확인）
   ↓  검증 실패 시 자동으로 한 번 재시도
기록（이벤트 → 실행 → 건별 동작 → 보고서 → 섀도 복기）
```

## 수집기

여섯 가지 상주 수집, 전부 읽기 전용:

| 수집기 | 관찰 대상 | 일반 등급 |
|---|---|---|
| 로그 폭증 | 시간별 버킷 EWMA 베이스라인 + 20MB/min 하드 임계값, 해당 파일을 보유한 프로세스 역추적 | high |
| 로그인 이상 | 비업무 시간대, 최초 등장 IP, 브루트포스 후 성공, `authorized_keys` 방금 변경됨 | high |
| Web 디렉터리 스크립트 생성 | 14종 WebShell 특징, 강한 특징은 즉시 high | high |
| 의심 프로세스 파생 | Web 사용자가 shell / curl / python 실행, 채굴 프로세스명 | critical |
| 비정상 외부 연결 | 예상치 못한 대상과 포트로의 아웃바운드 연결 | high |
| 지표 알람 | CPU / 메모리 / 디스크 / 부하 / 서비스 상태 등 24개 규칙 | medium–high |

수집 주기는 카테고리별로 등급이 나뉘며(2s–20s), 전부 폴링 또는 파일 읽기 방식으로, 상주 agent 프로세스가 필요 없고 시스템 설정도 변경하지 않습니다.

## 이벤트 집계: 하나인가 여러 개인가

같은 대상에서 문제가 반복적으로 발생하면 반드시 하나의 이벤트에 카운트를 붙여야 하며, 화면을 도배해서는 안 됩니다. 규칙:

| 시나리오 | 동작 |
|---|---|
| 동일 객체의 반복 변화(설정 변경, 서비스 재시작 루프) | 미처리 기간 동안 계속 접힘, `次数` 증가 |
| 동일 시나리오의 여러 소스(10개 IP 브루트포스) | 하나로 접힘, 구성원 목록 펼치기 가능(최대 50, 총수는 실제대로 기록) |
| **지표 알람 / 로그 폭증** | **이벤트가 처리되지 않는 한 계속 접힘**——아무도 처리하지 않은 알람은 「하나의 할 일」이지, 10분마다 새로운 이벤트가 아님 |
| 로그인 이상(성공 로그인) | 동일 IP는 반나절 내 접힘, 날짜가 바뀌면 새로운 관측으로 간주 |
| 무시됨 / 처리된 후 다시 발생 | **새로 하나 생성**, 기존 이벤트에 병합하지 않음 |

> v1.4 이전에는 지표 알람이 10분 윈도우로 분할되어, 하나의 CPU 규칙이 하룻밤에 8개의 미처리 항목을 만들어낼 수 있었습니다. 이제는 「미처리 시 계속 접힘」으로 변경되어, 한 번의 알람은 한 줄입니다.

## 정책 엔진

정책은 **데이터**이며(패널에서 추가·삭제·수정 가능), 코드가 아닙니다. 각 정책은 다음을 결정합니다: 어떤 시나리오인지, 어떤 등급부터 시작할지, 어떤 모드를 사용할지, 얼마만큼의 예산을 줄지.

세 가지 모드:

| 모드 | 읽기 작업 | 쓰기 작업 | 적용 |
|---|---|---|---|
| `shadow` 섀도 | 자동 | **일괄 거부**, "어떻게 할 예정인지"만 기록 | 새 시나리오는 먼저 2주간 관찰 |
| `assist` 지원 | 자동 | 팝업/사용자 승인 대기 | 기본 권장 |
| `auto` 자동 | 자동 | **화이트리스트 내 저위험 동작만** 자동 실행 | 충분히 검증된 시나리오 |

여섯 가지 내장 정책:

| 정책 | 시나리오 | 기본 모드 | 할 수 있는 것 |
|---|---|---|---|
| `webshell-respond` | WebShell | assist | 포렌식 → 파일 격리, 프로세스 동결, 임시 IP 차단(모두 복원 가능) |
| `auth-anomaly` | 로그인 이상 | assist | 포렌식 → 출처 IP 임시 차단 |
| `proc-anomaly` | 의심 프로세스 | assist | 포렌식 → 동결(kill 아님) |
| `log-growth` | 로그 폭증 | shadow | 누가 쓰고 있는지, 왜 쓰는지 찾아내고 어떻게 할 예정인지만 기록 |
| `net-anomaly` | 이상 외부 연결 | shadow(기본 비활성) | 읽기 전용 조사 |
| `change-review` | 의심 변경 | shadow(강제) | 이번 수정이 악의적인지 판단하고 롤백/허용 제안 |

각 정책에는 네 가지 예산 상한과 하나의 쿨다운이 있습니다: **쓰기 동작 상한, 최대 단계 수, 최장 실행 초 수, 최대 token 수, 쿨다운 초 수**. 어느 하나라도 초과하면 이번 라운드는 즉시 종료되고 사실대로 기록됩니다.

쿨다운이 발동 중일 때 이벤트에는 "정책 X에 매칭되었으나 해당 정책이 쿨다운 중(남은 N)이므로 이번에는 자동 분석을 하지 않습니다. 수동으로 판단하십시오"라고 명시됩니다——조용히 건너뛰지 않습니다.

## 공격 체인

단일 이벤트는 놓치기 쉽습니다. WebShell이 02:10에 생성되고, 의심스러운 프로세스가 02:14에 나타나며, 외부 연결이 02:20에 발생하면 세 개의 독립 이벤트는 세 가지 별개의 사건처럼 읽힙니다. 공격 체인은 이들을 하나의 침해로 연결합니다.

다섯 단계: **초기 접근 → 실행 및 생성 → 지속성 확보 → 외부 연결 제어 → 영향**.

연관 근거(모두 설명 가능하고 논쟁 가능):

- 공유 지표(동일 IP, 동일 경로 루트, 동일 도메인)
- 시간 근접성(15분 이내가 가장 강함, 1시간 이내는 약한 증거로 간주)
- 단계 진행(새 단계 추가 시 가점, 단계 역행은 더 강한 공유 지표가 있어야 허용)
- 종합 점수 ≥ 0.45여야 병합

의도적으로 엄격하게 설정한 몇 가지 규칙:

- **단독 브루트포스는 체인을 열지 않습니다**. 모든 공인 호스트는 매일 스캔당하므로 실패한 로그인을 "공격 체인의 시작점"으로 삼으면 이 기능은 즉시 신뢰성을 잃습니다. 이후에 생성/외부 연결이 나타나야만 병합합니다
- **지표 알람, 로그 급증은 절대 체인에 포함되지 않습니다**. 이들은 증상이지 단계가 아닙니다
- **변경 사항은 기본적으로 체인에 포함되지 않습니다**. 단, 다음 조건을 모두 충족할 때만: 규칙 재검토에서 의심스러운 것으로 판정 + 재시작을 견딜 수 있는 위치(`authorized_keys`, cron, systemd, sudoers, `ld.so.preload`, PAM, profile 등)를 변경 + 체인에 이미 생성 또는 외부 연결이 나타난 경우
- **세 단계 이상이거나 "실행 및 생성 + 외부 연결 제어"가 동시에 나타날 때**만 critical로 승격하고 알림

> 공격 체인은 주의 우선순위만 높입니다. **Agent의 권한을 확대하지 않습니다**: 예산, 모드, 사용 가능한 도구는 일절 변경되지 않으며, "공격 체인에 속한다"는 이유로 더 많은 쓰기 작업이 허용되지도 않습니다.

## 처리 트랜잭션: 작업은 되돌릴 수 있거나, 불가능함을 명확히 밝혀야 함

Agent가 쓰기 작업을 실행할 때, 각 항목을 처리 트랜잭션 로그에 기록합니다:

- **가역 작업**(파일 격리, 프로세스 동결, IP 차단, 로그 절단, 스냅샷 생성)은 처리 실패 시 **역순 롤백**
- **비가역 작업**(파일 삭제, 명령 실행, 설정 변경)은 롤백할 수 없으며, 보고서에 「N개 항목 되돌릴 수 없음, 수동 확인 필요」라고 명확히 기재합니다 — 롤백된 것처럼 가장하지 않습니다
- 롤백 결과는 사실대로 세 가지로 분류합니다: 철회됨 / 철회 불가 / 롤백 실패

이벤트 상세 페이지에서 롤백되지 않은 작업에 대해 직접 「롤백」을 클릭할 수 있으며, Agent를 기다릴 필요가 없습니다.

## 섀도우 복기

`shadow` 모드로 실행한 처리는 사후에 자동 복기가 한 건 생성됩니다: **사실**을 보고 당시 그 계획이 여전히 필요한지 판단합니다.

| 결론 | 의미 |
|---|---|
| `would_help` | 당시 실행한 것이 실제로 유용했음 (문제가 지속적으로 존재) |
| `unnecessary` | 당시 하지 않은 것도 옳았음 (문제가 스스로 해결됨 / 오탐이었음) |
| `unknown` | 증거가 불충분하여 결론을 내리지 않음 |

이는 「섀도우 모드」를 「보기만 하고 연습하지 않음」에서 「연습하면 누군가 첨삭해 줌」으로 바꾸는 핵심입니다: 연속으로 여러 건의 `unnecessary`는 정책 임계값이 너무 낮게 설정되었음을 의미하므로 낮춰야 하고, 연속된 `would_help`는 assist로 승격할 수 있음을 의미합니다.

## 피드백 억제

동일한 이벤트 그룹이 7일 이내에 수동으로 2회 무시된 경우, 이후 동일 유형은 **더 이상 Agent를 깨우지 않습니다**(여전히 기록되고, 여전히 목록에 나타나지만, 자동 분석만 하지 않습니다).

이유는 명확합니다. 한 번 무시하는 것은 일시적인 상황일 수 있지만, 두 번 무시하는 것은 설정 문제입니다. 이 규칙은 "당신이 관심 없는 알람"이 더 이상 토큰을 소모하지 않도록 합니다.

## 변경 유형 이벤트의 철칙

정책을 어떻게 구성하든, `family=change`의 이벤트는 **조사만 가능하고 조치는 불가능**합니다:

- 강제로 shadow로 강등하고, 쓰기 예산을 0으로 설정하며, 쓰기 도구를 전부 비활성화하고, 단계 상한을 8로 설정

이것은 결벽이 아니라 공격 표면입니다. 만약 "모니터링 중인 설정 파일에 쓰기"만으로 Agent가 조치를 실행할 수 있다면, 이는 공격자에게 원격 트리거 경로를 하나 더 제공하는 것과 같습니다.

## 패널 사용 방법

「이벤트 센터」 페이지 상단의 여섯 가지 필터에는 모두 카운트가 표시됩니다:

| 필터 | 확인할 내용 |
|---|---|
| 처리 대기 | 이미 발생했지만 아직 아무도 처리하지 않음 |
| 깨우기 대기 | 아직 트리거 조건에 도달하지 않았고 후속 신호를 기다리는 중 |
| 전체 | 필터링 없음 |
| 처리 완료 | 조사 완료 또는 수동으로 해결 표시 |
| 실패 | 실행 실패 / 검증 미통과 |
| 무시됨 | 관리할 필요가 없다고 판단함 |

이벤트 상세에서 드릴다운할 수 있습니다: 연관 신호, Agent 실행 기록, 개별 액션 체인(도구, 파라미터, 판정, 원시 출력), 보고서, 공격 체인 컨텍스트.

두 가지 수동 작업:

- **무시**: 관리할 필요가 없다고 표시하고, 피드백 억제 통계에 반영
- **내가 직접 처리**: 「이 일은 내가 직접 처리하겠다」고 선언하면 Agent가 더 이상 자동으로 행동하지 않음(새 신호는 계속 기록됨)

## 스케줄링 및 기록

- 매 실행마다 `AgentRun` 기록을 하나 남깁니다 (모드, 단계 수, 도구 수, 쓰기 횟수, 소요 시간, 결론, 재시도 여부)
- 보고서는 단일 파일 HTML로 보관되며, 이벤트별로 열거나 다운로드할 수 있습니다
- 모든 동작(도구 호출, 승인, 거부, 롤백)은 감사 로그에 기록됩니다

## 한 문장 경계

OpsMini는 무인 root 자율 에이전트를 **제공하지 않습니다**. 목표 형태는 「자율 조사 + 등급별 권한 부여」입니다. Agent는 발견, 증거 수집, 판단, 제안을 담당하고, 파괴적 작업은 사람이 권한을 부여하거나 화이트리스트로 제한합니다.
