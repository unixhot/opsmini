# 호스트 보안 설계

> 이 문서는 **「호스트 보안」이라는 기능이 어떻게 설계되고 구현되었는지** 설명합니다: 각 점검이 무엇을 보는지, 판단 기준은 무엇인지, 점수는 어떻게 계산하는지, 경계는 어디인지, 왜 이렇게 선택했는지.
>
> 대응 코드: `internal/service/{security,baseline,loginsecurity,firewall,fim,threat,securitymonitor}.go`, `internal/api/v1/{security,baseline,fim,threat,firewall}.go`, `internal/router/router.go`.

---

## 1. 설계 목표 및 비목표

### 목표

| 목표 | 구체적 의미 |
| --- | --- |
| **제로 의존성** | agent를 설치하지 않고, 커널 모듈에 의존하지 않으며, 중앙 서비스에 연결하지 않고, 바이너리만 있으면 바로 점검 가능 |
| **설명 가능** | 모든 탐지 항목을 펼쳐서 「어떤 파일을 읽었고, 어떤 값을 보았으며, 왜 불합격으로 판정했고, 어떻게 수정할 것을 권장하는지」 확인 가능 |
| **실행 가능** | 문제를 발견한 후 패널에서 직접 수정 가능 (방화벽 변경, 점검 실행, 베이스라인 재구축, 위협 처리 완료 표시) |
| **사람에게도, AI에게도** | 동일한 결론을 페이지로 렌더링하는 동시에 읽기 전용 도구로 내장 Agent에 제공 |
| **권한 남용 없음** | 읽기 전용 기능은 로그인만 하면 사용 가능하며, 시스템을 변경하는 모든 동작은 별도의 권한 포인트 + root 신원 필요 |

### 비목표 (트레이드오프이며, 미완성이 아님)

- **HIDS 대체품이 아님**: 커널 syscall 훅을 만들지 않고, eBPF 프로브를 만들지 않으며, 전流量 탐지를 하지 않음. 이러한 기능은 상시 고권한 수집이 필요하며, "단일 바이너리, 수십 MB, 간편 설치"라는 포지셔닝과 충돌함.
- **다중 호스트 상황 판단을 하지 않음**: 단일 호스트에 대해 단일 호스트 결론을 제공함. 여러 호스트의 집계는 OpsMini Server / Proxy의 역할임.
- **자체 규칙 라이브러리 엔진을 갖지 않음**: 베이스라인 판단 기준은 코드에 작성되어 있으며(14개 항목), YAML 규칙 핫 로딩을 허용하지 않음. 규칙 핫 로딩은 유연해 보이지만 "왜 이 호스트가 62점인지"를 재현할 수 없게 만듦. 규칙 외부화는 발전 방향임(§16 참조).
- **전문 컴플라이언스 스캔을 대체하지 않음**: 등급보호/CIS의 전체 항목 커버리지와 증적 발급을 하지 않으며, "일상적으로 확인 가능하고 실행 가능한" 부분만 수행함.

## 2. 기능 맵

호스트 보안 페이지는 여섯 개의 탭으로 구성되며, 본질적으로 **다섯 개의 탐지 모듈 + 하나의 요약 뷰**입니다:

| 탭 | 탐지 대상 | 데이터 출처 | 트리거 방식 | 시스템 변경 여부 |
| --- | --- | --- | --- | --- |
| 보안 개요 | 요약 집계: 총점, 등급, 다섯 모듈 점수 및 한 줄 결론 | 나머지 다섯 모듈의 저장 결과 | 페이지 열기 | 아니오 |
| 베이스라인 점검 | 14개 호스트 강화 현황 | `/etc/ssh/sshd_config`、`/etc/passwd`、`/etc/shadow`、`/etc/login.defs`、crontab、리스닝 포트 | 수동으로 「점검 시작」 클릭 | 아니오 |
| 로그인 보안 | 무차별 대입, 비정상 로그인, SSH 강화 권장 사항 | `/var/log/auth.log` 또는 `/var/log/secure` | 페이지 열기 | 아니오 |
| 방화벽 | 현재 백엔드 및 규칙; 포트 허용/차단, 시작/중지 | `ufw` / `firewall-cmd` / `iptables`의 실제 상태 | 수동 조작 | **예** |
| 파일 무결성 | 핵심 파일의 변경/삭제 여부 | 8개 시스템 핵심 파일의 SHA256 | 백그라운드에서 60초마다 | 아니오 |
| 위협 탐지 | 채굴 프로세스, 의심스러운 예약 작업, 의심스러운 자동 시작 | `/proc`、crontab、`/etc/rc.local`、systemd 서비스 목록 | 백그라운드에서 5분마다 + 수동 | 아니오 (처리는 사람이 수행) |

설계상의 명확한 결정: **방화벽만이 시스템을 변경합니다**. 나머지 네 모듈은 순수 관찰자로서, 오판이 발생하더라도 점수가 나빠질 뿐 머신에 문제가 생기지는 않습니다.

## 3. 아키텍처: 서로 독립적인 두 개의 경로

OpsMini에는 보안과 관련된 두 가지 시스템이 있으며, 겉보기에는 비슷해 보이지만 실제로는 두 개의 독립적인 경로입니다:

```
                  ┌──────────── 점검 경로（pull，사람이 보는 용도） ────────────┐
  /etc、/proc ───▶ │ BaselineService  로그인 분석  FIM  위협 스캔        │ ──▶ SQLite ──▶ 보안 페이지 + 점수
  인증 로그        │ SecurityService  종합 점수 산정                        │
                  └──────────────────────────────────────────────────┘

                  ┌──────────── 감지 경로（push，Agent용） ──────────┐
  auth.log、사이트   │ sentinel 수집기（logwatch/authwatch/           │ ──▶ 신호 ──▶ 이벤트 ──▶ 정책
  디렉터리、프로세스 목록     │ filewatch/procwatch/netwatch/metricwatch）      │        ──▶ Agent 처리
                  └──────────────────────────────────────────────────┘
```

**왜 하나로 합치지 않고 두 개로 나누었는가?**

| 차원 | 점검 경로 | 감지 경로 |
| --- | --- | --- |
| 상호작용 모델 | 풀: 페이지를 열거나 스캔을 클릭 | 푸시: 수집기가 항상 실행 중 |
| 출력 | 목록 + 점수（장기 보존 가능한 상태 스냅샷） | 신호 → 이벤트（시효성이 있는 스트림） |
| 소비자 | 사람 | 정책 엔진 + AI Agent |
| 판정 성격 | 「현재 상태가 규정을 준수하는가」 | 「방금 무슨 일이 발생했는가」 |
| 오판 비용 | 점수가 나빠짐 | 자동 처리가 트리거될 수 있음 |

합치면 양쪽이 서로 발목을 잡게 됩니다: 점검은 언제든 재계산할 수 있어야 하고, 감지는 지속적으로 증분 처리해야 합니다. 한 경로에 상태 머신을 추가하면 다른 경로도 강제로 그것을 끌고 가야 합니다.

**비용도 분명히 밝혀야 합니다**: 두 경로가 각각 인증 로그를 파싱하며（`service/loginsecurity.go`와 `sentinel/authwatch.go`은 두 세트의 정규식입니다）, 기준이 어긋날 위험이 존재합니다. 이는 알려진 기술 부채이며, §16을 참조하십시오.

## 4. 보안 점수 모델

총점 100점, 다섯 개 모듈의 고정 가중치:

| 모듈 | 만점 | 이 가중치인 이유 |
| --- | --- | --- |
| 베이스라인 점검 | 40 | 유일하게 「당신이 주도적으로 개선할 수 있는」 부분이며, 일상 운영 수준을 가장 잘 반영함 |
| 로그인 보안 | 20 | 공인망 호스트의 사고는 십중팔구 여기서 시작됨 |
| 방화벽 | 15 | 있거나 없거나, 노출 면을 직접 결정함 |
| 파일 무결성 | 15 | 핵심 파일이 변경되었다는 것은 보통 이미 침해당했다는 의미임 |
| 위협 탐지 | 10 | 가중치가 낮은 이유는 오탐이 가장 쉽기 때문임 (§10 참조) |

### 각 모듈 채점 규칙 (코드와 일대일 대응)

**베이스라인 (0–40)**: 항목 수가 아니라 가중치로 가중합산함.

```
got   = Σ(pass 항목 가중치) + Σ(warn 항목 가중치 × 0.5)
total = Σ(전체 항목 가중치) = 32
점수  = int(40 × got / total)
```

삼태 의미: `pass`는 만점, `warn`은 반점, `fail`는 0으로 계산함. warn이 존재하는 이유는 일부 항목이 「하지 않았지만 틀린 것은 아닌」 경우이기 때문임 (예: SSH가 여전히 22 포트를 사용: 위험은 실제이지만 흔한 일이라 바로 0점을 주면 점수의 변별력이 사라짐).

**로그인 보안 (0–20)**:

| 상황 | 점수 |
| --- | --- |
| 무차별 대입 미탐지, 24h 내 실패 없음 | 20 |
| 24h 내 실패 로그인 있으나 무차별 대입 임계값 미달 | 16 (고정 4점 감점) |
| 무차별 대입 의심 대상 n개 탐지 | `20 − 5n`, 하한 0 |

**방화벽 (0–15)**: 활성화 15, 미활성화 0. 이원 판정, 중간 상태 없음.

**파일 무결성 (0–15)**: `15 − 3n` (n = 24h 내 변경 건수), 하한 0. 변경 1건당 3점 감점은 핵심 파일 5개를 변경하면 0점이 된다는 의미임.

**위협 탐지 (0–10)**: 10에서 시작하여 감점, `critical` 5점 감점, `warning` 2점 감점, 기타 1점 감점, 하한 0.

### 등급 매핑

| 점수 | 등급 |
| --- | --- |
| ≥ 90 | 우수 |
| ≥ 75 | 양호 |
| ≥ 60 | 보통 |
| < 60 | 위험 |

### 이 모델의 트레이드오프

- **자산 가치 가중치를 주지 않음**: OpsMini는 이 머신에서 어떤 업무가 돌아가는지 알지 못하며, "중요도 계수"를 추측하는 것은 점수를 미신으로 만들 뿐임.
- **CVSS를 사용하지 않음**: CVSS는 취약점 심각도를 평가하는 것이고, 여기서는 호스트 설정과 운영 현황을 평가하는 것으로, 둘은 같은 것이 아님.
- **마이너스 점수를 두지 않음**: 단일 항목이 0에서 멈추므로, 한 모듈이 전체를 끌어내려 점수가 의미를 잃는 것을 방지함.
- **점수 재현 가능**: 입력이 같고 코드가 같으면 점수는 반드시 같음. 이것이 「수정 후 다시 확인」 비교에 활용할 수 있는 전제임.

## 5. 베이스라인 점검

### 실행 방식

한 번의 스캔으로 하나의 `ScanID`(나노초 타임스탬프)를 생성하고, 14개 항목의 결과를 각각 한 줄씩 `baseline_results`에 기록하며, 페이지에는 **최신 배치**만 표시되고 과거 배치는 데이터베이스에 남아 비교할 수 있습니다.

순수 파일 파싱 방식으로, `lynis` / `oscap` 같은 외부 도구를 호출하지 않습니다. 해당 도구들은 최소화된 시스템에 존재하지 않는 경우가 많고 출력을 구조화하기 어렵기 때문입니다.

### 판정 세부 사항

- `sshd_config`는 메인 파일과 `/etc/ssh/sshd_config.d/*.conf`를 동시에 읽습니다(최신 배포판은 설정을 drop-in 디렉터리로 분리하므로 메인 파일만 읽으면 오판합니다).
- 「명시적으로 설정되지 않음」과 「명시적으로 잘못 설정됨」을 구분합니다. 전자는 `warn`(배포판 기본값이 불확실함)을, 후자는 `fail`을 부여합니다.
- `/etc/shadow`, `/etc/passwd`는 텍스트를 직접 파싱하며 NSS 설정에 의존하지 않습니다. LDAP/SSSD가 관여하는 머신에서 판정이 흔들리는 것을 방지합니다.
- 고위험 포트는 고정 목록을 사용합니다: `23 Telnet`, `445 SMB`, `135 RPC`, `1433 MSSQL`, `3389 RDP`.

전체 14개 항목 목록은 [부록 A]](#附录-a基线-14-项清单)를 참조하십시오.

### 가중치를 코드에 하드코딩한 이유

가중치를 바꾸면 점수가 바뀝니다. 가중치를 설정 가능하게 하면 동일한 머신이 두 고객사에서 서로 다른 점수를 받게 되어 "점검"의 공신력이 사라집니다. 가중치를 조정하려면 코드 리뷰를 거쳐야 합니다.

## 6. 로그인 보안

### 데이터 소스와 오버헤드

인증 로그의 테일만 읽기 전용으로 조회합니다: `tail -n 5000`, `/var/log/auth.log`(Debian 계열)을 우선하고 그다음 `/var/log/secure`(RHEL 계열)을 사용하며, 없으면 오류를 반환하지 않고 빈 보고서를 반환합니다. 로그는 수백 MB에 달할 수 있어 전체를 읽으면 메모리가 터집니다.

**통계 윈도우를 정확히 말해야 합니다**: 구현상의 윈도우는 「로그 테일 5000줄」이며, 엄격한 시간 윈도우가 아닙니다. 필드명은 `failed_count_24h` / `success_count_24h`를 그대로 따랐는데, 스캔에 노출된 공인 IP 머신은 5000줄이 24시간도 안 되는 경우가 많고, 조용한 머신은 5000줄이 며칠치일 수 있기 때문입니다. 이 편차는 알려진 문제이며(§15), 엄격한 24시간 필터를 하지 않은 이유는 아래와 같습니다.

### 세 가지 판별 기준

| 판별 기준 | 규칙 | 출력 |
| --- | --- | --- |
| 무차별 대입 | 동일 계정이 통계 윈도우 내에서 실패(`Failed password` 및 `Invalid user` 포함) **누적 ≥ 5회** | 계정명 + 횟수 + 관련 IP 목록, 횟수 내림차순 |
| Top 실패 소스 | IP별로 실패 횟수를 집계하여 상위 10개 추출 | IP + 횟수 |
| 비정상 로그인 | 성공 로그인 중 `user == root` | 시간 + 사용자 + IP + 사유 「root 계정 직접 SSH 로그인」 |

SSH 강화 권장 사항은 문구를 하드코딩하지 않고, 현재 `sshd_config`을 읽어 각 항목이 이미 적용되었는지 판단합니다(`PermitRootLogin`, `PasswordAuthentication`, 포트 변경, Protocol 2). 페이지에는 「적용됨/미적용」을 바로 표시합니다.

### GeoIP와 UA 분석을 하지 않는 이유

오프라인 환경은 필수 요건입니다. 내부망에 설치할 수 있고, 인터넷에 연결되지 않으며, 외부 서비스로 로그를 보내지 않는 보안 패널이, 예쁜 세계 지도를 그릴 수 있지만 인터넷 연결이 필요한 패널보다 더 유용합니다. 그래서 비정상 판정은 본机에서 확인 가능한 사실(시간, 계정, IP 빈도)에만 의존합니다.

### 엄격한 24시간 필터를 하지 않은 이유

`syslog`의 타임스탬프에는 연도가 없으므로(`Aug 14 07:00:01`), 시간으로 필터링하려면 연도를 추론하고 연도 경계 넘김을 처리해야 합니다. 자정 0시 전후, 컨테이너 간 타임존 불일치, logrotate로 로그가 잘리는 경우 모두 추론을 틀리게 만듭니다. 1년을 틀리면 전체 이력을 「방금」으로 계산하게 됩니다.

「테일 N줄」로 시간 윈도우를 대체하면 윈도우 길이가 유동적이라는 대가가 있지만, **시간 파싱 오류로 인한 오판이 절대 발생하지 않는다**는 장점이 있습니다. 정확성이 정말 필요하다면, 정석은 인지 계층이 `observed_at`에 따라 DB에서 윈도우 쿼리를 수행하는 것이며(원래 시간이 포함되어 있음), 이것이 §16에서 통합 사실 계층을 만든 동기 중 하나입니다.

### 임계값 5에 대한 설명

5회 미만은 대부분 사람이 비밀번호를 잘못 입력한 것입니다. 5회 이상이 24시간 이내에 동일한 IP 대역에서 발생해야 "시도 중"이라는 특징을 갖습니다. 이 임계값은 실제 공인 IP 머신에서 대량 스캔에 의해 쉽게 초과되는데, 바로 이것이 이 임계값의 용도입니다: **정확한 식별을 위한 것이 아니라, 이 머신이 스캔당하고 있음을 알려주기 위한 것입니다**.

## 7. 방화벽

### 백엔드 자동 감지

시스템에 무엇이 설치되어 있는지 가정하지 않고, 실제 상태를 읽어 백엔드를 결정합니다:

| 백엔드 | 판정 | 지원되는 쓰기 작업 |
| --- | --- | --- |
| `ufw` | `ufw status` 읽기 가능 | 포트 허용/차단, 활성화, 비활성화, 번호로 규칙 삭제 |
| `firewalld` | `systemctl is-active firewalld` | 포트 허용/차단(`--permanent` + `--reload`), 활성화, 비활성화 |
| `iptables` | 규칙 체인 존재 | 포트 허용/차단(`-I INPUT 1`), 번호로 규칙 삭제; **패널 내 비활성화 미지원** |

`iptables` 백엔드는 의도적으로 「비활성화」를 제공하지 않습니다: 규칙 체인을 비우는 것은 모든 머신을 무방비 상태로 만드는 것과 같아 파괴성이 너무 높기 때문에, 사용자가 직접 머신에 접속해 작업하도록 요구합니다.

### 잠금 방지 설계 (이 모듈에서 가장 중요한 항목)

**방화벽을 활성화하기 전에, 먼저 패널 자체 포트와 SSH 22를 자동으로 허용**한 다음 `enable`합니다.

순서를 바꾸면 안 됩니다. 순서를 바꾸면 고전적인 사고가 됩니다: 방화벽을 켜는 순간 8888과 22가 동시에 차단되어 콘솔만 사용할 수 있게 됩니다. `panelPort`은 시작 시 설정에서 주입되며, 하드코딩된 8888이 아닙니다.

### 파라미터 검증 및 타임아웃

| 방어선 | 방식 |
| --- | --- |
| 권한 | 모든 쓰기 작업 `requireRoot()`, 비 root는 즉시 `ErrNeedRoot` 반환 |
| 포트 | `int` 타입 + 1–65535 범위 검증, 문자열 불허 |
| 프로토콜 | 열거형 `tcp`/`udp` |
| 인젝션 | 전부 `exec.Command(name, args...)`를 통해 처리, shell을 거치지 않아 파라미터가 두 번째 명령으로 조합될 수 없음 |
| 멈춤 | 각 방화벽 명령 10초 타임아웃(`context.WithTimeout`), 실패 시 stderr 원문 반환 |

### Agent 차단과의 관계

시스템에는 두 가지 차단이 있으며, 의도적으로 분리하여 관리합니다:

| 출처 | 저장 위치 | 수명 주기 | 정리 주체 |
| --- | --- | --- | --- |
| 페이지 규칙 (사용자 설정) | `ufw`/`firewalld` 규칙 테이블 | 장기, 사용자가 삭제할 때까지 | 사용자 |
| Agent 차단 (이벤트 기반) | `iptables -I INPUT -s <ip> -j DROP` + `blocked_ips` 테이블 | TTL 적용, 만료 시 자동 해제 | `SweepBlocks()` 자동 해제 |

분리하는 이유: Agent의 차단은 반드시 자동 해제되어야 하며(오탐 차단이 스스로 해결되어야 함), 사용자의 규칙은 자동 해제 로직에 의해 함께 삭제되어서는 안 됩니다. 두 체계는 각자 관리되며, 페이지에서 각각 확인할 수 있습니다.

## 8. 파일 무결성(FIM)

### 모니터링 대상

기본적으로 8개의 시스템 핵심 파일을 대상으로 하며, 최초 시작 시(베이스라인이 비어 있을 때) 자동으로 베이스라인을 생성합니다:

```
/etc/passwd  /etc/shadow  /etc/group   /etc/ssh/sshd_config
/etc/crontab /etc/sudoers /etc/hosts   /etc/resolv.conf
```

이 중 `/etc/passwd`、`/etc/shadow`、`/etc/sudoers`의 변경은 `critical`로 기록되고, 나머지는 `warning`입니다.

### 탐지 루프

60초마다 활성화된 각 항목에 대해 `SHA256 + size + mtime`를 한 번씩 계산합니다:

- 계산 불가(파일 없음) → 「파일 삭제됨」 한 건 기록, `critical` 등급은 경로로 판단
- 해시 불일치 → 「파일 내용 변경됨」 한 건 기록, 신구 해시 포함
- 일치 → 아무것도 하지 않음

### 핵심 설계: 변경 후 베이스라인 자동 전진

변경이 탐지되어 DB에 기록된 후, **베이스라인은 즉시 새 해시로 업데이트됩니다**.

이는 의도된 설계입니다: 베이스라인이 전진하지 않으면 동일한 변경이 60초마다 한 번씩 보고되어 하루 1440건의 알람이 발생하고, 사람은 더 이상 보지 않게 됩니다. 전진시킨 후의 효과는 「한 번의 변경에 한 건의 알람」이며, **다음에 또 변경되면 여전히 보고됩니다**—정말로 반복해서 수정된다면 여전히 확인할 수 있습니다.

대가: 연속된 두 번의 변경이 동일한 60초 윈도우 내에 발생하면 기록은 한 건만 남습니다. 이 정밀도에서는 수용 가능합니다(더 세밀하게 하려면 inotify를 사용해야 하며, §16 참조).

「베이스라인 재구성」은 수동 작업입니다: `sudoers`을 수정한 후 버튼을 한 번 눌러 시스템에 "현재 상태가 맞다"고 알려주는 것입니다.

### 인지 계층 filewatch와의 분업

|  | 보안 페이지 FIM | 인지 계층 filewatch |
| --- | --- | --- |
| 보는 대상 | 8개의 시스템 핵심 파일 | 사이트 루트 디렉터리에 추가된 실행 가능 스크립트 |
| 판단 기준 | 해시 비교 | 확장자 + WebShell 내용 특징(`eval($_POST`、`base64_decode` 등) |
| 목적 | 「시스템이 조작되었음」 발견 | 「웹사이트에 악성 코드가 심어졌음」 발견 |

둘은 중복되지 않으며, 서로를 참조하지도 않습니다.

## 9. 위협 탐지

세 개의 스캐너가 5분마다 한 라운드씩 실행되며, 시작 시 먼저 한 번 실행됩니다.

| 스캐너 | 보는 대상 | 판정 기준 | 레벨 |
| --- | --- | --- | --- |
| 프로세스 | `/proc` 전체 프로세스 (이름 + 명령줄) | 채굴 키워드 적중 (`xmrig`, `minerd`, `kdevtmpfsi`, `kinsing`, `stratum` 등 11개) | critical |
| 프로세스 | 프로세스 실행 파일 경로 | `/tmp` 또는 `/dev/shm`에 위치 (정상 서비스는 여기서 시작하면 안 됨) | warning |
| 예약 작업 | 시스템 + 사용자 crontab | 명령에 `curl`, `wget`, `base64 -d`, `/dev/shm` 포함 | warning |
| 시작 항목 | `/etc/rc.local` 비주석 줄 | `curl`, `wget`, `/tmp` 포함 | warning |
| 시작 항목 | systemd 활성화된 서비스 이름 | `miner`, `xmrig`, `kdevtmpfs` 포함 | critical |

### 중복 제거 및 생명주기

`kind + name` 기준으로 중복 제거: 이미 존재하는 기록에 적중하면 `last_seen`과 상세 정보만 갱신하고 새 항목을 추가하지 않습니다. 상태는 `active` / `resolved`만 있으며, **오직 사람만이 이를 해결됨으로 표시할 수 있습니다**——프로세스가 종료되기 전까지 스캐너는 5분마다 다시 이를 보게 되며, 이것이 바로 우리가 원하는 것입니다 (진짜 위협은 스스로 사라져서는 안 됩니다).

### 이 탐지 방식에 대한 솔직한 평가

키워드 블랙리스트는 **이름만 바꾸면 우회됩니다**, 이는 공공연한 비밀입니다. 따라서 이 기능의 위치는 "모든 채굴을 잡아낼 수 있다"가 아니라 다음과 같습니다:

1. **게으른 공격**을 잡습니다——대다수 봇넷이 침투할 때 사용하는 것은 기성 바이너리이며, 이름조차 바꾸지 않습니다;
2. 「임시 디렉터리 실행 가능」과 같은 **행위 특징**과 결합하여 이름을 바꾼 부분을 커버합니다;
3. 나머지는 인지 계층의 프로세스 행위와 로그인 행위 신호로 보완합니다.

잡아낼 수 있다고 과장하지 않으며, 발견하면 보고하고, 처리는 사람에게 맡깁니다 (또는 사람이 Agent에게 권한을 부여).

## 10. 데이터 모델

| 테이블 | 한 행이 나타내는 것 | 주요 필드 |
| --- | --- | --- |
| `baseline_results` | 한 번의 스캔에서 나온 결과 하나 | `scan_id`(배치), `category`, `item_key`, `status`](pass/fail/warn), `detail`, `suggestion`, `weight` |
| `fim_baselines` | 모니터링 중인 파일의 현재 기준값 | `path`](unique), `sha256`, `size`, `mod_time`, `enabled` |
| `fim_changes` | 한 번의 파일 변경 이벤트 | `path`, `old_sha256`, `new_sha256`, `level`](warning/critical), `message`, `created_at` |
| `threat_findings` | 위협 항목 하나 | `kind`](process/cron/startup), `name`, `detail`, `severity`, `status`, `first_seen`, `last_seen`, `resolved_at` |

설계 요점:

- 베이스라인 결과는 `scan_id` 기준으로 배치 처리되며, **이력을 절대 덮어쓰지 않음**: "지난주와 이번 주"를 비교하고 싶을 때 조회할 수 있다.
- `fim_baselines`과 `fim_changes`는 테이블을 분리한다. 하나는 상태이고 하나는 이력 흐름이라, 한 테이블에 섞으면 "현재 기준값"과 "변경 이력"이 서로 오염된다.
- `threat_findings`에는 `first_seen/last_seen`가 있어, 방금 나타난 것인지 아니면 사흘째 방치된 것인지 한눈에 알 수 있다.
- 별도의 보안 라이브러리 파일은 없으며, 전부 `opsmini.db`에 저장되어 백업을 따라간다(패널의 다른 데이터와 동일).
- 테이블 이름 주의: 보안 베이스라인 결과는 `baseline_results`이고, 인지 계층의 「학습 베이스라인」(EWMA 기댓값)은 `baselines`이며, 둘은 무관하니 혼동하지 말 것.

## 11. API 및 권한

모든 인터페이스는 `/api/v1` 하위에 있으며, JWT 인증 후 접근할 수 있습니다. 쓰기 작업은 여기에 권한 포인트가 추가로 적용됩니다.

| POST | `/security/firewall/port` | 포트 허용 | `security.firewall` |

## 12. 패널 자체의 보안 경계

보안 모듈 자체도 공격 표면이므로:

| 위험 | 처리 |
| --- | --- |
| 명령 주입 | 모든 외부 명령은 `exec.Command` + 매개변수 배열로만 실행하며, 셸을 조합하지 않음; 포트는 `int`, 프로토콜은 열거형 |
| 권한 상승 | 쓰기 작업은 먼저 `requireRoot()`, 비 root는 즉시 거부하며 "최선을 다하는" 방식은 하지 않음 |
| 장시간 멈춤 | 외부 명령 10초 타임아웃 |
| 자기 잠금 | 방화벽 활성화 전에 패널 포트와 22를 먼저 허용 |
| 프라이버시 | 로그에서 로그인 이벤트만 읽으며, 비밀번호와 명령 전문은 저장하지 않음(판정에만 쓰이는 필드만 DB에 저장) |
| 권한 외 호출 | 모든 쓰기 인터페이스에 독립적인 권한 포인트가 있으며, 프런트엔드에서 버튼을 숨기는 방식으로 "제어"하지 않음 |

## 13. 성능 및 리소스 오버헤드

| 동작 | 오버헤드 | 설명 |
| --- | --- | --- |
| 베이스라인 점검 | 14회의 작은 파일 읽기 + 한 번의 포트 테이블, 밀리초 수준 | 사용자가 클릭할 때만 실행 |
| 로그인 분석 | `tail -5000` 1회, 단일 실행 < 50ms | 페이지를 열 때 실행, 캐시하지 않음 |
| FIM 점검 | 8개 파일 SHA256, 60초마다 | 전부 KB급 작은 파일, CPU 무시 가능 |
| 위협 스캔 | `/proc` 수백 개 프로세스 순회 + crontab + systemctl 1회, 5분마다 | 유일한 "무거운" 동작, 여전히 수백 밀리초 수준 |
| 상주 메모리 | 추가 캐시 없음, 전부 동일한 SQLite 연결 사용 | 독립 프로세스 없음, 백그라운드 큐 없음 |

상주 샘플러도 없고 추가 goroutine 풀도 없습니다: FIM과 위협 스캔은 하나의 루프를 공유하며(`SecurityMonitor`), 하나의 ticker가 한 가지 일을 담당합니다.

## 14. 자율 Agent와의 관계

세 곳의 인터페이스는 모두 **단방향으로 사실만 제공**하며, "보안 모듈이 Agent를 지휘한다"는 식의 결합은 존재하지 않습니다:

| 방향 | 형태 | 설명 |
| --- | --- | --- |
| 보안 → AI | 읽기 전용 도구 `security_status` | Agent는 「점수 + 5개 모듈 요약」을 읽어 "이 머신은 안전한가"에 답할 수 있으며, 도구는 `RiskReadonly` + `security.view`입니다 |
| 보안 → AI (쓰기) | 도구 `firewall_rule` | 방화벽 변경은 쓰기 작업으로, L1/L2 등급을 거치며 확인이 필요합니다 |
| 인지 계층 → Agent | 신호 → 이벤트 → 정책 | sentinel이 독립적으로 담당하며, 본 절의 보안 모듈과 상태를 공유하지 않습니다 |

**현재 하지 않는 일(의도적임)**: 위협 탐지 결과와 FIM 변경은 이벤트 버스에 넣지 않습니다. 그 이유는 이 두 가지 결과의 오탐률이 인지 계층의 신호(키워드 매칭, 베이스라인 자동 전진 모두 노이즈를 발생시킴)보다 높아, 자동 처리 정책에 직접 투입하기에는 위험이 너무 크기 때문입니다. 오탐률에 대한 실측 데이터가 확보된 후에 연결할 예정이며, §16을 참조하십시오.

## 15. 알려진 제한 사항

| 제한 사항 | 영향 | 비고 |
| --- | --- | --- |
| 커널 수준 탐지 없음 | rootkit, 숨겨진 프로세스(`/proc`가 hook된 경우)를 볼 수 없음 | 설계 방침상 의도적으로 미구현 |
| FIM이 8개 파일만 커버 | 사용자 정의 경로, 디렉터리 재귀, 신규 파일 모니터링 모두 없음 | 현재는 인지 계층 filewatch로 사이트 디렉터리를 보완 |
| 위협 탐지가 키워드 기반 | 이름만 바꾸면 우회 가능 | §9의 솔직한 평가 참조 |
| 베이스라인 14개 항목 고정 | 등급보호/CIS 전체 항목을 커버할 수 없음 | 발전 방향은 규칙 외부화 |
| 점수에 비즈니스 중요도 미반영 | 테스트 머신과 핵심 데이터베이스 서버가 동일 점수 | 미구현, 주관적 요소 배제 |
| 인증 로그 형식 의존 | rsyslog/journald 텍스트 형식이 아닌 머신에서는 읽지 못할 수 있음 | 호환성은 `/var/log/secure`로 보완 |
| 로그인 통계 윈도우 부동 | `tail -5000` 행, 엄격한 24시간 아님(필드명은 24h 유지) | §6 「왜 엄격한 24시간 필터링을 하지 않았는가」 참조 |
| 두 가지 로그 파싱 | 보안 페이지와 인지 계층의 기준이 어긋날 수 있음 | 알려진 기술 부채 |
| 보고서 내보내기 없음 | 페이지만 볼 수 있고 PDF/HTML 컴플라이언스 보고서를 출력할 수 없음 | 발전 방향 |

## 16. 발전 방향

우선순위에 따라:

1. **FIM 구성 가능**: 사용자 정의 경로, 디렉터리 재귀, 화이트리스트(`/etc/` 하위에서 빈번하게 변경되는 파일은 먼저 제외)를 지원하고, inotify 이벤트 기반으로 60초 폴링을 대체합니다.
2. **베이스라인 규칙 외부화**: 14개 항목 → YAML 규칙 패키지로 전환하고, CIS / 등보 2급 항목 세트 가져오기를 지원하며, 동시에 "현재 어떤 규칙 세트를 사용 중인지"를 결과에 기록하여 점수를 재현 가능하게 보장합니다.
3. **통합 로그 팩트 계층**: `service/loginsecurity.go`과 `sentinel/authwatch.go`가 하나의 파서를 공유하여 기준 불일치를 제거합니다.
4. **위협 탐지 강화**: `ausearch`(auditd 감사 로그)와 선택적 YARA 규칙을 연동하여 키워드 기반에서 행위 및 시그니처 이중 트랙으로 업그레이드합니다.
5. **보안 결과를 이벤트 버스로**: 오탐률이 정량화된 이후, `critical`급 위협과 `critical`급 FIM 변경을 정책 엔진에 연동하여 Agent가 자율적으로 처리(예: WebShell 탐지 → 격리 → 보고)할 수 있도록 합니다.
6. **컴플라이언스 보고서 내보내기**: 원클릭으로 단일 파일 HTML 보고서를 생성(예약 작업 보고서의 렌더링 방식 재사용)하며, 점수, 항목별 결론, 개선 권고를 포함합니다.
