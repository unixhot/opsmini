## 1. เป้าหมายและไม่ใช่เป้าหมายของการออกแบบ

### เป้าหมาย

| เป้าหมาย | ความหมายเฉพาะ |
| --- | --- |
| **ไม่มีการพึ่งพา** | ไม่ต้องติดตั้ง agent ไม่พึ่งพาโมดูลเคอร์เนล ไม่เชื่อมต่อบริการศูนย์กลาง แค่พาไบนารีไปก็ตรวจสอบได้ |
| **อธิบายได้** | ทุกรายการตรวจสอบสามารถคลิกเปิดดูได้ว่า «อ่านไฟล์ใด เห็นค่าอะไร ทำไมจึงตัดสินว่าไม่ผ่าน แนะนำให้แก้อย่างไร» |
| **ลงมือได้** | เมื่อพบปัญหาแล้วสามารถแก้ได้โดยตรงในแผง (แก้ไฟร์วอลล์ รันการตรวจสุขภาพ สร้างพื้นฐานใหม่ ทำเครื่องหมายภัยคุกคามว่าจัดการแล้ว) |
| **ให้คนดู และให้ AI ดู** | ข้อสรุปชุดเดียวกันทั้งเรนเดอร์เป็นหน้าเว็บ และส่งมอบเป็นเครื่องมือแบบอ่านอย่างเดียวให้ Agent ที่มีในตัว |
| **ไม่ล้ำอำนาจ** | ความสามารถแบบอ่านอย่างเดียวใช้ได้เพียงเข้าสู่ระบบ ส่วนการกระทำใดๆ ที่แก้ระบบต้องมีจุดสิทธิ์แยกต่างหาก + สถานะ root |

### ไม่ใช่เป้าหมาย (เป็นการแลกเปลี่ยน ไม่ใช่ทำไม่เสร็จ)

- **ไม่ทำตัวแทน HIDS**: ไม่ทำฮุก syscall ของเคอร์เนล ไม่ทำโพรบ eBPF ไม่ทำการตรวจจับทราฟฟิกทั้งหมด ความสามารถประเภทนี้ต้องเก็บข้อมูลด้วยสิทธิ์สูงแบบประจำการ ซึ่งขัดกับจุดยืน «ไบนารีเดี่ยว ขนาดหลายสิบ MB ติดตั้งได้ทุกเมื่อ»
- **ไม่ทำภาพรวมหลายเครื่อง**: เครื่องเดียวให้ข้อสรุปของเครื่องเดียว การสรุปหลายเครื่องเป็นหน้าที่ของ OpsMini Server / Proxy
- **ไม่มีเอนจินคลังกฎในตัว**: เกณฑ์พื้นฐานเขียนไว้ในโค้ด (14 รายการ) ไม่รับการโหลดกฎ YAML แบบร้อน การโหลดกฎแบบร้อนฟังดูยืดหยุ่น แต่จะทำให้ «ทำไมเครื่องนี้ได้ 62 คะแนน» ไม่สามารถทำซ้ำได้ การแยกกฎออกภายนอกเป็นทิศทางการพัฒนา (ดู §16)
- **ไม่แทนที่การสแกน-compliance มืออาชีพ**: ไม่ทำการครอบคลุมรายการครบถ้วนและการออกใบรับรองของ 等保/CIS ทำเฉพาะส่วนที่ «มองเห็นได้ในชีวิตประจำวันและลงมือปฏิบัติได้»

## 2. แผนผังความสามารถ

หน้าความปลอดภัยโฮสต์ประกอบด้วยหกแท็บ โดยแท้จริงแล้วคือ**ห้าโมดูลตรวจสอบ + หนึ่งมุมมองสรุป**:

| แท็บ | ตรวจสอบอะไร | แหล่งข้อมูล | วิธีการทริกเกอร์ | แก้ไขระบบหรือไม่ |
| --- | --- | --- | --- | --- |
| ภาพรวมความปลอดภัย | สรุปภาพรวม: คะแนนรวม ระดับ คะแนนห้าโมดูล และข้อสรุปหนึ่งประโยค | ผลลัพธ์ที่บันทึกลงฐานข้อมูลของอีกห้าโมดูล | เปิดหน้า | ไม่ |
| การตรวจสอบพื้นฐาน | สถานะการเสริมความแข็งแกร่งโฮสต์ 14 รายการ | `/etc/ssh/sshd_config`、`/etc/passwd`、`/etc/shadow`、`/etc/login.defs`、crontab、พอร์ตที่รับฟัง | คลิก「เริ่มตรวจสอบ」ด้วยตนเอง | ไม่ |
| ความปลอดภัยการเข้าสู่ระบบ | การโจมตีแบบ brute force การเข้าสู่ระบบผิดปกติ คำแนะนำการเสริมความแข็งแกร่ง SSH | `/var/log/auth.log` หรือ `/var/log/secure` | เปิดหน้า | ไม่ |
| ไฟร์วอลล์ | แบ็กเอนด์และกฎปัจจุบัน; อนุญาต/บล็อกพอร์ต เปิด/หยุด | สถานะจริงของ `ufw` / `firewall-cmd` / `iptables` | ดำเนินการด้วยตนเอง | **ใช่** |
| ความสมบูรณ์ของไฟล์ | ไฟล์สำคัญถูกแก้ไข/ถูกลบหรือไม่ | SHA256 ของไฟล์สำคัญในระบบ 8 ไฟล์ | เบื้องหลังทุก 60 วินาที | ไม่ |
| การตรวจจับภัยคุกคาม | กระบวนการขุดเหมือง งานตามกำหนดที่น่าสงสัย การเริ่มต้นอัตโนมัติที่น่าสงสัย | `/proc`、crontab、`/etc/rc.local`、รายการบริการ systemd | เบื้องหลังทุก 5 นาที + ด้วยตนเอง | ไม่ (การจัดการต้องให้คนดำเนินการ) |

การตัดสินใจที่ชัดเจนในการออกแบบ: **มีเพียงไฟร์วอลล์เท่านั้นที่แก้ไขระบบ** โมดูลอีกสี่โมดูลเป็นเพียงผู้สังเกตการณ์ล้วน แม้ตัดสินผิดก็เพียงทำให้คะแนนดูไม่ดี ไม่ทำให้เครื่องเกิดปัญหา

## 3. สถาปัตยกรรม: สองเส้นทางที่เป็นอิสระต่อกัน

ใน OpsMini มีสองสิ่งที่เกี่ยวข้องกับความปลอดภัย ซึ่งดูคล้ายกันแต่แท้จริงแล้วเป็นสองเส้นทางที่แยกจากกัน:

```
                  ┌──────────── เส้นทางการตรวจสุขภาพ (pull, ให้คนดู) ────────────┐
  /etc、/proc ───▶ │ BaselineService  การวิเคราะห์การเข้าสู่ระบบ  FIM  การสแกนภัยคุกคาม        │ ──▶ SQLite ──▶ หน้าความปลอดภัย + คะแนน
  บันทึกการยืนยันตัวตน        │ SecurityService สรุปและให้คะแนน                        │
                  └──────────────────────────────────────────────────┘

                  ┌──────────── เส้นทางการรับรู้ (push, ให้ Agent) ──────────┐
  auth.log、เว็บไซต์   │ sentinel ตัวเก็บข้อมูล (logwatch/authwatch/           │ ──▶ สัญญาณ ──▶ เหตุการณ์ ──▶ นโยบาย
  ไดเรกทอรี、ตารางโปรเซส     │ filewatch/procwatch/netwatch/metricwatch)      │        ──▶ Agent จัดการ
                  └──────────────────────────────────────────────────┘
```

**ทำไมต้องแบ่งเป็นสองเส้นทาง แทนที่จะรวมเป็นหนึ่ง?**

| มิติ | เส้นทางการตรวจสุขภาพ | เส้นทางการรับรู้ |
| --- | --- | --- |
| รูปแบบการโต้ตอบ | ดึง: คุณเปิดหน้า / คลิกสแกน | ผลัก: ตัวเก็บข้อมูลทำงานตลอดเวลา |
| เอาต์พุต | รายการ + คะแนน (สแนปช็อตสถานะที่เก็บได้ระยะยาว) | สัญญาณ → เหตุการณ์ (สตรีมที่มีข้อจำกัดด้านเวลา) |
| ผู้บริโภค | คน | เอนจินนโยบาย + AI Agent |
| ลักษณะการตัดสิน | "สถานะปัจจุบันเป็นไปตามข้อกำหนดหรือไม่" | "เพิ่งเกิดอะไรขึ้น" |
| ต้นทุนการตัดสินผิด | คะแนนดูไม่ดี | อาจกระตุ้นการจัดการอัตโนมัติ |

การรวมจะทำให้ทั้งสองฝ่ายฉุดกัน: การตรวจสุขภาพต้องคำนวณใหม่ได้ทุกเมื่อ การรับรู้ต้องเพิ่มขึ้นอย่างต่อเนื่อง; เมื่อเส้นทางหนึ่งเพิ่มสเตตแมชชีน อีกเส้นทางก็ถูกบังคับให้ต้องพาไปด้วย

**ต้องบอกต้นทุนให้ชัดด้วย**: ทั้งสองเส้นทางแยกวิเคราะห์บันทึกการยืนยันตัวตนกันเอง (`service/loginsecurity.go` และ `sentinel/authwatch.go` เป็นชุด regex สองชุด) มีความเสี่ยงที่มาตรฐานจะคลาดเคลื่อน นี่คือหนี้ทางเทคนิคที่ทราบแล้ว ดู §16

## 4. โมเดลการให้คะแนนความปลอดภัย

คะแนนเต็ม 100 โดยห้าโมดูลมีน้ำหนักคงที่:

| โมดูล | คะแนนเต็ม | ทำไมถึงให้น้ำหนักแบบนี้ |
| --- | --- | --- |
| การตรวจสอบพื้นฐาน | 40 | เป็นส่วนเดียวที่ "คุณปรับปรุงให้ดีขึ้นได้เอง" และสะท้อนระดับการปฏิบัติการประจำวันได้ดีที่สุด |
| ความปลอดภัยการเข้าสู่ระบบ | 20 | เครื่องที่เปิดสู่อินเทอร์เน็ตมีปัญหาเกือบทั้งหมดเริ่มจากตรงนี้ |
| ไฟร์วอลล์ | 15 | มีหรือไม่มี ตัดสินพื้นที่การเปิดเผยโดยตรง |
| ความสมบูรณ์ของไฟล์ | 15 | ไฟล์สำคัญถูกแก้ไขมักหมายความว่าถูกบุกรุกแล้ว |
| การตรวจจับภัยคุกคาม | 10 | น้ำหนักต่ำเพราะ容易被ตัดสินผิด (ดู §10) |

### กฎการให้คะแนนแต่ละโมดูล (สอดคล้องกับโค้ดแบบหนึ่งต่อหนึ่ง)

**พื้นฐาน (0–40)**: ถ่วงน้ำหนักตามน้ำหนัก ไม่ใช่ตามจำนวนรายการ

```
got   = Σ(น้ำหนักรายการ pass) + Σ(น้ำหนักรายการ warn × 0.5)
total = Σ(น้ำหนักทุกรายการ) = 32
คะแนน = int(40 × got / total)
```

ความหมายสามสถานะ: `pass` นับเป็นคะแนนเต็ม, `warn` นับเป็นครึ่งคะแนน, `fail` นับเป็น 0 เหตุผลที่มี warn คือบางรายการ "ยังไม่ได้ทำแต่ไม่ถือว่าผิด" (เช่น SSH ยังใช้พอร์ต 22: ความเสี่ยงมีจริงแต่พบได้บ่อย การตัดสินเป็น 0 คะแนนทันทีจะทำให้คะแนนขาดความสามารถในการแยกแยะ)

**ความปลอดภัยการเข้าสู่ระบบ (0–20)**:

| สถานการณ์ | คะแนน |
| --- | --- |
| ไม่พบการโจมตีแบบ brute force, 24h ไม่มีความล้มเหลว | 20 |
| 24h มีการเข้าสู่ระบบล้มเหลวแต่ไม่ถึงเกณฑ์ brute force | 16 (หักคงที่ 4) |
| พบเป้าหมายต้องสงสัยถูก brute force จำนวน n | `20 − 5n`, ขั้นต่ำ 0 |

**ไฟร์วอลล์ (0–15)**: เปิดใช้งาน 15, ไม่เปิดใช้งาน 0 ตัดสินแบบสองค่า ไม่มีสถานะกลาง

**ความสมบูรณ์ของไฟล์ (0–15)**: `15 − 3n` (n = จำนวนรายการที่เปลี่ยนแปลงภายใน 24h), ขั้นต่ำ 0 การเปลี่ยนแปลงหนึ่งรายการหัก 3 คะแนนหมายความว่าแก้ไขไฟล์สำคัญ 5 ไฟล์ก็เหลือศูนย์

**การตรวจจับภัยคุกคาม (0–10)**: เริ่มหักจาก 10, `critical` หัก 5, `warning` หัก 2, อื่น ๆ หัก 1, ขั้นต่ำ 0

### การ映射ระดับ

| คะแนน | ระดับ |
| --- | --- |
| ≥ 90 | ดีเยี่ยม |
| ≥ 75 | ดี |
| ≥ 60 | ปานกลาง |
| < 60 | อันตราย |

### ข้อแลกเปลี่ยนของโมเดลนี้

- **ไม่ถ่วงน้ำหนักด้วยมูลค่าทรัพย์สิน**: OpsMini ไม่รู้ว่าเครื่องนี้รันธุรกิจอะไรอยู่ การเดา "ค่าสัมประสิทธิ์ความสำคัญ" ขึ้นมาจะทำให้คะแนนกลายเป็นเรื่องลี้ลับ
- **ไม่ใช้ CVSS**: CVSS ประเมินความรุนแรงของช่องโหว่ ส่วนที่นี่ประเมินการตั้งค่าโฮสต์และสถานะการทำงานจริง สองสิ่งนี้ไม่ใช่เรื่องเดียวกัน
- **ไม่มีการติดลบ**: หักถึง 0 แล้วหยุด ป้องกันไม่ให้โมดูลเดียวลากทั้งระบบจนคะแนนหมดความหมาย
- **คะแนนทำซ้ำได้**: อินพุตเหมือนกัน โค้ดเหมือนกัน คะแนนต้องเหมือนกัน นี่คือเงื่อนไขที่ทำให้ใช้เปรียบเทียบแบบ "แก้เสร็จแล้วดูอีกครั้ง" ได้

## 5. การตรวจสอบพื้นฐาน

### วิธีการทำงาน

การสแกนหนึ่งครั้งจะสร้าง `ScanID` หนึ่งรายการ (timestamp ระดับนาโนวินาที) ผลลัพธ์ทั้ง 14 รายการจะเขียนเป็นหนึ่งบรรทัดใน `baseline_results` หน้าเพจจะแสดงเฉพาะ**แบตช์ล่าสุด** ส่วนแบตช์ย้อนหลังจะเก็บไว้ในฐานข้อมูลเพื่อเปรียบเทียบ

เป็นการแยกวิเคราะห์ไฟล์ล้วน ๆ ไม่เรียกใช้เครื่องมือภายนอกเช่น `lynis` / `oscap` — เครื่องมือเหล่านั้นมักไม่มีอยู่ในระบบที่ถูกย่อส่วนให้เล็กที่สุด และผลลัพธ์ก็ยากต่อการจัดโครงสร้าง

### รายละเอียดการตัดสิน

- `sshd_config` จะอ่านทั้งไฟล์หลักและ `/etc/ssh/sshd_config.d/*.conf` พร้อมกัน (ดิสทริบิวชันสมัยใหม่แยกการตั้งค่าไปยังไดเรกทอรี drop-in การอ่านเฉพาะไฟล์หลักจะทำให้ตัดสินผิด)
- แยกความแตกต่างระหว่าง "ไม่ได้ตั้งค่าอย่างชัดเจน" กับ "ตั้งค่าผิดอย่างชัดเจน": กรณีแรกให้ `warn` (ค่าเริ่มต้นของดิสทริบิวชันไม่แน่นอน) กรณีหลังให้ `fail`
- `/etc/shadow`、`/etc/passwd` แยกวิเคราะห์ข้อความโดยตรง ไม่พึ่งพาการตั้งค่า NSS — เพื่อหลีกเลี่ยงการตัดสินที่คลาดเคลื่อนบนเครื่องที่มี LDAP/SSSD เข้ามาเกี่ยวข้อง
- พอร์ตความเสี่ยงสูงใช้รายการคงที่: `23 Telnet`、`445 SMB`、`135 RPC`、`1433 MSSQL`、`3389 RDP`

รายการครบ 14 ข้อดูได้ที่ [ภาคผนวก A]](#附录-a基线-14-项清单)

### ทำไมค่าน้ำหนักจึงถูกเขียนตายตัวในโค้ด

การเปลี่ยนค่าน้ำหนักก็เปลี่ยนคะแนนได้ หากค่าน้ำหนักสามารถกำหนดค่าได้ เครื่องเดียวกันจะมีคะแนนต่างกันในสองลูกค้า "การตรวจสอบพื้นฐาน" ก็จะสูญเสียความน่าเชื่อถือ หากต้องการปรับค่าน้ำหนัก ให้ผ่านการรีวิวโค้ด

## 6. ความปลอดภัยการเข้าสู่ระบบ

### แหล่งข้อมูลและค่าใช้จ่าย

อ่านเฉพาะส่วนท้ายของบันทึกการยืนยันตัวตน: `tail -n 5000` โดยให้ความสำคัญกับ `/var/log/auth.log` (ตระกูล Debian) ก่อน แล้วจึงเป็น `/var/log/secure` (ตระกูล RHEL) หากไม่มีให้คืนรายงานว่างแทนที่จะเกิดข้อผิดพลาด บันทึกอาจมีขนาดหลายร้อย MB การอ่านทั้งหมดจะทำให้หน่วยความจำเต็ม

**ต้องระบุหน้าต่างการนับให้ชัดเจน**: หน้าต่างในการใช้งานจริงคือ "5000 บรรทัดท้ายของบันทึก" ไม่ใช่หน้าต่างเวลาที่เข้มงวด ชื่อฟิลด์ยังคงใช้ `failed_count_24h` / `success_count_24h` เนื่องจากเครื่องที่เปิดสู่อินเทอร์เน็ตและถูกสแกนหนักๆ 5000 บรรทัดมักไม่ถึง 24 ชั่วโมง ขณะที่เครื่องที่เงียบสงบ 5000 บรรทัดอาจกินเวลาหลายวัน ความคลาดเคลื่อนนี้เป็นปัญหาที่ทราบแล้ว (§15) เหตุผลที่ไม่ได้กรอง 24 ชั่วโมงอย่างเข้มงวดมีอธิบายด้านล่าง

### เกณฑ์สามประเภท

| เกณฑ์ | กฎ | เอาต์พุต |
| --- | --- | --- |
| การเดารหัสผ่านแบบ brute force | บัญชีเดียวกันล้มเหลวภายในหน้าต่างการนับ (รวม `Failed password` และ `Invalid user`) **สะสม ≥ 5 ครั้ง** | ชื่อบัญชี + จำนวนครั้ง + รายการ IP ที่เกี่ยวข้อง เรียงจากจำนวนครั้งมากไปน้อย |
| แหล่งที่มาของความล้มเหลวสูงสุด | รวมจำนวนครั้งที่ล้มเหลวตาม IP แล้วเลือก 10 อันดับแรก | IP + จำนวนครั้ง |
| การเข้าสู่ระบบผิดปกติ | ในบรรดาการเข้าสู่ระบบที่สำเร็จ `user == root` | เวลา + ผู้ใช้ + IP + เหตุผล "บัญชี root เข้าสู่ระบบ SSH โดยตรง" |

คำแนะนำการเสริมความปลอดภัย SSH ไม่ได้เขียนข้อความตายตัว แต่จะอ่าน `sshd_config` ปัจจุบันเพื่อตรวจสอบว่าแต่ละข้อได้ทำแล้วหรือไม่ (`PermitRootLogin`, `PasswordAuthentication`, เปลี่ยนพอร์ต, Protocol 2) และแสดงบนหน้าเว็บว่า "ทำแล้ว/ยังไม่ได้ทำ" โดยตรง

### ทำไมจึงไม่ทำ GeoIP และการวิเคราะห์ UA

สภาพแวดล้อมแบบออฟไลน์เป็นความต้องการที่จำเป็น แผงความปลอดภัยที่ติดตั้งในเครือข่ายภายในได้ ไม่เชื่อมต่ออินเทอร์เน็ต และไม่ส่งบันทึกไปยังบริการภายนอก มีประโยชน์มากกว่าแผงที่วาดแผนที่โลกสวยงามได้แต่ต้องเชื่อมต่ออินเทอร์เน็ต ดังนั้นการตัดสินความผิดปกติจึงอาศัยเพียงข้อเท็จจริงที่มองเห็นได้จากเครื่องนี้เท่านั้น (เวลา, บัญชี, ความถี่ของ IP)

### ทำไมจึงไม่กรอง 24 ชั่วโมงอย่างเข้มงวด

การประทับเวลาของ `syslog` ไม่มีปี (`Aug 14 07:00:01`) การกรองตามเวลาจำเป็นต้องอนุมานปีและจัดการกับการวนกลับข้ามปี ช่วงก่อนและหลังเที่ยงคืน เขตเวลาของคอนเทนเนอร์ที่ไม่ตรงกัน และบันทึกที่ถูก logrotate ตัดทอน ล้วนทำให้การอนุมานผิดพลาดได้ ผิดพลาดไปหนึ่งปีก็เท่ากับนับประวัติทั้งหมดเป็น "เมื่อสักครู่"

การใช้ "N บรรทัดท้าย" แทนหน้าต่างเวลา มีต้นทุนคือความยาวของหน้าต่างลอยไปมา แต่มีข้อดีคือ**ไม่ตัดสินผิดพลาดจากการแยกวิเคราะห์เวลาที่ผิดพลาดเลย** หากต้องการความแม่นยำจริงๆ วิธีที่ถูกต้องคือให้ชั้นการรับรู้ทำการสืบค้นหน้าต่างในฐานข้อมูลตาม `observed_at` (ซึ่งมีเวลาอยู่แล้ว) นี่ก็เป็นหนึ่งในแรงจูงใจของชั้นข้อเท็จจริงแบบรวมศูนย์ใน §16

### คำอธิบายของเกณฑ์ 5

ต่ำกว่า 5 ครั้งส่วนใหญ่เป็นการพิมพ์รหัสผ่านผิดของมนุษย์ ตั้งแต่ 5 ครั้งขึ้นไปภายใน 24 ชั่วโมงจากกลุ่ม IP เดียวกัน จึงจะมีลักษณะของ "กำลังลอง" เกณฑ์นี้บนเครื่องที่เปิดสู่อินเทอร์เน็ตจริงจะถูกการสแกนจำนวนมากข้ามผ่านไปได้ — นั่นแหละคือประโยชน์ของมัน: **มันไม่ได้มีไว้เพื่อระบุอย่างแม่นยำ แต่มีไว้เพื่อบอกคุณว่าเครื่องนี้กำลังถูกสแกน**

## 7. ไฟร์วอลล์

### การตรวจจับแบ็กเอนด์อัตโนมัติ

ไม่สมมติว่าระบบติดตั้งอะไรไว้ อ่านสถานะจริงเพื่อกำหนดแบ็กเอนด์:

| แบ็กเอนด์ | การตัดสิน | การดำเนินการเขียนที่รองรับ |
| --- | --- | --- |
| `ufw` | `ufw status` อ่านได้ | อนุญาต/บล็อกพอร์ต, เปิดใช้งาน, ปิดใช้งาน, ลบกฎตามหมายเลข |
| `firewalld` | `systemctl is-active firewalld` | อนุญาต/บล็อกพอร์ต (`--permanent` + `--reload`), เปิดใช้งาน, ปิดใช้งาน |
| `iptables` | มีเชนกฎอยู่ | อนุญาต/บล็อกพอร์ต (`-I INPUT 1`), ลบกฎตามหมายเลข; **ไม่รองรับการปิดใช้งานภายในแผง** |

แบ็กเอนด์ `iptables` จงใจไม่ให้มี "ปิดใช้งาน": การล้างเชนกฎเท่ากับปล่อยให้ทุกเครื่องโล่งเกินไป ความเสียหายสูงเกินไป จึงต้องให้ผู้ใช้ไปดำเนินการบนเครื่องเอง

### การออกแบบป้องกันการล็อกตัวเอง (นี่คือข้อสำคัญที่สุดของโมดูลนี้)

**ก่อนเปิดใช้งานไฟร์วอลล์ ให้อนุญาตพอร์ตของแผงเองและ SSH 22 โดยอัตโนมัติก่อน** แล้วจึง `enable`

ลำดับห้ามสลับกัน หากสลับกันจะเป็นอุบัติเหตุคลาสสิก: พอเปิดไฟร์วอลล์ 8888 และ 22 ถูกบล็อกพร้อมกัน ผู้ใช้เหลือเพียงคอนโซลให้ใช้ `panelPort` ถูกฉีดผ่านการกำหนดค่าตอนเริ่มต้น ไม่ใช่ 8888 ที่เขียนตายตัว

### การตรวจสอบพารามิเตอร์และ timeout

| แนวป้องกัน | วิธี |
| --- | --- |
| สิทธิ์ | การดำเนินการเขียนทั้งหมด `requireRoot()` ผู้ที่ไม่ใช่ root จะได้รับ `ErrNeedRoot` โดยตรง |
| พอร์ต | ตรวจสอบชนิด `int` + ช่วง 1–65535 ไม่รับสตริง |
| โปรโตคอล | ระบุเป็น enum `tcp`/`udp` |
| การฉีด | ทั้งหมดผ่าน `exec.Command(name, args...)` ไม่ผ่าน shell พารามิเตอร์ไม่สามารถถูกต่อเป็นคำสั่งที่สองได้ |
| ค้าง | ทุกคำสั่งไฟร์วอลล์มี timeout 10 วินาที (`context.WithTimeout`) หากล้มเหลวคืนค่า stderr ตามต้นฉบับ |

### ความสัมพันธ์กับการบล็อกของ Agent

ในระบบมีการบล็อกสองแบบ จงใจแยกจัดการ:

| แหล่งที่มา | จุดเก็บ | วงจรชีวิต | ใครล้าง |
| --- | --- | --- | --- |
| กฎจากหน้าเว็บ (ผู้ใช้กำหนด) | ตารางกฎ `ufw`/`firewalld` | ระยะยาว จนกว่าผู้ใช้จะลบ | ผู้ใช้ |
| การบล็อกของ Agent (ขับเคลื่อนด้วยเหตุการณ์) | `iptables -I INPUT -s <ip> -j DROP` + ตาราง `blocked_ips` | มี TTL หมดอายุแล้วหายเอง | `SweepBlocks()` ปลดบล็อกอัตโนมัติ |

เหตุผลที่แยก: การบล็อกของ Agent ต้องหายเองได้ (บล็อกผิดต้องแก้เองได้) ส่วนกฎของผู้ใช้ต้องไม่ถูกลบไปพร้อมกับตรรกะการหายเอง ทั้งสองชุดจัดการแยกกัน บนหน้าเว็บมองเห็นแยกกัน

## 8. ความสมบูรณ์ของไฟล์ (FIM)

### วัตถุประสงค์การตรวจสอบ

ค่าเริ่มต้นคือไฟล์สำคัญของระบบ 8 ไฟล์ เมื่อเริ่มทำงานครั้งแรก (เมื่อฐานข้อมูลพื้นฐานว่างเปล่า) จะสร้างฐานข้อมูลพื้นฐานโดยอัตโนมัติ:

```
/etc/passwd  /etc/shadow  /etc/group   /etc/ssh/sshd_config
/etc/crontab /etc/sudoers /etc/hosts   /etc/resolv.conf
```

โดยการเปลี่ยนแปลงของ `/etc/passwd`, `/etc/shadow`, `/etc/sudoers` จะถูกบันทึกเป็น `critical` ส่วนที่เหลือเป็น `warning`

### ลูปการตรวจจับ

ทุก 60 วินาที จะคำนวณ `SHA256 + size + mtime` สำหรับแต่ละรายการที่เปิดใช้งาน:

- คำนวณไม่ได้ (ไฟล์ไม่มีอยู่) → บันทึกหนึ่งรายการ "ไฟล์ถูกลบ" ระดับ `critical` กำหนดตามพาธ
- แฮชไม่ตรงกัน → บันทึกหนึ่งรายการ "เนื้อหาไฟล์เปลี่ยนแปลง" พร้อมแฮชเก่าและใหม่
- ตรงกัน → ไม่ทำอะไรเลย

### การออกแบบสำคัญ: ฐานข้อมูลพื้นฐานเลื่อนไปข้างหน้าอัตโนมัติหลังการเปลี่ยนแปลง

หลังจากตรวจพบการเปลี่ยนแปลงและบันทึกลงฐานข้อมูลแล้ว **ฐานข้อมูลพื้นฐานจะอัปเดตเป็นแฮชใหม่ทันที**

นี่เป็นเจตนา: หากฐานข้อมูลพื้นฐานไม่เลื่อนไปข้างหน้า การเปลี่ยนแปลงครั้งเดียวกันจะถูกรายงานทุก 60 วินาที วันหนึ่ง 1440 การแจ้งเตือน คนก็จะไม่ดูอีกเลย หลังจากเลื่อนไปข้างหน้า ผลลัพธ์คือ "หนึ่งการเปลี่ยนแปลงหนึ่งการแจ้งเตือน" และ**หากเปลี่ยนแปลงอีกครั้งก็ยังจะรายงาน**——หากถูกแก้ไขซ้ำๆ จริง ก็ยังมองเห็นได้

ข้อแลกเปลี่ยน: หากการเปลี่ยนแปลงสองครั้งติดต่อกันเกิดขึ้นภายในหน้าต่าง 60 วินาทีเดียวกัน จะเหลือเพียงบันทึกเดียว ซึ่งยอมรับได้ที่ความละเอียดระดับนี้ (หากต้องการละเอียดกว่านี้ต้องใช้ inotify ดู §16)

"สร้างฐานข้อมูลพื้นฐานใหม่" เป็นการกระทำด้วยมือ: หลังจากคุณแก้ไข `sudoers` เสร็จแล้วคลิกหนึ่งครั้ง เพื่อบอกระบบว่า "สถานะปัจจุบันถูกต้องแล้ว"

### การแบ่งงานกับ filewatch ในชั้นการรับรู้

|  | FIM หน้าความปลอดภัย | filewatch ชั้นการรับรู้ |
| --- | --- | --- |
| ดูอะไร | ไฟล์สำคัญของระบบ 8 ไฟล์ | สคริปต์ที่เรียกใช้งานได้ใหม่ในไดเรกทอรีรากของเว็บไซต์ |
| เกณฑ์ | การเปรียบเทียบแฮช | นามสกุล + ลักษณะเนื้อหา WebShell (`eval($_POST`, `base64_decode` เป็นต้น) |
| วัตถุประสงค์ | ตรวจจับ "ระบบถูกแก้ไข" | ตรวจจับ "เว็บไซต์ถูกฝังมัลแวร์" |

ทั้งสองไม่ทับซ้อนกัน และไม่อ้างอิงถึงกัน

## 9. การตรวจจับภัยคุกคาม

สแกนเนอร์สามตัว ทำงานรอบละ 5 นาที และรันหนึ่งครั้งตอนเริ่มระบบ

| สแกนเนอร์ | ตรวจอะไร | เกณฑ์ตัดสิน | ระดับ |
| --- | --- | --- | --- |
| โพรเซส | โพรเซสทั้งหมดของ `/proc` (ชื่อ + command line) | ตรงกับคีย์เวิร์ดขุดเหมือง (`xmrig`, `minerd`, `kdevtmpfsi`, `kinsing`, `stratum` และอื่น ๆ รวม 11 รายการ) | critical |
| โพรเซส | พาธไฟล์ปฏิบัติการของโพรเซส | อยู่ใน `/tmp` หรือ `/dev/shm` (บริการปกติไม่ควรเริ่มจากที่นี่) | warning |
| งานตามกำหนด | crontab ของระบบ + ผู้ใช้ | คำสั่งมี `curl`, `wget`, `base64 -d`, `/dev/shm` | warning |
| รายการเริ่มระบบ | บรรทัดที่ไม่ใช่คอมเมนต์ใน `/etc/rc.local` | มี `curl`, `wget`, `/tmp` | warning |
| รายการเริ่มระบบ | ชื่อบริการที่เปิดใช้งานใน systemd | มี `miner`, `xmrig`, `kdevtmpfs` | critical |

### การตัดรายการซ้ำและวงจรชีวิต

ตัดรายการซ้ำตาม `kind + name`: หากตรงกับระเบียนที่มีอยู่แล้ว จะอัปเดตเฉพาะ `last_seen` และรายละเอียด โดยไม่เพิ่มรายการใหม่ สถานะมีเพียง `active` / `resolved` และ**มีเพียงคนเท่านั้นที่ทำเครื่องหมายเป็นแก้ไขแล้วได้**——ก่อนที่โพรเซสจะถูกฆ่า สแกนเนอร์จะเห็นมันอีกทุก 5 นาที ซึ่งเป็นสิ่งที่เราต้องการ (ภัยคุกคามจริงไม่ควรหายไปเอง)

### การประเมิน这套การตรวจจับอย่างตรงไปตรงมา

บัญชีดำคีย์เวิร์ด**เปลี่ยนชื่อก็หลบได้** นี่คือความลับที่ใครก็รู้ ดังนั้นจุดยืนของมันไม่ใช่ "จับการขุดเหมืองได้ทั้งหมด" แต่คือ:

1. จับ**การโจมตีแบบขี้เกียจ**——บอทเน็ตส่วนใหญ่ใช้ไบนารีสำเร็จรูปที่ชื่อไม่เปลี่ยน;
2. ใช้**ลักษณะพฤติกรรม**อย่าง "ไฟล์ปฏิบัติการในไดเรกทอรีชั่วคราว" ครอบคลุมส่วนที่เปลี่ยนชื่อ;
3. ส่วนที่เหลืออาศัยสัญญาณพฤติกรรมโพรเซสและพฤติกรรมการเข้าสู่ระบบจากชั้นการรับรู้เสริม

ไม่โอ้อวดว่าฆ่าได้ แต่ถ้าตรวจพบก็รายงาน การจัดการให้คน (หรือคนมอบอำนาจให้ Agent)

## 10. โมเดลข้อมูล

| ตาราง | หนึ่งแถวแทน | ฟิลด์สำคัญ |
| --- | --- | --- |
| `baseline_results` | ผลลัพธ์หนึ่งรายการในการสแกนหนึ่งครั้ง | `scan_id` (แบตช์), `category`, `item_key`, `status`](pass/fail/warn), `detail`, `suggestion`, `weight` |
| `fim_baselines` | เกณฑ์ฐานปัจจุบันของไฟล์ที่ถูกตรวจสอบหนึ่งไฟล์ | `path`](unique), `sha256`, `size`, `mod_time`, `enabled` |
| `fim_changes` | เหตุการณ์เปลี่ยนแปลงไฟล์หนึ่งครั้ง | `path`, `old_sha256`, `new_sha256`, `level`](warning/critical), `message`, `created_at` |
| `threat_findings` | รายการภัยคุกคามหนึ่งรายการ | `kind`](process/cron/startup), `name`, `detail`, `severity`, `status`, `first_seen`, `last_seen`, `resolved_at` |

จุดสำคัญของการออกแบบ:

- ผลลัพธ์เกณฑ์ฐานแบ่งเป็นแบตช์ตาม `scan_id` และ **ไม่เคยเขียนทับประวัติ**: หากต้องการเปรียบเทียบ "สัปดาห์ก่อนกับสัปดาห์นี้" สามารถสอบถามได้
- `fim_baselines` และ `fim_changes` แยกตารางกัน: หนึ่งคือสถานะ อีกหนึ่งคือบันทึกรายการ หากรวมไว้ในตารางเดียวจะทำให้ "เกณฑ์ฐานปัจจุบัน" และ "ประวัติการเปลี่ยนแปลง" ปนเปื้อนซึ่งกันและกัน
- `threat_findings` มี `first_seen/last_seen`: มองแวบเดียวก็รู้ว่านี่เพิ่งเกิดขึ้นหรือค้างมาสามวันแล้วไม่มีใครดูแล
- ไม่มีไฟล์ฐานข้อมูลความปลอดภัยแยกต่างหาก ทั้งหมดเก็บอยู่ใน `opsmini.db` และไปพร้อมกับการสำรองข้อมูล (สอดคล้องกับข้อมูลอื่น ๆ ของแผง)
- หมายเหตุชื่อตาราง: ผลลัพธ์เกณฑ์ความปลอดภัยคือ `baseline_results` ส่วน "เกณฑ์ฐานการเรียนรู้" (ค่าexpected EWMA) ของชั้นการรับรู้คือ `baselines` ทั้งสองไม่เกี่ยวข้องกัน อย่าสับสน

## 12. ขอบเขตความปลอดภัยของแผงเอง

โมดูลความปลอดภัยเองก็เป็นพื้นผิวการโจมตีเช่นกัน ดังนั้น:

## 13. ประสิทธิภาพและภาระทรัพยากร

| การกระทำ | ภาระ | คำอธิบาย |

| การตรวจสอบพื้นฐาน | อ่านไฟล์ขนาดเล็ก 14 ครั้ง + ตารางพอร์ตหนึ่งครั้ง ระดับมิลลิวินาที | ทำงานเฉพาะเมื่อมีคนกด |
| การวิเคราะห์การเข้าสู่ระบบ | `tail -5000` หนึ่งครั้ง ต่อครั้ง < 50ms | ทำงานเมื่อเปิดหน้า ไม่แคช |
| การตรวจสอบ FIM | SHA256 ของ 8 ไฟล์ ทุก 60 วินาที | เป็นไฟล์ขนาดเล็กระดับ KB ทั้งหมด CPU มองข้ามได้ |

## 14. ความสัมพันธ์กับ Agent อัตโนมัติ

อินเทอร์เฟซสามจุด ล้วนเป็น**การให้ข้อเท็จจริงแบบทางเดียว** ไม่มีความเชื่อมโยงแบบ "โมดูลความปลอดภัยสั่งการ Agent" เช่นนั้น:

| ทิศทาง | รูปแบบ | คำอธิบาย |
| --- | --- | --- |
| ความปลอดภัย → AI | เครื่องมืออ่านอย่างเดียว `security_status` | Agent สามารถอ่าน "คะแนน + สรุปห้าโมดูล" เพื่อตอบคำถาม "เครื่องนี้ปลอดภัยหรือไม่" เครื่องมือคือ `RiskReadonly` + `security.view` |
| ความปลอดภัย → AI (เขียน) | เครื่องมือ `firewall_rule` | การแก้ไขไฟร์วอลล์เป็นการดำเนินการเขียน ผ่านการแบ่งระดับ L1/L2 ต้องยืนยัน |
| ชั้นรับรู้ → Agent | สัญญาณ → เหตุการณ์ → นโยบาย | sentinel รับผิดชอบอย่างอิสระ ไม่แชร์สถานะกับโมดูลความปลอดภัยในส่วนนี้ |

**สิ่งที่ยังไม่ได้ทำในปัจจุบัน (เจตนา)**: ผลการตรวจจับภัยคุกคามและการเปลี่ยนแปลง FIM ไม่เข้าสู่บัสเหตุการณ์ เหตุผลคือผลลัพธ์สองประเภทนี้มีอัตราการแจ้งเตือนผิดสูงกว่าสัญญาณของชั้นรับรู้ (การจับคู่คำสำคัญ การเลื่อน基线อัตโนมัติล้วนสร้างสัญญาณรบกวน) การป้อนเข้าสู่นโยบายจัดการอัตโนมัติโดยตรงมีความเสี่ยงสูงเกินไป จะเชื่อมต่อหลังจากมีข้อมูลจริงของอัตราการแจ้งเตือนผิดแล้ว ดู §16

| ไม่มีการส่งออกรายงาน | ดูได้เฉพาะบนหน้าเว็บ ไม่สามารถออกรายงานการปฏิบัติตามข้อกำหนดเป็น PDF/HTML | ทิศทางการพัฒนา |

## 16. ทิศทางการพัฒนา

ตามลำดับความสำคัญ:

1. **FIM กำหนดค่าได้**: รองรับเส้นทางที่กำหนดเอง การเรียกซ้ำของไดเรกทอรี รายการที่อนุญาต (ไฟล์ที่เปลี่ยนแปลงบ่อยภายใต้ `/etc/` ให้ยกเว้นก่อน) และใช้เหตุการณ์ inotify ขับเคลื่อนแทนการ polling ทุก 60 วินาที
2. **กฎพื้นฐานแยกออกภายนอก**: 14 รายการ → แพ็กเกจกฎ YAML รองรับการนำเข้า CIS / ชุดรายการระดับสองของการคุ้มครองความปลอดภัยข้อมูล พร้อมบันทึก "ชุดกฎที่ใช้อยู่ในปัจจุบัน" ลงในผลลัพธ์ เพื่อให้คะแนนสามารถทำซ้ำได้
3. **ชั้นข้อเท็จจริงของบันทึกแบบรวมศูนย์**: `service/loginsecurity.go` และ `sentinel/authwatch.go` ใช้ตัวแยกวิเคราะห์ชุดเดียวกัน ขจัดความคลาดเคลื่อนของมาตรฐานการวัด
4. **เสริมความแข็งแกร่งการตรวจจับภัยคุกคาม**: เชื่อมต่อ `ausearch` (บันทึกการตรวจสอบ auditd) และกฎ YARA ที่เลือกได้ อัปเกรดจากคีย์เวิร์ดเป็นสองแนวทางคือพฤติกรรมและลายลักษณ์
5. **ผลลัพธ์ด้านความปลอดภัยเข้าสู่บัสเหตุการณ์**: หลังจากอัตราการแจ้งเตือนผิดสามารถวัดเป็นปริมาณได้แล้ว เชื่อมต่อภัยคุกคามระดับ `critical` และการเปลี่ยนแปลง FIM ระดับ `critical` เข้าสู่กลไกนโยบาย เพื่อให้ Agent สามารถจัดการได้เอง (เช่น ตรวจพบ WebShell ถูกวาง → แยกกัก → รายงาน)
6. **ส่งออกรายงานการปฏิบัติตามข้อกำหนด**: สร้างรายงาน HTML ไฟล์เดียวได้ในคลิกเดียว (ใช้การเรนเดอร์ชุดเดียวกับรายงานงานตามกำหนด) ประกอบด้วยคะแนน ข้อสรุปรายรายการ ข้อเสนอแนะในการแก้ไข

## ภาคผนวก A: รายการพื้นฐาน 14 ข้อ

| หมวดหมู่ | รายการ | น้ำหนัก | การตัดสิน |
| --- | --- | --- | --- |
| ssh | SSH ห้ามเข้าสู่ระบบด้วยรหัสผ่าน root | 3 | `PermitRootLogin` เป็น `no`/`prohibit-password` ตัดสิน pass; ไม่ได้กำหนดค่า ตัดสิน warn; อื่นๆ ตัดสิน fail |
| ssh | SSH ปิดการเข้าสู่ระบบด้วยรหัสผ่าน | 3 | `PasswordAuthentication no` ตัดสิน pass, มิฉะนั้น warn |
| ssh | SSH เปลี่ยนพอร์ตเริ่มต้น 22 | 1 | ไม่ใช่ 22 ตัดสิน pass, มิฉะนั้น warn |
| ssh | เวอร์ชันโปรโตคอล SSH เป็น 2 | 1 | ไม่ได้กำหนดค่าหรือเป็น `2` ตัดสิน pass, มิฉะนั้น fail |
| password | ไม่มีบัญชีที่ใช้รหัสผ่านว่างเปล่า | 3 | `/etc/shadow` ฟิลด์รหัสผ่านว่างเปล่า ถือเป็น fail, แสดงชื่อบัญชี |
| password | อายุการใช้งานสูงสุดของรหัสผ่าน ≤ 90 วัน | 2 | `PASS_MAX_DAYS` ≤ 90 ตัดสิน pass, มิฉะนั้น warn |
| account | ไม่มีบัญชี UID=0 เกินจำเป็น | 3 | นอกจาก root แล้วมี UID=0 ตัดสิน fail, แสดงชื่อบัญชี |
| account | ไม่มีบัญชีที่เข้าสู่ระบบได้โดยไม่มีรหัสผ่าน | 2 | มี login shell และ shadow ว่างเปล่า/ถูกล็อก ตัดสิน fail |
| file_perm | สิทธิ์ของ `/etc/shadow` ปลอดภัย | 2 | สิทธิ์กว้างเกินไป ตัดสิน warn/fail |
| file_perm | สิทธิ์ของ `/etc/passwd` ปลอดภัย | 2 | เช่นเดียวกัน |
| file_perm | สิทธิ์ของ `/etc/ssh/sshd_config` ปลอดภัย | 1 | เช่นเดียวกัน |
| firewall | เปิดใช้งานไฟร์วอลล์แล้ว | 3 | ตรวจพบ ufw/firewalld/iptables ทำงานอยู่ ตัดสิน pass, มิฉะนั้น fail |
| firewall | ไม่มีพอร์ตความเสี่ยงสูงที่กำลังรับฟัง | 3 | 23/445/135/1433/3389 มีการรับฟัง ตัดสิน warn, แสดงพอร์ต |
| cron | ไม่มีงานตามกำหนดที่น่าสงสัย | 3 | คำสั่ง crontab มี `curl`/`wget`/`base64 -d`/`/tmp/`/`/dev/shm` ตัดสิน warn (แสดงสูงสุด 5 รายการ) |

น้ำหนักรวม 32 แปลงเป็น 40 คะแนนตามสูตรข้างต้น

## ภาคผนวก B: ตัวอย่างการคำนวณคะแนน

เครื่อง Ubuntu สาธารณะทั่วไปหนึ่งเครื่อง:

| โมดูล | ค่าที่วัดได้ | คะแนน |
| --- | --- | --- |
| พื้นฐาน | ผ่าน 12 จาก 14 รายการ, เตือน 2 รายการ (SSH ใช้พอร์ต 22, `PASS_MAX_DAYS` ยังไม่ได้ตั้งค่า) | got = 32 − 1×0.5 − 2×0.5 = 30.5 → `int(40×30.5/32)` = **38** |
| การเข้าสู่ระบบ | ล้มเหลว 2000 ครั้งภายใน 24 ชม., ตรงเป้าหมาย brute force 3 รายการ | `20 − 5×3` = **5** |
| ไฟร์วอลล์ | เปิดใช้งาน ufw แล้ว | **15** |
| ความสมบูรณ์ของไฟล์ | มีการเปลี่ยนแปลง 1 จุดภายใน 24 ชม. (`/etc/hosts`) | `15 − 3` = **12** |
| การตรวจจับภัยคุกคาม | คำเตือน 1 รายการ (โปรเซสที่รันได้ภายใต้ `/tmp`) | `10 − 2` = **8** |
| **คะแนนรวม** |  | **78 → ดี** |

คะแนนนี้อธิบายได้อย่างสมเหตุสมผล: การกำหนดค่าพื้นฐานเหมาะสม (พื้นฐาน 38) แต่กำลังถูก brute force (การเข้าสู่ระบบ 5) การหักคะแนนส่วนใหญ่มาจากการโจมตีจริงไม่ใช่การตัดสินผิด แนวทางแก้ไขก็ชัดเจน——เปิดการจำกัดแหล่งที่มาของไฟร์วอลล์, ใช้ fail2ban หรือบล็อกด้วย Agent, คะแนนการเข้าสู่ระบบก็จะกลับมา
