# ระบบปลั๊กอิน

เคอร์เนลทำเฉพาะ "สิ่งที่ทุกโฮสต์ต้องการ": การเก็บข้อมูล การตรวจสอบ รันไทม์ของ Agent และราวกั้นความปลอดภัย ความสามารถทางธุรกิจ (เมตริกของมิดเดิลแวร์บางตัว การแยกวิเคราะห์บันทึกบางประเภท การเชื่อมต่อการดำเนินการของแพลตฟอร์มบางแห่ง) ขยายผ่าน**ปลั๊กอิน**

จุดประสงค์ของการทำเช่นนี้ไม่ใช่เพื่อความสวยงามของสถาปัตยกรรม แต่เพื่อหลีกเลี่ยงสองสิ่งที่เป็นรูปธรรม: **ไบนารีที่บวมไม่สิ้นสุด** และ**การต้องออกรีลีสใหม่หนึ่งเวอร์ชันเพียงเพื่อความสามารถใหม่หนึ่งอย่าง**

## ปลั๊กอินเป็นโปรเซสแยก ไม่ใช่ Go plugin

- แพ็กเกจ `plugin` ของ Go กำหนดให้สภาพแวดล้อมการ-build ต้องตรงกันทุกประการในตอนคอมไพล์ ข้ามเวอร์ชันจะพังแน่นอน จึงตัดออกไปเลย
- ปลั๊กอินเป็น**ไฟล์ปฏิบัติการแยกอิสระ** แผงจะเริ่มมันในรูปแบบโปรเซสลูก และสื่อสารผ่าน Unix socket ด้วย**JSON ที่คั่นด้วยบรรทัด**
- ปลั๊กอินพังไม่ส่งผลกระทบต่อแผง: การที่โปรเซสออกจะถูกบันทึก ถูกดึงขึ้นมาตามนโยบายรีสตาร์ท หากล้มเหลวต่อเนื่องจะถูกทำเครื่องหมายเป็น failed และหยุดลองใหม่

## รูปแบบแพ็กเกจ

```
foo-collector-1.2.0-linux-amd64.tar.gz
├── plugin.yaml          # แมนิเฟสต์
├── bin/plugin           # จุดเข้า (ไฟล์ปฏิบัติการ)
├── SIGNATURE            # ลายเซ็น ed25519 (ลงนามบน sha256 ของทั้งแพ็กเกจ)
└── README.md            # ไม่บังคับ
```

ตัวอย่างแมนิเฟสต์:

```yaml
apiVersion: opsmini.plugin/v1
id: foo-collector              # ไม่ซ้ำทั่วโลก, ^[a-z0-9][a-z0-9-]{2,40}$
name: Foo คอลเลกเตอร์
version: 1.2.0                 # semver
vendor: ซูยุนเทค
description: เก็บความลึกของคิวและอัตราการบริโภคของบริการ Foo
kind: collector                # collector | action | panel
entry: bin/plugin              # พาธสัมพัทธ์ภายในแพ็กเกจ
platform: [linux/amd64, linux/arm64]

capabilities:                  # การประกาศความสามารถ ใช้เป็นหลักฐานการตรวจสอบด้วย
  - metrics
  - read:/etc/foo
  - exec:systemctl
  - net:outbound

runtime:
  memoryLimitMB: 128
  cpuQuotaPercent: 20
  restartPolicy: on-failure    # always | on-failure | never

requires:
  opsmini: ">=1.4.0"           # ข้อกำหนดเวอร์ชัน Agent ของโฮสต์
```

ลำดับการตรวจสอบตอนติดตั้ง (ล้มเหลวข้อใดข้อหนึ่งให้ปฏิเสธทันที ไม่ติดตั้ง "ปลั๊กอินครึ่งๆ กลางๆ"):

1. sha256 ของแพ็กเกจ (คำนวณฝั่งเซิร์ฟเวอร์ สามารถตรวจสอบไขว้กับที่ผู้อัปโหลดประกาศไว้)
2. ลายเซ็น ed25519
3. `apiVersion` ความเข้ากันได้
4. `platform` ตรงกับโฮสต์ปัจจุบันหรือไม่
5. ความถูกต้องของฟิลด์ในแมนิเฟสต์、ข้อกำหนดเวอร์ชัน

## สามช่องทาง

ปลั๊กอินและเคอร์เนลสื่อสารกันผ่าน socket ด้วยข้อความเพียงสี่ชนิด ทั้งหมดเป็น JSON บรรทัดเดียว:

| ข้อความ | ทิศทาง | การใช้งาน |
|---|---|---|
| `hello` | ปลั๊กอิน → แผง | แฮนด์เชกตอนเริ่มต้น ประกาศว่าตนเองเป็นใคร เวอร์ชัน และความสามารถ |
| `metric` | ปลั๊กอิน → แผง | รายงานเมตริก (เข้าสู่การตรวจสอบและกฎการแจ้งเตือน) |
| `event` | ปลั๊กอิน → แผง | รายงานเหตุการณ์ (สามารถแปลงเป็นสัญญาณเข้าสู่ศูนย์เหตุการณ์) |
| `heartbeat` | ปลั๊กอิน → แผง | สถานะการทำงานอยู่และการตรวจสอบตนเอง |

ปลั๊กอินไม่แตะฐานข้อมูลโดยตรง ไม่เรียกอินเทอร์เฟซของแผงโดยตรง และไม่สืบทอดเซสชันของแผง

## วงจรชีวิต

```
ติดตั้ง (อัปโหลดแพ็กเกจ → ตรวจสอบ → แตกไฟล์ไปที่ releases/<version>/ → symlink current ชี้ไปที่ไดเรกทอรีนั้น)
   ↓
เปิดใช้งาน → เริ่มโปรเซส → รอ handshake hello → เข้าสู่ running
   ↓
ทำงาน → crash/ออก → จัดการตาม restartPolicy บันทึกจำนวนครั้งที่รีสตาร์ทและข้อผิดพลาดล่าสุด
   ↓
ปิดใช้งาน → SIGTERM → รอให้ออก → สถานะ stopped
   ↓
อัปเกรด → แตกไฟล์เวอร์ชันใหม่ → สลับ symlink current → รีสตาร์ท (เก็บไดเรกทอรีเวอร์ชันเก่าไว้ สามารถย้อนกลับได้)
   ↓
ลบ → หยุดโปรเซส → ลบไฟล์โปรแกรม (เก็บไดเรกทอรีข้อมูลไว้)
```

## ขอบเขตสิทธิ์: ชี้แจงให้ชัดว่าอะไรทำได้แล้วบ้าง

ส่วนนี้ต้องซื่อสัตย์ มิฉะนั้น "ความปลอดภัยของปลั๊กอิน" จะกลายเป็นเพียงคำพูดลอยๆ

**ทำได้แล้ว:**

- ปลั๊กอินเป็นโปรเซสแยก หากล่มจะไม่ทำให้แผงล่มตาม
- การติดตั้งต้องตรวจสอบลายเซ็น (เว้นแต่จะเปิดโหมด unsigned อย่างชัดเจน) และตรวจสอบเวอร์ชัน แพลตฟอร์ม และ manifest
- การติดตั้ง เปิดใช้งาน ปิดใช้งาน และลบ ทั้งหมดถูกบันทึกในบันทึกการตรวจสอบ
- ปลั๊กอินสื่อสารผ่าน socket ไม่สามารถเข้าถึงฐานข้อมูลของแผงโดยตรง

**เวอร์ชันปัจจุบันยังทำไม่ได้ (อย่าสมมติว่ามี):**

- **ยังไม่สลับไปใช้ผู้ใช้ระบบแยก**: ปลั๊กอินทำงานภายใต้ผู้ใช้ของโปรเซสแผง ซึ่งโดยปกติคือ `root`
- **ยังไม่มีข้อจำกัดทรัพยากรผ่าน cgroup**: `memoryLimitMB` / `cpuQuotaPercent` ใน manifest ขณะนี้เป็นเพียงการประกาศ ยังไม่ได้บังคับใช้
- **`capabilities` ยังไม่ได้บังคับใช้**: เป็นเพียงพื้นฐานสำหรับการประกาศและการตรวจสอบ ไม่ใช่ไวท์ลิสต์ระดับเคอร์เนล
- **ไม่สามารถตรวจสอบ system call ภายในปลั๊กอินได้**

ดังนั้นข้อสรุปคือ: **ลายเซ็นพิสูจน์ว่า "แหล่งที่มาเชื่อถือได้" ไม่ได้พิสูจน์ว่า "พฤติกรรมปลอดภัย"** ติดตั้งเฉพาะปลั๊กอินจากแหล่งที่คุณเชื่อถือเท่านั้น; ปลั๊กอินของบุคคลที่สามโปรดตรวจสอบโค้ดด้วยตนเอง

## ข้อกำหนดเบื้องต้นในการติดตั้ง (ข้อควรระวังสำหรับเวอร์ชันปัจจุบัน)

ระหว่างการติดตั้ง ระบบจะตรวจสอบตามลำดับ: `sha256` → ลายเซ็น → แมนิเฟสต์ ในการกำหนดค่าเริ่มต้น **ไม่มีคีย์สาธารณะในตัว และไม่ได้เปิดโหมด unsigned** ดังนั้นการอัปโหลดโดยตรงจะถูกปฏิเสธ โดยแจ้งข้อความ «ยังไม่ได้กำหนดค่าคีย์สาธารณะของปลั๊กอินและยังไม่ได้เปิดโหมด unsigned»

มีสองวิธีแก้ไข เลือกอย่างใดอย่างหนึ่ง (หลังจากบันทึกลงในการตั้งค่าแล้ว **ต้องรีสตาร์ทแผง** จึงจะมีผล เนื่องจากคีย์สาธารณะจะถูกอ่านตอนเริ่มต้นระบบ):

```bash
# วิธีที่หนึ่ง: กำหนดค่าคีย์สาธารณะ ed25519 (แนะนำ สำหรับสภาพแวดล้อมจริง)
curl -X POST http://127.0.0.1:8888/api/v1/settings \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"plugin_public_key":"<คีย์สาธารณะ 32 ไบต์ที่เข้ารหัสแบบ hex>"}'

# วิธีที่สอง: สำหรับสภาพแวดล้อมการพัฒนา/เครือข่ายภายใน อนุญาตแพ็กเกจที่ไม่ได้ลงนามชั่วคราว
curl -X POST http://127.0.0.1:8888/api/v1/settings \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"plugin_allow_unsigned":"true"}'
```

หลังจากแก้ไขแล้ว `systemctl restart opsmini` จากนั้นกลับไปที่ «การตั้งค่าแผง → ปลั๊กอิน» เพื่ออัปโหลด

> แผงเวอร์ชันปัจจุบันยังไม่มีหน้าจอสำหรับป้อนค่าการตั้งค่าสองรายการนี้ ทำได้เพียงผ่าน API ข้างต้นหรือแก้ไขตารางการตั้งค่าโดยตรง เวอร์ชันถัดไปจะเพิ่มให้

## การดำเนินการบนแผง

**การตั้งค่าแผง → ปลั๊กอิน**:

| การดำเนินการ | คำอธิบาย |
|---|---|
| อัปโหลดและติดตั้ง | เลือกแพ็กเกจ `*.tar.gz` ขนาดสูงสุด 64MB |
| เปิดใช้งาน / ปิดใช้งาน | มีผลทันที ไม่ต้องรีสตาร์ทแผง |
| รีสตาร์ท | รีสตาร์ทปลั๊กอินใดปลั๊กอินหนึ่งแยกต่างหาก (เช่น เมื่อแก้ไขการกำหนดค่าของปลั๊กอินนั้น) |
| ลบ | ลบไฟล์โปรแกรมออก โดยเก็บไดเรกทอรีข้อมูลไว้ |
| เหตุการณ์ | ดูเมตริกและเหตุการณ์ที่ปลั๊กอินนั้นรายงานล่าสุด |

ในรายการสามารถดูข้อมูลของแต่ละปลั๊กอินได้แก่: ชื่อ เวอร์ชัน ประเภท สถานะ (running / stopped / failed / installed) จำนวนครั้งที่รีสตาร์ท และข้อผิดพลาดล่าสุด

## คำอธิบายสถานะปัจจุบัน

กลไกมีความสมบูรณ์ **ระบบนิเวศขณะนี้ยังว่างเปล่า** — v1.4.0 ไม่ได้แนบแพ็กเกจปลั๊กอินอย่างเป็นทางการมาด้วย ซึ่งหมายความว่าหลังจากติดตั้ง OpsMini แล้ว หน้าปลั๊กอินจะว่างเปล่า นี่คือสถานะที่คาดไว้ ไม่ใช่ความผิดพลาด

ทิศทางปลั๊กอินอย่างเป็นทางการที่วางแผนไว้ (ยังไม่เผยแพร่): การตรวจสอบเพิ่มเติมตามพื้นฐานความปลอดภัย, การเก็บเมตริกของมิดเดิลแวร์เฉพาะ, แพ็กเกจกฎการแยกวิเคราะห์บันทึก, การเชื่อมต่อการดำเนินการกับแพลตฟอร์มบุคคลที่สาม
