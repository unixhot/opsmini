# การสำรองข้อมูลและการกู้คืน

## ระดับความเป็นคลิกเดียวไม่เหมือนกัน

| การกระทำ | ระดับความเป็นคลิกเดียว | เหตุผล |
|---|---|---|
| สำรองข้อมูล | ✅ คลิกเดียวก็ทำงานจริง และตั้งเวลาล่วงหน้าได้ | อ่านข้อมูลต้นทางเท่านั้น + เขียนไปยังไดเรกทอรีเป้าหมาย หากล้มเหลวก็ลองใหม่ได้ ไม่มีการทำลายข้อมูล |
| กู้คืน | ⚠️ เป็น "คลิกเดียว" แต่มีเงื่อนไขเบื้องต้นสามขั้น | การกู้คืนจะเขียนทับข้อมูล在生产 จำเป็นต้องมีการตรวจสอบล่วงหน้า สแนปช็อตก่อนกู้คืน และการย้อนกลับอัตโนมัติ |

การทำให้การกู้คืนเป็น "คลิกเดียวแล้วเขียนทับ" เท่ากับมอบปุ่มลบที่ไม่มีปุ่มเลิกทำให้กับผู้ใช้ ดังนั้นบนอินเทอร์เฟซจึงเรียกว่า **การกู้คืนคลิกเดียว (พร้อมการตรวจสอบล่วงหน้าและการย้อนกลับอัตโนมัติ)**

## สำรองข้อมูลอะไร

สามประเภท เขียนไว้ใน "วัตถุที่สำรองข้อมูล" บรรทัดละหนึ่งรายการ:

| รูปแบบการเขียน | ความหมาย |
|---|---|
| `/var/www` | ไดเรกทอรี (หรือไฟล์เดี่ยว) แพ็กเป็น `tar.gz` |
| `mysql:opsmini` | ฐานข้อมูล ส่งออกผ่าน `mysqldump` แล้วบีบอัด |
| `redis:/var/lib/redis/dump.rdb` | ไฟล์สแนปช็อต Redis แพ็กไฟล์นั้นโดยตรง |

การสำรองข้อมูล MySQL ใช้ข้อมูลการเชื่อมต่อที่กำหนดค่าไว้แล้วในแผง (ซ็อกเก็ตเครื่องนี้) พารามิเตอร์คือ `--single-transaction --routines --triggers` เพื่อรับประกันสแนปช็อตที่สอดคล้องกันของตาราง InnoDB โดยไม่ล็อกตาราง

**ไม่รองรับ**: PostgreSQL, Docker volume, สแนปช็อตระดับบล็อกดีไวซ์/ระบบไฟล์, การสำรองข้อมูลแบบเพิ่มพูน, การเข้ารหัสการสำรองข้อมูล ทั้งหมดนี้พิจารณาในเวอร์ชันถัดไป เวอร์ชันนี้ไม่รับประกัน

## สแนปช็อตมีหน้าตาอย่างไร

```
<ไดเรกทอรีข้อมูล>/data/backups/web-20261029-020000/
├── manifest.json                 # เมทาดาทา: ออบเจกต์, ขนาด, sha256, ชื่อโฮสต์, เวอร์ชัน
└── data/
    ├── var_www.tar.gz
    ├── opsmini.sql.gz
    └── redis.rdb.gz
```

สิทธิ์ของไดเรกทอรี `0700` ไฟล์ `0600` ใน `manifest.json` บันทึก sha256 ของแต่ละชาร์ด เมื่อกู้คืนจะตรวจสอบทีละรายการ

ไม่นำเข้าเครื่องมือสำรองข้อมูลแบบ "รีโพซิทอรี" อย่าง restic/borg: เครื่องมือเหล่านี้มีการขจัดข้อมูลซ้ำ การเข้ารหัส และเชนสแนปช็อต ฟังก์ชันทรงพลังแต่จะนำมาซึ่ง dependency 15–25MB และเมื่อกู้คืนจำเป็นต้องใช้เครื่องมือเดียวกัน ปัจจุบันเป็น "ชาร์ดที่บรรจุในตัวเอง + แมนิเฟสต์" เครื่องใดก็ตามที่แตกไฟล์ออกก็สามารถกู้คืนได้

## ขั้นตอนการสำรองข้อมูล

```
ตรวจสอบวัตถุทั้งหมด (พาธมีอยู่ ชื่อฐานข้อมูลไม่ว่าง พาธ redis อ่านได้)
   ↓  ตรวจสอบทั้งหมดก่อนแล้วจึงลงมือ: มิฉะนั้นหากวัตถุที่ 2 จาก 5 เขียนผิด
      จะล้มเหลวหลังจากสร้างไฟล์เก็บถาวรไปแล้ว 4 รายการ ทิ้งสแนปช็อตไว้ครึ่งเดียว
ดำเนินการทีละรายการ (แบบอนุกรม เพื่อหลีกเลี่ยง IO เต็ม)
   ↓  เมื่อแต่ละวัตถุเสร็จสิ้นให้เขียนลง manifest ความล้มเหลวจะไม่ก่อให้เกิด "การสำรองข้อมูลครึ่งเดียว"
คำนวณเช็กซัมรวม → ล้างสแนปช็อตเก่าตามนโยบายการเก็บรักษา → เขียนประวัติการสำรองข้อมูล
```

จำนวนชุดที่เก็บรักษาโดยค่าเริ่มต้นคือ 7 โดย `0` หมายถึงเก็บรักษาทั้งหมด การล้างจะลบไดเรกทอรีที่เก่าที่สุดแบบ**ทั้งไดเรกทอรี** โดยเด็ดขาดจะไม่ลบชิ้นส่วนย่อย单个 (มิฉะนั้นรายการจะใช้ไม่ได้)

## ขั้นตอนการกู้คืน (สามด่านตรวจ)

**① ตรวจสอบล่วงหน้า**

- ต้องป้อนชื่อสแนปช็อตเพื่อยืนยันซ้ำ (ป้องกันการเลือกผิด)
- ไดเรกทอรีหลักปลายทางมีอยู่และเขียนได้
- ไคลเอนต์ `mysql` ใช้งานได้ (เมื่อกู้คืนฐานข้อมูล)
- ไฟล์สแนปช็อตครบถ้วน, sha256 ตรงกับรายการ

**② สแนปช็อตอัตโนมัติก่อนกู้คืน**

สำรองสถานะปัจจุบันไว้ก่อนหนึ่งชุด (ไดเรกทอรีใช้ตรรกะการแพ็กเดียวกัน, ฐานข้อมูลใช้ dump) หากล้มเหลวสามารถกลับมาที่ขั้นตอนนี้ได้

**③ ดำเนินการและย้อนกลับ**

- กู้คืน → ตรวจสอบสุขภาพ
- รายการตรวจสอบใดล้มเหลว → **ย้อนกลับอัตโนมัติไปยังสแนปช็อตของขั้นตอน②** → สร้างเหตุการณ์ระดับ critical หนึ่งรายการในศูนย์เหตุการณ์

รายการตรวจสอบสุขภาพ: ไดเรกทอรีเปรียบเทียบจำนวนไฟล์และสุ่มตรวจ checksum, MySQL รัน `SELECT 1` และตรวจสอบจำนวนแถวของตารางสำคัญ, Redis `PING` เปรียบเทียบกับ keyspace

ความน่าเชื่อถือของการย้อนกลับมาจาก "การ rename ในพาร์ทิชันเดียวกันเป็นแบบ atomic": ก่อนกู้คืนเปลี่ยนชื่อไดเรกทอรีเป้าหมาย `mv` เป็น `xxx.pre-restore-<时间戳>`, เมื่อล้มเหลวเปลี่ยนชื่อ `mv` กลับมา

## การดำเนินการบนแผง

**การตั้งค่าแผง → สำรองและกู้คืน**:

| พื้นที่ | เนื้อหา |
|---|---|
| วัตถุที่สำรอง | หนึ่งรายการต่อบรรทัด รองรับไดเรกทอรี / `mysql:库名` / `redis:路径` |
| จำนวนชุดที่เก็บรักษา | ค่าเริ่มต้น 7, 0 หมายถึงไม่ล้างข้อมูล |
| สำรองทันที | รันหนึ่งครั้ง เมื่อเสร็จแล้วรีเฟรชรายการสแนปช็อต |
| รายการสแนปช็อต | ชื่อ เวลา ขนาด จำนวนวัตถุ ผลการตรวจสอบล่วงหน้า |
| กู้คืน | ป้อนชื่อสแนปช็อตเพื่อยืนยันแล้วดำเนินการ ส่งคืนรายละเอียดการตรวจสอบล่วงหน้าและผลลัพธ์ |
| ประวัติการสำรอง | ผลลัพธ์ของการรันแต่ละครั้ง (รวมถึงสาเหตุที่ล้มเหลว) |

## การสำรองข้อมูลตามกำหนดเวลา

การสำรองข้อมูลเป็น**ประเภทที่สี่ของงานตามกำหนด** (เทียบเท่ากับงานแผง / crontab ของระบบ / crontab ของผู้ใช้) ใช้กลไกการจัดตาราง การเริ่ม-หยุด และการแจ้งเตือนเมื่อล้มเหลวชุดเดียวกัน

กำหนดค่าได้ที่ **งานตามกำหนด → สร้างงานใหม่ → เลือกประเภทเป็น「งานสำรองข้อมูล」**:

| ฟิลด์ | คำอธิบาย |
|---|---|
| วัตถุที่สำรอง | ไวยากรณ์แถวเดียวกับหน้าสำรองข้อมูล |
| จำนวนชุดที่เก็บไว้ | นโยบายการเขียนทับสแนปช็อตเก่า |
| รอบการทำงาน | นิพจน์ cron มีพรีเซ็ตที่ใช้บ่อย (เช่น ทุกวัน 02:00) |
| ช่องทางแจ้งเตือน | แผง / อีเมล / WeCom / DingTalk / Feishu |
| เก็บสำเนาในเครื่อง | เมื่อใช้ปลายทางระยะไกล จะเก็บสำเนาในเครื่องไว้หรือไม่หลังอัปโหลดสำเร็จ |

ใช้**เอนจินเดียวกัน**กับการ「สำรองข้อมูลทันที」แบบ manual ผลลัพธ์เหมือนกันทุกประการ——ไม่มีกรณีที่「manual กู้คืนได้ แต่แบบตามกำหนดเวลาไม่ได้」

เมื่อล้มเหลวจะเขียนสถานะกลับไปยังงาน (`上次状态 / 上次错误 / 连续失败次数`) พร้อมบันทึกประวัติการสำรองข้อมูลหนึ่งรายการ และกระตุ้นกฎการแจ้งเตือนในตัว「จำนวนการสำรองข้อมูลที่ล้มเหลว」

## เป้าหมายระยะไกล: โค้ดพร้อมใช้งาน แต่เวอร์ชันนี้ยังไม่เปิดใช้งาน

ใน `internal/backup` ได้มีการใช้งานที่เก็บข้อมูลระยะไกลสองแบบแล้ว คือ S3 ที่เข้ากันได้ (OSS / MinIO / AWS พร้อมลายเซ็น SigV4 ที่เขียนเอง) และ SFTP แต่ **v1.4.0 ไม่ถือเป็นเนื้อหาที่ส่งมอบ**:

- แผงไม่แนะนำให้กำหนดค่าที่เก็บข้อมูลระยะไกล
- เอกสารไม่แนะนำให้ใช้ในสภาพแวดล้อมการผลิต
- ยังไม่ได้ทดสอบร่วมกับเครื่องจริง (มีเพียงการทดสอบยูนิตและการทดสอบเวกเตอร์ลายเซ็น S3)

หากต้องการจัดเก็บข้อมูลในพื้นที่อื่น ให้เพิ่มเป้าหมายใน `config.yaml` ก็สามารถเปิดใช้งานได้ โดยไม่ต้องแก้โค้ด:

```yaml
backup:
  targets:
    - name: oss-bj
      type: s3
      endpoint: oss-cn-beijing.aliyuncs.com
      bucket: my-backup
      region: cn-beijing
      access_key: "..."
      secret_key: "..."
```

หลังจากกำหนดค่าแล้ว หน้าแบ็กอัปจะมีตัวเลือก «เป้าหมายระยะไกล» ซึ่งสามารถอัปโหลดสแนปช็อตและเรียกดู/ดึงสแนปช็อตระยะไกลกลับมาได้ การอัปโหลดจะเกิดขึ้นหลังจากสแนปช็อตภายในถูกเขียนลงดิสก์อย่างสมบูรณ์แล้ว ดังนั้นหากการอัปโหลดล้มเหลวจะไม่เหลือแบ็กอัปที่ค้างอยู่บนระยะไกล

**หมายเหตุ**: เส้นทางนี้ยังไม่ได้ผ่านการทดสอบร่วมกับเครื่องจริง ก่อนใช้งานจริงโปรดตรวจสอบการไป-กลับแบบสมบูรณ์หนึ่งครั้ง (อัปโหลด → แสดงรายการ → กู้คืนไปยังไดเรกทอรีชั่วคราว) บนไดเรกทอรีที่ไม่ใช่สภาพแวดล้อมการผลิตก่อน

## ข้อจำกัดที่ทราบ

- ระหว่างการสำรองข้อมูลไดเรกทอรีขนาดใหญ่จะใช้ IO อย่างต่อเนื่อง แนะนำให้หลีกเลี่ยงช่วงเวลาที่ธุรกิจใช้งานหนัก (ค่าเริ่มต้น 02:00)
- MySQL สำรองข้อมูลผ่าน socket ของเครื่องนี้ ไม่รองรับอินสแตนซ์ฐานข้อมูลระยะไกล
- การกู้คืนเป็นแบบ "เขียนทับ": จะกู้คืนเฉพาะออบเจ็กต์ที่อยู่ในสแนปช็อตเท่านั้น ไม่ลบไฟล์ใหม่ที่เพิ่มเข้ามานอกสแนปช็อต
- สแนปช็อตแต่ละรายการไม่ได้เข้ารหัส สำหรับไดเรกทอรีที่มีข้อมูลอ่อนไหว โปรดตรวจสอบให้แน่ใจว่าสิทธิ์ของไดเรกทอรีข้อมูลและสื่อสำรองข้อมูลมีความปลอดภัย
