# 백업 및 복구

## 원클릭의 정도는 다릅니다

| 작업 | 원클릭 정도 | 이유 |
|---|---|---|
| 백업 | ✅ 정말 한 번 클릭하면 실행되며, 예약도 가능 | 소스 데이터 읽기 전용 + 대상 디렉터리 쓰기, 실패 시 재시도하면 되고 파괴성 없음 |
| 복구 | ⚠️ 「원클릭」이지만 세 가지 사전 조건이 있음 | 복구는 프로덕션 데이터를 덮어쓰므로 반드시 사전 점검, 복구 전 스냅샷, 자동 롤백이 있어야 함 |

복구를 「클릭 한 번에 덮어쓰기」로 만드는 것은 사용자에게 실행 취소 키가 없는 삭제 버튼을 주는 것과 같습니다. 그래서 인터페이스에서는 **원클릭 복구(사전 점검 및 자동 롤백 포함)** 라고 부릅니다.

## 무엇을 백업하는가

세 가지 대상이 있으며, 「백업 대상」에 작성하고 한 줄에 하나씩 입력합니다:

| 작성 방식 | 의미 |
|---|---|
| `/var/www` | 디렉터리(또는 단일 파일)이며, `tar.gz`로 패키징됩니다 |
| `mysql:opsmini` | 데이터베이스이며, `mysqldump`를 통해 내보낸 후 압축합니다 |
| `redis:/var/lib/redis/dump.rdb` | Redis 스냅샷 파일이며, 해당 파일을 직접 패키징합니다 |

MySQL 백업은 패널에 이미 구성된 연결 정보(로컬 socket)를 사용하며, 파라미터는 `--single-transaction --routines --triggers`로, InnoDB 테이블의 일관된 스냅샷을 보장하면서 테이블을 잠그지 않습니다.

**지원하지 않음**: PostgreSQL, Docker volume, 블록 디바이스/파일 시스템 수준 스냅샷, 증분 백업, 백업 암호화. 이들은 모두 후속 버전에서 고려할 예정이며, 이 버전에서는 보장하지 않습니다.

## 스냅샷의 구조

```
<데이터 디렉터리>/data/backups/web-20261029-020000/
├── manifest.json                 # 메타데이터: 객체, 크기, sha256, 호스트명, 버전
└── data/
    ├── var_www.tar.gz
    ├── opsmini.sql.gz
    └── redis.rdb.gz
```

디렉터리 권한은 `0700`, 파일은 `0600`입니다. `manifest.json`에는 각 샤드의 sha256이 기록되며, 복구 시 하나씩 검증합니다.

restic/borg 같은 "저장소형" 백업 도구는 도입하지 않습니다. 이들은 중복 제거, 암호화, 스냅샷 체인을 지원하여 기능은 강력하지만 15–25MB의 의존성을 발생시키고, 복구 시 반드시 동일한 도구를 사용해야 합니다. 현재는 "자체 포함 샤드 + 매니페스트" 방식으로, 어느 머신에서든 압축을 풀면 복구할 수 있습니다.

## 백업 프로세스

```
모든 객체 검증 (경로 존재, 데이터베이스 이름 비어 있지 않음, redis 경로 읽기 가능)
   ↓  먼저 전부 검증한 후 작업 시작: 그렇지 않으면 5개 객체 중 2번째에서 오류가 발생했을 때
      이미 4개의 아카이브가 생성된 후에야 실패하여 반쪽짜리 스냅샷이 남음
하나씩 실행 (직렬, IO 포화 방지)
   ↓  각 객체 완료 시 즉시 manifest에 기록, 실패 시 「반쪽 백업」이 생기지 않음
총 체크섬 계산 → 보존 정책에 따라 오래된 스냅샷 정리 → 백업 이력 기록
```

보존 개수 기본값은 7이며, `0`는 전체 보존을 의미합니다. 정리는 **디렉터리 전체**를 기준으로 가장 오래된 것을 삭제하며, 개별 샤드를 절대 삭제하지 않습니다 (그렇지 않으면 목록이 무효화됨).

## 복구 절차 (세 가지 게이트)

**① 사전 점검**

- 반드시 스냅샷 이름을 입력하여 2차 확인 (잘못 선택 방지)
- 대상 상위 디렉터리가 존재하고 쓰기 가능해야 함
- `mysql` 클라이언트 사용 가능 (데이터베이스 복구 시)
- 스냅샷 파일이 완전하고 sha256이 매니페스트와 일치

**② 복구 전 자동 스냅샷**

현재 상태를 먼저 백업 (디렉터리는 동일한 패키징 로직 사용, 데이터베이스는 dump 사용), 실패 시 이 단계로 되돌릴 수 있음.

**③ 실행 및 롤백**

- 복원 → 상태 점검
- 점검 중 하나라도 실패 → **자동으로 단계②의 스냅샷으로 롤백** → 이벤트 센터에 critical 이벤트 생성

상태 점검 항목: 디렉터리 파일 수 대조 및 표본 체크섬 검증, MySQL에서 `SELECT 1` 실행 및 주요 테이블 행 수 확인, Redis `PING`와 keyspace 비교.

롤백의 신뢰성은 「동일 파티션 내 rename은 원자적이다」에서 비롯됨: 복구 전에 대상 디렉터리를 `mv`하여 `xxx.pre-restore-<时间戳>`로 만들고, 실패 시 `mv`하여 되돌림.

## 패널 작업

**패널 설정 → 백업 복구**:

| 영역 | 내용 |
|---|---|
| 백업 대상 | 한 줄에 하나씩, 디렉터리 / `mysql:库名` / `redis:路径` 지원 |
| 보존 개수 | 기본값 7, 0은 정리하지 않음을 의미 |
| 즉시 백업 | 한 번 실행하고 완료 후 스냅샷 목록 새로고침 |
| 스냅샷 목록 | 이름, 시간, 크기, 대상 수, 사전 점검 결과 |
| 복구 | 스냅샷 이름 입력 후 확인하면 실행되며, 사전 점검 상세와 결과 반환 |
| 백업 이력 | 매 실행 결과 (실패 원인 포함) |

## 정기 백업

백업은 **예약 작업의 네 번째 유형**입니다(패널 작업 / 시스템 crontab / 사용자 crontab과 병렬). 동일한 스케줄링, 시작·중지, 실패 알람을 재사용합니다.

**예약 작업 → 새 작업 → 유형에서 「백업 작업」 선택**에서 구성합니다:

| 필드 | 설명 |
|---|---|
| 백업 대상 | 백업 페이지와 동일한 행 구문 |
| 보존 개수 | 오래된 스냅샷을 덮어쓰는 정책 |
| 실행 주기 | cron 표현식, 자주 쓰는 프리셋(매일 02:00 등) |
| 알림 채널 | 패널 / 이메일 / 위챗 워크 / 딩톡 / 페이수 |
| 로컬 사본 보존 | 원격 대상 사용 시, 업로드 성공 후 로컬 사본을 보존할지 여부 |

수동 「즉시 백업」과 **동일한 엔진**을 사용하며, 산출물이 완전히 같습니다——「수동은 복구되는데 정기 백업은 안 된다」는 상황은 존재하지 않습니다.

실패 시 작업 상태(`上次状态 / 上次错误 / 连续失败次数`)에 기록되며, 동시에 백업 이력 한 건이 남고, 내장 알람 규칙 「백업 실패 수」가 트리거됩니다.

## 원격 대상: 코드 준비 완료, 이 버전에서는 활성화하지 않음

`internal/backup`에는 S3 호환(OSS / MinIO / AWS, 자체 작성 SigV4 서명)과 SFTP 두 가지 원격 스토리지가 이미 구현되어 있지만, **v1.4.0에서는 제공 항목으로 포함하지 않습니다**:

- 패널에서 원격 대상 구성을 안내하지 않음
- 문서에서 프로덕션 사용을 권장하지 않음
- 실제 장비 연동 검증 미실시(단위 테스트와 S3 서명 벡터 테스트만 존재)

원격지에 보관해야 할 경우 `config.yaml`에 대상을 추가하면 코드 수정 없이 활성화됩니다:

```yaml
backup:
  targets:
    - name: oss-bj
      type: s3
      endpoint: oss-cn-beijing.aliyuncs.com
      bucket: my-backup
      region: cn-beijing
      access_key: "..."
      secret_key: "..."
```

구성 후 백업 페이지에 「원격 대상」 선택 항목이 나타나며, 스냅샷을 업로드하고 원격 스냅샷을 탐색/가져올 수 있습니다. 업로드는 로컬 스냅샷이 완전히 디스크에 기록된 후에 진행되므로, 업로드 실패 시 원격지에 반쪽짜리 백업이 남지 않습니다.

**주의**: 이 경로는 실제 장비 연동 검증을 거치지 않았으므로, 정식 사용 전에 비프로덕션 디렉터리에서 전체 왕복(업로드 → 목록 → 임시 디렉터리로 복원)을 한 번 검증하시기 바랍니다.

## 알려진 제한 사항

- 대용량 디렉터리 백업 중에는 IO를 지속적으로 점유하므로 업무 피크 시간대를 피하는 것을 권장합니다(기본 02:00)
- MySQL은 로컬 socket을 통해 백업하며, 원격 데이터베이스 인스턴스는 지원하지 않습니다
- 복구는 "덮어쓰기" 방식입니다: 스냅샷에 포함된 객체만 복원하며, 스냅샷 외부의 신규 파일은 정리하지 않습니다
- 단일 스냅샷은 암호화하지 않으므로, 민감한 데이터가 포함된 디렉터리는 데이터 디렉터리 권한과 백업 매체 보안을 반드시 확보하시기 바랍니다
